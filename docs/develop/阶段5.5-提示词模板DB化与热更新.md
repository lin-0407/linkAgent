# 阶段 5.5 - 提示词模板 DB 化与热更新（提示词热更库）

> 承接 5.4（Agent 内核结构化输出升级）。**作者 2026-06-09 重定方向时的原话**：「提示词也必须进行封装使用，不要硬编码到代码里，我推荐是使用数据库进行存储，这样就可以实现热更改，然后提供前端展示和接口进行用户自定义。」
>
> 一句话说清这一步要干嘛：**现在每条大模型提示词都写死在 Java 代码里，想改一个字就得改代码、重新打包、重启服务；这一步把提示词搬进数据库，改完即时生效（热更新），并提供接口让人在前端直接编辑。**
>
> 编码、编译、测试由作者执行。本文件是需求 + 现状核实 + 设计 + 切片 + 决策。

---

## 1. 需求分析

### 1.1 痛点（为什么要做）

- **改提示词 = 改代码**：目前 17 条左右的提示词全是 Java 文本块（`"""..."""`），散落在 9 个类里。调一句话就要重新编译、打包、发版，调提示词的成本和改业务逻辑一样高。
- **不能给非开发者用**：作者想让使用者（甚至自己在线上）直接调提示词。提示词埋在代码里，前端拿不到、也改不了。
- **和「设置面板」是上下游**：路线里「设置面板」要做提示词的前端展示和编辑，那它必须先有一个「按 key 读写提示词」的后端接口。本阶段就是把这个后端底座搭好。

### 1.2 本阶段做什么 / 不做什么

**做**：
- 新建一张表 `llm_prompt_template`：一行存一条提示词，用 `prompt_key`（如 `pre_publish.system`）当唯一标识。
- 新建 `PromptService`：调用方按 key 取提示词；内存缓存一份，避免每次调模型都查库；提供「刷新缓存」让 DB 里改完的提示词即时生效（这就是「热更新」）。
- 提供读写接口：列出所有提示词、按 key 查一条、改一条（改完即时生效）。
- 把代码里硬编码的提示词逐步搬进库（增量迁移，分刀做，先搬最安全的）。

**不做（本阶段边界，避免过度设计）**：
- **不做提示词的版本管理 / A-B 实验平台**。一条 key 只存「当前这一版」。理由见 §2.3：评测闭环（4.9）评测时会**自己**把当时用的提示词原文和哈希快照下来，版本追踪那条线已经独立闭环，本表不必再扛一套版本系统。
- **不做提示词的前端编辑界面**：那是下一步「设置面板」的事。本阶段只交付后端接口。
- **不引入模板引擎**（Freemarker/Thymeleaf 之类）。占位符替换用最朴素的字符串替换就够，不为这点小事加一个第三方依赖。

### 1.3 输入输出

- 对内：各 Service 调模型前，把原来写死的提示词字符串，换成「找 `PromptService` 按 key 要」。
- 对外：新增 3 个提示词管理接口（列表 / 查一条 / 改一条）。其余业务接口、返回结构全不变。

## 2. 现状与可行性核实（已用工具实际核对，非凭印象）

### 2.1 提示词盘点结论

全后端约 **17 条**提示词，全部是 Java 文本块，分两类：

- **系统提示词（SYSTEM）约 9 条**：给模型设定角色、规则、输出格式。**绝大多数是纯静态文本**（没有运行期变量），只有 `AgentExecutor` 的两条里带一个工具列表占位符。
  - 分布：`PrePublishSuggestionService`、`CreatorFeedbackService`（2 条）、`CreatorCompetitorService`、`CreatorReportService`、`HydeQueryTransformer`、`KnowledgeReferenceCleaningService`、`LongTermMemoryExtractor`、`SummaryMemory`、`AgentExecutor`（2 条，带占位符）。
- **用户提示词（USER）约 7 条**：把任务标题、材料等运行期数据拼进模板。**全部用 Java 的 `.formatted(参数1, 参数2, ...)` 按位置填空**（模板里写一串 `%s`，调用处按顺序传值）。
  - 分布：`PrePublishSuggestionService`、`CreatorFeedbackService`（2 条）、`CreatorCompetitorService`、`CreatorReportService`、`KnowledgeReferenceCleaningService`、`LongTermMemoryExtractor`。

> 关键差异：**系统提示词好搬**（纯文本，搬进库直接取就行）；**用户提示词难搬**（`%s` 是「位置占位符」——靠出现顺序对应参数。一旦让用户在前端编辑，少打一个 `%s`、或顺序错了、或手滑打了个 `%`，`.formatted()` 当场抛异常）。所以两类要分开处理，见 §3.3 和切片。

### 2.2 建表与数据访问风格（照搬现有规范）

- 表都在 `backend/src/main/resources/sql/init.sql` 里维护（这就是约定的 `sql/` 目录），用 `CREATE TABLE IF NOT EXISTS` + 紧跟 `INSERT IGNORE` 灌种子数据，每列必有中文 COMMENT，统一带 `id / create_time / update_time / is_deleted` 这套字段。
- 数据访问层是 **MyBatis 注解式**（全项目 10 个 Mapper、89 处注解，没有一个 XML 文件）。`@Mapper` 接口里直接写 `@Insert/@Select` 文本块，用 `#{属性}` 占位，用 `@Results/@Result` 把蛇形列名映射到驼峰属性。新建的 `PromptTemplateMapper` 照这个写。

### 2.3 与评测闭环（4.9）的关系：解耦，不耦合

评测结果表 `creator_eval_result` 已经有 `prompt_version` / `prompt_hash`（SHA-256）/ `prompt_snapshot` 三个字段——它在**每次评测时把当时用的提示词原文和哈希自己快照下来**，用来对比「同一道题在不同提示词下表现差异」。

这意味着：**提示词的「版本追踪」职责已经由评测侧独立扛着，和提示词存在哪无关。** 所以本表只管「当前生效的这一版」，不做版本表。两边互不依赖。

## 3. 设计

### 3.1 表 `llm_prompt_template`

```sql
-- ------------------------------------------------------------
-- NN. 提示词模板表
--     把原本硬编码在各 Service 里的大模型提示词搬到数据库，
--     调用方按 prompt_key 取词，支持运行期热更新和前端自定义，
--     避免改一句提示词就要改代码、重新打包发布
-- ------------------------------------------------------------
CREATE TABLE IF NOT EXISTS llm_prompt_template
(
    id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY COMMENT '主键',
    prompt_key  VARCHAR(128) NOT NULL COMMENT '提示词唯一键，调用方用它取词，命名用「场景.类型」如 pre_publish.system',
    prompt_type VARCHAR(16)  NOT NULL COMMENT '提示词类型：SYSTEM=系统角色设定，USER=用户输入模板',
    scene       VARCHAR(64)  NOT NULL COMMENT '所属业务场景，给前端分组展示用，如 发布前优化、评论弹幕分析、ReAct内核',
    content     LONGTEXT     NOT NULL COMMENT '提示词正文；USER 类型里用 {名字} 表示运行期才填入的变量',
    description VARCHAR(255)          DEFAULT NULL COMMENT '这条提示词的用途说明，给前端编辑者看懂它是干嘛的',
    create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间，热更新时刷新',
    is_deleted  TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除：0=正常，1=已删除',
    UNIQUE KEY uk_prompt_key (prompt_key),
    KEY idx_scene (scene)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = 'LLM 提示词模板表';
```

字段刻意只留这些——key、类型、场景、正文、说明，加标准四件套。没有 version、没有 enabled、没有 author，因为本阶段不做版本/开关/多租户（§1.2、§2.3）。

### 3.2 `PromptService`：取词 + 缓存 + 热更新

```
String get(String key)                       // 取一条提示词正文（系统提示词直接用）
String render(String key, Map<String,Object> vars)  // 取模板并把 {名字} 替换成实际值（用户提示词用）
List<PromptTemplate> listAll()               // 列出全部，给读接口
void update(String key, String content)      // 改一条：写库 + 立即刷新缓存（热更新）
void refresh()                               // 清空缓存，强制下次从库重读（应对有人直接改库）
```

- **缓存**：内部一个 `ConcurrentHashMap<String,String>`。`get` 走「缓存没有就查库、查到放进缓存」（即 `computeIfAbsent`）。这样除了第一次，取词不查库，不给每轮模型调用加 DB 开销。
- **热更新怎么实现**：
  - 走接口改（`update`）：先写库，再把缓存里这条直接换成新值 → 下一次模型调用立刻用新提示词，**不用重启**。
  - 有人绕过接口直接改库：调一次 `refresh()` 清空缓存即可。
- **取不到怎么办（fail-loud，见 §6 决策）**：key 在库里查不到时，`get` 直接抛一个说明清楚的异常（如「提示词 key=xxx 未配置，请确认 init.sql 已执行」），**不静默兜底**。理由：本表是提示词的唯一来源，查不到一定是种子没灌或被误删，应该当场报错让人看见，而不是偷偷用一个别的值导致诡异结果。

### 3.3 用户提示词的占位符：从「位置 `%s`」改成「命名 `{名字}`」

用户提示词搬进库后要让人能编辑，位置占位符 `%s` 太脆（§2.1）。改成命名占位符：

- 模板里写 `任务名称：{taskName}`，`render` 时传 `Map.of("taskName", 实际值)`，做简单的「把 `{taskName}` 替换成值」。
- 好处：① 编辑者看到的是有意义的名字，不是一串没头没尾的 `%s`；② 不再依赖顺序；③ 不碰 `String.format`，用户文本里出现 `%` 也不会炸；④ 万一某个变量没传，就让 `{taskName}` 原样留在文本里（看得见、好排查），而不是抛异常。
- 代价：用户提示词的调用处要从「按顺序传一串参数」改成「传一个 Map」。这是 5.5-3 的活，单独一刀，见 §9 待确认。

### 3.4 包结构与接口

新建 `com.link.linkagent.prompt` 模块，沿用项目分层：
- `prompt/model/PromptTemplate.java`（表实体）
- `prompt/mapper/PromptTemplateMapper.java`（`@Mapper` 注解式）
- `prompt/service/PromptService.java`
- `prompt/controller/PromptTemplateController.java`
- `prompt/dto/`（请求/响应 DTO，写接口入参带 Jakarta `@NotBlank` 校验）

接口（前缀 `/api/prompt-templates`）：
- `GET /api/prompt-templates`：列出全部（前端分组展示用）。
- `GET /api/prompt-templates/{key}`：查一条。
- `PUT /api/prompt-templates/{key}`：改正文，改完即时生效。

## 5. 5.5-1 详细设计（本刀只新增、不改旧路径）

1. **init.sql**：在文件末尾按现有分节风格加 `llm_prompt_template` 建表语句；紧跟 `INSERT IGNORE` 灌入 9 条静态系统提示词的**逐字原文**（原文必须和代码里现有文本一字不差，这样 5.5-2 切换调用处时行为不变）。SQL 里单引号 `'` 转义成 `''`。
2. **`PromptTemplate` 实体**：对应表字段，驼峰命名。
3. **`PromptTemplateMapper`（`@Mapper`）**：`listAllEnabled`（查全部未删）、`findByKey`、`updateContentByKey`（5.5-2 才用到，可本刀先建好）。`@Results/@Result` 映射列名。
4. **`PromptService`**：`get(key)`（缓存 + fail-loud）、`listAll()`。`render` / `update` / `refresh` 留到对应刀，本刀可先放空壳或暂不建（避免无人调用的死代码——本刀只建 `get` + `listAll`）。
5. **`PromptTemplateController`**：`GET` 列表 + `GET /{key}`。
6. **不动任何现有 Service** → 现有所有功能字节级不变，零回归。读接口能列出种子提示词即验证底座通了。

## 6. 关键决策

- **DB 是提示词的唯一来源 + 取不到就响亮报错（fail-loud），不在代码里留一份兜底默认**：兑现作者「不要硬编码到代码里」。提示词原文以种子形式落在 `init.sql`（属于 `sql/` 目录的 schema/种子，不算「硬编码进业务逻辑」）。取不到当场抛异常，比静默用错值安全、好排查。
- **用户提示词改用命名占位符 `{名字}`**：让前端编辑安全（§3.3），这是「用户自定义」真正可用的前提，不是过度设计。
- **不做版本/AB 平台**：评测侧已独立做提示词快照与哈希（§2.3），本表只存当前版，遵循「简单优先、不过早抽象」。
- **先搬静态系统提示词、内核提示词最后搬**：把底座在低风险料子上验稳，保护刚在 5.4 稳定的 `AgentExecutor`。
- **不引模板引擎**：占位符替换用字符串替换，遵守「禁止引入没用到的抽象/第三方库」。

## 9. 运行期待确认 / 待作者拍板

- **5.5-3 用户提示词占位符方案（需作者确认后再做那一刀）**：本设计推荐「命名占位符 `{名字}` + 传 Map」（安全、可前端编辑，但要改 7 个调用处的签名）。备选是「保留位置 `%s` + 继续 `.formatted`」（改动最小，但用户编辑易弄坏）。5.5-1/5.5-2 不涉及此点，可先推进；做到 5.5-3 前确认。

- **收尾**：5.5 全部切片自测通过后，在 `docs/error` 补踩坑记录、`docs/reference` 补说明文档，并更新 `AGENTS.md` / 内层 `CLAUDE.md` 文档表。
