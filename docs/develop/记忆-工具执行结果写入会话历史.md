# 记忆：工具执行结果写入会话历史

## 需求结论

Agent 每轮执行过的工具步骤（调用 + 结果）要像 Codex/DSH 那样写进会话历史，下一轮请求能带上；
上下文里工具执行记录和用户贴材料要能区分开。目标不是让模型多看到一份工具输出，而是让「agent 自己的执行证据」
成为上下文增长的主要来源，而不是靠用户贴长材料把窗口顶大。

消息形态按作者要求采用 OpenAI/DeepSeek 原生协议：**assistant 的工具调用一条消息、tool 的结果一条消息**，
用 `tool_call_id` 配对，而不是把「调用 + 结果」拼进同一条 role=tool 消息。

本轮只改代码和评测栈，不动运行中的生产容器；256k 压缩阈值和 768k guard 保持不变。

## 方案

### 生产写入侧

1. `AgentExecutor` 的 6 个 `persistChatTurn` 调用点都传入本轮工具步骤：
   - 规划模式（Plan & Execute / Multi-Agent）传 `AgentRunResult.steps()`；
   - 文本 ReAct / 结构化 ReAct 传本轮 `steps`；
   - 流式链路没有单独的步骤列表，由 `persistAgentStep` 在执行时收进 `AgentPersistenceContext.toolSteps`。
2. 每个工具步骤写**两条消息**（消息表 `t_conversation_message`）：

   | 消息 | role | content | tool_name | tool_arguments | tool_call_id |
   |---|---|---|---|---|---|
   | 工具调用 | `assistant` | 空串（不存 thinking/reasoning） | 工具名 | 参数摘要 ≤300 字 | 配对 id |
   | 工具结果 | `tool` | 工具结果 ≤2000 字 | 同一工具名 | `NULL` | 与调用相同 |

   - `t_conversation_message` 新增 `tool_call_id VARCHAR(64)`、`tool_arguments TEXT` 两列
     （`init.sql` 表定义 + 幂等补列补丁）。
   - 参数摘要 300 字、结果 2000 字都是原文截断，持久化时不再调模型压缩（`ToolResultCompressor` 的 2000
     是「超过才触发压缩」的阈值，压缩输出上限 6000 字，两者不是同一个口径，见代价）。
   - 非工具步骤（action 为空）不写；取消/断开的一轮仍只保留用户消息。
3. 落库顺序固定 `user -> (assistant 调用 -> tool 结果)... -> assistant 最终回答`，消息 id 按发生顺序递增：
   - 长期记忆提取的区间终点仍是最终 assistant id；增量查询加 `tool_call_id IS NULL`，
     工具调用/结果都不会被当成助手发言抽进长期记忆。
4. 短期记忆的 `MemoryMessage` 增加 `toolCallId/toolName/toolArguments` 字段，工具调用消息 content 为空、
   `promptText()` 渲染为 `ToolCall: 工具名(参数摘要)`；工具结果消息 content 就是结果。渲染处
   （上下文组装、摘要、复核、事实点抽取、长期记忆抽取）统一走 `promptText()`，避免多处各写一套格式。
5. Redis 短期记忆序列化升到 v2：`id \t v2 \t role \t toolCallId \t toolName \t toolArguments \t content`，
   null 用 `\N` 占位；同时兼容旧的 3 列（id/role/content）和 2 列（role/content）格式，升级后旧历史还能读。
6. 保留尾部从固定 2 条消息改成按 token 预算：
   - 新增配置 `agent.memory.summary.retained-token-budget`（默认 16000，`SUMMARY_MEMORY_RETAINED_TOKEN_BUDGET`）；
   - 用 `TokenCounter`（官方词表）按 `promptText()` 从尾部往前累计整条消息，够了就停，至少留 1 条历史；
   - 原生协议的配对边界：如果裁剪起点落在 tool 结果上，把前一条 assistant 调用一起留下，
     模型不会看到「没有调用的结果」；
   - 拿不到 token 计量器或预算配 0 时，退回 `retained-message-count`。
7. 摘要/复核/事实点提示词同步改口径：
   - `summary_memory.system`：Human 是用户本人，AI 是助手建议，以 `ToolCall:` 开头的消息是工具调用，
     紧随的 Tool 是结果；保留结果里的关键数字、路径、结论、错误信息，重复调用可以合并；AI 建议不算用户偏好。
   - `summary_review.system`：增加「ToolCall 与 Tool 结果是否成对保留、工具证据是否丢失」的漏抽检查，
     以及「把 AI 建议/工具参数/工具结果写成用户偏好」的归因错误检查。
   - `summary_fact.system`：只抽 Human 里用户明确说过的事实，AI/工具内容不算用户事实，`original` 必须来自 Human。
   - `AgentExecutor.MEMORY_CONFLICT_RULES`：告诉主 Agent，ToolCall/Tool 是执行证据，不是用户本人陈述。

### 评测栈

1. eval 协议 `sessions[].turns[]` 支持原生两条消息：
   - 工具调用轮：`role=assistant`、`content` 可为空串，带 `tool_call_id`/`tool_name`/`tool_arguments`；
   - 工具结果轮：`role=tool`、`content` 为结果，`tool_call_id` 与前面调用一致；
   - `engine.py` 校验 id/name ≤64、arguments ≤2000、结果与调用一一配对且工具名一致、id 会话内唯一；
   - `linkagent_adapter.py` 把三个工具字段原样透传给后端并保留在运行结果里；
   - DeepEval 4.3.0 的 `Turn` 只接受 user/assistant，打分时过滤 tool 轮和带 `tool_call_id` 的 assistant 调用轮，
     原始 turns 仍保留。
2. 后端评测适配器 `MemoryEvaluationRequest` / `MemoryEvaluationService`：
   - 接受新字段，回放时按消息表两条行写入、短期记忆按 `MemoryMessage` 工具字段配对；
   - 工具调用/结果不触发 `prepare`/`afterTurn`，不参与重要性预算与消息区间；
   - 非法配对（tool 结果前面不是同 id 的 assistant 调用）直接让任务 failed，不静默写脏历史；
   - `capabilities` 增加 `summary_retained_tokens`，policy 文案改为原生协议口径。
3. 评测环境 compose 增加 `db-init` 服务：每次启动用统一 `init.sql` 生成的脚本跑一遍幂等补丁，
   旧数据卷也能补上 `tool_call_id/tool_arguments` 等新列（之前 initdb 只在空库时执行，旧卷会缺列）。
4. 25 题摘要压缩数据集重造成原生消息形态：用户短句 100~800 字、每轮 8~15 对
   （assistant 工具调用 + tool 结果）、assistant 最终回答 300~1500 字，30~45 轮自然到 300k；
   事实点埋进工具结果，旧 25 题数据集保留作对照。

## 代价与边界

- 每轮请求都会带历史工具调用与结果，输入 token 和成本会上升；大部分是缓存命中的稳定前缀，但当轮新增工具结果仍是 miss。
- 消息表会多存行（每个工具步骤 2 行）和参数摘要列；token 量级与单条方案相当，结果原文仍在 `t_agent_step`。
- 超长工具结果存的是「原文前 2000 字」，不是当轮模型看到的压缩摘要（≤6000 字）：下一轮看到的信息比当轮少，
  这是为了不增加持久化侧模型调用而接受的取舍。
- 旧数据兼容：旧行没有 `tool_call_id` 按普通消息读；旧 Redis 3 列/2 列格式可读；旧「一条 role=tool 装调用+结果」
  的历史不会参与新配对裁剪，但读取不报错。
- 提示词种子只影响新库；已有库（生产/评测）需要重新同步提示词才生效。本轮不碰生产容器。

## 已知口径差异

- `ToolResultCompressor` 的 2000 是「超过 2000 才压缩」的触发阈值，压缩输出上限是 6000 字。
  会话历史里存的是原文前 2000 字（不再调模型压缩），和「当轮模型看到的那份」对超长结果不完全一致；
  这是为了不在持久化阶段增加模型调用而接受的取舍，已在 `docs/error/工具执行记录写入会话历史注意事项.md` 记录。
