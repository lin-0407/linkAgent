# 阶段 4 - UP 主智能工作台总流程大纲

> 本文档用于承接项目方向调整：`linkAgent` 不再以“通用 Agent 框架”作为对外主叙事，而是转向一个面向 B 站内容创作者的 AI 应用项目。底层仍复用现有 Agent、工具调用、记忆、SSE、可观测等能力，但所有新增开发都要优先服务“创作者工作流”。

---

## 1. 项目新定位

项目名称暂定：

```text
LinkAgent Creator Copilot
```

一句话定位：

```text
面向 B 站内容创作者的 AI 创作与复盘工作台，帮助 UP 主完成稿件理解、标题简介生成、评论弹幕分析、创作复盘和历史偏好沉淀。
```

对外表述：

```text
基于 Spring AI 构建的视频创作者智能工作台，支持字幕/文稿分析、标题简介生成、标签建议、评论弹幕聚类、创作复盘报告、SSE 流式输出和 Agent 执行链路观测。
```

项目目标不是替代剪辑软件，也不是模拟 B 站内部推荐系统，而是做一个公开业务链路中真实存在的创作辅助闭环。

---

## 2. 核心问题

中小 UP 主常见痛点：

1. 发布前不知道标题、简介、标签怎么写更清楚、更贴合 B 站语境。
2. 视频稿件或字幕内容较长，难以快速提炼卖点和风险点。
3. 发布后评论、弹幕信息分散，很难系统化理解观众反馈。
4. 每期视频复盘靠感觉，缺少历史沉淀和下一期选题建议。
5. 多轮创作缺少持续记忆，AI 每次都像第一次认识这个创作者。

本项目要解决的问题：

```text
把“内容输入 -> 发布前优化 -> 发布后反馈分析 -> 创作复盘 -> 偏好沉淀”做成一个可演示、可观测、可评测的 AI 应用闭环。
```

## 3. MVP 范围

第一版只做必要闭环，避免项目失控。

### 3.1 必做能力

| 模块 | 输入 | 输出 | 技术重点 |
|---|---|---|---|
| 创作任务 | 标题草稿、视频字幕、视频简介 | 任务记录 | REST API、参数校验、MySQL |
| 稿件分析 | 字幕/文稿 | 内容摘要、受众判断、风险点 | Prompt 模板、LLM 调用 |
| 发布前优化 | 字幕、标题草稿、创作者偏好 | 标题、简介、标签、分区建议 | 同步 LLM 基线，后续升级为工作流 Agent + SSE |
| 评论弹幕分析 | 评论样例、弹幕样例、用户主动导入的样例文件 | 高频观点、情绪倾向、争议点 | 同步 LLM 基线，后续补充清洗、分类、图表和追问 |
| 竞品分析 | 用户主动整理的同类型视频样例 | 相对竞品的优势、短板、差距 | 对照分析、结构化输出 |
| 复盘报告 | 稿件分析 + 评论弹幕分析 + 竞品分析 | 完整创作复盘报告 | 报告生成、历史存储 |
| Agent 工作流融合 | 任务上下文、用户补充资料、分析阶段事件 | 可追踪消息流、步骤记录、确认状态 | 工作流会话、SSE、消息落库 |
| 流式过程 | Agent 执行步骤 | 前端实时展示中间过程 | SSE |
| 执行观测 | 工具调用、耗时、异常 | Trace / 日志 / 失败原因 | 可观测、排障 |

### 3.2 暂不做能力

| 暂不做 | 原因 |
|---|---|
| 自动投稿 B 站 | 涉及开放平台授权和合规边界，简历项目第一版不需要 |
| 批量或定时采集评论和弹幕 | 容易碰到反爬和数据合规问题，第一版只做用户显式触发的单 BV 限量采集 |
| 视频自动剪辑 | 会引入 FFmpeg、音视频处理和素材管理，容易偏离主线 |
| 推荐算法模拟 | B 站推荐系统不可见，做出来也难以验证 |
| 复杂多 Agent 协作 | 当前阶段先保证单 Agent 工作流稳定可解释 |

## 4. 业务流程

第一版业务流程如下：

```text
创建创作任务
  -> 输入字幕/文稿/标题草稿
  -> 发布前优化同步基线生成建议
  -> 工作流消息流展示任务上下文和 Agent 分析过程
  -> 用户确认标题、简介、标签建议
  -> 输入评论/弹幕样例
  -> 评论弹幕同步基线生成反馈报告
  -> 输入同类型视频样例
  -> 生成竞品对照报告
  -> 生成复盘报告
  -> 保存任务历史和创作者偏好
  -> 下一次任务读取历史偏好继续优化
```

对应页面流程：

```text
任务列表页
  -> 新建任务页
  -> 创作分析页
  -> Agent 工作流消息页
  -> 复盘报告页
  -> 历史任务页
```

## 5. 技术架构

现有 `linkAgent` 能力继续作为底座：

```text
Vue3 前端
  -> Spring Boot API / SSE
  -> Creator 业务层
  -> Agent 编排层
  -> Tool Registry
  -> Memory
  -> MySQL / Redis
  -> LLM API
```

建议新增业务包：

```text
com.link.linkagent.creator
├── task          # 创作任务：任务创建、状态流转、任务查询
├── manuscript    # 稿件材料：字幕、文稿、标题草稿、简介草稿
├── suggestion    # 发布前建议：标题、简介、标签、分区建议
├── feedback      # 评论弹幕分析：观点聚类、情绪倾向、争议点
├── competitor    # 同类型视频竞品分析：样例、优劣势、差距
├── workflow      # 创作者业务工作流：会话、消息、步骤、SSE
├── report        # 复盘报告：生成、保存、查询
└── preference    # 创作者偏好：标题风格、内容领域、历史偏好
```

包结构只在真正开发对应功能时逐步创建，不要一次性空建所有目录。

## 6. 数据来源策略

第一阶段只允许以下数据来源：

1. 用户手动粘贴字幕、文稿、评论、弹幕。
2. 项目内置样例数据。
3. 用户上传本地文本文件。
4. 用户输入单个 BV 后显式触发脚本生成并自动导入的评论弹幕 JSON/TXT 样例文件。

暂不做批量 BV、定时任务或后台同步，暂不接入 B 站开放平台真实账号授权。

这样做的原因：

1. 降低合规风险。
2. 降低上线难度。
3. 保证项目核心能力集中在 AI 应用工程化，而不是爬虫和平台接入。

## 7. 开发阶段规划

### 阶段 4.0：方向收敛与文档同步

目标：

1. 新增本文档，明确项目转向。
2. 同步 `AGENTS.md`、`CLAUDE.md`、`项目开发大纲.md` 的项目定位。
3. 明确第一版不做的能力，防止后续跑偏。

验收：

1. 后续助手读取提示词后，会优先按 UP 主智能工作台方向开发。
2. 文档中能说明项目解决什么问题、业务流程是什么、MVP 做到哪里。

### 阶段 4.1：创作任务与稿件输入

目标：

1. 建立创作任务表。
2. 支持新建任务、查询任务、保存字幕/文稿/标题草稿。
3. 所有对外 API 增加 Jakarta Validation 校验。

预期接口：

```text
POST /api/creator/tasks
GET  /api/creator/tasks
GET  /api/creator/tasks/{taskId}
POST /api/creator/tasks/{taskId}/materials/import
```

预留扩展：

```text
待补充：任务状态机
待补充：任务归档与删除策略
```

### 阶段 4.2：发布前优化 Agent

目标：

1. 基于字幕/文稿生成内容摘要。
2. 生成标题、简介、标签建议。
3. 输出每条建议的理由和风险。
4. 保留 `rawOutput` 和结构化结果，为后续 SSE 工作流展示提供基础数据。

预期接口：

```text
POST /api/creator/tasks/{taskId}/pre-publish/analyze
GET  /api/creator/tasks/{taskId}/pre-publish/suggestions
```

预留扩展：

```text
待补充：阶段 4.4.1 承接 SSE 工作流展示和建议确认
待补充：标题风格模板
待补充：不同分区的提示词模板
待补充：标题质量评分规则
```

### 阶段 4.3：评论弹幕分析

目标：

1. 支持粘贴评论和弹幕样例。
2. 分析高频观点、情绪倾向、争议点、用户误解点。
3. 生成下一期内容建议。

预期接口：

```text
POST /api/creator/tasks/{taskId}/feedback
POST /api/creator/tasks/{taskId}/feedback/analyze
GET  /api/creator/tasks/{taskId}/feedback/report
```

预留扩展：

```text
待补充：评论分层规则
待补充：弹幕时间轴分析
待补充：负面反馈风险等级
```

### 阶段 4.4：创作复盘报告

目标：

1. 支持保存用户主动整理的同类型视频样例。
2. 基于样例生成同类型视频竞品分析。
3. 汇总发布前分析、评论弹幕分析和竞品分析。
4. 生成一份结构化复盘报告。
5. 将报告保存到 MySQL。
6. 支持历史报告查询。

报告结构：

```text
内容摘要
核心卖点
标题与简介建议
观众关注点
竞品对照结论
争议与误解
下一期选题建议
创作者偏好沉淀
```

预留扩展：

```text
待补充：PDF 导出（Markdown 导出已由阶段 4.14 补齐）
待补充：报告版本管理
待补充：多人协作批注
```

### 阶段 4.4.1：创作工作台 Agent 工作流融合

目标：

1. 将发布前优化从“表单触发同步 LLM”升级为“任务驱动的 Agent 消息流”。
2. 新增工作流会话、消息、步骤和附件设计，支撑 SSE 流式展示和失败回放。
3. 为发布前优化增加用户确认机制，避免 AI 自动推进业务阶段。
4. 将评论弹幕分析扩展为导入、清洗、分类、图表、追问的可解释流程。
5. 保持平台数据边界：第一版只处理用户主动提供或脚本导出的样例数据。

预期接口：

```text
POST /api/creator/tasks/{taskId}/workflow/pre-publish/start
GET  /api/creator/tasks/{taskId}/workflow/sessions/{sessionId}/events
POST /api/creator/tasks/{taskId}/workflow/sessions/{sessionId}/messages
POST /api/creator/tasks/{taskId}/workflow/sessions/{sessionId}/pre-publish/analyze
POST /api/creator/tasks/{taskId}/workflow/sessions/{sessionId}/pre-publish/confirm
POST /api/creator/tasks/{taskId}/feedback/import
GET  /api/creator/tasks/{taskId}/feedback/dashboard
POST /api/creator/tasks/{taskId}/feedback/chat
```

实施顺序：

```text
发布前优化消息流
  -> SSE 与建议确认
  -> 评论弹幕导入与仪表盘
  -> 反馈追问与 RAG 预留
```

### 阶段 4.5：创作者偏好记忆

目标：

1. 从历史任务中提取创作者偏好。
2. 下次生成建议时读取长期记忆。
3. 区分短期会话记忆和长期偏好记忆。

预留扩展：

```text
待补充：偏好人工编辑
待补充：偏好可信度评分
待补充：偏好过期策略
```

### 阶段 4.6：评测集与失败回放

目标：

1. 建立 5 到 10 组样例任务。
2. 记录每次 Agent 执行步骤、耗时、token、失败原因。
3. 对标题质量、报告完整性、评论分析准确性做人工评分。

评测维度：

| 维度 | 说明 |
|---|---|
| 可读性 | 标题和报告是否像人写的 |
| 贴合度 | 是否贴合输入稿件和评论 |
| 稳定性 | 多次运行结果是否大体稳定 |
| 成本 | token 消耗是否可接受 |
| 可解释性 | 是否能看到中间步骤和失败原因 |

预留扩展：

```text
待补充：自动评分脚本
待补充：多模型对比
待补充：Prompt 版本对比
```

### 阶段 4.7：上线演示

目标：

1. 使用 Docker Compose 部署前端、后端、MySQL、Redis、Nginx。
2. 准备 2 到 3 个演示任务。
3. 编写 README 和演示说明。
4. 录制简短演示视频，服务简历投递。

预留扩展：

```text
待补充：公网域名
待补充：演示账号
待补充：访问限流
待补充：成本保护
```

### 阶段 4.8：演示环境成本保护

目标：

1. 在统一 LLM 调用入口增加输入规模保护。
2. 让公开演示环境可以通过环境变量控制单次模型输入上限。
3. 在超限时返回清晰的业务提示，避免已经发起模型请求后才失败。

预期配置：

```text
LLM_GUARD_ENABLED
LLM_GUARD_MAX_PROMPT_CHARS
```

预留扩展：

```text
待补充：演示口令
待补充：IP 级限流
待补充：token 用量记录
待补充：多模型成本对比
```

### 阶段 4.9：Prompt 版本评测闭环

目标：

1. 让每次评测结果绑定 Prompt 版本、快照和哈希。
2. 支持按 Prompt 版本聚合人工评分、耗时和 token。
3. 让 Prompt 调优从“凭感觉改”变成“有样例、有版本、有结果对照”。

预期接口：

```text
GET /api/creator/evaluations/cases/{caseId}/prompt-version-stats
```

预留扩展：

```text
待补充：自动批量跑评测
待补充：多模型横向对比
待补充：Prompt 模板后台
```

### 阶段 4.10：LLM 用量采集与评测统计口径

目标：

1. 从 Spring AI 响应元数据中提取模型名称、token 和调用耗时。
2. 让反馈追问真实返回本次 LLM 调用成本信息。
3. 将 Prompt 版本统计扩展为成功率、分项评分、评分覆盖率、分数波动和 token 成本。
4. 明确人工 `accuracyScore` 不是自动准确率，避免作品集叙事虚高。

预期接口：

```text
GET /api/creator/evaluations/cases/{caseId}/prompt-version-stats
POST /api/creator/tasks/{taskId}/feedback/chat
```

预留扩展：

```text
待补充：独立 LLM 调用流水表
待补充：多评审人一致性统计
待补充：LLM-as-judge 辅助评分
待补充：模型价格表和人民币成本估算
```

### 阶段 4.11：创作者语境与建议质量升级

目标：

1. 解决发布前优化建议过于宽泛的问题。
2. 让模型输出必须覆盖创作者困境、观众钩子、内容定位和可执行修改计划。
3. 升级标题建议结构，补充观众心理、点击理由、信任风险和适用场景。
4. 在前端结果弹窗展示这些高信号字段。
5. 让复盘和竞品分析继续读取发布前建议中的创作者语境。

实施边界：

```text
先升级分析框架和输出结构
  -> 再升级反馈分析质量
  -> 最后用 RAG 补证据来源
```

本阶段不接入向量库，不抓取平台数据，不模拟推荐算法。


## 11. 当前开发原则

1. 先做业务闭环，再补高级能力。
2. 不为炫技引入复杂抽象。
3. 每个阶段都要能单独演示。
4. 所有新增 API 都必须做入参校验。
5. 所有数据库变更都维护在 `backend/src/main/resources/sql/`。
6. 平台数据优先使用用户输入、上传文件或显式触发的单 BV 限量样例采集，不做批量或定时同步。
7. 任何 Agent 能力都必须能解释它服务了哪个创作者场景。
