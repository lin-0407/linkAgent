# 阶段 5.9 - LLM API 开销统计与全链路追溯

> 承接路线：LLM 用量采集与评测统计口径（4.10） → 高级检索链路（5.2） → **任务级 API 开销统计（5.9）**。
>
> 本阶段定位：把一次创作者任务中的文本 LLM、Embedding、Rerank 调用记录下来，让作者能看到总开销、分类开销和每次调用明细。

---

## 一、需求分析

### 1. 背景与痛点

- 发布前优化、评论弹幕分析、反馈追问和知识库检索都会触发模型调用。
- 过去只能在单个业务结果里看到部分 usage，无法知道一个任务总共花了多少 token 和时间。
- 向量化和 rerank 不属于文本对话，但它们也是真实 API 成本，不能被统计遗漏。
- 模型调用失败时也需要留痕，否则很难判断是业务逻辑失败、模型失败还是外部服务超时。

### 2. 目标用户

- 需要评估 AI 功能成本的项目作者。
- 需要复盘一次创作任务完整模型链路的开发者。
- 后续需要做模型评测、成本控制和故障排查的维护者。

### 3. 本阶段做什么

1. 新增模型 API 调用流水表，记录调用分类、场景、模型名、token、耗时、状态和错误摘要。
2. 文本 LLM 调用记录成功和失败。
3. EmbeddingModel 通过代理自动记录向量化调用。
4. Rerank 客户端记录成功、失败和跳过。
5. 创作者业务链路通过上下文写入 `taskId`、`traceId`、`requestId` 和场景名。
6. 新增任务级统计 API，支持总览、分类汇总和调用明细分页。
7. 前端工作台新增“开销统计”入口，展示总览卡片、分类卡片和调用明细。

### 4. 本阶段不做什么

- 不估算 token。供应商或 SDK 未返回 usage 时保持 `null`，前端显示“未返回”。
- 不做价格换算。不同供应商价格变动较快，本阶段只做 token 和耗时的事实记录。
- 不引入新的监控系统。
- 不把“查看统计”本身做成会触发模型调用的动作。

## 二、设计方案

### 2.1 数据表

新增表：`llm_api_call_log`

| 字段 | 说明 |
|---|---|
| `call_id` | 单次模型调用 ID |
| `task_id` | 当前创作者任务 ID；非任务链路允许为空 |
| `trace_id` | 一条业务链路 ID，用于串联多次调用 |
| `request_id` | 一次请求 ID，用于排查同一请求内的调用 |
| `model_category` | `TEXT`、`EMBEDDING`、`RERANK` |
| `scene` | 调用场景，例如发布前优化、反馈追问回答 |
| `model_name` | 模型名称 |
| `prompt_tokens` | 输入 token，未知时为空 |
| `completion_tokens` | 输出 token，未知时为空 |
| `total_tokens` | 总 token，未知时为空 |
| `elapsed_ms` | 调用耗时毫秒 |
| `status` | `SUCCESS`、`FAILED`、`SKIPPED` |
| `error_message` | 失败或跳过原因摘要 |
| `input_count` | Embedding 文本段数或 Rerank 候选数 |

### 2.2 后端模块

| 类 / 文件 | 职责 |
|---|---|
| `LlmUsageContext` | 用 `ThreadLocal` 保存当前任务和场景，避免每层业务方法都传统计参数 |
| `LlmApiUsageService` | 写入调用流水、聚合任务统计、分页查询明细 |
| `LlmApiUsageMapper` | MyBatis SQL |
| `LlmApiUsageController` | 只读统计 API |
| `MeteredEmbeddingModel` | 代理真实 `EmbeddingModel` 并记录向量调用 |
| `MeteredEmbeddingModelBeanPostProcessor` | 自动给容器里的 `EmbeddingModel` 包一层统计代理 |
| `KnowledgeRerankClient` | 在 rerank 成功、失败、跳过时记录开销 |

### 2.3 API 设计

#### 任务总览

```http
GET /api/llm-usage/tasks/{taskId}/summary
```

响应核心字段：

```json
{
  "taskId": "task-id",
  "callCount": 8,
  "successCount": 7,
  "failedCount": 1,
  "skippedCount": 0,
  "totalTokens": 12345,
  "totalElapsedMs": 9200,
  "averageElapsedMs": 1150,
  "categories": []
}
```

#### 调用明细

```http
GET /api/llm-usage/tasks/{taskId}/calls?page=1&pageSize=20&modelCategory=TEXT
```

校验规则：

- `taskId` 必填，最大 64 字符。
- `modelCategory` 只能是 `TEXT`、`EMBEDDING`、`RERANK`。
- `page` 最小 1。
- `pageSize` 范围 1 到 100。

### 2.4 上下文设计

`LlmUsageContext.open(taskId, scene)` 用于任务链路。

`LlmUsageContext.scene(scene)` 用于没有任务 ID 的通用知识库或记忆链路。

使用 `ThreadLocal` 的原因是：模型调用分散在业务服务、检索服务和 SDK 内部代理里。只把追踪元数据放到线程上下文，可以减少业务方法签名污染。

### 2.5 边界异常机制

- 写统计失败只打日志，不影响主业务。
- 供应商 usage 缺失时保持 `null`，不伪造 0。
- 失败调用也写入流水，便于前端展示错误摘要。
- Rerank 未启用、未配置 Key 或候选不足时记录为 `SKIPPED`。
- 明细分页在服务层限制 `pageSize <= 100`，避免一次拉太多。
- 前端刷新统计失败时不覆盖主流程成功提示。

### 2.6 前端设计

入口：创作工作台顶部 tabs 新增“开销统计”。

页面分三层：

1. 总览卡：总 token、总耗时、失败调用。
2. 分类卡：文本 LLM、向量化模型、Rerank 模型。
3. 明细列表：模型分类、场景、状态、模型名、token、耗时、输入数量、时间、call/trace/request ID。

页面保持轻量，不上复杂图表。这样更适合调试和核对，不会让初期功能变重。

## 四、验证清单

后端：

- 文本 LLM 成功后 `llm_api_call_log` 有 `TEXT/SUCCESS`。
- 文本 LLM 抛异常后有 `TEXT/FAILED`。
- 向量索引或检索触发 Embedding 后有 `EMBEDDING` 记录。
- Rerank 未启用或候选不足时有 `RERANK/SKIPPED`。
- `GET /api/llm-usage/tasks/{taskId}/summary` 能返回分类汇总。
- `GET /api/llm-usage/tasks/{taskId}/calls` 能分页和按分类过滤。

前端：

- 选择任务后打开“开销统计”能看到总览。
- 运行发布前优化后统计自动刷新。
- 运行反馈分析、反馈追问、证据索引后统计自动刷新。
- 分类筛选能切换全部、文本 LLM、向量化和 Rerank。
- 小屏下统计卡和明细不横向溢出。
