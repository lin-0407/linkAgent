# 视频自动制作 S0：代码基线与 S1 接入清单

> 核对日期：2026-10-19。依据：[详细设计](面向新手与小UP的视频自动制作与修改方案.md)第 21.2 节。
>
> 本轮为 S0，只核对代码、运行资源和测试基线，交付后续具体改动范围。没有实施自动出片、修改、选版、任务预算或新界面，没有修改真实任务、原片、BV 绑定和数据库。

## 1. 核对结论

业务主线保持“方案确认 → 制作蓝图 → 成片处理与试映 → 用户投稿 → BV 绑定 → 反馈与复盘”。新增制作能力接入原业务服务，不另建一套试映、存储或 Agent 框架。

S1 的首要前置问题是**真实多版本和发布版本归属**。当前数据库虽然允许不同版本号，但上传、当前成片查询和发布后门禁仍按单一 V1 运作。仅新增渲染器会使后续修改、用户自有成片上传和旧版报告发生冲突。

本轮开始时 `git status --short --untracked-files=no` 有 57 项已有变更，包括 SQL、LLM、记忆、前端和媒体服务。保持原状，不清理、暂存或覆盖。`docs/` 当前受本地忽略规则影响，新文档不会自动出现在普通 `git status`，本轮不改变作者的 Git 隐藏规则。

## 2. 当前业务事实及写入位置

| 事实 | 当前代码 | S1 接入差异 |
|---|---|---|
| 当前成片 | `MediaUploadMapper.findDraftVideo` 限定 `version_no = 1` | 改为明确当前版本指针；没有工作区的旧任务继续回退原 V1，不能用最大版本号推断用户选择 |
| 创建上传 | `MediaUploadService.createUpload` 使用 `P0_VERSION_NO = 1`；完成或上传中的 V1 会拒绝覆盖 | 新文件分配新版本；未完成上传的续传始终绑定自己的目标版本 |
| 失败重传 | `MediaUploadPersistenceService.saveCreatedUpload` 锁旧上传会话，重置原成片对象键，返回旧会话供事务外清理 | 区分同会话恢复与新文件上传；完整历史版本、历史对象和报告不可因新上传而重置 |
| 完成上传响应 | `MediaUploadService.completeUpload` 在首次完成及幂等返回时，通过 `requireDraft(ownerId, taskId)` 查当前 V1 | 必须按上传会话的 `versionId` 返回；否则旧会话完成可能返回另一条视频 |
| 探测 | `DraftVideoProbeService` 精确探测按版本；`getCurrentDraftVideo` 仍通过固定 V1 查询 | 保留精确版本接口，当前查询跟随明确指针；恢复旧探测不得改新版本 |
| 媒体预处理 | `MediaProcessingService`、`MediaProcessingWorker` 已按版本和 job 处理 | 复用精确版本关系，不把别的版本结果当当前结果 |
| 试映与修改清单 | `PreflightReviewService` 创建试映按版本；`listEditTasks` 从固定 V1 查当前报告 | 当前清单跟随当前版本，旧报告继续按其真实版本读取 |
| BV 绑定 | `CreatorBilibiliService.bindBvToTask` 检查当前媒体后保存任务与 BV；`creator_task_video_binding` 没有 `published_version_id` | 同事务核对并记录正式版本与发布快照，避免选版并发使检查对象和绑定对象不一致 |
| BV 同步通过 | `BilibiliVideoSyncPersistenceService.canUpdateBindingStatus` 推进 `BOUND` 前检查媒体门禁 | 延迟校验也必须对应原绑定的版本；不能把后来选中的视频当原发布视频 |
| 反馈与复盘 | `CreatorFeedbackService`、`CreatorFeedbackEvidenceIndexService`、`CreatorReportService` 进入发布后时调用媒体门禁 | 有正式发布版本时按发布快照读取，不能跟随工作区后来选择；缺失历史版本信息保留未知 |
| 主动删除媒体 | `MediaDeletionService.deleteMedia` 锁指定版本，删除该版上传对象与派生素材，保留报告并标记证据不可用 | 保持按版本删除；检查当前指针和发布快照的处理，不能误删其他版本；没有可用媒体的旧版不能被重新选为可发布版 |

关键源码位于 `backend/src/main/java/com/link/linkagent/creator/`。多版本唯一键 `uk_draft_video_task_version(task_id, version_no)` 已存在，保留；不重建成片表。

## 3. 门禁必须一起保留

- `ProductionPlanGateService.ensurePrePublishConfirmed`：最新发布前会话真实确认，确认结果对应当前方案。
- `ProductionPlanGateService.ensureReadyForPreflight`：普通任务蓝图为 `READY` 且无未完成步骤；已有成片只使用用户显式保存的 `planning_skipped`。
- `CreatorMediaWorkflowGateService`：当前媒体探测就绪、对应版本预处理完成、试映对应该预处理 job 且已完成。
- `ProductionPlanGateService.ensureRepositionAllowed`：已有发布事实的任务不重新定位制作蓝图。

这些判断目前分布在方案、蓝图和媒体服务中。S1 需要统一版本上下文，不能把新视频写成已试映，不能让模型代填确认或伪造跳过事实。

现有 `CreatorMediaWorkflowGateServiceTest` 覆盖已有成片跳过、缺失试映、旧处理 job 报告、只读就绪检查等；`ProductionPlanGateServiceTest`、`MediaUploadServiceTest`、`MediaDeletionServiceTest` 可作为兼容回归入口。它们不能替代 S1 所需的真实数据库并发验证。

## 4. Agent 与媒体接入

- 当前 `ProductionBlueprintGenerator`、`PrePublishSuggestionService`、`AudienceScreeningService` 仍调用 Java `LLMService`。Python 的 `agent/src/linkagent_agent/api/agent_api.py` 提供 `/agent/text`、`/agent/structured` 协议入口，不代表创作业务已切换到 Python。
- Java 继续拥有业务表、授权、费用和状态；渲染器只收结构化工程，不能读取 `.env` 或自行调用供应商。
- `ObjectStorageService` 已有 `putObject`、`downloadObject`、`headObject` 和分用途私有读取签名，可用于自动成片入库，不新增存储客户端。
- `LlmApiUsageService` 已有按任务、工作流汇总调用用量的入口；不能把已有用量汇总当成新方案的并发预算预留。S1b 需让实际调用、预留和最终流水关联，并避免同一次调用重复入账。
- 配置来源是 `storage.s3`、`MEDIA_S3_*` 和 `creator.media`；主 Compose 把媒体工作目录挂到 `/var/lib/linkagent-media-work`。后端、浏览器和供应商端点分开配置。
- `.env` 中实际 `MEDIA_S3_INTERNAL_ENDPOINT / BROWSER_ENDPOINT / PROVIDER_ENDPOINT`、密钥对、桶和 `DASHSCOPE_API_KEY` 均非空；本轮只检查存在性，没有打印其值。配置非空不证明网络、CORS、签名或供应商读取可用。

## 6. 下一步 S1 的具体范围

按可闭环子步骤推进，不同时启动后续 S2–S8：

1. **S1a：真实多版本与发布版本归属。** 在现有 `init.sql` 增量维护工作区的当前版本、下一序号和乐观锁等必要字段；改固定 V1 查询、上传创建/完成/续传返回、精确版本读取，接好 BV 的正式版本关系和既有门禁。提供工作区只读恢复、版本列表及显式选版的必要接口，路径沿用详细方案第 13 节。新文件是新版，选旧版不复制或覆盖原媒体；历史绑定不按最大版本号猜补。
2. **S1b：制作运行与任务预算基础。** 按实际使用建立授权、运行、步骤和费用字段；完成指纹、幂等、工作区乐观锁、唯一活动运行、预算预留及释放。故事板和资产字段随真实用例增加，不先生成无人调用的空服务。

S1a 主要修改范围：`init.sql`、`creator/media/upload`、当前媒体查询、工作流门禁、`creator/bilibili` 的绑定持久化与读取，以及 `creator/creation` 必要领域服务；前端旧成片入口按接口变化做最小适配。不改变账号、租户、长期记忆、RAG 和全局 Node 配置。

S1 必须增加隔离 MySQL 行为测试：旧任务 V1 回退、两版并存、续传只对应目标版、完成响应不串版、并发分配序号不冲突、旧乐观锁不能覆盖新选择、缺失或删除媒体不能被选为可发布版、绑定与选版竞态、发布后读取不随当前指针漂移。S1b 再验证同时启动只成功一个、预算并发不能透支、未知费用不能按零释放。不连接作者现有评测库。

### 6.1 进入 S1 前的自查补充

2026-10-19 按作者“先审查再继续”的要求复核：S0 的 31 项结果只能作为单元测试基线；完成上传的三条返回路径（首次成功、已完成重放、`VERIFYING` 恢复）都需要精确按会话版本读取，不能只修改某一条成功分支。
