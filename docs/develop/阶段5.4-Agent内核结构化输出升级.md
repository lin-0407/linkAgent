# 阶段 5.4 - Agent 内核结构化输出升级（结构化 ReAct）

> 承接 5.3（Agent 工具化 + 内核统一）。**作者 2026-06-09 在 5.3 进行中拍板重定方向**：现有自研 ReAct 只能「提示词哄 JSON + 正则解析」、无法保证确定性、不足以成为亮点。本阶段把 ReAct 内核从「自由文本 + 正则」升级为「**受 schema 约束的结构化每步 I/O**」，并为后续 PAE / 多智能体打底。
>
> **路线已定（作者 2026-06-09 拍板）**：① 推进顺序 = **内核优先**（先做本阶段，再提示词热更库，再设置面板，再回到 5.3b）；② 确定性档位 = **json_object + 自校验**（保留自研循环、可移植、可靠性大升；不走 strict-mode function-calling 那种把工具选择交给模型、偏离纯自研循环的路）。
>
> 编码、测试由作者执行。本文件是需求 + 可行性核实 + 设计 + 切片 + 决策。

---

## 1. 需求分析

### 1.1 痛点

自研 ReAct（`core.AgentExecutor`）每轮把 LLM 自由文本用正则抠 `Thought/Action/Action Input/Final Answer`（见 `AgentExecutor` 的 `FINAL_ANSWER/ACTION/ACTION_INPUT/THOUGHT` Pattern）。问题：

- **不确定性**：模型一旦格式漂移（多一行、少冒号、JSON 混在文本里），正则就解析失败，只能回喂「格式错误请重试」，靠模型自觉。
- **业务结构化更脆**：发布前优化等 4 个 service（`PrePublishSuggestionService` / `CreatorFeedbackService` / `CreatorCompetitorService` / `CreatorReportService`）产固定 JSON 时，全是「`LlmJsonUtil.extractJsonObject` 截 `{}` + Jackson 解析、失败回落 `RAW_ONLY`」，零 schema 约束、零重试。
- **没亮点**：纯文本 ReAct 是「最低等配置」。真正的系统设计亮点是「**自研编排内核 + 每步 schema 约束 + 校验的结构化 I/O**」，模型负责生成、编排智能归己。

### 1.2 本阶段做什么 / 不做什么

**做**：
- 新增**结构化输出原语** `LLMService.chatStructured(system, user, type)`：`response_format=json_object`（API 级保证合法 JSON）+ `BeanOutputConverter`（按目标类型生成 schema 指令并解析为强类型）+ 失败重试。
- 定义 ReAct 每步的结构化载体 `core.ReActStep`。
- 让 `AgentExecutor` 多一条**结构化循环**：每步产 `ReActStep` 对象而非正则解析自由文本；**默认关、与现有文本循环并存**，开关切换。
- 保留自研循环骨架与 `ToolRegistry`（不走 Spring AI `.tools()` 原生 function-calling）。

**不做（本阶段边界）**：
- 不删除现有文本 ReAct（保留为默认、零回归兜底；结构化路验证稳了再议默认值）。
- 不做提示词 DB 热更库、不做设置面板（排在本阶段之后，见总体路线）。
- 不做 PAE / 多智能体（本阶段只把「结构化每步」这块地基打好，它是 PAE 的步骤表示与多智能体结构化消息的前置）。
- 业务 JSON（11 字段建议等）的结构化改造列为 **5.4-3（可选）**，与 5.3b 发布前优化接入合流再做，避免本阶段铺太宽。

### 1.3 输入输出

- 输入：现有 `/api/agent/chat` 的用户消息、现有任务材料。
- 输出：开启结构化内核开关时，ReAct 每步走 `ReActStep` 强类型；对外接口与返回 DTO（`AgentChatResponse`）不变。
- 不新增对外业务接口。

## 2. 现状与可行性核实（已联网 + javap 字节码核实）

### 2.1 底座已就绪

- `LLMService` 底层就是 Spring AI **`ChatClient`**（构造器注入 `ChatClient.Builder` 后 `build()`），统一入口 `chatWithUsage(system,user)`：先 `validatePromptLength` 成本 guard，再 `ChatClient.prompt().system().user().call().chatResponse()`，回 `LlmCallResult`（含 usage）。**新原语必须复用这套 guard，不另起一套。**
- 5.2b 的 `HydeQueryTransformer` / `KnowledgeQueryEnhancer` 已直接用 `ChatClient`，证明 ChatClient 工程化可用。
- `AgentExecutor` 是**全栈唯一**还在「自由文本 + 正则」的地方。

### 2.2 DeepSeek V4 能力（`.env`=`deepseek-v4-flash`，OpenAI 兼容，已联网核实）

| 能力 | 支持 | 用法 / 限制 |
|---|---|---|
| `response_format:{type:"json_object"}` | ✅ | 只保证 **JSON 语法合法**，不强制字段 schema；**prompt 必须含 "json" 字样**（API 级 400），故 schema 仍须自校验 |
| `response_format:{type:"json_schema"}`（最终消息严格 schema）| ❌ | 标准 response_format 不支持 |
| function-calling + strict 模式 | ✅ | 服务端强校验工具入参 schema——本阶段**不用**（会把工具选择交给模型、偏离自研循环，留作后续「最硬确定性」可选项）|

> 结论：DeepSeek 上「保留自研循环」的最优确定性 = **json_object（语法保证）+ 自校验/重试**，正是作者拍板档位。

### 2.3 Spring AI 1.1.4 结构化输出 API（javap 反编译 `.m2` 1.1.4 jar 核实，签名可用）

| 符号 | 核实结果 |
|---|---|
| `org.springframework.ai.openai.api.ResponseFormat.Type` | 枚举含 `TEXT / JSON_OBJECT / JSON_SCHEMA` |
| `new ResponseFormat(Type, String)` / `ResponseFormat.builder()` | 均存在 |
| `OpenAiChatOptions.builder().responseFormat(ResponseFormat).build()` | Builder 有 `responseFormat(ResponseFormat)`；类 `implements StructuredOutputChatOptions` |
| `ChatClientRequestSpec.options(T extends ChatOptions)` / `.system(String)` / `.user(String)` / `.call()` | 均存在 |
| `CallResponseSpec.entity(Class<T>)` | 存在（另有 `entity(StructuredOutputConverter<T>)`、`responseEntity(Class<T>)` 可同时拿 ChatResponse+T 做 usage）|
| `BeanOutputConverter<T>(Class<T>)` + `getFormat()` / `getJsonSchema()` / `convert(String)` | 均存在；`.entity(Class)` 内部即隐式用它 |

## 3. 设计

### 3.1 结构化原语 `LLMService.chatStructured`

```
<T> T chatStructured(String systemPrompt, String userMessage, Class<T> type)
```

- 复用 `validatePromptLength`（同一成本 guard）。
- `OpenAiChatOptions.builder().responseFormat(new ResponseFormat(JSON_OBJECT, null)).build()` → `.options(...)` 挂到本次请求（仅设 responseFormat，**模型等默认项经 Spring AI option 合并保留**，见 §9 运行期待确认）。
- `.entity(type)`：隐式 `BeanOutputConverter` 既把目标类型的 schema 指令追加进 prompt（同时满足 DeepSeek「prompt 含 json」要求），又把响应解析成强类型 `T`。
- **失败重试**：`.entity()` 解析失败抛异常 → 捕获重试，最多 `STRUCTURED_MAX_ATTEMPTS=3` 次，仍失败抛出最后异常（交由调用方按场景兜底）。
- 泛型 `<T>`：本阶段服务 `ReActStep`，5.4-3 / 5.3b 复用于业务 JSON（11 字段建议等）——这是全应用唯一的结构化出口，不是过早抽象（已有 5+ 个手搓解析点等着收敛）。

### 3.2 `core.ReActStep`

ReAct 每步的结构化载体（record）：

| 字段 | 含义 |
|---|---|
| `thought` | 本步推理 |
| `action` | 要调用的工具名（终止步为空）|
| `actionInput` | 工具输入（终止步为空）|
| `finalAnswer` | 终止答案（非空即终止）|

语义与文本 ReAct 完全一致，只是把「正则抠四段」换成「强类型四字段」：`finalAnswer` 非空 → 终止；否则 `action+actionInput` → 调工具。

### 3.3 双路并存（零回归核心）

`AgentExecutor` 加一条结构化循环（5.4-2），由开关 `agent.kernel.structured.enabled`（默认 **false**）切换：

- 关（默认）：走现有文本 + 正则循环，**字节级不动 = 现有 `/agent/chat` 零回归**。
- 开：每轮 `llmService.chatStructured(structuredSystemPrompt, conversation, ReActStep.class)` → 强类型步 → 同一套 `ToolExecutor` 执行 → 拼回对话。终止/工具分发逻辑与文本路一致。

> 自研循环骨架、`ToolRegistry`、`ToolExecutor`、记忆全部不变；**只把「每步怎么从 LLM 拿到决策」从正则换成结构化**。这才是「同一自研内核、I/O 升级」，不是另起 Spring AI 一套。

## 5. 5.4-1 详细设计（已编码）

**新增 `core.ReActStep`（record）**：四字段 + `isFinal()` / `hasAction()` 便捷判断；中文注释解释每字段为何存在。

**改 `llm.LLMService`**：新增 `chatStructured`（见 §3.1）+ 常量 `STRUCTURED_MAX_ATTEMPTS=3` + 一个 logger（重试告警）。新增 import：`OpenAiChatOptions` / `ResponseFormat` / slf4j。其余方法、构造器、guard 不动。

- 为什么放 `LLMService`：结构化输出是「调模型」的能力，归 LLM 服务层最自然，且能复用其成本 guard 与（后续）usage 统计，不让 AgentExecutor 直接持有 ChatClient 选项细节。
- 为什么泛型而非专为 ReActStep：见 §3.1，唯一结构化出口、多调用点在即。

**5.4-2 落地要点（已编码）**：
- 开关 `agent.kernel.structured.enabled`（`@Value` 默认 false、不入 yml，沿用「Java 默认不入 yml」惯例；测试时在 yml/env 置 true）。
- `run()` / `runTask()` 顶部各加开关分支：开 → 结构化路，关 → 原文本循环（**文本循环字节级不变 = 零回归**）。
- **只抽结构化共享循环** `runStructuredLoop`（run + runTask 共用）；文本两份循环保持独立不动（守零回归）——这是 rule of three 在 5.4 被越过后的应有动作。记忆写回抽成 `persistChatTurn`（文本-run + 结构化-run 共用），结构化-runTask 与文本-runTask 一致不写记忆。
- `runStructuredLoop` **不**包 try/catch：`chatStructured` 内部已重试，仍失败（或成本 guard 的 400）直接上抛、不误当格式错误；仅「合法 JSON 但无 finalAnswer / 无 action」在循环内回喂错误重试。对话历史仍用文本回灌（模型读历史无需结构化、省 token），下一步仍按 schema 产出。

## 6. 关键决策

- **确定性档位 = json_object + 自校验（作者拍板）**：可移植到任何 OpenAI 兼容模型、保留自研循环、可靠性大升；strict-mode function-calling 留作后续「最硬确定性」可选项（§2.2）。
- **保留自研循环、不走 `.tools()` 原生协议**：兑现「自研内核编排」叙事，且与 5.3a 的自研 `Tool` 接口、5.3b-1 的 `runTask` 直接兼容。
- **双路并存、默认关**：承袭 5.2/5.3 的零回归纪律，文本路作兜底，结构化路验证稳了再议默认。
- **5.4-1 不碰 AgentExecutor**：碰内核的风险隔离到 5.4-2。

## 9. 运行期待确认 / 已知坑

- **option 合并保留模型**：`chatStructured` 的 `.options(...)` 只设 `responseFormat`，未设 `model`。Spring AI 在 `OpenAiChatModel.call` 内把运行期 options 合并到模型默认 options（非空覆盖、null 回落默认），故配置的 `deepseek-v4-flash` 应被保留。**待作者实跑确认**：若结构化调用报模型缺失，则在该 options 上显式补 `.model(...)`。
- **DeepSeek json_object 偶发空内容**：官方文档注明 json_object 模式偶发返回空 content，本设计的重试可兜一部分；若高频出现，需在 prompt 内补一个目标 JSON 示例。
- **记录踩坑**：本阶段结束（5.4 全部切片自测通过）后，在 `docs/error` 补阶段性踩坑记录、`docs/reference` 补说明文档，并更新 `AGENTS.md` / 内层 `CLAUDE.md` 文档表。
