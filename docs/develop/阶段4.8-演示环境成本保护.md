# 阶段 4.8 - 演示环境成本保护

## 需求分析

阶段 4.7 已经把项目整理成 Docker Compose 演示环境，但如果后续把演示地址发给面试官或同学试用，最大风险不是页面打不开，而是用户提交超长文稿、评论或弹幕样例后直接触发大模型调用，导致成本不可控。

本轮目标用户是项目作者和演示环境试用者，解决的具体场景是：

1. 作者希望演示环境可以放心接入真实 `LLM_API_KEY`。
2. 试用者输入过长内容时，系统能在调用模型前给出明确提示。
3. 后续作者可以通过环境变量调整保护强度，而不是改代码。

本轮做：

1. 在统一 LLM 调用入口增加输入规模保护。
2. 新增 `agent.llm.guard` 配置项。
3. 在 Docker Compose 和 README 中暴露对应环境变量。
4. 增加后端单元测试，覆盖开启和关闭保护两种路径。

本轮不做：

1. 不做登录账号体系。
2. 不做 IP 级限流。
3. 不做 token 级精算。
4. 不做模型供应商账单统计。

## 设计方案

### 保护位置

保护逻辑放在：

```text
backend/src/main/java/com/link/linkagent/llm/LLMService.java
```

原因：

1. 发布前优化、评论追问、复盘报告和通用 Agent 都会经过 `LLMService`。
2. 放在统一入口可以避免每个业务 Service 重复写一遍限制。
3. 在调用 Spring AI 前短路，可以避免已经产生模型请求后才失败。

### 配置项

新增配置：

```yaml
agent:
  llm:
    guard:
      enabled: true
      max-prompt-chars: 30000
```

对应环境变量：

```text
LLM_GUARD_ENABLED=true
LLM_GUARD_MAX_PROMPT_CHARS=30000
```

这里先用字符数作为粗粒度保护，而不是 token 计算。原因是项目当前没有统一 tokenizer，强行引入 token 计算会增加依赖和学习成本；MVP 演示阶段先挡住明显超长输入即可。

### 错误返回

当 `system prompt + user prompt` 超过限制时，后端返回 `400 BAD_REQUEST`，提示用户先精简文稿、评论或弹幕样例。

## 编码实现

新增后端文件：

```text
backend/src/main/java/com/link/linkagent/llm/LlmCallGuardProperties.java
backend/src/test/java/com/link/linkagent/llm/LLMServiceTest.java
```

修改文件：

```text
backend/src/main/java/com/link/linkagent/llm/LLMService.java
backend/src/main/resources/application.yml
docker-compose.yml
README.md
```

关键实现：

1. `LlmCallGuardProperties` 负责绑定 `agent.llm.guard` 配置。
2. `LLMService` 在 `chat` 方法里先调用 `validatePromptLength`。
3. 超限时抛出 `ResponseStatusException(HttpStatus.BAD_REQUEST, ...)`。
4. 单元测试覆盖开启保护超限、关闭保护放行两条路径。

## 测试验证

作者本地执行：

```bash
cd backend
mvn test
```

重点观察：

1. `LLMServiceTest` 应通过。
2. 原有创作者工作台相关测试不应受影响。
3. 将 `LLM_GUARD_MAX_PROMPT_CHARS` 调小后，提交长文稿应返回 400。
4. 将 `LLM_GUARD_ENABLED=false` 后，保护逻辑应放行。

## 后续扩展

1. 如果演示环境真正公网开放，再补 IP 级限流或演示口令。
2. 如果后续要做多模型成本对比，再引入 token 统计。
3. 如果作者开始录制完整演示视频，可以把默认限制压得更小，确保所有样例都在可控范围内。
