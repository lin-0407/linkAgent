# 阶段 2.5：长期记忆 MySQL 读写骨架

## 上下文

阶段 2.1 到 2.4 已经完成短期记忆、Redis 存储、摘要触发和摘要后裁剪。本轮开始补长期记忆，但只做最小可验证的 MySQL 读写，不接 LLM 自动抽取，也不接 Milvus 向量检索。

## 本轮目标

先让系统具备“保存用户事实 / 偏好”和“按用户读取长期记忆”的基础能力。后续 Agent 自动抽取记忆时，只需要调用这一层，不需要重新设计存储边界。

## 本轮变更

- 新增 `LongTermMemoryRecord`：长期记忆记录对象。
- 新增 `LongTermMemoryMapper`：基于 MyBatis 注解访问 `t_long_term_memory`。
- 新增 `LongTermMemory`：封装长期记忆保存、按 key 查询、按用户列表查询。
- 新增 `MemoryController`：提供长期记忆手动读写接口。
- 新增 `LongTermMemorySaveRequest` 和 `LongTermMemoryResponse`。
- 修改 `sql/init.sql`：将 `(user_id, memory_key)` 改成唯一键，支持同一用户同一记忆键覆盖更新。
- 新增 `LongTermMemoryTest`：验证参数清洗、空来源会话处理和 limit 兜底。

## API

### 保存或更新长期记忆

```http
POST /api/memory/long-term
Content-Type: application/json

{
  "userId": "default",
  "memoryKey": "user.preference.language",
  "content": "用户偏好使用 Java 和 Spring AI 开发 AI 应用",
  "sourceSessionId": "session-1"
}
```

### 查询用户长期记忆列表

```http
GET /api/memory/long-term/users/default?limit=20
```

### 按 key 查询单条长期记忆

```http
GET /api/memory/long-term/users/default/keys/user.preference.language
```

## 设计说明

`memory_key` 使用类似 `user.preference.language` 的命名方式，是为了让早期长期记忆保持可解释、可调试。当前阶段不做复杂的事实合并，遇到同一个用户的同一个 key 时直接覆盖，这是最容易验证的策略。

Mapper 使用注解 SQL，而不是 XML。原因是当前 SQL 很短，注解更容易在学习阶段快速定位读写逻辑。等长期记忆查询复杂起来，再迁移到 XML 或专门的 Mapper 文件更合适。

## 验证方式

```bash
cd backend
mvn test -Dtest=LongTermMemoryTest
```

完整验证需要先执行数据库脚本：

```bash
mysql -u root -p < src/main/resources/sql/init.sql
```
