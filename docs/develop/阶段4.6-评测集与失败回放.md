# 阶段 4.6：评测集与失败回放

## 需求分析

阶段 4.5.2 之后，工作台已经能把创作任务、发布前优化、评论弹幕分析和复盘报告串起来，但还缺两样关键能力：

1. 没有一套稳定的样例评测集，后续很难比较同一任务在不同调整后的表现。
2. 工作流步骤虽然已经落库，但还没有统一的回放入口，失败后只能靠日志猜。

本轮只解决“评测样例可沉淀、结果可记录、步骤可回放”这三个问题，优先服务创作者工作流，不把项目做成通用评测平台。

本轮做：

1. 新增评测用例表和评测结果表。
2. 提供评测用例的创建、查询、列表接口。
3. 提供评测结果的记录、查询、列表接口。
4. 暴露工作流步骤查询接口，给失败回放留入口。
5. 在初始化脚本里补 5 组可直接演示的样例用例。
6. 在创作工作台提供“开发者测试”入口，打开独立弹窗进行样例筛选、结果录入和最近结果查看。

本轮不做：

1. 不做自动评分 Agent。
2. 不做批量评测调度。
3. 不做多模型对比页面。
4. 不做独立评测后台。

## 设计方案

### 后端接口

新增评测集接口：

```text
POST /api/creator/evaluations/cases
GET  /api/creator/evaluations/cases
GET  /api/creator/evaluations/cases/{caseId}
POST /api/creator/evaluations/cases/{caseId}/results
GET  /api/creator/evaluations/cases/{caseId}/results
```

新增工作流步骤查询接口：

```text
GET /api/creator/tasks/{taskId}/workflow/sessions/{sessionId}/steps
```

评测结果会保留：

1. 模型原始输出。
2. 失败原因。
3. 耗时和 token。
4. 人工评分项。

这样后续复盘时可以直接看“样例输入 -> 工作流步骤 -> 模型输出 -> 人工评分”这一整条链路。

### 数据表

新增两张表：

1. `creator_eval_case`
2. `creator_eval_result`

字段设计原则：

1. 用例表保存输入快照，不依赖外部临时输入。
2. 结果表保存原文、耗时、token、失败原因和人工评分。
3. 表字段注释全部用中文，便于直接读建表脚本。

### 前端交互

本轮不做独立评测后台，但要把开发者评测和创作者主流程分开：

1. 工作台右上角提供“开发者测试”按钮，点击后打开独立弹窗。
2. 主导航只保留创作者主流程：任务输入、发布前优化、评论弹幕、分析结果。
3. 开发者测试弹窗展示内置样例、阶段筛选、输入快照、期望要点、人工评分表单和最近结果。
4. 发布前优化工作流区继续保留“步骤回放”面板，供具体 session 排障。

原因：

1. 失败回放最常用的是工作流上下文，不是独立报表。
2. 评测集不是创作者主流程，不能和创作者任务页签并列，否则会打乱页面信息架构。
3. 现有工作台已经围绕 `taskId` 展开，继续放在同一页更顺手。

## 测试验证点

作者本地后端验证：

```bash
cd backend
mvn test
```

作者本地前端验证：

```bash
cd link-agent-frontend
npm run type-check
npm run build
```

联调验收：

1. 能创建评测用例并查到完整输入快照。
2. 能记录一次评测结果，并保留 raw output、失败原因和人工评分。
3. 能通过工作流步骤接口看到发布前优化的步骤回放。
4. 页面里能直接刷新步骤，而不是只看最终结果。
5. 创作者主导航不出现样例评测，只保留用户主工作流。
6. 点击“开发者测试”后，独立弹窗能展示样例详情和评测结果录入表单。
7. 在窄屏下，开发者测试弹窗、样例详情和评分项不会横向溢出。

## 后续扩展

1. 后续可以补评测样例创建表单，但优先级低于主业务闭环。
2. 可以再把评分项汇总成统计图表，但先把样例积累起来。
3. 如果后续要做多模型对比，再基于这两张表扩展，而不是重新设计一套评测模型。
