# 视频自动制作 S1：重新定位与历史版本隔离修复

> 日期：2026-10-19。接续 [S1a-1 独立版本上传](视频自动制作-S1a-1独立版本上传实现说明.md)，依据详细方案第 12.7 节的历史保留要求。
>
> 本轮修复多版本接入后的业务兼容问题，没有上线版本列表、选版、发布快照或自动出片。没有部署作者服务或修改真实业务库。

## 1. 发现的问题

1. **重新定位会损坏历史事实。** `ProductionPlanPersistenceService.startGenerating` 原先批量重置所有成片的探测字段，将所有上传会话标记为被替代，并逻辑删除预处理和试映任务。普通新文件上传虽已独立存版本，重新定位仍会让已完成旧版及其报告不可用。此前 59 项回归没有验证这条链路。
2. **旧请求可能跨越制作方向。** 上传请求在事务外检查蓝图并创建 OSS 分片，在这段时间内可能已经重新定位；只在最后检查是否存在上传和 BV，无法确认这个请求仍属于当前制作上下文。
3. **本地续传记录可能把历史版本显示成当前版。** `useMediaUpload.restoreStoredUpload` 原来只读取本地保存会话的精确成片。旧会话保持 `COMPLETED` 后，页面刷新可能把它恢复为当前成片，忽略后端当前版本已撤下或切换的事实。

## 2. 修复后的行为

### 2.1 重新定位只撤下当前指针，保留已完成媒体和试映

`ProductionPlanPersistenceService` 与上传、BV 绑定共用任务行锁，并在事务内重新检查 `BOUND` 或 `published_flag` 等正式发布事实。已经发布的任务继续要求新建修订任务，不能依赖事务外的旧检查放行。

随后按稳定顺序锁定任务的成片行，保持与媒体删除、探测和试映的锁顺序一致。显式写入才采纳工作区，清空 `current_video_version_id` 并递增 `workspace_revision`；新方向不再依靠旧片和旧报告进入发布后链路。旧任务也建立明确空指针，不会因为 V1 回退而把原片选回来。

| 对象状态 | 本轮处理 |
|---|---|
| 已完成上传、完整旧视频 | 保留对象身份、版本号、探测字段和关联信息 |
| 已完成或其他终态的预处理、试映 | 保留状态、报告正文和读取资格，不逻辑删除 |
| `CREATED/UPLOADING/VERIFYING` 上传 | 标记 `SUPERSEDED`，旧会话不能再登记完成并切回当前 |
| `QUEUED/RUNNING` 预处理 | 标记 `FAILED`，释放租约并记录终止原因 |
| 活动试映 | 标记 `CANCELLED`，清除租约和下次领取时间，保留已有输出 |
| 未完成上传的成片 | 收敛为 `UPLOAD_ABORTED` |
| `PROBING` 成片 | 收敛为 `PROBE_FAILED` 并撤销探测领取标识，迟到探测不能登记为成功 |

任务级反馈、竞品、总体复盘和派生偏好的失效规则仍沿用原业务；本轮保留的是按具体视频版本存储的媒体与试映历史，不把旧任务级复盘当成新方向的复盘。

指针撤下、活动任务收敛、未核验 BV 清理及新蓝图插入在同一事务中。插入新蓝图失败时全部回滚。模型与 OSS 请求仍在事务外，没有为了加锁延长到网络调用期间。

### 2.2 上传创建校验原始制作上下文

`MediaUploadService` 在门禁检查和 OSS 创建前读取工作区修订号；`MediaUploadPersistenceService.saveCreatedUpload` 在任务锁内核对该修订号。上下文变化时返回 409，事务外补偿只取消本请求新建的 OSS 分片，保留历史对象。

因此，即使新方向的蓝图在旧请求返回前已经变成 `READY`，旧请求也不会被误认为新方向的上传。同一幂等请求已成功时仍返回原会话，不重复分配版本。

### 2.3 页面恢复服从后端当前指针

`frontend/src/composables/creator/useMediaUpload.ts` 恢复已完成会话时，先查询后端当前成片并核对 `versionId`。匹配后才把会话和成片写入当前页面状态。

- 当前成片为 404：清除本地旧续传指针和上传展示状态。
- 当前成片已是另一版：清除本地旧指针，让页面原有流程恢复真正当前版。
- 网络异常：沿用错误处理，不把旧会话提前显示为已确认的当前成片。
- 未完成的续传仍使用原上传会话；历史版本的精确读取接口不变。

原 `PreflightTab.restorePersistedDraft` 已处理当前成片 404；工作台重新定位回调也会清空当前媒体展示。没有新增页面入口、样式或 Node 配置。

## 3. 范围

修改了 `ProductionPlanMapper`、`ProductionPlanPersistenceService`、`MediaUploadMapper`、上传应用/持久化服务及上传恢复 hook；更新原单元测试并扩展真实 MySQL 集成测试。

外部 API 路径、请求与响应字段、Jakarta Validation 和统一 SQL Schema 均未变。新增的任务内版本锁与上下文参数是内部调用调整。用户已经确认的发布方案和真实发布数据没有被补造或修改。

版本列表/选版、精确发布版本快照、按版本恢复完整方案与蓝图上下文仍待后续阶段，不能把本次历史保留修复说成完整 S1 已完成。

## 4. 实际验证

使用 Java 21 一次性构建容器和 Testcontainers 独立 `mysql:8.4`，初始化本轮统一 SQL。执行的命令：

```powershell
docker run --rm --name linkagent-creation-reposition-tests-20261019 --mount type=bind,source=E:/linkAgent/linkAgent/backend,target=/workspace,readonly --mount type=bind,source=/var/run/docker.sock,target=/var/run/docker.sock --tmpfs /workspace/target:rw,size=768m --env TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal --env TESTCONTAINERS_RYUK_DISABLED=true --workdir /workspace linkagent-first-video-final-compiled:20261018 mvn -B '-Dstyle.color=never' '-Dtest=MediaVersionPersistenceIntegrationTest,MediaUploadServiceTest,CreatorMediaWorkflowGateServiceTest,ProductionPlanGateServiceTest,MediaDeletionServiceTest,CreatorBilibiliServiceTest,ProductionPlanPersistenceServiceTest,ProductionPlanApplicationServiceTest' test
```

实际结果：`BUILD SUCCESS`，64 项通过，0 失败、0 错误、0 跳过。项目没有 `ProductionPlanApplicationServiceTest`，该名称未匹配用例，不能计为应用服务测试覆盖；实际运行的是其余 7 个测试类。539 个主源码文件和 119 个测试源码文件编译通过。

其中 `MediaVersionPersistenceIntegrationTest` 使用真实 MySQL 的 14 项测试全部通过。在前次 9 项基础上新增验证：

1. 重新定位保留已完成视频的时长、画幅、对象身份、报告正文和可读状态；只收敛活动任务。旧上传、探测、预处理和试映的迟到结果不能恢复当前指针或成功状态。
2. 新蓝图插入失败时，当前指针、修订号、旧报告及待核验 BV 记录整体回滚。
3. OSS 创建期间已经重新定位，且新蓝图已经就绪时，旧请求仍被 409 拒绝；仅补偿取消自己的新分片，不删除旧对象。
4. BV 绑定与重新定位竞争时，事务内能读到先提交的正式绑定并拒绝重新定位；显式发布标记也会阻止。
5. 旧任务正在探测时重新定位，撤销原领取标识；旧 V1 不被自动选回，下一版本序号继续保留。

数据库状态由隔离测试构造，验证的是实际 SQL、锁、事务和服务编排，不是实际视频制作或供应商链路。前端遵守 AGENTS 的命令限制，本轮仅静态核对 API、状态恢复路径和差异，没有运行前端功能脚本、`npm run type-check` 或真实浏览器验收。上传恢复 hook 的页面行为仍需后续浏览器验证。

本轮修改已执行 `git diff --check`。测试构建产物位于容器 tmpfs，独立数据库由 Testcontainers 删除；按 `linkagent.scope=creation-s1` 标签及本轮 runner 名称确认无遗留。原有 `dafeiyu-napcat` 容器保持运行，没有改动其他服务、端口或数据。

没有付费模型、真实 OSS 调用和业务库 Schema 写入，没有需要作者补跑的后端测试。当前服务尚未部署这些修改。
