# 阶段 4 - 创作工作台

## 1. 项目定位与业务背景

项目从通用 Agent 框架转向面向 B 站内容创作者的 AI 创作与复盘工作台，命名为 LinkAgent Creator Copilot。

**核心定位**：基于 Spring AI 构建的视频创作者智能工作台，帮助 UP 主完成稿件理解、标题简介生成、标签建议、评论弹幕聚类、创作复盘和历史偏好沉淀。

**目标用户痛点**：

1. 发布前无法系统化判断标题、简介、标签的吸引力和贴合度。
2. 视频稿件或字幕内容较长，难以快速提炼卖点和风险点。
3. 发布后评论和弹幕信息分散，无法结构化理解观众反馈。
4. 每期视频复盘靠感觉，缺少历史沉淀和下一期选题依据。
5. 多轮创作缺少持续记忆，AI 每次都需要重新认识创作者的风格。

**MVP 边界**：第一版只覆盖从"内容输入"到"复盘报告"的完整闭环，暂不做自动投稿、视频剪辑、批量采集和复杂多 Agent 协作。

---

## 2. 核心业务流程

完整创作者工作流链路：

```
创建创作任务
  -> 输入字幕/文稿/标题草稿
  -> 发布前优化 Agent 工作流（动态消息流 + SSE）
  -> 用户确认标题、简介、标签建议
  -> 导入评论/弹幕样例（手动粘贴或 BV 脚本采集导入）
  -> 评论弹幕分析（明细分类、仪表盘、反馈追问）
  -> 输入同类型视频竞品样例
  -> 生成竞品对照报告
  -> 生成创作复盘报告
  -> 导出 Markdown 复盘报告
  -> 沉淀创作者偏好至长期记忆
  -> 下一次任务自动读取历史偏好
```

**数据来源策略**：

- 用户手动粘贴字幕、文稿、评论、弹幕。
- 用户上传本地文本文件。
- 用户输入单个 BV 后通过项目内置 Python 脚本生成并自动导入的评论弹幕 JSON/TXT 样例文件。
- 不接入 B 站开放平台真实账号授权，不做批量或定时采集。

## 3. 架构设计

### 3.1 MVC 分层

后端 Web 相关代码按标准 MVC 分层整理：

- `controller`：HTTP 接口层，只放 REST 接口定义。
- `service`：业务流程和编排层。
- `mapper`：MyBatis 数据访问层。
- `model`：请求、响应、实体、枚举等数据结构。

Agent、Tool、Memory 等底座能力保持独立包，不硬塞进 Web 分层。

### 3.2 业务包划分

```
com.link.linkagent.creator
├── task          # 创作任务：创建、状态流转、查询、编辑、删除
├── suggestion    # 发布前建议：标题、简介、标签、分区建议生成
├── feedback      # 评论弹幕分析：导入、清洗、分类、仪表盘、追问、证据索引
├── competitor    # 竞品分析：竞品视频样例、优劣势对照
├── report        # 复盘报告：生成、Markdown 导出、偏好沉淀
├── workflow      # 工作流：会话、消息、步骤、附件、SSE 事件
├── preference    # 创作者偏好：长期偏好快照存储与读取
└── evaluation    # 评测：评测用例、评测结果、Prompt 版本统计
```

### 3.3 工作流引擎

创作工作台核心升级是将"表单触发 LLM"改造为"任务驱动的 Agent 工作流"。

**核心模型**：

- 一个创作任务可包含多个工作流会话（session），每个 session 属于一个业务阶段（PRE_PUBLISH / FEEDBACK / REPORT）。
- 每个 session 包含多条消息（message），按角色分为 SYSTEM、USER、AGENT、TOOL、RESULT。
- 每个 session 包含多条执行步骤（step），记录 LOAD_CONTEXT、LLM_CALL、TOOL_CALL 等步骤的输入输出和状态。
- 每个 session 可关联用户上传的文本附件（attachment）。

**会话状态机**：

```
CREATED -> CONTEXT_LOADING -> WAITING_USER_INPUT -> RUNNING -> WAITING_CONFIRMATION -> CONFIRMED
                                                         |
                                                         v
                                                      FAILED（可重试）
```

**为什么选单 Agent + 多节点工作流**：当前目标是通过创作者业务闭环，不是展示多 Agent 编排。发布前优化和评论弹幕分析都可以拆成清晰步骤，先做清楚工作流状态比先做复杂编排更有价值。

### 3.4 SSE 消息流设计

SSE 作为实时展示通道，不是唯一数据来源。核心设计原则：

1. 工作流消息必须先落库，再发送 SSE 事件。
2. SSE 事件类型包括：session_status、message_created、step_started、step_completed、step_failed、result_ready、heartbeat。
3. 前端断线后先拉取历史消息，再重新订阅 SSE，按 sequenceNo 去重。
4. SSE 发送失败不应导致业务事务回滚。

## 4. 各业务模块核心逻辑

### 4.1 创作任务与稿件管理

**设计思路**：创作任务是整个工作台的业务入口和数据挂载点。任务主表与材料表分离，材料表按类型（TITLE_DRAFT、DESCRIPTION_DRAFT、MANUSCRIPT、SUBTITLE）拆行存储，后续可继续挂载更多材料类型而不修改主表。

**关键决策**：

- 文件导入复用材料表，不新建附件表。导入本质是"覆盖当前材料"，和手工编辑是同一类操作。
- 创建模式下先在浏览器端读取文件填入表单，编辑模式下才走后端导入接口覆盖数据库材料。
- 材料变化后任务状态回退至 DRAFT，避免旧分析结果被继续当成有效输入。
- 任务删除采用软删除（is_deleted + ARCHIVED 状态），保留历史分析和复盘记录。

### 4.2 发布前优化 Agent

**设计思路**：基于任务材料生成结构化发布前优化建议，覆盖内容摘要、受众判断、卖点、风险、标题建议、简介建议、标签建议和分区建议。第一版使用同步 LLM 调用，保留 rawOutput 用于失败回放和人工检查。后续阶段 4.4.1 升级为完整工作流 Agent。

**创作者语境升级（阶段 4.11）**：在基础建议之上新增创作者困境、观众钩子、内容定位和可执行修改计划四个高信号字段。标题建议结构增强为包含观众心理、点击理由、信任风险和适用场景的对象结构。Prompt 增加硬约束：禁止"更吸引人""提升互动"等空泛话术，每条建议必须说明"为什么当前材料会让观众点击、跳出、怀疑或收藏"。

**关键决策**：

- 不把新增字段拆成子表。当前每个任务只需一份最新建议，新增字段属于同一分析结果的一部分。
- 先升级分析框架，再升级反馈分析质量，最后用 RAG 补证据来源。

### 4.3 评论弹幕分析

**设计思路**：用户提供评论和弹幕样例后，系统生成结构化反馈分析报告。分析结果包括高频观点、情绪倾向、争议点、误解点和下一期内容建议。

**评论分类体系**：有效评论分为认可、提问、质疑、建议、情绪表达、互动六类；无效评论分为无意义、重复刷屏、广告、无关四类。弹幕分类分为知识点反应、时间点疑问、情绪高峰、共鸣认可、吐槽不满五类。

**数据采集脚本**：项目提供 `scripts/bilibili_feedback_fetcher.py`，支持按单个 BV 限量采集评论和弹幕，输出 JSON/TXT 到 `export/bilibili_feedback/`，使用标准库实现，不新增 Python 依赖。此脚本仅作为本地辅助工具，不嵌入后端定时任务。

**仪表盘与导入（阶段 4.4.1.3）**：页面支持通过 BV/视频链接触发后端受控执行固定脚本采集并自动导入，同时保留 JSON/TXT 文件上传入口。导入后自动解析并保存单条评论/弹幕明细（creator_feedback_item）和基础指标（creator_feedback_metric）。仪表盘展示评论分类、弹幕分类、情绪分布、高频关键词、弹幕时间段热度、高反馈评论和最近明细。第一版使用轻量规则进行分类，后续可替换为 LLM 分类。

**关键决策**：

- 明细表与指标表分开：明细用于分类筛选、证据查看和 RAG；指标仅服务当前任务复盘。
- 规则分类优先于 LLM 批量分类：先跑通明细层和仪表盘，避免把大量评论一次性塞进 LLM 导致成本和稳定性问题。
- 脚本路径和输出目录固定，不接收页面传入的任意脚本路径。

### 4.4 工作流融合

#### 4.4.1 发布前优化消息流（阶段 4.4.1.1）

发布前优化页面从传统表单演进为"材料栏 + Agent 消息流 + 详情抽屉 + 底部输入框"布局。任务材料不再是表单里的一次性展示，而是以系统消息逐条动态装载。用户可随时发送补充要求，补充内容作为 USER 消息保存。

#### 4.4.2 SSE 与发布前建议确认（阶段 4.4.1.2）

引入 SSE 事件流让前端实时展示 Agent 分析步骤。分析完成后会话进入 WAITING_CONFIRMATION 状态，用户必须点击"采用本轮建议"后才会推进到 COMMITTED 状态并开放下一阶段。核心设计：SSE 只负责实时通知，每条消息仍然先落库再发布事件；确认只能针对当前任务下的建议，重复确认保持幂等。

#### 4.4.3 结果弹窗化（阶段 4.4.1.4）

AI 生成结果和脚本解析结果不再直接铺在表单下方，改为通过独立弹窗展示。发布前建议、评论弹幕仪表盘和反馈报告各自独立弹窗，保留当前任务上下文，关闭后仍回到原输入阶段。

#### 4.4.4 反馈追问与证据链（阶段 4.4.1.5 / 阶段 4.13）

反馈报告弹窗内增加追问入口，用户可针对报告结论追问"为什么这么判断""依据是哪几条评论"。第一版基于 MySQL 中的反馈报告和评论弹幕明细做关键词评分检索，第二版接入 Milvus 做双层检索。

**双层检索策略（阶段 4.13）**：

```
用户追问
  -> RAG 业务开关 + Milvus 可用？
    -> 是：向量检索（FilterExpression 按 taskId 过滤） -> itemId 回查 MySQL
           -> 命中充足：MODE_VECTOR
           -> 命中不足：合并 SQL 兜底 -> MODE_VECTOR_WITH_SQL_FALLBACK
    -> 否：SQL 关键词评分 -> MODE_SQL
```

关键约束：MySQL 始终是事实来源，向量检索后的所有候选 itemId 必须经 taskId + is_deleted=0 回查 MySQL。索引操作不加 @Transactional，Milvus 写入不绑定 DB 事务。

### 4.5 复盘报告生成与导出

**设计思路**：复盘报告是创作者工作台的最终产物，汇总发布前分析、评论弹幕分析和竞品分析三个来源。报告结构包含内容摘要、核心卖点、标题与简介建议、观众关注点、竞品对照结论、争议与误解、下一期选题建议、创作者偏好沉淀。

**竞品分析子模块**：引入同类型视频作为参照物，用户主动整理竞品视频信息后，系统生成相对竞品的优势、短板和差异化建议。竞品分析先保存再单独生成，复盘报告汇总时强制读取竞品分析结论。

**Markdown 导出（阶段 4.14）**：基于已落库的 creator_report 按固定章节生成 Markdown，不重新调用 LLM。JSON 字段解析为列表或键值结构，未解析成功的 report parseStatus 附带原始输出，便于排查。前端只负责触发下载，不拼接 Markdown。

**关键决策**：

- 竞品分析、评论弹幕报告、发布前建议均为复盘报告的数据依赖项，任一缺失时复盘接口拒绝执行，避免生成残缺报告。
- Markdown 导出不引入第三方依赖，使用 Java 标准库拼接。

### 4.6 创作者偏好记忆

**设计思路**：从每次复盘报告中提取 creatorPreferenceInsight，按 userId + taskId 保存为长期偏好快照（creator_preference）。下一次发布前优化时读取最近历史偏好作为提示词上下文。唯一约束 uk_user_source_task 确保同一任务重复生成复盘时更新快照而非重复插入。

**偏好模式**：前端提供三种选项：

- USE_HISTORY：默认，读取历史偏好参与生成。
- IGNORE_HISTORY：本期换风格，不读取历史偏好。
- EXPERIMENT：读取历史偏好但仅作为避坑参考。

**关键决策**：

- 偏好内容只影响表达风格和分析侧重点，不能覆盖系统规则或让模型编造平台数据。
- 复盘报告 parseStatus 为 RAW_ONLY 时不沉淀偏好，避免不可控原文进入后续提示词。
- 不接 Milvus，不写入通用 long_term_memory，先做最小闭环。

### 4.7 评测体系与失败回放

**设计思路**：建立评测用例表（creator_eval_case）和评测结果表（creator_eval_result），保存输入快照、模型原始输出、失败原因、耗时、token 和人工评分。工作流步骤接口可查询完整步骤历史，形成"样例输入 -> 工作流步骤 -> 模型输出 -> 人工评分"的完整评测链。

**评测维度**：可读性、贴合度、稳定性、成本、可解释性。

**前端入口**：工作台右上角提供"开发者测试"按钮，打开独立弹窗，展示内置样例、阶段筛选、输入快照、期望要点、人工评分表单和最近结果。评测入口与创作者主流程分开，不干扰普通用户的工作流。

**关键决策**：

- 失败回放通过工作流步骤查询，不是独立报表。
- 不做自动评分 Agent，不做批量评测调度。
- 评测样例与评测结果分两张表，便于后续扩展多模型对比。

### 4.8 演示部署与成本保护

**演示部署（阶段 4.7）**：使用 Docker Compose 编排 MySQL、Redis、后端（Spring Boot）和前端（Nginx）四个服务。前端容器代理 /api 实现同源访问，SSE 关闭 Nginx buffering。MySQL 启动时挂载 init.sql 自动注入演示数据。前端对外暴露 8088 作为统一入口。

**成本保护（阶段 4.8）**：在 LLMService 统一调用入口增加字符数保护，通过环境变量 LLM_GUARD_ENABLED 和 LLM_GUARD_MAX_PROMPT_CHARS 控制。system prompt + user prompt 超过限制时在调用模型前返回 400，避免已经产生模型请求后才失败。使用字符数而非 token 作为粗粒度保护，因为项目当前没有统一 tokenizer。

### 4.9 Prompt 版本管理

**设计思路（阶段 4.9）**：评测结果新增 promptVersion、promptHash 和 promptSnapshot 三个字段，让每次评测结果绑定 Prompt 版本、快照和 SHA-256 哈希。Prompt 版本统计接口按版本聚合结果数量、成功率、分项评分均值、评分覆盖率、分数波动和 token 成本。后端在未提供哈希时根据快照自动计算 SHA-256。

**关键决策**：

- promptVersion 用于人类识别，promptHash 用于判断是否真的同一份 Prompt，promptSnapshot 用于复现。
- 这个能力服务作者调试 Prompt，不直接给普通 UP 主使用。

### 4.10 LLM 用量统计

**设计思路（阶段 4.10）**：在 LLMService 新增 chatWithUsage 方法，从 Spring AI ChatResponse 元数据中提取模型名称、prompt/completion/total token 和耗时，返回 LlmCallResult 对象。token 缺失时保留 null 不伪造为 0，Spring AI 返回三个 token 都为 0 时统一归一成 null。反馈追问接口返回本次 LLM 调用的 token 与耗时，让真实调用链可以观察成本。

**关键决策**：

- 保留原 chat 方法降低改造成本，需要统计的调用方改用 chatWithUsage。
- 人工 accuracyScore 明确为人工评分分项，不包装成客观准确率。

### 4.11 前端交互台浮窗化（阶段 4.15）

通用 Agent 控制台作为创作工作台上的可拖拽、可缩放浮窗（AgentFloatingWindow），复用 useAgentChat 的底层聊天能力，支持拖动标题栏移动、拖动右下角调整大小、最小化和关闭。浮窗和原 Agent 控制台共享后端接口但 UI 互不污染。

**关键决策**：不直接复用 AgentConsole.vue 的完整页面壳，避免页面级布局规则进入小窗口；拖动和缩放使用浏览器原生 Pointer Events，不引入第三方拖拽库。

## 5. 数据库设计要点

### 5.1 核心表及用途

| 表名 | 用途 |
|---|---|
| creator_task | 创作任务主表，含任务名称、状态、软删除标记 |
| creator_material | 任务输入材料（标题草稿、简介草稿、文稿、字幕），按类型+任务拆行 |
| creator_suggestion | 发布前优化建议结果，含摘要、卖点、风险、标题/简介/标签/分区建议、创作者语境 |
| creator_user_feedback_detail | 用户主动提供的评论/弹幕样例 |
| creator_llm_feedback_report | LLM 对评论弹幕生成的结构化分析报告 |
| creator_feedback_item | 单条评论/弹幕明细与分类结果，含情绪、噪声标记、embedding 状态 |
| creator_feedback_metric | 用户导入的视频基础指标（播放、点赞、投币、收藏、分享） |
| creator_competitor_sample | 用户主动整理的竞品视频信息 |
| creator_competitor_report | 竞品对比分析报告 |
| creator_report | 最终创作复盘报告，汇总发布前/反馈/竞品三个分析来源 |
| creator_workflow_session | 工作流会话，按任务+阶段记录状态和确认结果 |
| creator_workflow_message | 工作流消息流，按角色（SYSTEM/USER/AGENT/TOOL/RESULT）记录每一条 |
| creator_workflow_step | Agent 执行步骤，记录类型、状态、输入输出摘要和错误信息 |
| creator_workflow_attachment | 用户上传的文本资料元信息 |
| creator_preference | 创作者长期偏好快照，按 userId+taskId 唯一 |
| creator_eval_case | 评测用例，保存输入快照和评分标准 |
| creator_eval_result | 评测结果记录，含原始输出、失败原因、token、耗时、人工评分、Prompt 版本信息 |

### 5.2 设计原则

- 任务主表与材料表分离：后续可挂载更多材料类型而不修改主表结构。
- 原始样例与分析结果分表：允许独立排查和重跑，不把原始数据和分析结果捆绑。
- 软删除优先：任务软删除保留历史分析和复盘记录。
- 条件式 ALTER TABLE：init.sql 对已有库字段补充使用 information_schema.COLUMNS 判断，保证幂等执行。

## 6. 关键设计决策汇总

| 决策 | 理由 |
|---|---|
| 从通用 Agent 框架转向创作者业务 | 聚焦 B 站内容创作者真实痛点，形成完整业务闭环作为简历项目 |
| 先做业务闭环，再补高级能力 | 每个阶段都能单独演示，避免项目失控 |
| 单 Agent + 多节点工作流，不先做多 Agent | 当前目标是通过业务闭环，先做清楚工作流状态比对未来场景做复杂编排有价值 |
| SSE 必须先落库再推送 | 消息持久化是断线恢复的基础，SSE 仅作为实时通知通道 |
| 用户确认机制：AI 不自动推进业务阶段 | 防止不可信建议被自动当成正式结论 |
| 发布前优化建议等待确认后，任务状态才更新 | 旧同步接口在生成后直接改状态的做法不能用于交互式工作流 |
| 平台数据只做用户主动导入或显式触发限量采集 | 降低合规风险，保证项目核心在 AI 工程化而非爬虫 |
| 评论弹幕明细级存储（creator_feedback_item） | 支撑分类筛选、证据查看、仪表盘和后续 RAG 检索 |
| 第一版使用规则分类而非 LLM 批量分类 | 先跑通明细层和仪表盘，避免成本/耗时/稳定性问题 |
| 成本保护放在统一 LLM 入口而非各业务 Service | 避免每个业务重复写限制，在调用 Spring AI 前短路 |
| 使用字符数而非 token 做成本保护 | 项目当前没有统一 tokenizer，MVP 阶段字符数已够用 |
| 偏好记忆不与通用长期记忆表合并 | 创作者偏好有独立的业务语义和存储策略 |
| 复盘报告是唯一标记任务完成的分析产物 | 汇总三个分析来源后才生成最终报告 |
| 评测入口与创作者主流程分开 | 评测是开发者工具，不应干扰普通用户的创作流程 |
| Prompt 版本、哈希、快照三者共存在评测结果中 | 版本用于人类识别、哈希判断一致性、快照支持复现 |
| Token 缺失时保留 null 不伪造为 0 | 不同供应商 usage 返回完整度不一致，0 会污染成本统计 |
| Markdown 导出不引入第三方依赖 | 使用 Java 标准库拼接，导出内容基于已落库报告不重调 LLM |
| 索引不加 @Transactional | Milvus 写入不受 DB 事务管理，按批回写状态反映真实向量库现状 |
| 证据检索 MySQL 始终是事实来源 | 向量库里的旧批次或已删除明细不会进入最终证据 |
| 条件式 ALTER TABLE 保证 SQL 脚本幂等 | 已有库的字段补充可重复执行不报错 |
