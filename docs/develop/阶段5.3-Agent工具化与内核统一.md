## 1. 需求分析

### 1.1 创作者痛点

5.2 把跨分区「优品 + 竞品」案例库的高级检索链路（查询改写 / 父子召回 / hybrid / rerank）跑通了，但**这套能力目前只有一个孤立的 `/search` 调试接口在用**——创作者在真正高频的场景（发布前优化、竞品分析）里，AI 给的建议**完全没见过同赛道的优质案例**，只能凭模型自身先验空谈。系统提示词甚至明确写着「不得编造具体竞品数据」「不能编造真实平台数据」（见 `PrePublishSuggestionService` 第 138 / 148 行），等于主动把领域知识的门关上了。

同时，项目存在「两座孤岛」：通用 ReAct Agent 内核成熟却只有 3 个玩具工具（calculator/datetime/web_search），没有一个创作领域工具；创作工作台各能力（发布前优化/竞品/复盘）全是固定 prompt 链、绕过 Agent。简历主线「ReAct 内核 + 工具注册表编排创作能力」至今没有一处实证。

5.3 要解决：**让检索能力成为 Agent 工具、让发布前优化由 Agent 自主驱动地调用它**，既把「编不出平台数据」变成「有据可依」，又让「Agent 编排创作能力」第一次落地。

### 1.2 本阶段做什么 / 不做什么

**做（β 路线）**：
- 把 `KnowledgeReferenceRetrievalService.search()` 包成 `Tool` 注册进 `ToolRegistry`，通用 Agent 即得领域工具（5.3a，地基）。
- 把发布前优化改造成 **Agent 驱动**：由 Agent 自主决定检索什么、调用 `knowledge_search` 取证，再产出结构化建议（5.3b，核心）。
- 竞品分析同理 Agent 化 + 竞品工具（5.3c）。
- 全程双开关默认关、优雅降级；关时走原固定 prompt 链 → 对 5.2 / 4.x 零回归。

**不做（本阶段边界）**：
- 不抽公共 `rag` 内核、不动 4.13 反馈侧检索（`CreatorFeedbackEvidenceRetrievalService`）。只有 2 个差异很大的消费点，复用压力不足，过早抽象违反「不引入没用到的抽象」（5.3d 视复用情况再议）。
- 不改发布前优化的对外接口与 11 字段 JSON 输出契约（前端零破坏）。
- 不做平台实时数据采集（红线照旧：采集只走离线脚本 / 单 BV）。

### 1.3 输入输出

- 输入：现有创作任务的标题 / 文稿 / 字幕材料，以及 5.1 已入库的案例库。
- 输出：通用 Agent 多一个 `knowledge_search` 工具；发布前优化建议由 Agent 自主取证后生成（输出 JSON 结构不变，前端零改）。
- 不新增对外业务接口（5.3a 复用 `/api/agent/chat`；5.3b 复用现有 `/pre-publish/analyze`）。

## 2. 现状盘点（两座孤岛 + 三条检索）

### 2.1 通用 Agent 内核（成熟，但工具贫瘠）

- `core.AgentExecutor.run(sessionId, userId, userMessage)`：自研 ReAct 循环，正则解析 `Thought/Action/Action Input/Final Answer`，`MAX_ITERATIONS=10`，**Final Answer 是自由文本**。
- `tool.Tool`：极简接口 `getName()/getDescription()/execute(String)→String`（输入是自由文本，非 JSON）。
- `tool.ToolRegistry`：构造器注入 `List<Tool>` **按类型自动收集**所有 Tool Bean（与包无关）+ 经 `SpringAiToolCallbackAdapter` 接 MCP；工具名去重 + 字母序稳定排序。
- `tool.ToolExecutor`：超时 / 重试边界。入口 `controller.AgentController` → `POST /api/agent/chat`，session/memory 耦合。
- **现有工具仅 3 个**：`calculator` / `datetime` / `web_search`（全在 `tool.builtin`），**没有一个创作领域工具**。

### 2.2 创作工作台（业务完整，但绕过 Agent）

- `creator.suggestion.PrePublishSuggestionService`：固定 prompt 链 + 单次 `LLMService.chat()`，产 11 字段固定 JSON（`buildSystemPrompt` 第 132 行定义 schema、`buildUserPrompt` 第 166 行拼装；偏好上下文经 `buildPreferencePromptContext` 第 199 行注入——这是「调 Service 拿一段字符串拼进 prompt」的现成模式）。
- `creator.competitor.CreatorCompetitorService`：同形态，已实现。
- `creator.workflow.CreatorWorkflowService`（780 行）：编程式步骤编排 + SSE，步骤类型硬编码 enum，无 ToolRegistry、无自主推理。

### 2.3 三条检索路径并存

| 路径 | 类 | 语料 | 形态 |
|---|---|---|---|
| 知识库侧 | `knowledge.KnowledgeReferenceRetrievalService.search()` | 跨分区优品 + 竞品案例库 | 5.2 全链路（查询改写 / 父子召回 / hybrid / rerank / SQL 兜底）|
| 反馈侧 | `creator.feedback.CreatorFeedbackEvidenceRetrievalService.retrieve()` | 当前任务的评论弹幕 | 4.13（向量→MySQL 回查→SQL 兜底 + 意图打分）|
| 通用 `rag/` 包 | — | — | 空，预留 |

> 两套检索**差异很大**：知识库是跨分区案例 + 父子 + rerank + hybrid；反馈是当前任务评论 + 意图打分 SQL。共性目前只有「向量→回查→SQL 兜底」这一壳——不足以支撑现在就抽公共内核。

### 2.4 可复用资产与关键约束（写代码必须遵守）

- `search()` 是标准 `@Service`，可直接构造器注入；**优雅降级、从不抛异常**（RAG 关 / Milvus 不可用 → 返回 `mode=SQL` 的正常响应）。
- 隔离铁律：知识向量库**不是** `VectorStore` Bean（避免与反馈侧 `ObjectProvider<VectorStore>` 撞 `NoUniqueBeanDefinitionException`），只能经 `KnowledgeVectorStore` 持有。
- 工具化模式现成：`tool.builtin.WebSearchTool` = `@Component implements Tool`，输入纯字符串、`catch` 兜底返回文本；启动期被 `ToolRegistry` 自动发现。

## 4. 5.3a 详细设计：KnowledgeSearchTool（已编码）

**落点**：新增 `com.link.linkagent.knowledge.tool.KnowledgeSearchTool`（能力模块自持其 Agent 工具，只反向依赖最小 `Tool` 契约，避免玩具包 `tool.builtin` 耦合领域模块）。**全刀仅一个新文件，无 DDL、无 yml、无前端。**

- **门控（零回归核心）**：类上 `@ConditionalOnProperty(prefix="knowledge.rag", name="enabled", havingValue="true")`。RAG 主开关默认关时**工具 Bean 根本不存在** → 通用 Agent 工具集与今日字节级一致；只有作者显式 `knowledge.rag.enabled=true` 工具才现身。比「always 注册 + 内部判关」更干净（关时零footprint）。
- **工具契约**：`name=knowledge_search`；`description` 中文，点明「输入一句话查询词、返回同赛道真实案例」，作为 LLM 决定何时调用的唯一依据。
- **输入**：纯查询串（对齐自研 ReAct 的 `Action Input` 自由文本，比 JSON 在文本循环里健壮）；自行截断到 500（直接调 `search()` 不过 `@Valid`，须自兜 `query` 的 `@Size(500)`）。
- **检索参数**：`new ReferenceVideoSearchRequest(query, null, null, TOP_K=5, null)`——`category/tier` 传 null（案例库稀疏期先求召回）、`strategy` 传 null 走配置默认 REWRITE、topK=5 控 Observation 体积。
- **输出格式化**：压成可读 Observation——`检索模式 + 命中N条 + 每条(标题/分区/层级中文化/播放·点赞信号/亮点) + 最具代表性的一条观众原话`；丢弃 `enhancedQueries/reranked` 等对 Agent 推理无用的回显。
- **降级**：`search()` 不抛异常，工具侧只对返回值空判 + 一层 `catch` 兜底，任何意外只回降级文本、绝不把 Agent 循环带挂；零命中回「未检索到」提示。

## 5. 关键决策点

### 决策 1：5.3 推进野心 → ✅ 已定 β（Agent 中心·激进，作者 2026-06-09 拍板）

发布前优化本阶段就改 Agent 驱动，真正开始消灭孤岛。α（简单优先·直注）与 γ（先统一检索内核）未采纳；γ 的「检索内核共性上提」降级为 5.3d 的条件项。

### 决策 2（核心）→ ✅ 已定 C（作者 2026-06-09 拍板）：发布前优化 Agent 化用哪个内核？

发布前优化的难点是**「自主工具调用」与「11 字段固定 JSON 输出」要同时满足**，而自研 `AgentExecutor` 以自由文本 `Final Answer` 收尾。三条路：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A 纯自研 ReAct** | 让发布前优化跑自研 `AgentExecutor`，要求 LLM 以 `Final Answer: {json}` 收尾 | 内核完全统一、叙事最硬；但「文本循环里逼出严格 JSON」脆弱，且 AgentExecutor 现耦合 session/memory 与 `/agent/chat`，要改造支持「task 维度一次性带工具分析」 |
| **B Spring AI 原生 tool-calling** | 用 `ChatClient.tools()` 让框架跑 function-calling + 约束 JSON 输出 | 结构化 + 工具调用最稳、少手写循环；但工具要以 Spring AI `ToolCallback` 形态另供，且工作台用原生、通用 Agent 用自研 → 反而**没真正统一内核**，多一套 |
| **C 两段式：自研 ReAct 取证 + 结构化合成（推荐）** | 第一段：发布前优化先跑自研 Agent 轻量循环（带 `knowledge_search` 等工具），**自主决定查什么、查到什么**，产自由文本「检索发现」；第二段：把「检索发现」作上下文，喂现有固定 JSON prompt 产 11 字段建议（复用 `buildSystemPrompt`/schema） | Agent 真正负责「要不要查 / 查什么 / 取到什么证据」（这才是 Agent 的价值），结构化生成仍走确定性 JSON 链；真用上自研内核 + ToolRegistry（统一叙事成立）、输出零风险、前端零破坏、两段各自可测。代价：两次 LLM 调用（发布前优化低频，可接受）|

> 我的建议：**C**。它在「真正 Agent 驱动」与「结构化输出不破前端」之间取到最佳平衡，且兑现 β 的内核统一叙事（用的是自研 ReAct，不是另起 Spring AI 一套）。A 的脆弱性与 AgentExecutor 改造成本高；B 偏离统一目标。5.3a 工具用自研 `Tool` 接口，A/C 直接可用、B 需另适配——也佐证 C。
>
> **作者 2026-06-09 拍板 C。** 落地详细设计见 §6。

## 6. 5.3b 详细设计（C·两段式，内核已定 C）

### 6.1 总体：两段式

- **第一段（Agent 自主取证）**：用自研 ReAct 内核跑一个**任务维度、不碰会话记忆**的轻量循环（新增入口 `AgentExecutor.runTask`），工具集含 5.3a 的 `knowledge_search`。喂入「本次创作任务的标题 / 材料 + 取证目标」，由 Agent **自主决定查什么、查几次**，最终以 Final Answer 产出一段自由文本「检索发现」。
- **第二段（结构化合成）**：把「检索发现」作为新增的一段上下文注入现有固定 prompt，仍由 `buildSystemPrompt` 的 11 字段 schema 产出建议。对外接口与 JSON 契约零变（前端零破坏）。

### 6.2 为什么第一段不直接复用 `AgentExecutor.run`（关键）

`run()` 在循环里读写短期 / 摘要 / 长期记忆，并在 Final Answer 时抽取长期记忆——那是「面向用户的聊天回合」语义。发布前优化的取证是**任务内部一次性中间步骤**，若走 `run()`：① 内部推理被写进用户 `/agent/chat` 会话历史（污染）；② 触发无意义的长期记忆抽取（多余 LLM 调用 + MySQL 垃圾行）。故新增**记忆无关**的入口 `runTask(taskMessage)`：与 run 共用同一套 ReAct 解析 / 工具执行 / 系统提示词 / `ToolRegistry`（同一内核、同一工具生态），仅去掉记忆读写这一层。（工具集暂用全量 `getAllTools()`，发布前优化场景模型自然只会调 `knowledge_search`，无需收窄；如需限定工具留后续。）

### 6.3 为什么 `runTask` 是新增方法而非抽取共享循环

遵循「不重构没坏的代码 / 简单优先 / 避免过早抽象」：`run()` 的循环已稳定驱动 /agent/chat，为复用而抽取共享循环会改动它、需重测，且当前只有两个调用点（run + runTask）——未到 rule of three。代价是约 20 行循环骨架重复，但解析 / 提示词 / 工具执行等真正逻辑全部共享，且 `run()` **字节级不动 = /agent/chat 零回归**。待 5.3c（竞品）出现第三个调用点再评估上提为共享循环。

### 6.4 5.3b 子切片

| 子刀 | 目标 | 状态 |
|---|---|---|
| **5.3b-1** | `AgentExecutor.runTask`：记忆无关的任务维度带工具推理入口（`run` 不动）| **编码完成·待自测** |
| **5.3b-2** | 发布前优化接入：默认关开关 + 第一段取证 + 「检索发现」注入第二段 | 待 5.3b-1 自测 |

**5.3b-2 接入要点（下一刀，先记录设计）**：
- **双开关 + 降级**：新增默认关开关 `creator.suggestion.agent.enabled`；开关开 **且** `knowledge_search` 已注册（即 `knowledge.rag.enabled=true`）时才跑第一段，否则走原固定链（零回归）。承袭 5.2 的双开关默认关 / 优雅降级纪律。
- **第一段取证提示词**：自包含 =（标题草稿 + 材料摘要）+「请检索同赛道优质 / 竞品案例，总结对本次选题 / 标题 / 表达有参考价值的发现」，要求输出结构化要点（命中案例 + 可借鉴点 + 风险），而非空话。
- **第二段注入**：把「检索发现」作为 `buildUserPrompt` 新增的一段；`buildSystemPrompt` 增一行说明其用途——「若提供『检索发现』，可引用其中真实案例作为定位 / 差异化依据，但不得超出其内容编造数据」（与既有「不得编造平台数据」一致，只是现在有了真实可引用的来源）。11 字段 schema 不动。
- **依赖方向**：`creator.suggestion` → `core.AgentExecutor` / `tool.ToolRegistry`，即「创作能力被 Agent 内核编排」——这正是 β 的目标方向。

**5.3a（本刀）**：
1. **零回归（RAG 默认关）**：不设 `knowledge.rag.enabled` 或设 false → 编译通过、`KnowledgeSearchTool` Bean 不注册、`/api/agent/chat` 工具集与今日一致（系统提示词不含 `knowledge_search`）。
