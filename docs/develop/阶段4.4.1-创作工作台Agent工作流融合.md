# 阶段 4.4.1：创作工作台 Agent 工作流融合

## 需求分析

本阶段服务的目标用户是 B 站 UP 主、内容运营者和项目演示观看者。

当前创作工作台已经覆盖任务输入、发布前优化、评论弹幕分析和创作复盘，但发布前优化与评论弹幕分析本质上仍是“点击按钮后一次性调用 LLM”。这会带来两个问题：

1. 用户看不到 AI 是如何读取任务材料、分析卖点、识别风险和生成建议的。
2. 项目底层已有 ReAct Agent、工具调用、记忆、执行步骤等能力，但创作者业务链路没有真正复用这些能力。

本阶段要解决的问题是：

```text
把创作工作台从“表单触发 LLM”升级为“任务驱动的 Agent 工作流”，让发布前优化和评论弹幕分析具备可交互、可追踪、可确认的分析过程。
```

### 输入数据来源

本阶段允许的数据来源：

1. 用户在阶段 4.1 主动创建的创作任务和稿件材料。
2. 用户在工作台对话框中主动输入的补充要求。
3. 用户主动上传的本地文本类资料，例如 TXT、MD、JSON、CSV。
4. 用户通过脚本主动生成并导入的 B 站评论弹幕样例文件。

本阶段不默认接入的数据来源：

1. 不做后端自动爬取 B 站评论、弹幕或视频指标。
2. 不模拟 B 站推荐算法。
3. 不做自动投稿。
4. 不绕过平台登录、风控或权限限制。

### 本阶段做什么

1. 设计创作任务级 Agent 工作流会话。
2. 设计发布前优化的动态消息流和用户确认机制。
3. 设计评论弹幕分析的数据导入、清洗、分类、报表和追问入口。
4. 设计 SSE 事件流，让前端能展示 Agent 分析过程。
5. 设计工作流消息、步骤、附件和确认状态的数据结构。
6. 明确边界情况和失败处理策略。

### 本阶段不做什么

1. 不立即重写全部 AgentExecutor。
2. 不一开始就实现复杂多 Agent 并发协作。
3. 不直接把 Python 采集脚本嵌入后端定时任务。
4. 不在第一版做图片 OCR、视频解析、音频转写。
5. 不在第一版强依赖 Milvus；RAG 放到第二轮扩展。

## 当前问题定位

现有实现的关键事实：

1. `PrePublishSuggestionService` 当前直接调用 `LLMService.chat(systemPrompt, userPrompt)`，返回结构化 JSON 后保存。
2. `CreatorFeedbackService` 当前同样直接调用 `LLMService.chat(systemPrompt, userPrompt)`，没有中间步骤。
3. `AgentExecutor` 已经具备 ReAct 迭代、工具调用、短期记忆、长期记忆和步骤记录。
4. `CreatorWorkspace.vue` 现在主要是表单和结果展示，没有 Agent 执行过程，也没有任务级对话。

因此后续改造重点不是“把 Agent 控制台复制到工作台”，而是新增一个创作者业务专用的工作流层：

```text
CreatorWorkspace
  -> CreatorWorkflow API / SSE
  -> CreatorWorkflowService
  -> 任务上下文读取
  -> Agent / LLM / Tool 执行
  -> 工作流消息与步骤落库
  -> 前端动态展示
```

## 总体设计方案

### 核心概念

新增“工作流会话”作为创作任务和 Agent 分析之间的桥。

```text
一个创作任务 task
  -> 可以有多个 workflow session
  -> 每个 session 属于一个业务阶段
  -> 每个 session 有多条 workflow message
  -> 每个 session 有多条 workflow step
  -> 每个 session 可以关联上传附件
```

业务阶段建议枚举：

| 阶段 | 说明 |
|---|---|
| `PRE_PUBLISH` | 发布前优化 |
| `FEEDBACK` | 评论弹幕分析 |
| `REPORT` | 创作复盘 |

会话状态建议枚举：

| 状态 | 说明 |
|---|---|
| `CREATED` | 会话已创建，还没有开始执行 |
| `CONTEXT_LOADING` | 正在装载任务材料 |
| `WAITING_USER_INPUT` | 等待用户补充输入 |
| `RUNNING` | Agent 正在分析 |
| `WAITING_CONFIRMATION` | 已生成建议，等待用户确认 |
| `CONFIRMED` | 用户已确认当前结果 |
| `FAILED` | 执行失败 |
| `CANCELLED` | 用户取消 |

消息角色建议枚举：

| 角色 | 说明 |
|---|---|
| `SYSTEM` | 系统过程消息，例如已加载任务材料 |
| `USER` | 用户输入或上传行为 |
| `AGENT` | Agent 的分析、建议和追问 |
| `TOOL` | 工具执行结果，例如评论清洗完成 |
| `RESULT` | 结构化结果消息，例如发布前建议 |

### 为什么先做单 Agent + 多节点工作流

第一版不建议直接做复杂多 Agent，原因：

1. 当前项目目标是跑通创作者业务闭环，不是展示 Agent 数量。
2. 发布前优化和评论弹幕分析都可以先拆成清晰步骤。
3. 多 Agent 并发会引入结果合并、冲突处理、失败重试和成本控制问题。
4. 对学习型项目来说，先做清楚工作流状态，比先做复杂编排更有价值。

推荐第一版结构：

```text
PrePublishWorkflowAgent
  -> 读取任务材料
  -> 生成内容摘要
  -> 分析受众和卖点
  -> 分析风险
  -> 生成标题、简介、标签、分区建议
  -> 等待用户确认

FeedbackWorkflowAgent
  -> 导入评论弹幕样例
  -> 清洗无意义内容
  -> 评论分类
  -> 弹幕分类
  -> 指标汇总
  -> 生成反馈建议
  -> 支持用户追问
```

后续稳定后，再升级为：

```text
内容策略 Agent
评论分析 Agent
弹幕分析 Agent
数据解读 Agent
复盘建议 Agent
```

## 发布前优化工作流

### 用户流程

```text
用户创建创作任务
  -> 进入发布前优化页面
  -> 系统创建 PRE_PUBLISH 工作流会话
  -> 前端动态加载任务材料消息
  -> 用户点击消息查看详情
  -> 用户可继续输入补充要求或上传文本资料
  -> 点击生成建议
  -> Agent 分阶段分析
  -> Agent 输出结构化建议
  -> 用户选择确认、继续调整或重新生成
  -> 确认后进入评论弹幕分析阶段
```

### 页面布局建议

发布前优化页面不建议继续使用传统表单页。推荐布局：

```text
顶部：
任务名称、任务状态、当前阶段、保存时间

左侧：
任务材料摘要列表
标题草稿 / 简介草稿 / 文稿 / 字幕 / 上传附件

中间：
Agent 消息流
系统装载消息、用户消息、Agent 分析消息、结果消息

右侧：
详情抽屉
点击左侧材料或中间消息后展示完整内容

底部：
输入框、上传入口、生成建议按钮、停止按钮
```

### 动态消息设计

进入页面后，前端不应该突然展示全部材料，而是按事件逐条显示：

```text
SYSTEM: 已进入发布前优化阶段
SYSTEM: 已读取任务：Spring AI 项目复盘视频
SYSTEM: 已加载标题草稿，点击查看详情
SYSTEM: 已加载简介草稿，点击查看详情
SYSTEM: 已加载文稿，约 8600 字，点击查看详情
AGENT: 我将先提炼内容卖点，再检查标题和简介风险。
```

点击“生成建议”后：

```text
AGENT: 正在分析内容摘要...
AGENT: 已识别 3 个核心卖点。
AGENT: 正在检查标题表达风险...
AGENT: 正在生成标题、简介、标签和分区建议...
RESULT: 已生成发布前优化建议。
```

结果消息内展示操作按钮：

```text
[采用本轮建议] [继续调整] [重新生成]
```

### 用户确认机制

确认机制的目标是避免系统自动推进业务阶段。

规则：

1. Agent 生成建议后，工作流状态进入 `WAITING_CONFIRMATION`。
2. 用户点击“采用本轮建议”后，状态进入 `CONFIRMED`。
3. 只有发布前优化建议确认后，评论弹幕分析阶段才允许标记为正式可继续。
4. 用户选择“继续调整”时，会话保持当前阶段，用户输入补充意见后再次分析。
5. 用户选择“重新生成”时，保留旧消息和旧建议，新增一轮结果，方便对比。

### 发布前优化边界情况

| 场景 | 处理策略 |
|---|---|
| 任务不存在 | 返回 404，前端提示任务已不存在 |
| 任务没有任何材料 | 不允许开始工作流，提示先补充标题、简介、文稿或字幕 |
| 材料过长 | 后端按字段截断用于 LLM，完整原文仍保留在详情中 |
| 用户频繁点击生成建议 | 前端按钮置灰，后端用会话状态防止重复执行 |
| SSE 连接中断 | 前端提示连接断开，并允许重新连接读取历史消息 |
| LLM 调用失败 | 写入失败消息，状态改为 `FAILED`，允许用户重试 |
| LLM 输出非 JSON | 保留 rawOutput，状态可进入 `WAITING_CONFIRMATION`，但结果标记 `RAW_ONLY` |
| 用户未确认就切换阶段 | 允许查看其他页面，但不自动推进任务状态 |
| 用户确认后又想修改 | 新建一轮工作流或复制旧建议生成新版本，不直接覆盖确认记录 |
| 上传文件为空 | 拒绝上传，提示文件内容为空 |
| 上传文件过大 | 返回 400，提示文件超过限制 |
| 上传不支持格式 | 返回 400，提示仅支持 TXT、MD、JSON、CSV 等文本格式 |
| 用户补充要求包含越权提示 | 作为非可信业务输入处理，不允许覆盖系统规则 |

## 评论弹幕分析工作流

### 用户流程

```text
用户进入评论弹幕分析阶段
  -> 输入 BV 号或上传脚本导出的 JSON/TXT
  -> 系统校验导入数据
  -> 保存评论、弹幕和基础指标
  -> 执行数据清洗
  -> 执行评论分类
  -> 执行弹幕分类
  -> 生成报表和图表
  -> Agent 输出反馈总结和建议
  -> 用户可打开小弹窗追问
```

### 数据来源策略

第一版推荐只做“用户主动导入”：

1. 用户使用 `scripts/bilibili_feedback_fetcher.py` 本地生成样例文件。
2. 前端上传 JSON 或 TXT。
3. 后端解析后保存到任务下。

暂不做：

1. 后端根据 BV 自动请求 B 站接口。
2. 后端保存 Cookie。
3. 定时刷新评论和弹幕。
4. 大批量采集多个 BV。

如果后续要做后端一键采集，必须满足：

1. 用户主动输入 BV 并点击采集。
2. 每次采集有数量限制。
3. 不使用 Cookie 绕过权限。
4. 采集失败时给出明确原因。
5. 文档中明确这是公开视频样例采集，不是平台数据同步能力。

### 评论分类建议

评论先分为有效和无效两层。

有效评论：

| 类型 | 说明 |
|---|---|
| `APPROVAL` | 认可、感谢、觉得有帮助 |
| `QUESTION` | 提问、求补充、求教程 |
| `DOUBT` | 质疑、反驳、指出问题 |
| `SUGGESTION` | 对内容、选题、节奏提出建议 |
| `EMOTION` | 情绪表达，例如吐槽、惊讶、共鸣 |
| `INTERACTION` | 与 UP 主互动，例如催更、求资料 |

无效评论：

| 类型 | 说明 |
|---|---|
| `EMPTY_MEANING` | 纯表情、纯符号、无上下文短句 |
| `DUPLICATE` | 重复刷屏 |
| `AD` | 广告、引流 |
| `OFF_TOPIC` | 与视频内容无关 |

### 弹幕分类建议

有效弹幕：

| 类型 | 说明 |
|---|---|
| `KNOWLEDGE_REACTION` | 对知识点的即时反应 |
| `QUESTION_POINT` | 对某个时间点产生疑问 |
| `EMOTION_PEAK` | 明显情绪高峰 |
| `RESONANCE` | 共鸣、认可 |
| `COMPLAINT` | 吐槽、不满 |

无效弹幕：

| 类型 | 说明 |
|---|---|
| `EMPTY_MEANING` | 哈哈哈、纯符号、无语义短弹幕 |
| `DUPLICATE` | 重复刷屏 |
| `NOISE` | 无法归类的噪声 |

### 报表设计

第一版图表不要复杂，优先服务复盘判断：

1. 评论类型占比。
2. 弹幕类型占比。
3. 情绪倾向分布。
4. 高频关键词。
5. 争议点列表。
6. 误解点列表。
7. 下一期内容建议。
8. 弹幕时间段热度，前提是导入数据包含时间戳。

图表数据建议由后端返回结构化 JSON，前端只负责渲染，不在浏览器里重新做复杂分析。

### 反馈追问弹窗

评论弹幕分析结果页增加一个轻量 AI 追问入口：

```text
用户：为什么你认为观众误解了这个点？
AI：根据以下评论和弹幕，可以看到用户把“Agent 工具调用”误认为“普通提示词生成”...
```

第一版不强依赖 RAG，可以直接基于当前任务已保存的分类结果和报告回答。

第二版接入 RAG：

```text
用户问题
  -> 检索相关评论/弹幕向量
  -> 返回证据片段
  -> Agent 基于证据回答
```

### 评论弹幕分析边界情况

| 场景 | 处理策略 |
|---|---|
| BV 格式非法 | 前端提示格式错误，不进入导入流程 |
| 用户只输入 BV 但未上传数据 | 第一版提示使用脚本生成样例并上传 |
| 上传 JSON 结构不匹配 | 返回 400，提示文件格式与脚本输出不一致 |
| 评论和弹幕都为空 | 不允许分析，提示至少提供一种数据 |
| 只有评论没有弹幕 | 允许分析，弹幕图表显示为空状态 |
| 只有弹幕没有评论 | 允许分析，评论图表显示为空状态 |
| 指标缺失 | 报表隐藏对应指标，不能编造播放、收藏、投币数据 |
| 评论数量过少 | 给出低置信度提示，不输出过度结论 |
| 评论数量过多 | 分批清洗和分类，避免一次性塞入 LLM |
| 重复评论很多 | 清洗阶段标记重复，不直接删除原文 |
| 广告或无关内容很多 | 归入无效评论，并在报告中提示样例质量较低 |
| LLM 分类不稳定 | 保存原始分类和 rawOutput，允许后续人工复查 |
| 图表为空 | 前端展示空状态，不显示错误图表 |
| 用户追问没有检索结果 | 明确说明当前样例中没有足够证据 |
| RAG 服务不可用 | 降级为基于已保存报告回答 |

### API 设计

#### 创建或恢复发布前优化会话

```http
POST /api/creator/tasks/{taskId}/workflow/pre-publish/start
Content-Type: application/json
```

## SSE 设计

### 事件格式

建议统一事件载荷：

```json
{
  "eventId": "event-id",
  "sessionId": "workflow-session-id",
  "taskId": "creator-task-id",
  "eventType": "message_created",
  "sequenceNo": 12,
  "payload": {},
  "createTime": "2026-05-28T21:00:00"
}
```

### 断线恢复

前端断线后处理：

1. 先调用历史消息接口拉取当前会话消息。
2. 再重新订阅 SSE。
3. 根据 `sequenceNo` 去重，避免重复显示消息。

后端处理：

1. 工作流消息必须先落库，再发送 SSE。
2. SSE 只是实时展示通道，不是唯一数据来源。
3. 事件发送失败不应导致业务事务回滚。

### 心跳

SSE 长连接需要心跳：

```text
event: heartbeat
data: {"sessionId":"xxx","time":"2026-05-28T21:00:00"}
```

前端如果长时间没有收到心跳，应提示连接可能中断。

## RAG 扩展设计

RAG 不是第一版必做，但数据结构要预留。

### 第一版

```text
MySQL 保存评论、弹幕、分类结果和报告。
追问时基于已保存报告和分类明细回答。
```

### 第二版

```text
将有效评论和弹幕切分为检索文档。
写入 Milvus。
用户追问时按 taskId 过滤检索。
Agent 基于检索片段回答。
```

### RAG 边界

| 场景 | 处理策略 |
|---|---|
| 向量库不可用 | 降级使用 MySQL 分类结果 |
| 检索结果为空 | 明确说明当前样例不足 |
| 检索结果与问题无关 | 不强行回答，提示需要更多样例 |
| 评论包含隐私信息 | 第一版不做公开展示，后续需要脱敏策略 |

## 实施顺序

### 第 1 轮：发布前优化消息流

目标：

1. 新增工作流会话和消息表。

3. 前端展示消息流、详情抽屉和底部输入框。

目标：

2. 发布前优化分析按步骤写入消息和 step。

2. SSE 断开后刷新页面能恢复历史消息。

### 第 3 轮：评论弹幕导入与仪表盘

目标：

1. 支持导入脚本 JSON/TXT。
2. 保存单条评论和弹幕明细。
3. 做基础清洗和分类。
4. 输出图表数据。

验收：

1. 评论和弹幕可按类型筛选。

3. 图表能展示有效数据，缺失数据有空状态。

### 第 4 轮：反馈追问与 RAG 预留

目标：

3. 预留向量检索接口，不强制接 Milvus。

验收：

1. 用户可以针对报告结论追问。
2. AI 回答必须引用当前任务下的评论或弹幕依据。
3. 数据不足时明确说明，不编造证据。

## 风险与取舍

### 风险 1：一次性改造过大

处理：

1. 按 4 轮拆分。
2. 第一轮只做发布前优化消息流。
3. 评论弹幕导入、图表、RAG 后移。

### 风险 2：SSE 和业务事务耦合过深

处理：

1. 消息先落库。
2. SSE 只负责通知前端刷新。
3. 断线后通过历史消息恢复。

### 风险 3：多 Agent 过早引入复杂度

处理：

1. 第一版使用单 Agent 多节点工作流。
2. 节点边界稳定后再拆成多 Agent。

### 风险 4：平台数据边界不清

处理：

1. 第一版只支持用户主动上传样例。
2. BV 只作为文件来源说明，不作为后端自动抓取入口。
3. 后续若实现采集，也必须是用户主动触发和限量采集。
