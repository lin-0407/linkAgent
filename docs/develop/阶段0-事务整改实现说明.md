# 阶段 0 — 事务整改实现说明

> 对应 `docs/develop/Python Agent 迁移方案.md` 第 8 节与第 9 节的阶段 0。
> 状态：已实施（2026-09-21）。这一步只改 Java 侧事务边界，没有新增接口、没有改表结构、没有引入新依赖。
> 为什么先做它：Agent 能力迁到 Python 之后，模型调用会变成一次跨进程 HTTP 调用，耗时只会更长。
> 先把"模型调用不能包在数据库事务里"这件事在 Java 侧改对，阶段 2、3 迁 Python 时就不用再动事务结构。

## 1. 问题是什么

整改前这 7 组入口都带 `@Transactional`，模型调用在方法体中间：

- 事务从进入方法就开始，一直到报告落库才提交。模型推理几十秒，数据库连接和行锁就被占几十秒。
- 事务里还夹着别的东西：`CreatorFeedbackService.importFeedback` 把 LLM 分类包在导入事务里；
  `CreatorInteractiveService.triggerUnderstanding` 把"生成中"状态登记包在同一事务里，
  意味着其它请求要等推理结束才能看到这个状态，防重复点击的锁实际不生效。
- 并发连接数一上来，连接池先被长事务占满，与这次调用是否成功无关。

## 2. 拆法

统一按三段处理，和仓库里已有的 `ProductionPlanApplicationService.create` +
`ProductionPlanPersistenceService`（`startGenerating` / `markReady` / `markFailed`）是同一个套路：

1. 事务外读取输入、模板渲染和入口校验；
2. 事务外调用模型（阶段 2 之后是调用 Python）；
3. 新的短事务里重新检查任务存在性与业务门禁、复核输入没有变，再落库。

落库那次复核用的是"输入指纹"：生成前把决定模型输入的内容固定下来，保存前用同一套读法重新算一遍，
不一致就丢弃本次结果并返回 409，不写任何数据。判据不引入新列，全部复用现有字段：

| 组 | 入口 | 生成期间复核什么 |
|---|---|---|
| T01 | `CreatorFeedbackService.analyze` | 样例文本渲染出的提示词是否变化（`feedback_analyze.user`） |
| T02 | `CreatorFeedbackService.importFeedback` / `fetchFeedback` | 不做旧结果互斥，只把 LLM 分类移出事务；明细替换仍是覆盖 + 一个事务 |
| T03 | `CreatorInteractiveService.triggerUnderstanding` | 提示词输入是否变化 + 状态条件更新（`understanding_status` 仍是 `UNDERSTANDING` 才写 `READY`） |
| T04 | `generateCreativeOptions` / `regenerateOptions` | 方向卡提示词输入是否变化（想法、类型、背景资料、理解摘要、本轮额外要求） |
| T05 | `PrePublishSuggestionService.generateSuggestion` / `generateSuggestionByAgent` | 材料正文与偏好上下文的输入指纹是否变化 |
| T06 | `CreatorReportService.analyze` | 重跑入口校验（反馈/竞品报告仍在且 `PARSED`）+ 提示词输入是否变化 |
| T07 | `CreatorCompetitorService.analyze` / `analyzeByReferenceVideo` | 同上，读法按手动样例和参考案例两条路径分别复用 |

T07 的提示词用 `Supplier<String>` 传进 `executeAnalyze`，生成前和保存前各取一次，
是为了让两条入口共用同一份读法，避免只在入口读、保存时不重读。

## 3. 改了哪些文件

业务侧：

- `backend/src/main/java/com/link/linkagent/creator/feedback/service/CreatorFeedbackService.java`

  - 导入链路拆成 `applyTaskIdAndRuleFilters`（规则前置）→ `classifyItemsWithFallback`（事务外模型分类）→
    `persistImportedFeedback`（短事务落库），`fetchFeedback` 不再自己包一层事务模板。

## 4. 行为变化（需要作者知道）

1. 生成期间输入被改，本次结果被丢弃并返回 409（`CONFLICT`），错误文案说明"已丢弃，请重新生成/分析"。
   原实现是旧结果直接覆盖新状态。
2. `triggerUnderstanding` 的 `UNDERSTANDING` 状态现在提前提交，其它请求立刻可见，防重复点击的锁真正生效。
3. 保存阶段会比原来多读一次输入（重算提示词 / 重读材料与偏好）。这是复核的代价，查询量很小。
4. 并发生成同一份方向卡（T04）仍是后写覆盖：现有表没有每轮执行的标识，加一个标识属于 Schema 变更，
   按"不先引入新表/新列"暂不做；T03 因为已有 `understanding_status` 可以条件更新，已经改成拒绝后到者。
5. T02 的并发导入语义与整改前一致（后写覆盖）：原实现的事务只在写库时互斥，读取阶段没有互斥，
   所以这次拆分没有引入新的覆盖风险，也没有新增守卫。

## 5. 上层传播核对（阶段 0 顺带确认，不改代码）

按方案第 8 节要求，确认以下几处不能"因为调用模型就当成事务问题"，核对结果：

- `ProductionPlanApplicationService.create`：本身没有事务注解，顺序是
  `persistenceService.startGenerating`（短事务）→ 事务外生成蓝图 → `markReady`（短事务），
  已经是目标形态，本阶段不动。
- `CreatorWorkflowService.analyzePrePublishWorkflow` 与 `generatePrePublishManuscriptDraft`：
  都没有 `@Transactional`，内部的建议生成和文稿生成本来就在事务外；
  工作流审查通过后的保存调用 `PrePublishSuggestionService.saveSuggestion`（带注解、外部调用经代理），
  所以工作流路径也没有把模型包进事务。
- `AudienceScreeningService.screen`：由 `PreflightReviewWorker` 调用，Worker 本身没有事务注解，
  属于媒体业务 Worker（阶段 5 再迁 Provider），本阶段不改。

## 6. 验证记录

实际执行的命令（工作目录 `backend/`，本机 Maven `D:\apache-maven-3.9.11-bin\...\mvn.cmd`，JDK 25）：

```
mvn -DskipTests compile                  # BUILD SUCCESS
mvn -DskipTests test-compile             # BUILD SUCCESS
mvn -Dtest=CreatorFeedbackServiceTest,CreatorInteractiveServiceTest,PrePublishSuggestionServiceTest,CreatorReportServiceTest,CreatorCompetitorServiceTest -DfailIfNoSpecifiedTests=true test
                                         # Tests run: 24, Failures: 0, Errors: 0
mvn -Dtest=PhaseZeroTransactionBoundaryTest,PhaseZeroStaleResultTest -DfailIfNoSpecifiedTests=true test
                                         # Tests run: 14, Failures: 0, Errors: 0
mvn test                                 # Tests run: 398, Failures: 0, Errors: 0, Skipped: 4，BUILD SUCCESS
```

观察到的事实：

- 事务边界用例读的是真实 `TransactionSynchronizationManager` 状态，模型调用点为 false、落库点为 true；
  落库抛异常时 `connection.rollback()` 确实被调用。
- 旧结果拒绝用例在"输入被改"时都抛 409，且 `upsertReport` / `upsert` / `updateTaskStatus` /
  `insertOption` 等写入方法零调用。
- 全量 398 条用例通过，其中 4 条跳过：`PrePublishAgentGoldenQualityTest`、
  `CreativeIdeaManualEvaluationTest` 两条、`WebSearchToolTest` 一条，都是默认被系统属性关闭的评测/联网用例，
  与本次改动无关。`LinkAgentApplicationTests` 的 Spring 上下文启动正常，说明依赖注入没有因为新增构造参数断掉。

未验证的部分（不要当成已验证）：

- 没有连真实 MySQL/Redis 做行为验证：本机 3306、6379 都没有服务在监听，Docker 守护进程也没启动，
  本轮没有启停作者既有的容器或服务。因此真实数据库上的行锁表现、并发导入的先后顺序、
  实际隔离级别下的复核时序没有实测；事务边界是用真实 `DataSourceTransactionManager` + mock 连接证明的。
- 没有对模型做真实付费调用，验证都用 mock；用量流水与费用口径不在本阶段范围。
- 没有验证前端在收到 409 时的展示：前端是否已有统一错误提示未核对，作者可在页面上触发一次
  "生成中改资料"确认文案是否够清楚。
