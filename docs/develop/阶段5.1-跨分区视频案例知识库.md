## 1. 需求分析

- **目标用户**：B 站中小 UP 主（同一创作者跨多个创作任务复用同一套案例库）。
- **解决的痛点**：项目此前严重缺少高质量领域知识库；Agent 给发布前建议时只能凭模型先验，无法参照「同赛道里被验证过的成功视频」。
- **本阶段要解决的具体问题**：把「优品 + 竞品」视频案例（跨分区、跨任务）清洗、结构化、落库并向量化，形成一个可被语义检索的知识底座。
- **数据来源（严守平台边界）**：
  1. **离线采集脚本**产出的标准案例文件（`scripts/` 下独立脚本，作者用系统 cron 定时跑天/周/月榜 top-N，或手动指定 BV）。**部署后端不内置任何定时/后台采集任务。**
  2. 项目内置 seed 案例（少量，供演示）。
  3. 手动录入单条案例（可选）。
- **本阶段做**：案例库表结构、离线脚本产出契约、导入接口、AI 清洗（复用现有情绪/噪声分类）、质量打分 v1、专用 Milvus 集合向量入库、索引状态查询。
- **本阶段不做**：检索链路（5.2）、Agent 工具化（5.3）、前端（5.4）、部署后端内置定时采集、看视频内容评质量的多模态 AI、跨创作者共享知识库的权限隔离。

## 2. 设计方案

### 2.1 包结构

新建顶层业务包 `com.link.linkagent.knowledge`（跨任务、跨分区，不归属某个 creator_task，所以不放在 `creator.*` 下）：

```
com.link.linkagent.knowledge
├── config      # 知识库 RAG 配置 + 专用 Milvus 集合 Bean
├── controller  # 案例库导入/列表/索引接口
├── mapper      # 案例库 MyBatis Mapper
├── model       # 请求/响应/记录对象
└── service     # 导入+清洗+打分+向量索引
```

> 注：通用 RAG 内核（`com.link.linkagent.rag`）在 5.2 落地检索链路时再填充，本阶段不提前建空抽象（简单优先）。现有 `creator.feedback` 反馈 RAG 与 `creator.competitor` 竞品分析**保持不动**，与本知识库并行。

### 2.2 数据来源与边界：离线脚本产出契约

离线脚本（5.1b，`scripts/bilibili_reference_fetcher.py`）产出统一 JSON，后端只消费文件，不发起采集：

```json
{
  "source": "bilibili_rank_daily | bilibili_rank_weekly | bilibili_rank_monthly | manual_bv | seed",
  "fetchedAt": "2026-06-05T22:00:00",
  "category": "知识区·科技",
  "videos": [
    {
      "bvId": "BV1xxxxxxxxx",
      "title": "标题",
      "description": "简介",
      "tags": ["标签1", "标签2"],
      "category": "知识区·科技",
      "publishTimeText": "2026-05-30",
      "stats": { "view": 0, "like": 0, "coin": 0, "favorite": 0, "danmaku": 0, "reply": 0 },
      "comments": [ { "content": "评论原文", "like": 0, "reply": 0 } ],
      "danmaku":  [ { "content": "弹幕原文", "timeText": "00:01:12" } ]
    }
  ]
}
```

- `tier` 由 `source` 推导：排行榜来源 → `BENCHMARK`（优品标杆）；`manual_bv` 可由参数指定 `COMPETITOR` 或 `BENCHMARK`。
- 评论/弹幕是**原始全量**，清洗在后端入库时做（成本集中、可控、可关）。

### 2.3 表结构（维护在 `backend/src/main/resources/sql/init.sql`，新表用 `CREATE TABLE IF NOT EXISTS`，沿用现有命名与注释规范）

**表 A：`creator_reference_video`（案例主表，父）**

| 字段 | 类型 | 说明 |

| video_id | VARCHAR(64) | 案例唯一标识（UUID），UNIQUE |
| bv_id | VARCHAR(20) | B 站 BV 号，可空 |
| tier | VARCHAR(16) | 案例层级：BENCHMARK/COMPETITOR/OWN_HISTORY |
| category | VARCHAR(64) | 分区/主题，用于同赛道检索过滤 |
| title | VARCHAR(255) | 视频标题 |
| description | LONGTEXT | 简介 |
| tags | VARCHAR(512) | 标签 JSON |
| view_count / like_count / coin_count / favorite_count / danmaku_count / reply_count | BIGINT UNSIGNED | 热度指标，可空 |
| highlight_summary | LONGTEXT | 清洗后优质评论/弹幕亮点摘要 |

| source | VARCHAR(64) | 数据来源 |
| publish_time_text | VARCHAR(64) | 发布时间文本 |

索引：`uk_video_id`、`idx_category_tier(category, tier)`、`idx_bv_id`、`idx_embedding_status`。

**表 B：`creator_reference_video_item`（清洗后优质评论/弹幕，子）**

结构对标 `creator_feedback_item`，但外键是 `video_id`（跨任务）而非 `task_id`：字段含 `item_id`、`video_id`、`source_type(COMMENT/DANMAKU)`、`content`、`sentiment(POSITIVE/NEGATIVE/NEUTRAL)`、`is_noise`、`like_count`、`reply_count`、`occur_time_text`、`reason`、`embedding_*`、通用字段。索引 `idx_video_sentiment(video_id, sentiment)`、`idx_video_embedding_status`。

> 父子两表是为 5.2 的「父子召回（small-to-big）」打底：子表存可被精确召回的优质短文本，父表是召回后扩展的完整案例。本阶段先把两表建好、各存各的，5.1 的向量入库先只索引**父表案例卡片文档**（每视频 1 个向量），子表向量化 + 父子召回留 5.2。

### 2.4 专用 Milvus 集合与 Bean 隔离（关键技术点）

现状：`spring.ai.vectorstore.milvus` 自动配置**只管一个集合**（`creator_feedback_evidence` @1536），反馈 RAG 通过 `ObjectProvider<VectorStore>` 注入这个自动配置 Bean。

知识库需要**不同集合 + 不同维度（1024）**，且不能干扰反馈 RAG 的 `ObjectProvider<VectorStore>` 解析。设计：

- 知识库**不复用** `vectorstore.type=milvus` 自动配置，而是在 `knowledge.config.KnowledgeVectorStore` 里**自行构建并内部持有**一个 `MilvusVectorStore` 实例（集合 `creator_reference_video`、维度 1024），**不把它注册成 `VectorStore` 类型的 Spring Bean**，从根上避免和反馈的 `ObjectProvider<VectorStore>` 出现多 Bean 歧义。
- 通过 `knowledge.rag.enabled` + `EmbeddingModel` 是否存在两层判断决定是否启用；任一不满足 → 知识库走 SQL 关键词检索（5.2），写入接口在关闭时返回 400 并提示。
- Embedding 全局切到 **Qwen `text-embedding-v4` @1024**（见 2.6）；反馈集合维度默认值同步改成 1024 以保持一致（反馈集合当前无数据、未部署，无需迁移；代码不动）。

> ⚠️ **必须先联网核实再编码**：Spring AI 1.1.4 中 `MilvusVectorStore`/`MilvusServiceClient` 的构建 API（builder 签名、是否需要 `io.milvus` 客户端 Bean、`initialize-schema` 手动建集合方式）。不凭记忆写。

### 2.5 AI 清洗（复用现有能力，成本集中在入库时刻）

- 复用反馈侧已有的「情绪 + 噪声」分类思路：对每条评论/弹幕判定 `sentiment(POSITIVE/NEGATIVE/NEUTRAL)` 与 `is_noise`。
- **只保留 `is_noise=0` 且 `sentiment ∈ {POSITIVE, NEGATIVE}`** 的条目写入 `creator_reference_video_item`，中性灌水/无意义直接丢弃（符合「只取优质正负评论弹幕」）。
- 清洗在**导入时一次性**做，受 LLM_GUARD 输入上限保护；批量大时分批调用，避免单次超限。
- `highlight_summary` 由清洗后的优质条目让小模型汇总成一段，作为案例卡片的语义主体之一。

### 2.6 Embedding 选型（已核实）

- 模型：Qwen `text-embedding-v4`，OpenAI 兼容端点 `https://dashscope.aliyuncs.com/compatible-mode/v1`。
- 维度：**1024**（官方推荐平衡点），必须与 Milvus 集合维度严格一致。
- **批次上限 10**（v3/v4 OpenAI 兼容模式硬限制）：知识库索引批次常量设为 **≤10**（反馈侧是 25，本侧不能照抄）。
- 复用现有 `spring.ai.openai.embedding.*` 配置键，环境变量：
  ```
  EMBEDDING_MODEL_TYPE=openai
  LLM_EMBEDDING_MODEL=text-embedding-v4
  LLM_EMBEDDING_DIMENSIONS=1024
  LLM_EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
  LLM_EMBEDDING_API_KEY=<DashScope Key>
  ```

### 2.7 质量打分 v1（具体公式）

每个案例视频按所属 `category` 归一化出 0–100 的 `quality_score`。公式分四步，所有权重/常数集中在 `KnowledgeQualityProperties`，便于真实数据采回后标定（形态固定、数值可调）。

**输入**：六项热度指标 `view/like/coin/favorite/danmaku/reply`；清洗后子表条目数 `posCount`(优质正向)、`negCount`(优质负向)。

**第 1 步 互动率**（用「率」而非绝对量，避免大播放量碾压视频；`view` 缺失或为 0 时不打分，`quality_score=NULL`）：

```
likeRate    = like     / view
coinRate    = coin     / view
favRate     = favorite / view
danmakuRate = danmaku  / view
replyRate   = reply    / view
```

**第 2 步 加权互动分**（权重反映质量信号强弱，投币最高；五项权重和 = 1，取对数压制 B 站长尾爆款）：

```
engagement    = 0.40*coinRate + 0.25*favRate + 0.20*likeRate + 0.10*replyRate + 0.05*danmakuRate
engagementLog = ln(1 + 1000 * engagement)        // ×1000 让普遍偏小的“率”进入合适数值区间
```

**第 3 步 情绪因子**（含小样本置信度衰减，平滑常数 K=10：样本少时收敛到中性 0.5，避免“2 条评论全是好评”这种极端比例失真）：

```
n               = posCount + negCount
rawSentiment    = (n == 0) ? 0.5 : posCount / n          // 0~1
confidence      = n / (n + 10)                           // 0~1，样本越多越接近 1
sentimentFactor = 0.5 + (rawSentiment - 0.5) * confidence
sentimentMul    = 0.7 + 0.6 * sentimentFactor            // 0.7=全差评 1.0=中性 1.3=全好评
```

**第 4 步 分区归一化到 0–100**（按 `category` 分组对 `rawScore` 做 min-max；同组只有一条或全相等时给中性 60）：

```
rawScore = engagementLog * sentimentMul
对同一 category（is_deleted=0）的所有视频：
  qualityScore = (maxRaw == minRaw) ? 60.0 : 100 * (rawScore - minRaw) / (maxRaw - minRaw)
```

**计算时机**：导入新案例后，对**受影响的 category** 重算该分区全部视频的 `quality_score`（归一化是分区相对值，新增样本会改变该分区的 min/max）。

**可调常数（`KnowledgeQualityProperties`）**：五项互动权重、对数缩放系数 1000、平滑常数 K=10、情绪乘子区间 0.7–1.3、单条/全等兜底分 60。**公式形态固定，数值待真实排行榜数据采回后标定**——这就是作者说的“按已有视频数据反推”。

**边界**：`view` 缺失或为 0 → 不打分（`quality_score=NULL`），视频仍入库可检索；无清洗子条目 → `sentimentFactor=0.5`（中性，不奖不罚）。

### 2.8 对外接口（全部 Jakarta Validation 校验）

```text
POST /api/knowledge/reference-videos/import          # 导入离线脚本/seed 产出的案例 JSON（含清洗+打分+落库）
GET  /api/knowledge/reference-videos                 # 列表，支持 category/tier 过滤、分页
POST /api/knowledge/reference-videos/index/rebuild   # 重建向量索引（默认关时 400；批次≤10）
GET  /api/knowledge/reference-videos/index/status    # 索引状态（ragEnabled/vectorStoreReady/各状态计数/检索模式预测）
```

索引接口的响应结构、`embedding_status` 回写、按批提交、不加 `@Transactional`、失败收集 warnings——**完全沿用反馈索引服务的成熟范式**。

### 2.9 默认关 + 优雅降级

- `knowledge.rag.enabled` 默认 `false`：不连 Milvus、不调 Embedding，导入/清洗/打分/落库照常工作（这部分不依赖向量库），只是不能建向量索引；检索（5.2）在关闭时走 SQL。
- 与现有 `creator.feedback.rag` 完全独立的开关，互不影响。

### 7.2 相对设计的调整（重要）

1. **新增「单 BV 一键采集导入」接口与链路**（设计 §2.8 未列）。作者于 2026-06-07 确定：前端输入 BV → 后端**显式调用**采集脚本 → 自动清洗导入，一步到位，不要「先抓再手动导」。
   - 新接口：`POST /api/knowledge/reference-videos/fetch-import { bvInput, tier?, category? }`，复用 `CreatorFeedbackService.runFeedbackScript` 的 `ProcessBuilder` 套路（落在 `KnowledgeReferenceFetchService`），读脚本产物后转交现有 `importReferenceVideos`。
   - 合规：单 BV 显式触发是项目允许的采集方式；榜单批量仍只走离线脚本（cron），后端不内置后台采集。
2. **前端「案例库」surface 提前到本阶段**（设计原列在 5.4）。只做最小可测版：`App.vue` 第三个 surface + 采集表单（BV / 层级 / 分区）+ 结果提示 + 案例列表（过滤 / 分页）。完整知识库管理与检索可视化仍留 5.4。
3. **离线脚本产出契约对齐**：实际产出**不含 `fetchedAt`**（§2.2 示例里的该字段已弃用）；以导入请求记录字段为准（`source` / `tier?` / `category?` / `videos[]`）。脚本 `bv` / `rank` 两个子命令产出同一形状。

### 7.3 本阶段对外接口现状（已实现部分）

```text
POST /api/knowledge/reference-videos/import           # 导入脚本/seed 产出的案例 JSON（清洗+去重+落库+按分区重算质量分）
POST /api/knowledge/reference-videos/fetch-import      # 输入 BV → 调脚本采集 → 自动清洗导入（单 BV 一键）
GET  /api/knowledge/reference-videos                  # 列表，支持 category/tier 过滤、分页

GET  /api/knowledge/reference-videos/index/status     # 索引状态：ragEnabled/vectorStoreReady/各状态计数/检索模式预测
```

### 7.4 离线采集脚本 `scripts/bilibili_reference_fetcher.py`

纯公开接口、不带 Cookie、自带 WBI 签名、礼貌节流（复用反馈脚本同款抓取内核）。两个子命令产出导入契约 JSON：

```bash
# 榜单批量（作者本地 cron）：抓分区榜单前 N 条
python scripts/bilibili_reference_fetcher.py rank --category 知识 --limit 10
# 单 BV（后端 fetch-import 复用此模式）
python scripts/bilibili_reference_fetcher.py bv BV1xxxxxxxxx --source manual_bv
```

通用参数（`--max-comments` / `--max-danmaku` / `--tier` 等）用 argparse `parents=[common]` 承载，允许写在子命令之后。

### 7.5 验证入口（编译 / 运行由作者执行）

### 7.6 5.1c 实现要点与设计偏离（更新于 2026-06-07）

1. **质量打分 v1**：严格按 §2.7 四步（互动率 → 加权对数 → 情绪因子含 K=10 平滑 → 分区 min-max 归一化）。打分时机为「导入后对受影响分区重算」，与导入同一事务（跨 bean REQUIRED 传播，能读到刚插入的行）。`view` 缺失/为 0、或分区缺失 → 不打分（`quality_score=NULL`）；同分区孤例/全等 → 兜底 60。权重/常数集中在 `KnowledgeQualityProperties`（`knowledge.quality.*`），数值待真实数据标定。
2. **向量索引做成增量（相对反馈范式的有意偏离）**：反馈是「按 task 全量重建」；知识库是全局且持续增长的语料，故 `index/rebuild` 只索引 `embedding_status IN ('PENDING','FAILED')` 的案例，已 INDEXED 的不重复嵌入以省 Embedding。批大小取 `knowledge.rag.index-batch-size`（默认 10，Qwen 兼容模式硬上限），单次默认上限 `knowledge.rag.max-index-items`（默认 200）+ 接口 `@Max(1000)` + 服务硬上限三重防御。
3. **只索引父表案例卡片**（每视频 1 向量）：文档文本 = 标题/分区/层级/标签/简介/亮点摘要 + 热度 + 质量分；metadata 带 videoId/tier/category/qualityScore 等供 5.2 过滤。`embedding_id` 复用 `video_id`。子表向量化与父子召回仍留 5.2。
4. **索引服务不加 `@Transactional`**：Milvus 写入不归 DB 事务管，按批 `add` + 按批回写 `embedding_status`，部分失败写 `failedCount`/`warnings` 不整体回滚——沿用反馈索引成熟范式。
5. **前端**：案例卡片加「质量分」chip；新增「向量索引」面板（状态计数 + 检索模式 + 重建按钮），RAG 关闭时显示降级状态、按钮禁用，用于验证优雅降级。
