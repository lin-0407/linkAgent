# 阶段 4.9 - Prompt 版本评测闭环

## 需求分析

前一版项目已经能完成创作者工作流闭环，但简历亮点还不够硬：很多能力看起来只是“表单提交 -> 调用 LLM -> 展示结果”。真正能体现 AI 应用工程化能力的地方，是让模型输出可复现、可比较、可迭代。

本轮解决的问题：

1. 同一个评测样例下，不知道某次结果用了哪个 Prompt 版本。
2. 模型输出不好时，只能看 raw output，无法回到当时的 Prompt 快照复盘。
3. 多次评测结果没有按 Prompt 版本聚合，无法对比哪一版更稳、更省 token。

本轮目标用户是项目作者和面试讲解场景。这个能力不直接给普通 UP 主使用，而是服务作者调试发布前优化、评论弹幕分析和复盘报告的 Prompt。

本轮做：

1. 评测结果保存 Prompt 版本、Prompt 哈希和 Prompt 快照。
2. 后端在未提供哈希时，根据 Prompt 快照自动计算 SHA-256。
3. 新增 Prompt 版本统计接口，按版本聚合结果数量、成功次数、平均分、平均 token 和平均耗时。
4. 前端开发者测试弹窗支持录入 Prompt 信息，并展示版本对比摘要。

本轮不做：

1. 不做自动跑评测。
2. 不做多模型批量调度。
3. 不做 Prompt 模板后台。
4. 不把这个入口放到创作者主流程里。

## 设计方案

### 数据模型

扩展 `creator_eval_result`：

```text
prompt_version
prompt_hash
prompt_snapshot
```

设计原因：

1. `prompt_version` 用于人类识别，例如 `prepublish-v2`。
2. `prompt_hash` 用于判断两次评测是否真的使用同一份 Prompt。
3. `prompt_snapshot` 用于复现，不再只凭口头描述回忆当时怎么写的提示词。

### 接口

记录评测结果时新增字段：

```json
{
  "promptVersion": "prepublish-v2",
  "promptSnapshot": "system: ...\nuser: ..."
}
```

新增统计接口：

```text
GET /api/creator/evaluations/cases/{caseId}/prompt-version-stats
```

返回每个 Prompt 版本的：

1. 结果数量。
2. 成功数量。
3. 成功率。
4. 平均人工评分和分项均值。
5. 平均 token、token 总量和平均耗时。
6. 评分覆盖率和分数波动。
7. 最近一次 Prompt 哈希。

### 前端

开发者测试弹窗新增：

1. Prompt 版本输入。
2. Prompt 哈希输入。
3. Prompt 快照输入。
4. Prompt 版本对比摘要。

这样演示时可以直接讲：同一个样例不是只看一次结果，而是把不同 Prompt 版本的表现沉淀下来。

## 测试验证

作者本地执行：

```bash
cd backend
mvn test
```

```bash
cd link-agent-frontend
npm run type-check
npm run build
```

验收点：

1. 记录评测结果时填写 `promptSnapshot`，后端应自动生成 64 位 SHA-256 哈希。
2. 最近结果列表能看到 Prompt 版本。
3. 结果详情能看到 Prompt 版本和快照。
4. Prompt 版本对比区域能显示该样例下的版本数量、成功率、平均分、准确性均值、平均 token、评分覆盖率和分数波动。

说明：如果你本地已经启动过旧版 Docker Compose，MySQL 卷里旧表不会自动新增字段。演示环境可以重置 MySQL 卷后再启动，保留数据时则手动执行字段补齐 SQL。

## 简历表达

可以写成：

```text
设计 Prompt 版本评测闭环：评测结果绑定 Prompt 版本、快照和 SHA-256 哈希，并按版本聚合人工评分、耗时与 token，用于支撑 Prompt 迭代和失败复盘。
```

这比“调用大模型生成建议”更像 AI 应用工程化亮点。
