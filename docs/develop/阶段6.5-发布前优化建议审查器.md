# 阶段 6.5：发布前优化建议审查器

## 需求结论

本阶段继续提升发布前优化 Agent 的建议准确性。目标不是让模型多说，而是让系统能识别建议中哪些地方缺少依据、哪些地方可能误导 UP 主。

输入仍然是发布前优化生成后的结构化建议和证据包。输出新增一份审查报告，保存到 `creator_suggestion.audit_report`，并把 `quality_status` 更新为审查状态。

本阶段不做自动重写，不阻断建议入库。原因是第一版规则可能存在误判，先把问题暴露出来，比直接影响用户拿结果更稳妥。

## 设计方案

新增 `PrePublishSuggestionAuditor`，使用确定性规则审查建议。

审查维度：

- `titleSuggestions` 必须存在，且每条标题建议尽量带 `evidenceIds`。
- `actionableRevisionPlan` 必须存在，且 `HIGH` 优先级动作必须带 `evidenceIds`。
- 所有 `evidenceIds` 必须来自当前证据包，不能编造编号。
- 建议文本不能出现明显夸大承诺，例如“必爆”“爆款保证”“完播率翻倍”“推荐算法会”。
- 结构化字段如果不是合法 JSON 数组，会被标记为审查警告。

审查报告结构：

```json
{
  "status": "AUDIT_PASSED / AUDIT_WARNED / AUDIT_FAILED / AUDIT_SKIPPED",
  "score": 90,
  "summary": "审查发现 1 个需要复核的问题。",
  "issues": [
    {
      "severity": "WARN",
      "code": "TITLE_WITHOUT_EVIDENCE",
      "target": "titleSuggestions[0]",
      "message": "标题建议没有引用证据，作者难以判断这条标题为什么更适合当前内容。",
      "evidenceIds": []
    }
  ],
  "auditedAt": "2026-06-30T..."
}
```

## 验证点

开发者不能执行编译和测试命令。作者需要本地验证：

1. 执行后端编译，预期无编译错误。
2. 执行发布前优化接口，预期响应中出现 `auditReport`。
3. 构造一个标题建议引用不存在证据编号的输出，预期 `qualityStatus=AUDIT_FAILED`。
4. 构造一个标题建议不带证据编号的输出，预期 `qualityStatus=AUDIT_WARNED`。
5. 正常带证据的建议，预期 `qualityStatus=AUDIT_PASSED`。

## 边界

本阶段审查器不会判断“建议是否真的好看”。它只判断建议是否具备基础可信度：有没有证据、是否编造证据、是否承诺无法保证的增长结果。

后续可以扩展为：审查失败后自动触发一次低温重写，或者把审查问题展示到前端给作者人工复核。
