# 阶段 6.1 - Multi Agent 并发与引用审查

## 一、需求分析

本轮目标是在阶段 6 已有 PaE / Multi Agent 基础上，解决三个问题：

- Worker 串行执行导致复杂任务等待时间过长。
- Worker 结果全量塞给 Synthesizer，容易造成上下文膨胀。
- Synthesizer 输出缺少可追溯证据链，事实性结论容易混入幻觉。

本轮服务对象仍是 B 站内容创作者和内容运营者。典型场景是让 AI 同时分析选题、标题、观众反馈和案例检索，再给出可执行建议。

本轮做：

- Multi Agent 按 `dependsOn` 做依赖层级并发。
- Worker 输出增加摘要层 `WorkerBrief` 和证据列表 `AgentEvidence`。
- Synthesizer 改为生成带引用的 `CitedAnswer`，最终渲染为旧的 `finalAnswer` 字符串。
- Synthesizer 后新增 `AgentAnswerAuditor`，检查回答完整性、矛盾和引用缺失。
- 前端执行轨迹展示 Worker 摘要和证据。

本轮不做：

- 不引入完整 ReWOO 依赖图规划。
- 不做 PaE 每步 Replanner。
- 不新增数据库表。
- 不改变 `/api/agent/chat` 请求结构。

## 二、设计方案

### 2.1 Worker 并发

`MultiAgentOrchestrator` 保留 `WorkerPlan.calls.dependsOn` 作为依赖契约。

执行器每轮找出所有依赖已经成功的 Worker，使用 `CompletableFuture` 并行执行。同一轮的 Worker 之间没有依赖关系，因此可以并发。

如果依赖不存在、依赖失败或依赖形成循环，后续 Worker 标记为 `SKIPPED`，不继续执行。

并发上限暂用常量 `DEFAULT_MAX_PARALLEL_WORKERS = 4`，避免一次请求把 LLM 并发打满。后续可外置到配置。

### 2.2 结构化摘要和证据

新增结构：

- `WorkerBrief`：核心结论、关键点、置信度、证据 ID、未解决问题。
- `AgentEvidence`：证据 ID、来源类型、来源位置、内容摘录、置信度。
- `EvidenceSourceType`：区分工具观察、用户输入、上下文、Worker 推理和系统限制。

`PlanExecuteWorkerAgent` 会把内部 PaE 成功执行的 `PlanStepExecution.observation` 转成工具观察证据。

`DirectReasoningWorkerAgent` 只能产出 `WORKER_REASONING` 类型证据。这样 Synthesizer 可以把它当作建议依据，而不是外部事实。

### 2.3 引用合成

`AgentAnswerSynthesizer` 不再只要求模型输出自然语言。

它先要求模型输出 `CitedAnswer`：

- `statements`：回答句子或要点，每条带 `evidenceIds`。
- `limitations`：证据不足、执行失败或不确定处。

随后后端把结构化答案渲染成旧字段 `finalAnswer`，例如：

```text
- 当前标题需要强化目标人群，因为现有证据只说明内容主题，没有说明适合谁看。[W1-P2-E1]
```

这样保持前端和旧调用方兼容，同时让每句话有来源。

### 2.4 完备性审查

新增 `AgentAnswerAuditor`。

审查器输入用户问题、候选 `CitedAnswer` 和可用证据，输出 `AnswerAuditReport`。

审查重点：

- 是否回答完用户问题。
- 是否自相矛盾。
- 是否有未引用的事实性断言。
- 是否把 Worker 推理当成外部事实。

审查不通过时，Synthesizer 最多重写 2 轮。仍不通过时保留保守答案，并在最终回答追加审查提示。

## 四、验证清单

后端：

- `MULTI_AGENT` 下无依赖 Worker 能并发执行，并按 `callId` 稳定返回。
- 依赖失败的 Worker 被标记为 `SKIPPED`。
- Worker trace 中包含 `brief` 和 `evidences`。
- 最终回答每条事实性陈述带证据 ID。
- 审查器失败时不影响主回答返回。

前端：

- Worker 轨迹能展示核心结论、证据 ID、置信度。
- 证据详情可展开查看来源类型、来源位置和摘录。
- 旧的计划轨迹展示不受影响。
