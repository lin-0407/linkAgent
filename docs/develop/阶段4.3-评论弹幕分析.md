# 阶段 4.3：评论弹幕分析

## 需求分析

本阶段服务的目标用户仍然是 B 站 UP 主、内容运营者和内容复盘者。

要解决的场景是：当视频已经发布后，用户手动粘贴评论和弹幕样例，系统需要快速提炼高频观点、情绪倾向、争议点、误解点和下一期内容建议。

输入数据来源：

1. 用户主动粘贴的评论样例。
2. 用户主动粘贴的弹幕样例。
3. 用户补充的上下文信息，例如发布时间、视频表现或分析重点。
4. 后续阶段允许用户主动导入脚本生成的 JSON/TXT 样例文件。

本阶段只做同步分析基线：

1. 保存评论样例和弹幕样例。
2. 基于样例生成结构化反馈分析报告。
3. 按 `taskId` 查询样例和报告。
4. 将任务状态更新为 `FEEDBACK_ANALYZED`。

本阶段不做，后续由阶段 4.4.1 分步承接：

1. 真实 B 站评论/弹幕爬取。
2. SSE 流式过程展示。
3. 复盘总报告聚合。
4. 评论情绪打分模型。
5. 多轮 Agent 协作。
6. 评论弹幕明细级导入、清洗、分类、图表和 RAG 追问。

## 设计方案

### 后端包结构

新增业务包：

```text
com.link.linkagent.creator.feedback
```

这个包只负责评论弹幕样例和反馈分析，不和稿件材料、发布前建议、复盘报告混在一起。

### 数据表

新增 `creator_user_feedback_detail`：

```text
保存用户主动提供的评论样例、弹幕样例和补充背景。
```

新增 `creator_llm_feedback_report`：

```text
保存 LLM 对评论弹幕样例生成的结构化分析结果。
```

两张表分开，是为了让原始样例和分析结果可以独立排查和重跑。

### API

```text
POST /api/creator/tasks/{taskId}/feedback
GET  /api/creator/tasks/{taskId}/feedback
POST /api/creator/tasks/{taskId}/feedback/analyze
GET  /api/creator/tasks/{taskId}/feedback/report
```

### 入参校验

所有对外接口继续使用 Jakarta Validation：

1. `taskId` 长度不能超过 64。
2. 评论样例最长 20000。
3. 弹幕样例最长 20000。
4. 补充背景最长 500。
5. 评论样例和弹幕样例至少填写一项。
6. 分析重点和额外要求最长 500。

### 是否涉及 Agent

本阶段对外叫“评论弹幕分析”，但内部先用一次 LLM 调用完成结构化总结，不先接 ReAct 工具链。

原因很直接：

1. 当前阶段先验证“样例输入 -> 分析报告 -> 数据库存档”闭环。
2. 反馈分析更像结构化总结，先把 Prompt 和 JSON 输出跑稳更重要。
3. 后续做复盘报告时，再把发布前建议和反馈分析汇总起来。

### 与阶段 4.4.1 的关系

阶段 4.3 是已完成的同步 LLM 基线，职责是验证“用户主动提供样例 -> 反馈报告 -> 数据库存档”。

阶段 4.4.1 会在此基础上做增量升级：

1. 保留当前样例保存和反馈报告接口，继续作为简单联调入口。
2. 新增导入接口，支持用户上传脚本导出的评论弹幕 JSON/TXT。
3. 新增评论和弹幕明细表，用于保存单条内容、分类、情绪和无意义标记。
4. 新增反馈仪表盘接口，提供评论类型占比、弹幕类型占比、情绪分布、高频观点和指标展示。
5. 新增反馈追问接口，第一版基于 MySQL 中的分类结果和报告回答，后续再接 Milvus 做 RAG。
6. 平台数据边界不变：不默认实现后端自动采集，不保存 Cookie，不绕过平台限制。

## 编码实现

本轮新增：

- `CreatorFeedbackController`：评论弹幕接口。

- `backend/src/main/resources/sql/init.sql`
  - 新增 `creator_user_feedback_detail`
  - 新增 `creator_llm_feedback_report`

  - 新增 `FEEDBACK_ANALYZED`

## 接口示例

### 保存样例

```http
POST /api/creator/tasks/{taskId}/feedback
Content-Type: application/json

{
  "commentSamples": "这期节奏很清楚，我第一次看懂了整个流程。",
  "danmakuSamples": "讲得太实用了 / 这一段信息密度很高",
  "extraContext": "发布后 24 小时内收集的样例"
}
```

### 分析样例

```http
POST /api/creator/tasks/{taskId}/feedback/analyze
Content-Type: application/json

{
  "analysisFocus": "重点看观众是否理解核心方法",
  "extraRequirement": "给出下一期选题建议"
}
```

### 查询报告

```http
GET /api/creator/tasks/{taskId}/feedback/report
```

## 测试验证点

正常路径：

1. 保存评论和弹幕样例后，应能查询到样例内容。
2. 样例存在时执行分析，应生成反馈报告并保存。
3. 再次查询报告时应返回最新结果。
4. 任务状态应更新为 `FEEDBACK_ANALYZED`。

边界路径：

1. 任务不存在时返回 404。
2. 样例为空时返回参数校验失败。
3. 任务存在但没有样例时，分析接口返回 400。
4. LLM 输出不是 JSON 时，仍应保存原文并标记为 `RAW_ONLY`。

作者本地验证命令：

```bash
cd backend
mysql -u root -p < src/main/resources/sql/init.sql
mvn test
```

如果只想先检查编译：

```bash
cd backend
mvn test -DskipTests
```
