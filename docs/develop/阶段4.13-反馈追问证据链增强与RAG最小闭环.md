## 关键设计决策

### 双层检索

```
用户追问
  → RAG 业务开关 + Milvus 可用？
    → 是：向量检索（FilterExpression 按 taskId 过滤） → itemId 回查 MySQL
         → 命中 >= minVectorHitCount：返回 MODE_VECTOR
         → 命中不足：合并 SQL 兜底 → MODE_VECTOR_WITH_SQL_FALLBACK
    → 否：SQL 关键词评分 → MODE_SQL
```

### MySQL 始终是事实来源

向量检索后，所有候选 `itemId` 必须经 `taskId + is_deleted = 0` 回查 MySQL。向量库里的旧导入批次文档或已删除明细不会进入最终证据。

### 索引不加 `@Transactional`

Milvus 写入不受 DB 事务管理。按 25 条一批提交、按批回写状态，让 `embedding_status` 真实反映向量库现状。部分批次失败时，其余批次状态不受影响。

### 两层开关

- `spring.ai.vectorstore.type=milvus` 激活 Milvus 自动配置（基础设施层）
- `CREATOR_FEEDBACK_RAG_ENABLED=true` 让追问业务走向量链路（业务层）

两层独立，避免"基础设施连上了但业务还没准备好"时追问被动切到 RAG。

## 新增接口

```http
POST /api/creator/tasks/{taskId}/feedback/evidence-index/rebuild
GET  /api/creator/tasks/{taskId}/feedback/evidence-index/status
```

原 `POST /api/creator/tasks/{taskId}/feedback/chat` 请求/响应结构不变，只有 `retrievalMode` 和 `ragEnabled` 根据实际检索情况变化。

## 本阶段不做

- 不做跨任务知识库检索
- 不做导入后自动索引（索引由用户显式触发，避免隐藏 Embedding 成本）
- 不做定时索引或删除同步
- 不新增 docker-compose（Milvus 部署留给显式开启 RAG 时手动组合）

## 数据库变更

```sql
-- creator_feedback_item 新增 4 列（已有库走条件式 ALTER，重复执行不报错）
embedding_id          VARCHAR(128) -- 默认复用 item_id
embedding_status      VARCHAR(32)  -- PENDING/INDEXED/FAILED/SKIPPED
embedding_error       VARCHAR(512) -- 失败原因摘要
embedding_update_time DATETIME     -- 最近状态更新时间
```

## 配置开启步骤（可选）

1. 启动 Milvus Standalone（etcd + minio + milvus-standalone）
2. 在 `.env` 设置：
   ```
   EMBEDDING_MODEL_TYPE=openai
   VECTOR_STORE_TYPE=milvus
   MILVUS_HOST=localhost
   MILVUS_INITIALIZE_SCHEMA=true  # 首次建集合时
   CREATOR_FEEDBACK_RAG_ENABLED=true
   ```
3. 重启后端，确认集合创建成功
4. 把 `MILVUS_INITIALIZE_SCHEMA` 改回 `false`
5. 在反馈报告弹窗点击"重建证据索引"
