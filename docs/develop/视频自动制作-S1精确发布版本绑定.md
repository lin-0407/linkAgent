# 视频自动制作 S1：精确发布版本绑定

日期：2026-10-19。本轮只完成版本归属的后端子步骤，完整 S1 仍未结束。

## 需求与设计

独立版本上传后，任务与 BV 的绑定不能只保存 BV 号。否则后台同步可能在当前版本变化后，用另一个视频的试映结果放行旧绑定；旧同步请求也可能覆盖用户刚修正的 BV。

本轮沿用个人工作台、显式发布方案确认和已有成片跳过入口，不增加账号体系，不调用模型、OSS 或 B 站。数据库输入来自任务、当前版本、处理任务和试映记录，输出为明确版本的 BV 绑定和同步结果。

在统一 `init.sql` 的 `creator_task_video_binding` 增加可空 `published_version_id`，并提供同脚本内可重复执行的补列语句。旧数据保持 NULL，不根据 V1、最大版本或当前指针回填。

原 `POST /api/creator/bilibili/tasks/{taskId}/video-binding` 请求不变，仍沿用 Jakarta Validation；POST/GET 绑定响应增加 `publishedVersionId`，为空表示历史归属未知。前端只同步类型，不增加历史选版或页面入口。

## 实际行为

1. 用户显式新建或修正未核验绑定时，在原任务锁内检查当前版本的探测、对应预处理和对应试映，保存本次检查通过的 `versionId`。缓存命中直接 BOUND 和等待同步两条路径都保存版本。
2. 已经 BOUND 的重复请求原样返回。历史记录版本为空时也保持为空，不用现在的成片推断过去。
3. 后台同步仍在外部请求结束后进入短事务；按任务 ID 排序，先加任务行锁，再对绑定做 `FOR UPDATE` 当前读。绑定 ID、用户、UID、BV 或版本已经变化时，跳过过期结果；已删除绑定不复活。排序避免多个同步事务以不同顺序锁同一批任务。
4. 待核验绑定转 BOUND 时只检查其记录的精确版本。该版本未就绪、记录缺失或试映不匹配时不放行，也不回退当前版。历史待核验绑定未记录版本时，提示用户重新确认绑定；负向 UID/视频不存在结果仍可保存。
5. 反馈、复盘等调用原媒体门禁时，已正式绑定且记录了版本的任务，读绑定版本；只读就绪查询也使用同一选择规则。未记录版本的旧任务继续原有媒体检查路径，但不补造历史版本归属。

`CreatorBilibiliMapper` 的单条读取、BV 冲突查询、UID 列表和用户列表均携带新字段，避免同步时读丢版本。修正绑定时版本和 BV 在同一 SQL 中写入；同步仅更新状态和说明，不改变版本。

原媒体删除流程保留状态和文本报告，允许后续反馈与复盘识别已完成试映。本轮保持该规则：对象删除不会抹掉精确发布版本或历史完成事实。它与“历史选版必须有可用媒体”的后续选版规则属于不同操作。

## 边界

本轮没有发布标题/简介快照、方案/蓝图上下文快照、历史列表/选版或自动制作。方案确认门禁仍沿用现有规则；不能把“媒体门禁固定到发布版本”说成反馈与复盘已完整使用发布内容快照。用户实际发布仍在 B 站完成。

尚未部署业务服务、修改作者数据库或做浏览器验收；后续版本切换需要完整上下文和发布文案快照配套，不能只开放指针切换。

新增真实 MySQL 场景：

- 用户绑定精确版本，映射在任务/BV/UID/用户查询中一致，延迟同步后不因当前指针变化而改读另一个版本。
- 当前版已通过试映，但绑定版本探测失败时，同步不能借用当前版推进 BOUND。
- 历史未知版本不自动回填；用户显式修正时才写入，已 BOUND 的幂等返回保持原样。
- 同步事务先读旧快照，再由另一个事务修正 BV，当前读能识别过期结果并跳过。
- 同步与重新定位竞争时共用任务锁，已删除待核验绑定不被恢复。
- 绑定指向其他任务版本时拒绝，查询仍约束归属，不能回退当前版。
- 删除正式发布版本的媒体后，保留绑定身份和已完成试映，反馈/复盘门禁仍可读取历史完成事实；对象存储为替身，仅验证 SQL、事务与对象删除编排。
