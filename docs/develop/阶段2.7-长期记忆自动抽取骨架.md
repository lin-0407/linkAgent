# 阶段 2.7：长期记忆自动抽取骨架

## 上下文

阶段 2.5 和 2.6 已经完成长期记忆的手动写入和 Agent 自动读取。但手动维护长期记忆不符合真实产品体验，用户应该正常聊天，由系统在后台判断是否需要保存长期记忆。

## 本轮目标

让 Agent 在生成最终回答后，自动从“用户消息 + 最终回答”中抽取长期记忆候选，并在候选有效时写入 MySQL。

## 本轮变更

- 新增 `LongTermMemoryCandidate`：表示一条长期记忆候选。
- 新增 `LongTermMemoryExtractor`：调用 LLM 判断本轮对话是否值得长期保存。
- 修改 `AgentExecutor`：最终回答生成后自动调用抽取器并保存长期记忆。
- 新增 `LongTermMemoryExtractorTest`：覆盖有效候选、无需保存、非法响应三条路径。
- 扩展 `AgentExecutorLongTermMemoryTest`：验证最终回答后会自动保存长期记忆。

## 抽取规则

当前只保存这些类型：

- 用户长期偏好，例如喜欢 Java、希望回答简洁、偏好中文解释。
- 用户稳定身份，例如 Java 后端学习者、正在做作品集项目。
- 项目长期信息，例如项目技术栈、长期目标、固定约束。
- 用户明确要求后续持续遵守的规则。

当前不保存这些类型：

- 临时问题、一次性报错、天气时间、工具结果。
- 普通闲聊、情绪表达、短期任务进展。
- 只对当前会话有用的信息。

## 输出协议

抽取器要求 LLM 只输出 JSON：

```json
{"shouldRemember":true,"memoryKey":"user.preference.example","content":"用户偏好..."}
```

或者：

```json
{"shouldRemember":false,"memoryKey":"","content":""}
```

解析失败、LLM 异常、候选为空时，主对话不受影响，只跳过长期记忆保存。

## 设计说明

第一版自动记忆采用同步调用，目的是让链路最容易观察和调试。后续如果发现响应耗时明显增加，再把抽取逻辑改为异步任务。

长期记忆抽取必须保守。宁可漏掉一部分可记内容，也不要把临时问题和噪声写进长期记忆，否则后续 Prompt 会被污染。

## 验证方式

```bash
cd backend
mvn test -Dtest=LongTermMemoryExtractorTest,AgentExecutorLongTermMemoryTest
```
