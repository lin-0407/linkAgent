# 阶段 2.6：Agent 读取长期记忆上下文

## 上下文

阶段 2.5 已经完成长期记忆的 MySQL 读写骨架，但 Agent 对话还没有使用这些记忆。本轮只做读取链路：在 Agent 执行前读取用户长期记忆，并拼接到 Prompt。

## 本轮目标

让长期记忆真正参与 Agent 回答。用户通过 `/api/memory/long-term` 保存偏好后，再调用 `/api/agent/chat` 时，Agent 可以在上下文中看到这些偏好。

## 本轮变更

- `AgentChatRequest` 新增 `userId` 字段，默认由后端兜底为 `default`。
- `AgentController` 将 `userId` 传给 `AgentExecutor`。
- `AgentExecutor` 注入 `LongTermMemory`，执行前读取用户长期记忆。
- Prompt 新增 `Long-term memory` 区块，格式为 `memoryKey: content`。
- `LLMService` 新增 protected 空构造器，方便单元测试通过子类捕获 Prompt。
- 新增 `AgentExecutorLongTermMemoryTest`，验证默认用户和显式用户 ID 两条路径。

## 请求示例

先保存长期记忆：

```http
POST /api/memory/long-term
Content-Type: application/json

{
  "userId": "default",
  "memoryKey": "user.preference.language",
  "content": "用户偏好使用 Java 和 Spring AI 开发 AI 应用"
}
```

再发起 Agent 对话：

```http
POST /api/agent/chat
Content-Type: application/json

{
  "sessionId": "session-1",
  "userId": "default",
  "message": "请根据我的技术偏好，推荐下一步学习内容"
}
```

## 设计说明

`userId` 和 `sessionId` 分开是长期记忆的关键。`sessionId` 代表一次对话，`userId` 代表一个用户。长期记忆挂在用户维度，才能跨会话复用。

当前只读取最近 10 条长期记忆。这个数字不是最终方案，只是为了避免 Prompt 初期无限膨胀。后续接入向量检索后，会从“固定取最近”升级为“按问题相关性检索”。

## 验证方式

```bash
cd backend
mvn test -Dtest=AgentExecutorLongTermMemoryTest
```
