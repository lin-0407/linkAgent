## 一、P0-A：结构化输出 Token 追踪

### 问题根因

`LLMService.chatStructured()` 调用链为 `.call().entity(type)`，Spring AI 的 `.entity()` 方法内部调用 `.chatResponse()` 拿到完整响应（含 metadata + usage）后只返回 entity 对象，usage 数据被丢弃。

但 `LLMService` 内部已有的 `chatWithUsage()` 方法证明了 `ChatResponse → Metadata → Usage` 这条路径是通的——`toCallResult()` 方法能从 `ChatResponse` 中提取 `promptTokens`/`completionTokens`/`totalTokens`。

### 解决方案

新增 `chatStructuredWithUsage()` 方法，用 `.chatResponse()` 替代 `.entity(type)` 拿到完整响应，手动从 `ChatResponse.getResult().getOutput().getText()` 提取 JSON 文本，通过 Jackson `ObjectMapper.readValue()` 反序列化为目标类型，同时保留 usage 数据。旧 `chatStructured()` 保留向后兼容。

### 涉及文件

| 类型 | 文件 | 说明 |
|------|------|------|
| 新增 | `backend/.../llm/StructuredCallResult.java` | 泛型包装记录：entity + promptTokens + completionTokens + totalTokens + elapsedMs |
| 修改 | `backend/.../llm/LLMService.java` | 新增 `chatStructuredWithUsage()` 方法；旧 `chatStructured()` 改为调用新方法后返回 `.entity()` |

### 关键代码

```java
// StructuredCallResult.java — 结构化调用结果，同时携带 entity 和 token 用量
public record StructuredCallResult<T>(
    T entity,
    Integer promptTokens,
    Integer completionTokens,
    Integer totalTokens,
    Long elapsedMs
) {}

// LLMService.java — 新增方法
public <T> StructuredCallResult<T> chatStructuredWithUsage(
        String systemPrompt, String userMessage, Class<T> type) {
    validatePromptLength(systemPrompt, userMessage);
    OpenAiChatOptions options = OpenAiChatOptions.builder()
            .responseFormat(new ResponseFormat(ResponseFormat.Type.JSON_OBJECT, null))
            .build();
    RuntimeException lastError = null;
    for (int attempt = 1; attempt <= STRUCTURED_MAX_ATTEMPTS; attempt++) {
        long startNanos = System.nanoTime();
        try {
            // 关键修改：.chatResponse() 替代 .entity(type)，拿到完整响应（含 usage metadata）
            ChatResponse chatResponse = chatClient.prompt()
                    .system(systemPrompt).user(userMessage)
                    .options(options).call().chatResponse();
            long elapsedMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startNanos);
            LlmCallResult callResult = toCallResult(chatResponse, elapsedMs);
            // 手动从响应文本反序列化为目标类型（替代 Spring AI 的 BeanOutputConverter）
            T entity = objectMapper.readValue(callResult.content(), type);
            recordTextSuccess(callResult); // 复用已有的用量统计记录逻辑
            return new StructuredCallResult<>(entity,
                    callResult.promptTokens(), callResult.completionTokens(),
                    callResult.totalTokens(), elapsedMs);
        } catch (RuntimeException ex) {
            long elapsedMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startNanos);
            recordTextFailure(elapsedMs, ex);
            lastError = ex;
            log.warn("结构化输出第 {}/{} 次解析失败：{}", attempt, STRUCTURED_MAX_ATTEMPTS, ex.getMessage());
        }
    }
    throw lastError;
}

// 旧方法保留向后兼容
public <T> T chatStructured(String systemPrompt, String userMessage, Class<T> type) {
    return chatStructuredWithUsage(systemPrompt, userMessage, type).entity();
}
```

### AgentExecutor 调用侧改动

| 路径 | 原调用 | 改为 |
|------|--------|------|
| 文本路 | `llmService.chat(sp, conv)` | `llmService.chatWithUsage(sp, conv)` → `LlmCallResult` |
| 结构化路 | `llmService.chatStructured(sp, conv, ReActStep.class)` | `llmService.chatStructuredWithUsage(sp, conv, ReActStep.class)` → `StructuredCallResult<ReActStep>` |

两个路径都能拿到 `promptTokens` / `completionTokens` / `totalTokens`，写入 `t_agent_step.token_count` 和累加到 `t_agent_trace.total_tokens`。

### 新增 Mapper 接口（2 个）

```java
// AgentTraceMapper — 管理 t_agent_trace + t_agent_step
@Mapper
public interface AgentTraceMapper {

    @Insert("INSERT INTO t_agent_trace (trace_id, session_id, user_input, final_output, " +
            "status, total_tokens, total_steps, start_time, end_time, error_msg, create_time) " +
            "VALUES (#{traceId}, #{sessionId}, #{userInput}, #{finalOutput}, #{status}, " +
            "#{totalTokens}, #{totalSteps}, #{startTime}, #{endTime}, #{errorMsg}, #{createTime})")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insertTrace(AgentTraceRecord trace);

    @Update("UPDATE t_agent_trace SET final_output = #{finalOutput}, status = #{status}, " +
            "total_tokens = #{totalTokens}, total_steps = #{totalSteps}, " +
            "end_time = #{endTime}, error_msg = #{errorMsg} " +
            "WHERE trace_id = #{traceId} AND is_deleted = 0")
    int completeTrace(AgentTraceRecord trace);

    @Insert("INSERT INTO t_agent_step (trace_id, step_index, step_type, content, " +
            "tool_name, tool_input, tool_output, token_count, create_time) " +
            "VALUES (#{traceId}, #{stepIndex}, #{stepType}, #{content}, " +
            "#{toolName}, #{toolInput}, #{toolOutput}, #{tokenCount}, #{createTime})")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insertStep(AgentStepRecord step);

    @Select("SELECT * FROM t_agent_trace WHERE session_id = #{sessionId} " +
            "AND is_deleted = 0 ORDER BY create_time DESC LIMIT #{limit}")
    List<AgentTraceRecord> listTracesBySession(@Param("sessionId") String sessionId,
                                               @Param("limit") int limit);

    @Select("SELECT * FROM t_agent_step WHERE trace_id = #{traceId} " +
            "AND is_deleted = 0 ORDER BY step_index ASC")
    List<AgentStepRecord> listStepsByTrace(@Param("traceId") String traceId);
}

// ConversationSessionMapper — 管理 t_conversation_session + t_conversation_message
@Mapper
public interface ConversationSessionMapper {

    @Insert("INSERT INTO t_conversation_session (session_id, user_id, title, status, " +
            "create_time, update_time) VALUES (#{sessionId}, #{userId}, #{title}, " +
            "#{status}, #{createTime}, #{updateTime}) " +
            "ON DUPLICATE KEY UPDATE title = VALUES(title), update_time = VALUES(update_time)")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int upsertSession(ConversationSessionRecord session);

    @Insert("INSERT INTO t_conversation_message (session_id, role, content, " +
            "tool_name, token_count, create_time) VALUES (#{sessionId}, #{role}, " +
            "#{content}, #{toolName}, #{tokenCount}, #{createTime})")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insertMessage(ConversationMessageRecord message);

    @Select("SELECT * FROM t_conversation_message WHERE session_id = #{sessionId} " +
            "AND is_deleted = 0 ORDER BY create_time ASC")
    List<ConversationMessageRecord> listMessagesBySession(@Param("sessionId") String sessionId);
}
```

### AgentExecutor 改造：5 个持久化节点

在 `AgentExecutor` 中注入 `AgentTraceMapper` 和 `ConversationSessionMapper`，在以下关键节点插入持久化调用。**所有 DB 写入 try-catch 包裹，失败只打 warn 日志不抛异常**——与 `saveLongTermMemory` 的异常策略一致。

| 节点 | 位置 | 操作 |
|------|------|------|
| ① 入口 | `run()` 方法 resolveSessionId 之后 | `upsertSession`(sessionId, userId, userMessage 首 60 字作为 title, status=0) → `insertTrace`(traceId, sessionId, userInput, status=0 运行中) |
| ② 每步 | 文本路/结构化路工具执行后 `steps.add()` 之后 | `insertStep`(traceId, stepIndex, stepType, content, toolName, toolInput, toolOutput, promptTokens, completionTokens) → 累加 `traceRecord.totalTokens`（promptTokens + completionTokens） |
| ③ 结束 | `persistChatTurn()` 方法内 | `insertMessage`(sessionId, "user", userMessage) → `insertMessage`(sessionId, "assistant", finalAnswer) |
| ④ 成功 | `return new AgentChatResponse(...)` 之前 | `completeTrace`(traceId, status=1 成功, finalOutput, totalTokens, totalSteps, endTime) |
| ⑤ 失败 | 超限 return / exception catch | `completeTrace`(traceId, status=2 失败, errorMsg, endTime) |

`runStreaming()` 流式路径在对应的 `runStructuredLoopStreaming` / `runTextLoopStreaming` 和 `persistChatTurn` 调用处插入相同的持久化逻辑。

### Token 累加规则

- 文本路每步：`LlmCallResult.promptTokens()` + `LlmCallResult.completionTokens()` → 累加到 `traceRecord.totalTokens`
- 结构化路每步：`StructuredCallResult.promptTokens()` + `StructuredCallResult.completionTokens()` → 同上
- 结束回填：`completeTrace` 时写入累计的 `totalTokens`
- step 表的 `token_count` 字段：记录本步的 LLM 调用消耗（promptTokens + completionTokens），为 null 时表示该步未调用 LLM（如纯格式错误回灌步骤）

## 三、P1-1：竞品分析 — 融入参考案例体系

### 核心思路

竞品视频就是参考案例中 `tier = COMPETITOR` 的那部分。已有的 BV 导入管道（`KnowledgeReferenceFetchService.fetchAndImport`）自动抓取视频的标题/播放量/互动数据/简介/评论/弹幕，直接复用。用户只需输入 BV 号 → 系统自动拉取 → 存入 `creator_reference_video`(tier=COMPETITOR) → 在参考案例页面每个竞品卡片上增加「对比我的创作」按钮 → 选择任务 → AI 产出对比报告。

不需要用户手动填写任何竞品的文稿或字幕。

## 六、P1-4：LLM / Embedding API Key 用户配置

### 加密方案

参照 one-api / new-api 等 LLM 中转站的实现：AES-256-GCM 加密，密钥从配置文件读取，数据库只存密文。前端展示时脱敏为 `sk-****{后4位}`。

**加密工具类 `AesGcmUtil`**：

```java
// 核心方法：
// - encrypt(plainText, base64EncodedKey) → Base64 密文（含随机 12 字节 IV 前缀）
// - decrypt(cipherText, base64EncodedKey) → 明文
// 算法：AES/GCM/NoPadding，GCM 认证标签长度 128 bit，IV 长度 12 字节
```

**配置项**（application.yml）：

```yaml
linkagent:
  secret:
    aes-key: ${LINKAGENT_AES_KEY:}  # Base64 编码的 32 字节密钥，生产环境通过环境变量注入
```

### 新表

```sql
CREATE TABLE IF NOT EXISTS user_llm_config (
    id                    BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY COMMENT '主键',
    config_id             VARCHAR(64) NOT NULL COMMENT '配置唯一标识（UUID）',
    user_id               VARCHAR(64) NOT NULL DEFAULT 'default' COMMENT '用户标识',
    provider              VARCHAR(32) NOT NULL COMMENT '供应商：DEEPSEEK / OPENAI / SILICONFLOW / CUSTOM',
    llm_base_url          VARCHAR(512) DEFAULT NULL COMMENT 'LLM API 地址，为空时使用系统默认',
    llm_api_key_enc       VARCHAR(1024) DEFAULT NULL COMMENT 'LLM API Key（AES-256-GCM 加密后的 Base64）',
    llm_model_name        VARCHAR(128) DEFAULT NULL COMMENT 'LLM 模型名称，为空时使用系统默认',
    embedding_base_url    VARCHAR(512) DEFAULT NULL COMMENT 'Embedding API 地址',
    embedding_api_key_enc VARCHAR(1024) DEFAULT NULL COMMENT 'Embedding API Key（加密）',
    embedding_model_name  VARCHAR(128) DEFAULT NULL COMMENT 'Embedding 模型名称',
    create_time           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    is_deleted            TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除：0=正常，1=已删除',
    UNIQUE KEY uk_llm_config_id (config_id),
    UNIQUE KEY uk_llm_user_provider (user_id, provider)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户LLM配置表';
```

> 注意：表中不存明文 key。`_enc` 后缀列存储 AES-256-GCM 加密后的 Base64 密文，每个密文前 12 字节为随机 IV。服务启动时如果 `aes-key` 为空则记录 warn 日志、加密/解密操作抛出明确异常。

### Controller / Service / Mapper

```java
// UserLlmConfigController — base path: /api/settings/llm-config
// GET    /                     → 列出当前用户所有配置（key 脱敏为 sk-****{后4位}，Base URL 明文返回）
// POST   /                     → 创建/更新配置（upsert by user_id+provider，body 中 key 为明文，服务端加密后存 enc 列）
// DELETE /{configId}           → 软删除配置
// POST   /{configId}/test      → 用此配置发起一次简单 LLM 调用（"回复 OK"），返回 { success, elapsedMs, error? }
```

```java
// UserLlmConfigService
// - listConfigs(userId) → 读取所有配置，解密后脱敏返回
// - saveConfig(userId, request) → 加密 key 字段后 upsert
// - deleteConfig(userId, configId) → 软删除（校验归属）
// - testConnectivity(userId, configId) → 用该配置创建临时 ChatClient 发一次调用
//   注意：测试连接时解密真实的 API Key，调用完成后立即丢弃，不缓存明文
```

**交互细节**：
- API Key 字段默认 `type="password"`，点击眼睛图标切换明文/密文
- 测试连接：调 `POST /{configId}/test`，显示绿色 "✓ 连接成功 (230ms)" 或红色 "✗ 连接失败: ..."
- 删除配置：弹出确认对话框
- 不强制要求同时配置 LLM 和 Embedding——可以只配 LLM 留空 Embedding（使用系统默认），反之亦然
