## 1. 需求分析

- **目标用户 / 场景**：B 站中小 UP 主。同一套跨分区案例库，被未来 Agent（5.3）在「发布前优化 / 竞品分析」时检索，给建议注入“同赛道里被验证过的成功视频”作证据。5.2 本身先把**检索能力**做出来并可独立自测。
- **要解决的痛点**：5.1 只把案例**存进去、向量化**了，但还**没有“查”的能力**。`index/status` 里的 `retrievalMode` 目前只是“预测值”，没有真正的检索本体。
- **输入**：一段自然语言查询 `query`（如“知识区高完播的开场怎么做”）+ 可选过滤 `category` / `tier` / `topK`。
- **输出**：按相关性排序的案例候选列表（父表案例卡片 + 命中的子条目证据）+ **本次实际走了哪种检索模式**（VECTOR / SQL / 混合 / 降级）。
- **本阶段做**：把 5.1 的存储底座变成**可检索链路**，并暴露 `/search` 接口与前端检索面板。完整链路 = 查询改写/多查询/HyDE → 原生混合(BM25)+RRF → Rerank → 父子召回 → SQL 兜底，**按 5.2a–e 逐刀落地**。
- **本阶段不做**：Agent 工具化与接入发布前优化/竞品（5.3）、知识库完整管理后台（5.4）、跨创作者权限隔离、看视频内容评质量的多模态。
- **降级红线（继承 5.1）**：`knowledge.rag.enabled=false` 或向量库未就绪时，检索**走 SQL 兜底且不报错**，沿用反馈侧 `CreatorFeedbackEvidenceRetrievalService` 的成熟范式。

## 4. 5.2a 详细设计（第一刀，本次编码目标）

### 4.1 范围界定（只做这些）

### 4.3 检索编排流程（照搬反馈侧三段式）

```
search(query, category, tier, topK):
  ragEnabled = knowledge.rag.enabled
  vectorStore = ragEnabled && KnowledgeVectorStore.isReady() ? getVectorStore() : null
  if vectorStore == null:
      return { mode: SQL, items: sqlKeywordFallback(query, category, tier, topK) }   // 优雅降级，不报错

  try:
      orderedVideoIds = denseSearch(query, category, tier, topK)   // similaritySearch + 元数据过滤
  catch 运行期异常(连接/维度/超时):
      log.warn; return { mode: SQL, items: sqlKeywordFallback(...) }   // 不中断，降级

  records = mapper.listByVideoIds(orderedVideoIds)   // 回查父表 is_deleted=0，向量库脏数据被过滤
  records = 按 orderedVideoIds 顺序重排(records)      // MySQL IN 不保证顺序

  if records.size() >= minVectorHitCount:
      return { mode: VECTOR, items: top(records, topK) }
  else:
      merged = 向量结果在前 + SQL 兜底补后，按 videoId 去重
      return { mode: VECTOR_WITH_SQL_FALLBACK, items: top(merged, topK) }
```

- `denseSearch`：`SearchRequest.builder().query(query).topK(topK).filterExpression(filter).build()` → `vectorStore.similaritySearch(...)`，从 `Document.metadata.videoId`（回退 `Document.id`）取 `videoId`。`filter` 用 `FilterExpressionBuilder` 按 `category`/`tier` 组合（与反馈侧按 `taskId` 过滤同款，**不手工拼字符串**）。
- **回查事实源**：向量库只给 `videoId`，父表才是真身；`is_deleted=0` 过滤掉旧批次/已删案例。
- **模式回显**：`VECTOR` / `SQL` / `VECTOR_WITH_SQL_FALLBACK` 三态，复用反馈侧字面量；给前端展示“本次走了哪条路”。

### 4.4 SQL 关键词兜底（父表，新增 mapper 查询）

5.1 的 `listReferenceVideos` 只按 `category/tier` 过滤、按 `id` 倒序，**没有关键词检索**。5.2a 新增：

```sql
SELECT <父表展示列>
FROM creator_reference_video
WHERE is_deleted = 0
  AND (#{category} IS NULL OR category = #{category})
  AND (#{tier}     IS NULL OR tier = #{tier})
  AND ( #{kw} IS NULL
        OR title LIKE CONCAT('%', #{kw}, '%')
        OR description LIKE CONCAT('%', #{kw}, '%')
        OR highlight_summary LIKE CONCAT('%', #{kw}, '%') )
ORDER BY quality_score DESC, raw_quality_score DESC, id DESC      -- 可靠相对分优先，低样本用原始分兜底
LIMIT #{limit}
```

- `kw` 由 `query` 取**主关键词**（先用最简单策略：去标点后整串 LIKE；分词/多词打分留给 5.2b 查询理解，不在 5.2a 过度设计）。
- `query` 为空或无命中 → 回退“最新若干条高质量案例”，让调用方判断“证据不足”而非空手。
- 排序用 `quality_score DESC, raw_quality_score DESC`：可靠相对分优先；低样本分区没有相对分时，用单视频原始分保留基础排序能力。

> 简单优先：5.2a 的 SQL 兜底刻意**不做**中文 2/3-gram 打分（反馈侧那套）。父表是“案例卡片”粒度、量级小，整串 LIKE + 质量信号排序已够用；要更细的关键词召回，等 5.2d 原生 BM25 一步到位，避免在兜底里堆砌注定被替换的临时分词逻辑。

### 4.5 对外接口

```text
POST /api/knowledge/reference-videos/search        # 案例库检索（5.2a 新增）
```

**请求体 `ReferenceVideoSearchRequest`（Jakarta Validation）**

| 字段 | 类型 | 校验 | 说明 |
|---|---|---|---|
| query | String | `@NotBlank` `@Size(max=500)` | 自然语言查询 |
| category | String? | `@Size(max=64)` | 可选分区过滤 |
| tier | String? | `@Size(max=16)` | 可选层级过滤（大写归一 + 白名单，非法 → 400） |
| topK | Integer? | `@Min(1)` `@Max(50)` | 返回上限，空时用 `knowledge.rag.topK`(默认 8) |

**响应体 `ReferenceVideoSearchResponse`**：`{ mode, items: ReferenceVideoSearchItem[] }`
`ReferenceVideoSearchItem`：`videoId / bvId / tier / category / title / rawQualityScore / qualityScore / qualitySampleCount / qualityScoreReliable / highlightSummary / embeddingStatus`（父表展示字段子集；相似度分数 5.2a 先不强求，Spring AI `similaritySearch` 默认按相似度倒序返回，顺序即相关性）。

**错误约定**：`query` 空/超长、`tier` 非法 → 400（`ResponseStatusException`，沿用现有风格）。RAG 关 / 向量库未就绪**不报错**，正常返回 `mode=SQL`（这是降级、不是错误）。

## 5. 后续切片技术预研（已联网核实，落地各刀时再详设）

### 5.2b 查询改写 / 多查询 / HyDE
- 纯加在检索前：用现有 LLM（Qwen/DeepSeek）把 `query` → ①改写规范化、②生成 N 条多查询、③HyDE 生成“假设答案文档”再嵌入检索。多路召回结果 Java 层去重合并。
- 不动存储；受 LLM_GUARD 输入上限保护。可配开关，关掉退回 5.2a 单查询。

### 5.2c 子表向量化 + 父子召回（small-to-big）
- 子表新增向量化：把 `creator_reference_video_item` 的优质短文本嵌入（child = small，精确召回），`embedding_*` 字段 5.1 已预留。
- 召回链：先 child 语义召回命中的子条目 → 按 `video_id` 扩展回父表案例卡片（big，富上下文）→ 父级去重。
- 子表向量入哪个集合：与父表分集合 or 同集合带 `docType` 字段——落地时定（倾向独立 child 集合，隔离清晰）。

### 5.2d 原生混合检索（dense + sparse BM25）—— 最重的一刀
**已核实（milvus-sdk-java 2.5.8 + Milvus 2.5 文档）**：
- BM25 全文检索是 **Milvus 2.5+ 服务端能力**（Standalone 支持；Milvus Lite 不支持）。
- Schema 需：`VarChar(enableAnalyzer=true)` 原文字段 + `SparseFloatVector` 字段 + `Function(FunctionType.BM25, text→sparse)` + dense `FloatVector` 字段。
- 检索：每字段一个 `AnnSearchReq`（dense 用 `FloatVec`，sparse 用原文 `EmbeddedText` 交服务端转 BM25 稀疏向量），`HybridSearchReq` + `RRFRanker`/`WeightedRanker`，`client.hybridSearch(...)`。
- **关键代价（必须让作者知情）**：Spring AI 的 `MilvusVectorStore` 按它**固定 schema** 建集合，**没有** sparse 字段与 BM25 Function。上原生 hybrid 必须把知识库集合**改成自建 schema**，并用 `KnowledgeVectorStore` 内部已持有的 raw `MilvusServiceClient`（或引入 `MilvusClientV2`）建集合 + 写入 + `hybridSearch`，即**替换 5.1c 的索引写法**。集合需重建并重灌——MySQL 是事实源，重灌无数据损失（`index/rebuild` 链路已具备）。

### 5.2e Rerank（重排序）
- 用重排模型对“混合 + 父子”后的候选精排。候选模型：DashScope `gte-rerank`（与现有 Qwen 同生态、同 Key）——**落地前需联网核实**模型名、OpenAI 兼容/DashScope 原生调用方式与限额。
- Spring AI 1.1.4 是否有一等 reranker 抽象待核实；大概率直接 HTTP 调 DashScope rerank。可配开关，关掉退回 RRF/质量信号排序。

## 8. 测试验证点（编译 / 运行由作者执行）

- **降级（RAG 关，默认）**：`POST /search {"query":"开场怎么做"}` → `mode=SQL`，返回关键词命中或最新高质量案例；向量库不连、不调 Embedding、不报错。

## 11. 5.2b 详细设计（查询理解 · 三策略可切换，待作者自检）

> 作者拍板（2026-06-07）：**rewrite / HyDE / multi-query 三种都做、可切换**。本节按此设计，但坚持「统一抽象 + 朴素合并」避免过度设计：三策略统一收敛为「把原始 query 变成 1~N 条检索文本」，正式 RRF 融合仍留 5.2d。

### 11.1 共性约束（三策略通用，先立规矩）

1. **只增强向量路径**：扩展产出的文本仅用于 dense 检索；**SQL 兜底始终用原始 query**（扩展串会让字面 LIKE 更难命中）。
2. **默认开启增强**：配置 `strategy` 默认 **`REWRITE`**（单路、最稳的增强）；`NONE` 仅作显式关闭 / 对照保留。RAG 关时向量路径不走，增强自然不触发。
3. **失败必降级**：扩展异常/超时/空结果 → 退回 `[原始 query]` 单路检索，**绝不让扩展失败中断检索**（照搬 5.2a「向量失败退 SQL」的容错哲学）。
4. **成本与护栏**：查询变换由 Spring AI 组件经 `ChatClient` 调 LLM（**绕过 `LLMService.validatePromptLength`**），但 query 受入参 `@Size(500)` 约束、远低于 30000 字符护栏，无实际影响；`MultiQueryExpander.numberOfQueries` 另设硬上限防检索次数放大。

### 11.2 统一抽象（关键设计：三策略 → 同一形状）

三种手段本质都是「原始 query → 1~N 条用于 dense 检索的文本」：

| 策略 | LLM 产出 | 返回检索文本数 |
|---|---|---|
| `NONE` | 不调 LLM | 1（原始 query，等于 5.2a） |
| `REWRITE` | 规范化/补词后的查询 | 1 |
| `HYDE` | 一段假设的优质视频案例描述 | 1 |
| `MULTI_QUERY` | N 条不同角度查询（`MultiQueryExpander` 产出）+ 并入原 query | ≤ `multi-query-count`（默认 3）+1 |

→ 统一接口 **`List<String> enhance(String query, QueryEnhanceStrategy strategy)`**；检索层只管「拿到 1~N 条文本、逐条检索、合并去重」，不关心策略。新增策略只加一个 `case`，不碰检索层。

### 11.3 包与类（基于 Spring AI 原生 Modular RAG 查询组件）

> 作者拍板用框架原生组件（非手写 prompt）。需新增依赖 `org.springframework.ai:spring-ai-rag`（版本由项目已引入的 spring-ai-bom 统一管理，1.1.x 含本组件；该 RAG 模块属实验性、API 可能随版本变——已知情接受）。

| 新增/改动 | 类型 | 职责 |
|---|---|---|
| `knowledge.model.QueryEnhanceStrategy` | 新增 enum | `NONE / REWRITE / HYDE / MULTI_QUERY` |
| `knowledge.rag.HydeQueryTransformer` | 新增 | 自定义实现 `QueryTransformer`（框架无内置 HyDE）：`transform(Query)` 内用 `ChatClient` 按中文 prompt 生成假设案例描述，返回 `new Query(假设文档)` |
| `knowledge.service.KnowledgeQueryEnhancer` | 新增 Service | 构造注入 `ChatClient.Builder`，持有 `RewriteQueryTransformer` / `MultiQueryExpander` / `HydeQueryTransformer`；`enhance(query, strategy)` 按策略调对应组件、统一产出 `List<String>`；含失败降级 |
| `knowledge.service.KnowledgeReferenceRetrievalService` | 改动 | `search()` 内：先 `enhance` 得多条文本 → 逐条 `denseSearch` → 按 videoId 合并去重 → 回查/兜底/模式回显**全不变** |
| `knowledge.model.ReferenceVideoSearchRequest` | 改动 | 加可选 `strategy`（覆盖配置默认，便于逐次切换不同策略对比检索效果） |
| `knowledge.model.ReferenceVideoSearchResponse` | 改动 | 加回显 `strategy` + 可选 `enhancedQueries`（回显扩展出的查询，便于核对增强是否合理、定位召回问题） |
| `knowledge.config.KnowledgeRagProperties` | 改动 | 加 `queryEnhancement.strategy`(默认 `REWRITE`) + `multiQueryCount`(默认 3) |

> 仍放 `knowledge` 模块（跟 5.2a 一起），**不**进 `creator/search`。`KnowledgeQueryEnhancer` 把三个框架组件包成统一 `enhance(query, strategy) → List<String>`，检索层不感知框架细节；不建通用策略框架（无第二消费方），策略分发就是一个 switch。

### 11.4 三策略落地（框架组件 + 中文 prompt）

`enhance(query, strategy)` 内按策略映射到框架组件，统一取出文本：

- **REWRITE** → `RewriteQueryTransformer.builder().chatClientBuilder(cb).promptTemplate(中文模板).build().transform(new Query(q)).text()`，得 1 条。
- **MULTI_QUERY** → `MultiQueryExpander.builder().chatClientBuilder(cb).numberOfQueries(n).includeOriginal(true).promptTemplate(中文模板).build().expand(new Query(q))` → `List<Query>` 逐个取 `.text()`（`includeOriginal(true)` 由框架并入原 query，无需自己拼）。
- **HYDE** → 自定义 `HydeQueryTransformer.transform(new Query(q)).text()`：内部用 `ChatClient` 按中文 prompt 生成一段假设的优质视频「亮点摘要」（标题感 + 要点；**只描述方法/共性，禁编造具体 UP 主、播放量、BV 号**防幻觉），返回 `new Query(假设文档)`。
- 任一策略异常/空 → 在 `KnowledgeQueryEnhancer` 内 try/catch 降级返回 `[原始 query]`。

> ⚠️ **必须传中文 `promptTemplate`**：`RewriteQueryTransformer` / `MultiQueryExpander` 内置默认 prompt 是**英文**，对中文 query / 案例库会劣化甚至输出英文。故二者都显式注入中文模板；HyDE 是自定义、本就中文。

### 11.4b 编码前必须核实的 API 点（不凭记忆，对照官方）

1. `spring-ai-rag` 在项目现用 spring-ai-bom 版本里、能否仅靠 BOM 不写死版本号。
2. `Query.text()` 取值访问器名、`new Query(String)` 构造可用。
3. `RewriteQueryTransformer` / `MultiQueryExpander` 的 `promptTemplate(..)` 参数类型与**模板占位符变量名**（中文模板要用对变量名，否则注入失败）。
4. `MultiQueryExpander` 的 `includeOriginal(..)` / `numberOfQueries(..)` 确实存在。
5. 这些组件入参是 `ChatClient.Builder`——确认可直接注入（项目 `LLMService` 已用 `ChatClient.Builder` 构造，bean 存在）。

### 11.5 检索编排改造（5.2a `search()` 的最小侵入）

```
search(request):
  query = 原始 query；strategy = request.strategy ?? 配置默认
  ...（RAG 关 / 向量库不可用 → SQL 兜底，用原始 query，不变）

  // 唯一新增：单 query → 多 query
  List<String> searchTexts = (strategy == NONE) ? [query]
                             : queryEnhancer.enhance(query, strategy)   // 内部失败已退回 [query]

  // 逐条 denseSearch，按 videoId 合并去重（保留首次出现 / 最高名次），取前 topK
  orderedVideoIds = mergeDistinct( searchTexts.map(t -> denseSearch(t, category, tier, topK)) )

  ...（回查父表 is_deleted=0、命中不足合并 SQL 兜底、mode 回显 —— 全部复用 5.2a，零改动）
```

- **合并去重**：朴素策略——按 `searchTexts` 顺序拼接各自 videoId 列表，`LinkedHashSet` 去重，取前 topK。**不做 RRF 加权**（正式 RRF 留 5.2d）。
- **mode 不变**：仍 VECTOR / SQL / VECTOR_WITH_SQL_FALLBACK；`strategy` 单独回显。
- **成本**：multi 会发 N+1 次 dense 检索（每条 query 各 1 次 embed + 1 次向量库往返），故 `multiQueryCount` 设硬上限；rewrite/HyDE 仍是单路（多 1 次 LLM 而已）。

## 13. 5.2c 详细设计（父子召回 · small-to-big，待作者自检）

> 作者拍板（2026-06-08）下一刀做 **5.2c**。本节按「子表向量化 + small-to-big 召回」设计。
> **两条贯穿全程的硬约束**：① 父集合（5.1c 已建、5.2a/b 在用）**零改动、零回归**；② 子召回是**附加召回源**，子集合建库失败要能**独立降级**、不拖垮父检索。
> **重要澄清**：5.2c **不依赖 Milvus ≥2.5**——那是 5.2d 服务端 BM25 的前置；子表向量化用的还是 5.1c 同款 dense（`similaritySearch`）能力，已验证可用。故本刀**不被 §6.1 的 Milvus 版本问题阻塞**。

### 13.1 需求回顾与边界

- **痛点**：父表案例卡片是「粗粒度大文档」（标题/简介/亮点摘要/热度拼成一段）。一条具体高赞评论/弹幕里的精确信号（如「这个开场三秒就把我留住了」）会被整张卡片稀释，dense 检索难精确命中。**small-to-big**：用**小而精的子条目**当召回单元（child=small，命中更准），命中后**扩展回父表富上下文卡片**（big，给 Agent 富证据）。
- **输入**：同 5.2a/b——`query` / `category?` / `tier?` / `topK?` / `strategy?`，接口不变。
- **输出**：父表案例卡片（不变）+（5.2c-2）**命中的子条目证据**（这条卡片是被哪几条评论/弹幕召回的）。
- **本刀做**：子表 `content` 向量化进**独立 child 集合**；检索时把子召回并入父召回。
- **本刀不做**：RRF 加权融合（留 5.2d）、Rerank（5.2e）、子条目独立检索接口（子召回只服务于父卡片召回，不单独对外）。

### 13.2 关键设计决策（D1–D6）

| # | 决策点 | 选择 | 为什么（工程理由） |
|---|---|---|---|
| **D1** | 子向量入**独立集合**还是**父集合带 docType** | **独立 child 集合** `creator_reference_video_item` | 父集合零改动 → 5.2a/b 零回归；两种粒度（卡片 ~4000 字 vs 评论短文）物理隔离、互不污染；同集合方案要给父文档全加 docType、父检索处处加 `docType=parent` 过滤、且要**重灌父集合**，代价大且有回归风险。延续 `KnowledgeVectorStore` 既有隔离哲学。 |
| **D2** | 父 / 子向量库就绪是否**独立** | **独立**：`isReady()`（父，语义不变）+ 新增 `isChildReady()`（子） | 子集合建库失败（维度冲突、集合损坏等）只 `warn`、不该让 5.2a/b 父检索跟着挂。检索仅在 `isChildReady()` 时叠加子召回，天然可降级。 |
| **D3** | 子表索引：**新 Service** 还是扩现有 | **新 `KnowledgeReferenceItemIndexService`** | 父索引服务 `toDocument/buildDocumentText` 是「父卡片」专用；子条目文本构造/批次/状态自成一体。新服务保持单一职责、父服务零改动。仅两个消费方且差异在表/集合/文本，**不提前抽公共索引器**（符合「不提前建空抽象」）；真出现第三个索引器再上提共性。 |
| **D4** | 子表索引 mapper：加现有还是新建 | **加到现有 `KnowledgeReferenceVideoMapper`** | 该 mapper 已含 `insertReferenceVideoItem`（父子混用先例）；子索引查询加在一起，域内聚合、简单优先。 |
| **D5** | small-to-big 召回如何并入检索 | 父-dense ∪ 子-small-to-big，**按 videoId 朴素去重**（`LinkedHashSet`，父在前、子派生在后），取前 topK；**无 RRF** | 与 5.2b 多查询合并复用同一原语；正式融合留 5.2d。子召回是**附加**：父卡片能直接命中的不丢（无回归），只有「卡片整体不匹配、但内部某条评论精确匹配」的案例被**新增**召回。 |
| **D6** | 子条目证据是否随响应回显（§1 要求） | **是，但放 5.2c-2**；本轮 5.2c-1 先只做索引侧 | 证据是 small-to-big 的价值落点（也是 5.3 Agent 要引用的「观众原话证据」）。但它要改响应结构（每张父卡片挂 matched 子条目），与索引侧正交。按项目切片法**先索引、后检索**，降低对 working search 路径的回归面。 |

### 13.4 子集合与就绪（`KnowledgeVectorStore` 改动 · 5.2c-1）

在隔离 Bean 内部**再持一个**指向子集合的 `MilvusVectorStore`，与父集合**共用同一个** `MilvusServiceClient`、同 `EmbeddingModel`、同维度（1024）、同 `IVF_FLAT`/`COSINE`，仅集合名不同。

| 改动 | 内容 |
|---|---|
| 字段 | 新增 `private MilvusVectorStore childVectorStore;`、`private volatile boolean childReady = false;` |
| `init()` | 在现有父集合 `try/catch` **之后**追加一段：`if (milvusClient != null) { try { 建子 store + afterPropertiesSet(); childReady=true } catch { childReady=false; log.warn } }`。父建库失败时 `milvusClient` 为 null 自然跳过；子建库失败只 warn，父 `ready` 不受影响。 |
| 访问器 | 新增 `boolean isChildReady()`、`Optional<VectorStore> getChildVectorStore()`（语义同父侧 `getVectorStore()`）。 |

> **必须自测确认的唯一集成点**：同一个 `MilvusServiceClient` 上构建**两个不同集合**的 `MilvusVectorStore` 并各自 `afterPropertiesSet()` 建集合（这是本刀唯一未在现有代码出现过的用法；`MilvusVectorStore` 的 builder API 本身已被 5.1c 父集合验证过）。Milvus 标准用法，预期可用；以作者启用 RAG+Milvus 后实跑为准。

#### 13.5.2 子文档组装（child = small）

- **doc id** = `item_id`（子表唯一，schema 注释「embedding_id 默认复用 item_id」）。
- **doc text** = 子条目 `content` 本身（评论/弹幕原文，已是短文本；保留原文是 small 精确召回的关键，仅设一个小上限如 1000 字防极端长评论）。
- **metadata**：`videoId`（**small-to-big 扩展回父表的关键**）、`itemId`、`sentiment`、`sourceType`，外加 **`category`/`tier`（从父表反范式带入）**。
  - *为什么子文档要带 category/tier*：5.2c-2 子召回要支持与父召回**同款** `category`/`tier` 过滤（复用 `buildFilter`）。子表本身没有这两列，故索引时 JOIN 父表带入。父表 category/tier 极少在导入后变更，偶有变更下轮重建即修正，可接受。

#### 13.5.3 mapper 新增查询（注解式，与现有风格一致）

| 方法 | 作用 | 关键点 |
|---|---|---|
| `listIndexableItems(limit)` | 扫待索引子条目 | `i.is_deleted=0 AND i.embedding_status IN ('PENDING','FAILED')`，**JOIN 父表** `creator_reference_video v ON v.video_id=i.video_id AND v.is_deleted=0`（不索引孤儿/已删父的子条目），SELECT 带 `v.category/v.tier`；`ORDER BY i.id`，`LIMIT`。命中 `idx_video_embedding_status` 仍有效。 |
| `updateItemEmbeddingIndexed(itemId, embeddingId)` | 标记成功 | `SET embedding_id, embedding_status='INDEXED', embedding_error=NULL, embedding_update_time=CURRENT_TIMESTAMP WHERE item_id=? AND is_deleted=0` |
| `updateItemEmbeddingFailed(itemId, errorMessage)` | 标记失败 | 同父侧范式，按 `item_id` |
| `countItemEmbeddingStatus()` | 子状态分组计数 | `GROUP BY embedding_status WHERE is_deleted=0` |
| `findLastItemEmbeddingUpdateTime()` | 子最近成功索引时间 | `MAX(embedding_update_time) WHERE embedding_status='INDEXED' AND is_deleted=0` |

#### 13.5.4 索引编排（照搬 5.1c 父索引成熟范式）

```
rebuildItems(request):
  if !rag.enabled            -> 400
  if !knowledgeVectorStore.isChildReady() -> 400  // 子集合未就绪
  childStore = getChildVectorStore().orElseThrow()
  maxItems = resolve(request)            // 复用 maxIndexItems / [1,1000] 硬上限
  batchSize = max(1, indexBatchSize)     // 10，Qwen 兼容单批上限
  rows = listIndexableItems(maxItems)
  if rows.isEmpty()          -> 400 「没有待索引的子条目」
  分批：childStore.add(docs)  成功→ updateItemEmbeddingIndexed 逐条；失败→ updateItemEmbeddingFailed 逐条 + warnings
  return ReferenceVideoIndexResponse(...)   // 不加 @Transactional，与父侧同因（Milvus 不归 DB 事务）
```

> 与父索引的**有意差异**：候选量级更大（一个视频多条评论弹幕）。本刀先复用同一套 `maxIndexItems`(默认 200)/硬上限 1000 的成本护栏；若实测子条目量级需要独立调参，再加 `maxIndexItemsChild`（简单优先，不提前加）。

### 13.6 small-to-big 检索（5.2c-2 · 本节为路线，落地时再详设细节）

`KnowledgeReferenceRetrievalService.search()` 最小侵入改造：

```
search(request):
  ...（RAG 关 / 父向量库不可用 → SQL 兜底，完全不变）
  parentVideoIds = denseSearchMulti(parentStore, searchTexts, cat, tier, topK)        // 5.2a/b 原样
  childHits      = isChildReady() ? childSearchMulti(childStore, searchTexts, cat, tier, topK) : []
  // 合并：父在前、子派生在后，LinkedHashSet 按 videoId 去重，取前 topK（复用 5.2b 同款原语，无 RRF）
  orderedVideoIds = mergeDistinct(parentVideoIds, childHits.videoIds, topK)
  ...（listByVideoIds 回查 is_deleted=0 + reorder + minHit + SQL 兜底 + mode 回显，全部复用 5.2a，零改动）
```

- `childSearchMulti`：镜像 `denseSearchMulti`，但查子集合、从子文档 metadata 取 `videoId`；复用 `buildFilter`（子文档已带 category/tier）。
- **证据回显**（§D6）：`childSearchMulti` 额外按 `videoId` 收集命中的 `itemId`（每卡片限 2~3 条），再 `listItemsByItemIds`（is_deleted=0，事实源回查）取回 `content/sentiment/sourceType` 挂到对应父卡片。**响应结构方案两选一，5.2c-2 落地时定**：
  - (a) 顶层加 `evidence`（按 videoId 关联的子条目列表），`items` 仍是 `ReferenceVideoResponse[]`、前端按 videoId join——对现有 `items` 复用零破坏；
  - (b) `items` 升级为 `{ card, evidence[] }` 包装——更直观但破坏 5.2a 的卡片复用。
- **mode**：仍 VECTOR / SQL / VECTOR_WITH_SQL_FALLBACK；另考虑加一个布尔/计数回显「本次子召回是否贡献、贡献几条」，便于核对 small-to-big 是否生效（沿用「回显实际生效」的排查友好原则）。

### 14.2 与 §13 设计的偏差（均为收敛细化，非功能变更）

1. **子文档 metadata 反范式带 `category/tier`**：子表无这两列，由 `listIndexableItems` JOIN 父表带出写进子向量文档，目的是让 5.2c-2 子召回能复用父检索**同一个** `buildFilter` 做 category/tier 过滤。父表这两列导入后极少变更，偶变下轮重建即修正。
2. **子集合建库放在父集合 `try/catch` 之后、独立 `try` + 独立 `childReady`**：`init()` 中父集合任一失败不连累子（反之亦然）；父集合连 `MilvusServiceClient` 都没建出来（`milvusClient==null`）时跳过子集合。这是「5.2c 对 5.2a/b 零回归」的代码落点。
3. **索引/状态响应复用父模型**：子 rebuild 复用 `ReferenceVideoIndexResponse`、子 status 复用 `ReferenceVideoIndexStatusResponse`（`vectorStoreReady` 映射 `isChildReady()`、`retrievalMode` 按子就绪+已索引预测）——同形不另造（延续 5.2a 复用 `ReferenceVideoResponse` 的收敛思路）。
4. **`max-index-items` 父子共享**：子条目量级更大，但本刀先共用同一成本护栏（默认 200 / 硬上限 1000）；实测需要再加 `maxIndexItemsChild`（简单优先，不提前加）。

## 15. 5.2c-2 详细设计（small-to-big 检索 · 证据回显，待作者自检）

> 承接 5.2c-1（子集合已可索引）。作者拍板（2026-06-08）证据响应走 **方案 (a)：顶层 `evidence`，`items` 复用 `ReferenceVideoResponse[]` 不变**。
> **编码前置**：5.2c-1 编译 + 自测通过（子集合可建、可索引）。本节为检索侧完整详设，待作者自检后编码。

### 15.1 范围

- **做**：`KnowledgeReferenceRetrievalService.search()` 在父-dense 之外并入**子-small-to-big** 召回；命中的子条目按 (a) 方案随响应顶层 `evidence` 回显；前端在结果卡片下展示「召回证据：观众原话」。
- **不做**：RRF/加权融合（→5.2d）、Rerank（→5.2e）、子召回的请求级开关（默认 `isChildReady()` 即开，需 A/B 对照再加）、证据缓存/分页。

### 15.2 关键决策（含 (a) 落定）

| 点 | 决策 | 理由 |
|---|---|---|
| 证据响应结构 | **(a)** 顶层 `evidence:[{videoId, items:[{itemId,content,sentiment,sourceType}]}]`；`items` 不变 | 5.2a/b 卡片渲染零破坏、无证据时前端零改动；5.3 Agent 也可按 videoId 取证据 |
| 子召回开关 | `isChildReady()` 即开，无新配置 | 简单优先；证据有无即反映子召回是否贡献（排查友好），无需额外回显字段 |
| 合并 | 父在前、子 `keySet` 在后，`LinkedHashSet` 去重取 topK，**无 RRF** | 复用 5.2b 多查询同款原语；正式融合留 5.2d |
| 证据来源 | **回查 MySQL**（`listItemsByItemIds`，is_deleted=0），不读子向量文档 | 延续「向量库只给 id、父表/子表才是真身」铁律；子文档 text 截断且绕过软删 |
| 子检索失败 | 独立 try，异常 → 退父-only、不报错 | small-to-big 是锦上添花，绝不拖挂已能用的父检索 |
| 每卡证据上限 | 常量 `MAX_EVIDENCE_PER_VIDEO=3`（Java 默认不入 yml） | 与 5.2a/b「默认值不入 yml」一致；防单卡证据刷屏 |

### 15.3 `search()` 改造（最小侵入，父链路尾段全复用）

```
search(request):
  ...（入参归一、RAG 关/父向量库不可用 → SQL 兜底，完全不变）...
  parentVideoIds = denseSearchMulti(parentStore, searchTexts, cat, tier, topK)        // 5.2a/b 原样
  childMap = {}                                                                       // LinkedHashMap<videoId, List<itemId>>
  if isChildReady():
      try: childMap = childSearchMulti(childStore, searchTexts, cat, tier, topK)
      catch: log.warn; childMap = {}                                                  // 子失败退父-only

  orderedVideoIds = mergeDistinct(parentVideoIds, childMap.keySet(), topK)            // 父在前、LinkedHashSet 去重
  records = reorderByVideoIds(listByVideoIds(orderedVideoIds), orderedVideoIds)        // 回查父表 is_deleted=0（不变）

  // minHit / SQL 兜底 / mode 回显：完全复用 5.2a（VECTOR / VECTOR_WITH_SQL_FALLBACK）
  finalRecords = ...（同 5.2a）
  evidence = buildEvidence(finalRecords, childMap)                                     // 仅对最终卡片中"有子命中"者回查挂证据
  return ReferenceVideoSearchResponse(mode, strategy, enhancedQueries, toResponses(finalRecords), evidence)
```

- **整条父尾段零改动**：`listByVideoIds`/`reorderByVideoIds`/`minHit`/`mergeDistinctByVideoId`(SQL 兜底)/`mode` 全部复用。唯一新增是 `childMap` 的产生与 `evidence` 的组装。
- **SQL/降级路径**：不走向量分支，`evidence` 回空列表（与 mode=SQL 一致）。

### 15.4 `childSearchMulti` + 证据回查

- `childSearchMulti(childStore, searchTexts, cat, tier, topK)` → `LinkedHashMap<String, List<String>>`（videoId → 命中的 itemId 有序列表）：
  - 逐条 `searchText` 对子集合 `similaritySearch`（复用 `buildFilter`——子文档 5.2c-1 已带 category/tier）；
  - 从子文档 metadata 取 `videoId` + `itemId`；按出现顺序累积进 map，每个 videoId 的 itemId 列表去重并截到 `MAX_EVIDENCE_PER_VIDEO`；
  - map 的 `keySet()` 即子召回的 videoId 顺序（喂合并），values 即证据候选 itemId（喂回查）。
- `buildEvidence(finalRecords, childMap)`：取 `finalRecords` 中存在于 `childMap` 的 videoId，汇总其 itemId → 一次 `listItemsByItemIds`（is_deleted=0 回查）→ 按 videoId 分组、按 finalRecords 顺序组装 `List<ReferenceVideoEvidence>`；回查后为空的组跳过（子条目可能已软删）。

### 15.5 响应模型（方案 a）

| 新增/改动 | 类型 | 内容 |
|---|---|---|
| `ReferenceVideoEvidenceItem` | 新增 record | `itemId / content / sentiment / sourceType`（单条证据） |
| `ReferenceVideoEvidence` | 新增 record | `videoId / List<ReferenceVideoEvidenceItem> items`（按 videoId 分组） |
| `ReferenceVideoSearchResponse` | 改动 | 末尾加 `List<ReferenceVideoEvidence> evidence`（5 字段：mode/strategy/enhancedQueries/items/evidence） |

> `items` 仍是 `ReferenceVideoResponse[]`——(a) 的核心收益：5.2a/b 的卡片渲染与列表复用完全不动。

### 15.6 mapper 新增查询

| 方法 | 作用 | 关键点 |
|---|---|---|
| `listItemsByItemIds(List<String> itemIds)` | 按 itemId 批量回查子条目证据 | `WHERE is_deleted=0 AND item_id IN (...)`，SELECT `item_id/content/sentiment/source_type/video_id`；`<script>`+`<foreach>`（同 `listByVideoIds`）；顺序由调用方按 childMap 重排，不加 ORDER BY；调用方保证非空。 |

### 15.7 前端（最小增量，挂在 5.2a/b 检索结果卡片）

- `api/knowledge.ts`：`searchReferenceVideos` 无需改（响应多一个字段，类型已覆盖）。

### 15.8 配置

### 15.9 测试验证点（编译/运行由作者执行）

### 17.1 联网核实结论（2026-06，关键避坑）

- **`gte-rerank` 已于 2026-05-30 下线**（作者指正属实），替代为 **`qwen3-rerank`**（纯文本）/ `qwen3-vl-rerank`（多模态）。
- **`qwen3-rerank` 走 OpenAI 兼容端点**：`POST https://dashscope.aliyuncs.com/compatible-api/v1/reranks`——注意是 `compatible-api`（rerank 专用），**不是** chat 用的 `compatible-mode`；用错老的 `/api/v1/services/rerank/...` 原生端点会报错。
- 请求 `{model, query, documents:[字符串], top_n?, return_documents?}`；**响应顶层 `results:[{index, relevance_score}]`**（已按相关性降序，非老接口的 `output` 包裹）。

### 17.2 关键决策

| 点 | 决策 | 理由 |
|---|---|---|
| 调用方式 | **RestClient 直连兼容端点** | Spring AI 1.1 无一等 reranker 抽象（只有 `DocumentPostProcessor`，本项目自研检索没走那条 advisor 链）；引 DashScope SDK 为单接口拉重依赖不值。 |
| 默认开关 | `knowledge.rag.rerank.enabled` **默认 false** | rerank 是每次检索额外一次外部调用（成本+延迟），opt-in（与 RAG 总开关默认关同思路）。 |
| 检索范式 | **retrieve-wide → rerank → 截 topK** | 开 rerank 时按 `candidatePoolSize`(默认 20) 召回更宽候选，精排后截 topK；关时候选即 topK。精排只重排不扩召回，候选越宽精排空间越大。 |
| 解析稳健性 | **只依赖 `results[].index` 返回次序**，不读分数字段 | API 已降序；不依赖 `relevance_score` 字段名，响应模型只声明 `index`，其余 Jackson 忽略。 |
| query 用哪条 | **原始 query**（非改写/HyDE 扩展文本） | 精排要贴用户真实意图。 |
| 失败处理 | 关闭/无 Key/候选≤1/异常 → 返回空序、**保持原检索顺序** | 同 5.2a「向量失败退 SQL」、5.2c「子失败退父-only」的容错哲学；rerank 是锦上添花。 |
| Key/端点 | api-key 默认复用 `${LLM_API_KEY}`（同一 DashScope Key）；base-url 独立配（compatible-api） | 不与 chat 的 compatible-mode 混用。 |

### 17.4 实现要点 / 踩坑

1. **RestClient URL 拼接坑（已规避）**：`baseUrl(".../compatible-api/v1")` + `.uri("/reranks")` 按 RFC 3986 前导斜杠会**替换** base 路径段 → `host/reranks`（丢 `/compatible-api/v1`）404。故改为**拼完整绝对 URL** 交给 `uri(...)`、不设 baseUrl。
2. **mode 不受 rerank 影响**：rerank 只重排序，VECTOR / VECTOR_WITH_SQL_FALLBACK / SQL 三态判定不变；`reranked` 单独回显。

4. **响应记录用 private 嵌套 record**：只映射 `index`，靠 Spring Boot 默认「忽略未知字段」吃掉 `relevance_score`/`document`。

- 核实签名（节选）：`MilvusClientV2.{createSchema()→CollectionSchema, createCollection(CreateCollectionReq), createIndex(CreateIndexReq), insert(InsertReq)→InsertResp, hybridSearch(HybridSearchReq)→SearchResp, dropCollection/hasCollection/loadCollection}`；`AddFieldReq.builder().{fieldName,dataType,isPrimaryKey,autoID,maxLength,dimension,enableAnalyzer,analyzerParams(Map)}`；`DataType.{VarChar,SparseFloatVector,FloatVector,Int64}`；`CreateCollectionReq.Function.builder().{name,functionType(FunctionType.BM25),inputFieldNames,outputFieldNames}`；`IndexType.SPARSE_INVERTED_INDEX`+`MetricType.BM25`（稀疏）、dense `AUTOINDEX`+`COSINE`；`InsertReq.data(List<com.google.gson.JsonObject>)`；`AnnSearchReq.builder().{vectorFieldName,vectors(List<BaseVector>),topK,expr}`，dense→`new FloatVec(float[])`、BM25→`new EmbeddedText(String)`；`HybridSearchReq.builder().{collectionName,searchRequests,ranker(BaseRanker),topK,outFields,consistencyLevel}`；`SearchResp.getSearchResults()→List<List<SearchResult>>`，`SearchResult.{getId()→Object 即 PK, getScore()→Float, getEntity()→Map}`；`ConnectConfig.builder().{uri,token,username,password,dbName,connectTimeoutMs}`。

### 18.2 架构与「零回归」策略

- 新增 **`KnowledgeHybridStore`**（隔离组件，内部私有持 `MilvusClientV2` + `ObjectProvider<EmbeddingModel>`）——延续 `KnowledgeVectorStore` 的隔离哲学（不暴露成 Spring Bean）。它负责：自建 schema 建/删集合、**手动 `EmbeddingModel.embed` 算 dense**、raw `insert`、`hybridSearch`。

## 20. 主题优先检索接入 hybrid 补召回（2026-06-19）

`/topic-search` 已在原有“中块主题召回 → 质量信号排序 → 评论弹幕证据 → rerank”的主链路上，接入现有父 / 子 hybrid 集合作为补召回：

1. **不新建中块 hybrid 集合**：当前 `KnowledgeHybridStore` 只有父卡片 hybrid 集合和子评论弹幕 hybrid 集合；中块仍走 Spring AI dense 集合。
2. **候选合并**：中块命中的 videoId、父 hybrid 命中的 videoId、子 hybrid 命中 item 上卷得到的 videoId 合并去重，最多保留 top20。
3. **排序不变**：候选池仍先按 MySQL 质量信号排序（可靠相对分优先，原始分兜底）；rerank 开启时，再结合命中主题和评论弹幕证据做精排。

5. **降级不变**：hybrid 任一路失败只记录 warn，并继续使用中块 dense / 子向量 / SQL 兜底；不会让 `/topic-search` 直接报错。
6. **模式回显**：最终候选确实包含 hybrid 来源时，响应 `mode=TOPIC_HYBRID`；否则仍是 `TOPIC_VECTOR` 或 `SQL`。
