# 视频自动制作 S1a-1：独立版本上传与续传

> 日期：2026-10-19。前置：[S0 基线与自查](视频自动制作-S0基线与S1接入清单.md)。
>
> 本轮交付 S1a 的上传持久化子步骤。源码已修改，验证结果见第 5 节；尚未部署到作者现有业务库或服务，不能把它描述为完整 S1、自动出片或新版前端已经可用。

后续已修复本记录第 4 节所述重新定位的历史保留问题，并补上传创建上下文校验和本地续传恢复修正，见 [S1 重新定位历史隔离修复](视频自动制作-S1重新定位历史隔离修复说明.md)。以下 59 项测试及“未改重新定位”是 S1a-1 当轮的历史边界，最新验证结果以修复记录为准。

## 1. 用户问题和结果

后续用户上传自己制作的修订成片，或自动制作系统输出新版时，需要保留完整旧版及其精确身份。原实现固定使用 V1，完成后拒绝新文件，失败后则会重置原成片记录。上传完成和网络恢复时还会读取“当前成片”，无法保证响应对应请求中的上传会话。

本轮实现新文件独立分配 `versionId` 和任务内序号；未完成的分片会话继续指向原版本。只有上传对象经原有大小/类型核对并登记为 `UPLOADED` 后，才在同一个数据库事务中切换当前版本。取消、上传失败不切换指针；新版本仍需自己的探测、预处理和试映。

## 2. 改动范围

| 位置 | 改动及依据 |
|---|---|
| `backend/src/main/resources/sql/init.sql` | 增量建立 `creator_creation_workspace`，仅增加当前版本、下一序号、乐观锁和通用归属/时间字段；保留成片表已有唯一键，没有改写作者原有 SQL 改动 |
| `creator/creation/model/CreationWorkspaceRecord` | 映射本步实际使用的工作区字段，不提前创建未使用的制作、资产、预算空服务 |
| `MediaUploadMapper.findDraftVideo` | 工作区存在时只读取明确指针；只有没有工作区的旧任务回退原 V1，空指针不会偷偷回退或选择最大版本号 |
| `MediaUploadPersistenceService.saveCreatedUpload` | 在任务行锁内复核幂等、发布事实和活动上传，分配序号并原子插入新版与会话；不再重置原完整成片、替代或删除旧上传对象 |
| `MediaUploadPersistenceService.markUploadCompleted` | 与会话完成、精确成片登记一起更新当前指针；完成旧会话的重放不重复切换指针 |
| `MediaUploadService` | 首次完成、已完成重放和 `VERIFYING` 恢复都按会话 `versionId` 返回。并发幂等请求只清理本请求多创建的 OSS 分片，保留胜出会话和旧成片 |
| `CreatorMediaWorkflowGateService.lockForVideoBinding` | 在 BV 事务内先锁任务；活动上传未结束时拒绝绑定，防止检查旧片后关联新版 |
| `CreatorBilibiliService.bindBvToTask` | 在第一次一致性读取之前取得上述锁，与上传分配/完成共用锁顺序；已确认 BV 仍不覆盖，也不重新执行媒体就绪检查 |
| `DraftVideoProbeService`、成片记录/响应注释 | 更新当前版本语义，现有精确版本探测路径保持可用 |

数据库只维护统一 `init.sql`，未新增迁移框架或依赖。当前工作区表是该方案的增量起点，后续按实际使用添加工程、授权和运行字段。

## 3. 行为与接口

沿用 `POST /api/creator/tasks/{taskId}/draft-video/uploads` 及其查询、分片签名、登记、完成和取消接口，请求/响应字段及 Jakarta Validation 约束不变。

- 同一任务同时最多一条活动上传，不同幂等键竞争时只有一个能写入；同键同文件竞争返回同一会话。
- 同键不同文件仍返回冲突，终止会话不自动复活；新上传使用新幂等键并分配新版本。
- 版本序号在任务锁内递增，事务失败回滚。采纳旧库时，下一序号考虑已有软删除行，避免撞上仍存在的历史唯一键。
- 旧任务只读查询不会创建工作区。显式上传写入时才采纳原 V1；初次上传尚未完成时当前指针为空，活动上传通过既有 `/uploads/current` 恢复。
- 任意现存 BV 关联（包括等待核验）或旧版 `published_flag` 都保护对应任务，要求新建任务上传修订作品。原有纠正 BV、已有成片跳过策划和重新定位接口本轮没有重做。
- 新片上传完成只表示对象已核对，状态仍为 `UPLOADED`；旧片的试映报告不会自动放行新版。

OSS 创建、合并、HEAD 和补偿清理仍在数据库事务外。任务锁只覆盖数据库判断和写入，不把网络调用搬进长事务。事务外预检查会在事务内重新核对，不作为唯一并发保护。

## 4. 自查及本步边界

自查补齐了容易漏掉的两点：完成响应共有三条路径，均已按精确版本处理；除了 BV 绑定，旧库的 `published_flag` 也不能被新上传绕过。

第一轮集成测试通过后，一条原 BV 单元测试因“媒体服务零交互”的旧断言失败。新增的是任务锁调用，已绑定请求仍不覆盖 BV，也不重新执行媒体就绪检查。已将断言收紧为只允许锁调用，禁止额外媒体交互，再执行回归。

本步尚未提供版本列表/选版 API、`published_version_id` 与正式发布快照、按版本保存的方案/蓝图上下文、制作运行/预算预留或前端“上传新版”入口。因此现有前端的完成态限制仍存在；本轮证明的是后端上传和持久化行为。

尤其是原“重新定位制作蓝图”的批量失效逻辑未改；后续 S1a 在允许历史选版前，必须完成精确版本上下文与失效范围，不能直接复用该方法来实现自动修改。本轮普通新文件上传不会调用该重新定位逻辑。
