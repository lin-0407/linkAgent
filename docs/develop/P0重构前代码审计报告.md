### 6.1 当前架构

```
api/
├── agent.ts     (48行) — 3 个接口（sendAgentMessage, loadAgentSessions, loadAgentSessionMessages）
├── creator.ts   (475行) — 30+ 个接口

```

**总计：4 个 API 模块，约 54 个接口函数。**

### 6.2 重复代码

**requestJson / readErrorMessage 被重复实现了 3 次：**

| 文件 | 实现 |
|------|------|
| api/creator.ts (43行) | 私有 requestJson + readErrorMessage |
| api/knowledge.ts (18行) | 私有 requestJson + readErrorMessage |
| api/settings.ts (4行) | 私有 requestJson + readErrorMessage（略有差异，处理了 204） |

**agent.ts 最简陋：** 直接内联 fetch + 错误处理，无 readErrorMessage（只用 HTTP status）。

### 6.3 缺失的能力

| 能力 | 现状 | 影响 |
|------|------|------|
| 统一 base URL | 无，每个 fetch 写完整路径 | 切换环境困难 |
| 请求超时 | 无 | 网络异常时长时间挂起 |
| Token 注入 | 无 | 当前项目暂无鉴权，未来需要时无处可加 |
| 请求日志 | 无 | 排查问题时缺乏调用记录 |
| 统一错误处理 | 无，各有各的 readErrorMessage | 错误格式不一致 |
| 重试逻辑 | 无 | 网络抖动直接失败 |
| 请求取消 | 无 | 切换任务时无法取消飞行中的请求 |
| 响应拦截 | 无 | 状态码统一处理无处可加 |

### 6.4 Axios 改造建议

1. **创建 `api/http.ts`**：封装 axios 实例，统一 timeout / token / errorHandler
2. **提取 `requestJson` 到公共层**：消除 3 处重复
3. **API 模块只保留业务函数**：每个模块体积减少 ~40 行
4. **禁止组件直接 fetch**：当前只有 API 模块调用 fetch，组件已遵守规范

## 七、SSE 分析

### 7.1 当前架构

**唯一 SSE 连接点：** `CreatorWorkspace.vue` 第 2197 行

```ts
// api/creator.ts
export function createWorkflowEventSource(taskId: string, sessionId: string) {
  return new EventSource(`/api/creator/tasks/.../events`)
}
```

```ts
// CreatorWorkspace.vue
function connectWorkflowEvents(taskId, sessionId) {
  closeWorkflowEventSource()
  const eventSource = createWorkflowEventSource(taskId, sessionId)
  workflowEventSource.value = eventSource
  eventSource.addEventListener('message_created', ...)
  eventSource.addEventListener('session_status', ...)
  eventSource.addEventListener('result_ready', ...)
  eventSource.addEventListener('step_started', ...)
  eventSource.addEventListener('step_completed', ...)
  eventSource.addEventListener('step_failed', ...)
  eventSource.addEventListener('heartbeat', ...)
}

function closeWorkflowEventSource() {
  if (!workflowEventSource.value) return
  workflowEventSource.value.close()
  workflowEventSource.value = null
}
```

### 7.2 连接生命周期

| 事件 | 触发位置 | 清理方式 |
|------|----------|----------|
| 建立连接 | connectWorkflowEvents()（loadPrePublishWorkflow 末尾） | -- |
| 关闭连接 | closeWorkflowEventSource() | 直接 .close() |
| 组件销毁 | onBeforeUnmount → closeWorkflowEventSource() | ✅ 正确 |
| 切换任务 | selectTask → resetGeneratedTaskResults → closeWorkflowEventSource | ✅ 正确 |
| 手动清理 | resetSelectedWorkspace → closeWorkflowEventSource | ✅ 正确 |

**重连机制：无。** 连接断开后 `workflowSseText = '连接中断'`，但不会自动重连。

### 7.3 风险点

| 问题 | 风险等级 | 说明 |
|------|---------|------|
| SSE 与组件耦合 | **高** | EventSource 的生命周期完全由 CreatorWorkspace 管理，组件销毁会导致连接断开 |
| 无自动重连 | **中** | 刷新页面或网络波动后需要手动重建工作流 |
| 单连接 | 低 | 只用于发布前优化工作流，场景单一 |

### 7.4 抽离建议

**适合抽离为 `services/sseService.ts`**，因为：
- SSE 只在 CreatorWorkspace 中使用，但不必要和 UI 组件耦合
- P1-B 拆解后，SSE 状态只需写入 workspaceStore
- 统一的重连策略可以避免遗漏
