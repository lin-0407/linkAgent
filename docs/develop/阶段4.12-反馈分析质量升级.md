# 阶段 4.12：反馈分析质量升级

## 需求分析

本阶段服务的目标用户是已经完成视频发布、并导入评论弹幕样例的 B 站 UP 主、内容运营者和复盘者。

承接阶段 4.11（发布前优化已经从“标题/简介/标签建议”升级为“创作者困境/观众钩子/内容定位/可执行修改计划”），本阶段把同样的质量要求推进到评论弹幕分析。

现状问题：反馈报告字段偏“总结型”（整体反馈、高频观点、情绪倾向、争议点、误解点、下一期建议、互动建议），只能回答“发生了什么”，对“为什么发生”和“下一步怎么改”表达不足。

本阶段做：

1. 升级反馈分析 Prompt，强制模型输出观众核心关注、创作者复盘困境、误解来源和行动计划。
2. `creator_llm_feedback_report` 新增 4 个高信号字段。
3. 后端 Record / Response / Mapper / 解析逻辑同步扩展。
4. 前端反馈报告弹窗展示新增字段。
5. 复盘报告、竞品分析读取新增反馈语境。

本阶段不做：

1. 不接 Milvus，不写向量数据，不新增 RAG 检索链路。
2. 不新增批量 BV、定时采集或后台同步。
3. 不做 LLM 批量分类每条评论弹幕。
4. 不新增聊天历史表，不新增对外 API。

## 设计方案

### 沿用现有接口

继续使用旧接口，只升级结构化输出质量，不新增入口：

```text
POST /api/creator/tasks/{taskId}/feedback/analyze
GET  /api/creator/tasks/{taskId}/feedback/report
```

原因：当前短板是报告结构质量，不是缺少入口；沿用旧接口能降低联调成本，旧任务和旧页面流程不被打断。

### 数据结构

`creator_llm_feedback_report` 新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `creator_feedback_dilemma` | TEXT | 本轮反馈暴露出的创作者复盘困境 |
| `audience_core_concern` | TEXT | 观众最集中的真实关注点和互动动机 |
| `misunderstanding_source_analysis` | TEXT | 误解来源分析列表 JSON |
| `feedback_action_plan` | TEXT | 评论区回应、内容修正、下一期动作计划列表 JSON |

两个 JSON 字段先整段保存为字符串，后端不强行反序列化成对象，结构波动的风险交给前端宽松解析（沿用 `parseJsonArray`）。

### 为什么不拆子表

当前每个任务仍只保留一份最新反馈报告，新增字段属于“报告结论”而不是“评论明细”，先放在 `creator_llm_feedback_report` 中最简单。等出现多版本对比、人工批注、多人协作或行动计划完成度追踪时再拆表。

### Prompt 升级与硬约束

`buildSystemPrompt()` 的 JSON 输出新增 `creatorFeedbackDilemma`、`audienceCoreConcern`、`misunderstandingSourceAnalysis`、`feedbackActionPlan` 四个顶层字段；并加强既有字段：`hotTopics` 增加 `creatorDecision`，`controversyPoints` 增加 `responseBoundary`，`misunderstandingPoints` 增加 `source`。

硬约束：不允许编造样例外数据、不允许虚构精确比例、每个判断必须能回到样例、行动计划必须可执行、禁止“提升互动/优化表达/加强引导”等空泛话术。

### 一个方案内部冲突的处理（重要）

方案 5.4.2 把 `nextContentSuggestions` 和 `interactionSuggestions` 从字符串数组升级为对象数组：

```json
"nextContentSuggestions": [{"topic": "...", "sourceSignal": "...", "executionHint": "...", "risk": "..."}],
"interactionSuggestions":  [{"channel": "...", "message": "...", "purpose": "..."}]
```

但 6.2 又把这两块列在“现有展示继续保留”。二者冲突：前端旧渲染用 `formatValue(item)`，对象会被打印成原始 JSON。

经与作者确认，采用**完整升级**：Prompt 按对象数组输出，前端这两块改为结构化展示，并对历史字符串数据 / 示例数据用 `getRecordText(item, key) || formatValue(item)` 做回退。这样新数据走结构化字段、旧数据走字符串，互不破坏。同理，前端把 `creatorDecision`、`responseBoundary`、`source` 等新子字段一并展示，避免模型产出却被 UI 静默丢弃。

## 编码实现

后端修改：

- `init.sql`
  - `creator_llm_feedback_report` 建表新增 4 列。
  - 为已建库追加条件式 `ALTER TABLE`（`information_schema.COLUMNS` 判断 + `PREPARE/EXECUTE`），保证旧库幂等加列、重复执行不报错。
  - 示例种子行保持新列为空，用于验证前端兜底路径。
- `CreatorFeedbackReportRecord`：新增 4 个字段及 getter/setter。
- `CreatorFeedbackReportResponse`：响应新增 4 个字段。
- `CreatorFeedbackMapper`：`upsertReport` 的 insert 列 / values / duplicate update，`findReportByTaskId` 的 select 列 / result map 同步补齐。
- `CreatorFeedbackService`
  - `fillParsedFields` 解析 4 个新字段（缺失返回 null，不会把报告打成 `RAW_ONLY`，旧字段照常解析）。
  - `buildSystemPrompt()` 升级 JSON 结构与硬约束。
  - `toReportResponse` 透传新字段。
- `CreatorReportService#buildFeedbackReportPrompt`、`CreatorCompetitorService#buildFeedbackReportPrompt`
  - 复盘 / 竞品上下文补充“创作者反馈困境、观众核心关注、误解来源分析、反馈行动计划”，缺失时经 `TextUtil.trimToDefault` 退化为“未提供”。

> 注：`CreatorFeedbackService#buildChatReportContext`（反馈追问上下文）本阶段不改，保持改动范围最小；追问仍读取既有字段。

前端修改：

- `src/types/creator.ts`：`CreatorFeedbackReport` 补齐 4 个 `string | null` 字段。
- `CreatorWorkspace.vue`
  - 新增 `misunderstandingSourceAnalysis`、`feedbackActionPlan` 两个 `parseJsonArray` computed。
  - 反馈报告弹窗新增“创作者复盘困境、观众核心关注、误解来源分析、反馈行动计划”四块展示。
  - “下一期内容建议”“互动建议”升级为结构化展示并兼容旧字符串数据。
  - “高频观点 / 争议点 / 误解点”补充展示 `creatorDecision` / `responseBoundary` / `source`。
  - 文本字段用 `值 || '未解析到…'` 兜底；列表字段用 `v-if=数组.length / v-else <p>` 兜底。

## 测试验证点

作者本地验证命令：

```bash
cd E:\linkAgent\linkAgent\backend
mysql -u root -p < src/main/resources/sql/init.sql
mvn test
```

```bash
cd E:\linkAgent\linkAgent\link-agent-frontend
npm run type-check
npm run build
```

重点检查：

1. 新库能创建新增字段；旧库执行 `init.sql` 不重复加列、不报未知列。
2. 新生成报告时响应包含 `creatorFeedbackDilemma`、`audienceCoreConcern`、`misunderstandingSourceAnalysis`、`feedbackActionPlan`。
3. LLM 输出缺新字段时，旧字段仍正常返回，`parseStatus` 不应被打成 `RAW_ONLY`。
4. 前端弹窗在新增字段为空时显示兜底文案；JSON 数组字段按列表展示；旧字符串数据不被打印成原始 JSON。
5. 反馈追问区域仍可用。
6. 复盘报告、竞品分析能承接新增反馈语境（可在竞品结论中体现“是否解决了本视频观众在意的问题”）。

## 后续扩展

1. 结构稳定后再接 RAG，用向量检索为反馈追问补充证据来源，而不是替代分析框架。
2. 出现多版本报告对比、人工批注或行动计划完成度追踪需求时，再把行动计划 / 误解来源拆为子表。
3. 可考虑把新增反馈语境也接入反馈追问上下文，让追问回答能引用“创作者困境/观众核心关注”。
