# 跨分区视频案例知识库说明（阶段 5.1）

> 对应开发文档 `/docs/develop/阶段5.1-跨分区视频案例知识库.md`。本文件是 5.1（a/b/c 全部）落地后的功能与接口说明，覆盖：表结构、5 个接口、AI 清洗、质量打分、向量索引与隔离、配置键、离线采集脚本、前端入口、优雅降级。检索链路（5.2）、Agent 工具化（5.3）不在本阶段。

## 1. 功能定位与边界

- **解决的痛点**：项目此前缺高质量领域知识库，Agent 给发布前 / 竞品建议时只能凭模型先验，无法参照「同赛道里被验证过的成功视频」。
- **本阶段做**：把「优品标杆 + 竞品」视频案例（跨分区、跨创作任务）清洗、结构化、落库、向量化，形成一个可被语义检索的**存储底座**。
- **数据来源（严守平台边界）**：
  1. 离线采集脚本 `scripts/bilibili_reference_fetcher.py`（作者本地用系统 cron 跑榜单，或显式指定 BV）产出的标准 JSON；
  2. 项目内置 seed 案例；
  3. 前端「输入单个 BV 一键采集导入」（用户显式触发的限量采集）。
- **红线**：部署后端**不内置任何定时 / 后台 / 批量采集**。榜单批量只发生在离线脚本（作者本地运行），后端只消费脚本产物或按单 BV 显式触发。

## 2. 模块与包结构

顶层业务包 `com.link.linkagent.knowledge`（跨任务、跨分区，不归属某个 `creator_task`，故不放在 `creator.*` 下）：

| `controller` | `KnowledgeReferenceVideoController` | 5 个对外接口 |
| `service` | `KnowledgeReferenceVideoService` / `KnowledgeReferenceFetchService` / `KnowledgeReferenceCleaningService` / `KnowledgeQualityScoringService` / `KnowledgeReferenceIndexService` | 导入落库 / 单 BV 采集 / 清洗 / 质量打分 / 向量索引 |
| `mapper` | `KnowledgeReferenceVideoMapper` | 注解式 MyBatis，父表 + 子表读写 |

## 3. 表结构

维护在 `backend/src/main/resources/sql/init.sql`（第 19、20 节），`CREATE TABLE IF NOT EXISTS`。

### 3.1 `creator_reference_video`（案例主表，父）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT UNSIGNED PK | 主键 |
| video_id | VARCHAR(64) | 案例唯一标识（UUID），`uk_video_id` 唯一；子表外键 + 向量文档 ID 来源 |
| bv_id | VARCHAR(20) | B 站 BV 号，可空（seed / 手动可能没有） |
| tier | VARCHAR(16) | 案例层级：`BENCHMARK`（优品标杆）/ `COMPETITOR`（竞品）/ `OWN_HISTORY`（历史），默认 BENCHMARK |
| category | VARCHAR(64) | 分区 / 主题，同赛道过滤 + 质量分按分区归一化；缺失不参与分区打分 |
| title | VARCHAR(255) | 标题（接口校验必填，DB 宽松以容纳 seed） |
| description | LONGTEXT | 简介原文 |
| tags | VARCHAR(512) | 标签 JSON 数组字符串（如 `["AI","教程"]`） |
| view_count / like_count / coin_count / favorite_count / danmaku_count / reply_count | BIGINT UNSIGNED | 六项热度指标，均可空 |
| highlight_summary | LONGTEXT | 清洗后优质评论 / 弹幕亮点摘要（5.1b 生成） |
| quality_score | DECIMAL(6,2) | 分区归一化质量分 0–100（5.1c 计算）；view 缺失 / 分区样本不足为空 |
| source | VARCHAR(64) | 数据来源（见 §4.1 白名单） |
| publish_time_text | VARCHAR(64) | 发布时间文本（仅展示，不做时间运算） |
| embedding_id / embedding_status / embedding_error / embedding_update_time | — | 向量索引状态字段，**完全沿用 `creator_feedback_item` 范式**；`embedding_status` 默认 `PENDING` |
| create_time / update_time / is_deleted | — | 通用字段（逻辑删除） |

索引：`uk_video_id`、`idx_category_tier(category, tier)`、`idx_bv_id`、`idx_embedding_status`。

### 3.2 `creator_reference_video_item`（优质评论弹幕子表，子）

结构对标 `creator_feedback_item`，外键是 `video_id`（跨任务）。关键字段：`item_id`(UUID 唯一)、`video_id`、`source_type`(COMMENT/DANMAKU)、`content`、`sentiment`(POSITIVE/NEGATIVE/NEUTRAL，**本表只落 POSITIVE/NEGATIVE**)、`is_noise`(本表只落 0)、`like_count`、`reply_count`、`occur_time_text`、`reason`(清洗分类原因)、`embedding_*`(默认 PENDING)、通用字段。索引 `uk_item_id`、`idx_video_sentiment(video_id, sentiment)`、`idx_video_embedding_status(video_id, embedding_status)`。

> 父子两表为 5.2「父子召回（small-to-big）」打底：子表存可被精确召回的优质短文本，父表是召回后扩展的完整案例。**5.1 的向量索引只索引父表案例卡片（每视频 1 个向量）**，子表向量化 + 父子召回留 5.2。

## 4. 对外接口

统一前缀 `/api/knowledge/reference-videos`。全部经 Jakarta Validation 校验，非法入参返回 400（`ResponseStatusException`）。

### 4.1 `POST /import` —— 导入案例 JSON

消费离线脚本 / seed 产出的契约 JSON，落父表 + 清洗子表 + 按分区重算质量分（**不**触发向量化）。

**请求体 `ReferenceVideoImportRequest`**

| 字段 | 类型 | 校验 | 说明 |
|---|---|---|---|
| source | String | `@NotBlank` `@Size(max=64)` | 白名单：`bilibili_rank_daily` / `bilibili_rank_weekly` / `bilibili_rank_monthly` / `manual_bv` / `seed`，非白名单 → 400 |
| tier | String? | `@Size(max=16)` | 可空，大写归一后须 ∈ {BENCHMARK,COMPETITOR,OWN_HISTORY}；**留空一律默认 BENCHMARK** |
| category | String? | `@Size(max=64)` | 整批默认分区，单条 video 未给 category 时回退到此 |
| videos | List\<VideoItem\> | `@NotEmpty` `@Valid` | 视频列表，不能为空 |

`VideoItem`：`bvId`(@Size max20)、`title`(@NotBlank @Size max255)、`description`(@Size max20000)、`tags`(List\<String\>)、`category`(@Size max64)、`publishTimeText`(@Size max64)、`stats`(VideoStats)、`comments`(List\<Comment\>)、`danmaku`(List\<Danmaku\>)。
`VideoStats`：`view`/`like`/`coin`/`favorite`/`danmaku`/`reply`（均 Long，可空）。
`Comment`：`content`/`like`(Long)/`reply`(Integer)。`Danmaku`：`content`/`timeText`。

> 评论 / 弹幕**不做长度校验**：它们是机器采集的批量数据，过度校验会让整批导入因个别脏数据失败；筛选交给清洗逻辑。

**响应 `ReferenceVideoImportResponse`**：`{ receivedCount, importedCount, skippedCount, source, tier }`，满足 `receivedCount = importedCount + skippedCount`。

**行为要点**
- 整批一个事务（`@Transactional`），中途异常不留半批脏数据。
- **按 BV 幂等去重**：带 BV 的视频，库内（`is_deleted=0`）已存在或本批已出现过同 BV → 跳过计入 `skippedCount`；无 BV 的 seed / 手动条目不去重。重复导入同批，第二次起 `importedCount=0`。
- 每条视频清洗 comments/danmaku → 优质子条目落子表 + 亮点摘要写父表（见 §5）。
- 导入后对**受影响分区**重算 `quality_score`（与导入同一事务，见 §6）。

### 4.2 `POST /fetch-import` —— 单 BV 一键采集导入

输入 BV → 后端显式调用采集脚本 `bv` 模式 → 读产物 → 转交 `/import` 链路，一步到位。

**请求体 `ReferenceVideoFetchImportRequest`**：`bvInput`(@NotBlank @Size max255，BV 号或视频链接)、`tier`?(@Size max16)、`category`?(@Size max64)。
**响应**：同 `ReferenceVideoImportResponse`。

**行为要点**
- 正则 `BV[0-9A-Za-z]{10}` 提取 BV，识别不到 → 400。
- `ProcessBuilder` 调 `python scripts/bilibili_reference_fetcher.py bv <bvid> --output-dir export/bilibili_reference --source manual_bv --max-comments 50 --max-danmaku 300 [--tier ..] [--category ..]`；工作目录为项目根（向上探测含脚本的根目录，兼容不同启动目录）。
- 脚本运行**不在 DB 事务内**（外部进程、耗时长）；真正落库事务在 `importReferenceVideos` 内部。
- 读 `export/bilibili_reference/<bvid>_reference.json`，限 20MB、非空。

**错误码**：没识别到 BV / 产物过大 / 产物为空 → 400；脚本超时(180s) → 504；脚本退出码≠0 → 502（附截断后脚本输出）；产物解析失败 → 502；脚本不存在 / python 不可用 / 产物缺失 → 500。

> 前端只暴露这条单 BV 路径；榜单批量只能走离线脚本（不进后端）。

### 4.3 `GET /` —— 分页列表

**查询参数**：`category`?(@Size max64)、`tier`?(@Size max16)、`page`(默认1,@Min1)、`size`(默认20,@Min1 @Max100)。
**行为**：`is_deleted=0` + 可选 category/tier 过滤（tier 大写归一 + 白名单校验，非法值 → 400 而非静默空列表）；`ORDER BY id DESC`（最近导入在前）。
**响应 `ReferenceVideoPageResponse`**：`{ items: ReferenceVideoResponse[], total, page, size }`。

`ReferenceVideoResponse` 字段顺序：`id, videoId, bvId, tier, category, title, description, tags(JSON 字符串，前端自行解析), viewCount…replyCount, highlightSummary, qualityScore, source, publishTimeText, embeddingStatus, createTime, updateTime`。

### 4.4 `POST /index/rebuild` —— 增量重建向量索引

把尚未成功索引的案例卡片写入 Milvus 并回写状态。

**请求体 `ReferenceVideoIndexRequest`**：`maxItems`?(@Min1 @Max1000)，请求体可空（`required=false`）。空时回落 `knowledge.rag.max-index-items`（默认 200）。
**响应 `ReferenceVideoIndexResponse`**：`{ ragEnabled, vectorStoreReady, requestedCount, indexedCount, skippedCount(恒 0), failedCount, warnings[], createTime }`。

**行为要点**
- `knowledge.rag.enabled=false` → 400；向量库未就绪（Milvus 没连上 / 无 EmbeddingModel）→ 400；没有待索引案例（PENDING/FAILED）→ 400。
- 只取 `embedding_status IN ('PENDING','FAILED')` 的案例（**增量**，已 INDEXED 不重复嵌入，相对反馈侧「按 task 全量重建」的有意差异）。
- 按 `index-batch-size`（默认 10，Qwen 兼容模式单批硬上限）分批 `vectorStore.add`；成功回写 `INDEXED`（`embedding_id` 复用 `video_id`）；某批失败回写 `FAILED` + 截断原因，收集 `warnings`（≤10 条），**不整体失败**。
- 服务**不加 `@Transactional`**：Milvus 写入不归 DB 事务管（见 §8）。
- 三重防御高成本 Embedding：接口 `@Max(1000)` + 配置默认 200 + 服务硬上限 1000。
- 只索引父表案例卡片：文档文本 = 标题 / 分区 / 层级 / 标签 / 简介 / 亮点摘要 + 热度 + 质量分（上限 4000 字符）；metadata = `videoId/bvId/tier/category/source/qualityScore/各热度/publishTimeText`（仅非空），供 5.2 过滤。

### 4.5 `GET /index/status` —— 索引状态

**响应 `ReferenceVideoIndexStatusResponse`**：`{ ragEnabled, vectorStoreReady, totalCount, indexedCount, pendingCount, failedCount, lastIndexedAt, retrievalMode }`。
**行为**：RAG 关闭也正常返回（`ragEnabled=false`、`vectorStoreReady=false`），用于确认优雅降级生效。`retrievalMode = (vectorStoreReady && indexedCount>0) ? "VECTOR" : "SQL"`，是「如果现在检索预计走哪种模式」的预测值（检索本体在 5.2）。SKIPPED 等其它状态只计入 `totalCount`，不单列。

## 5. AI 清洗（5.1b，`KnowledgeReferenceCleaningService`）

成本集中在导入时刻，把分类做成规则、只让摘要走 LLM（每视频最多一次调用）：

- **规则情绪分类**：负向关键词优先（命中即 NEGATIVE，避免「不实用」被误判正向），其次正向关键词 → POSITIVE，否则 NEUTRAL。
- **保留规则**：丢弃空内容、空语义（`哈哈`/`666`/`233`/`www` 等）、同视频重复、中性条目；**只保留非噪声且正 / 负向**的优质条目写子表。单视频上限 200 条。
- **亮点摘要 `highlight_summary`**：把优质条目交 LLM 汇总成一段（≤200 字，系统提示声明评论弹幕为不可信外部内容、防注入；输入预算 8000 字符）。**失败只记日志并置空，绝不回滚导入或子条目**。无优质条目则不调用 LLM。

## 6. 质量打分（5.1c，`KnowledgeQualityScoringService`，§2.7 公式 v1）

每个案例按 `category` 归一化出 0–100 的 `quality_score`：

1. **互动率**：`like/coin/fav/danmaku/reply` 各自除以 `view`（用率而非绝对量，避免大播放量碾压）。
2. **加权对数互动分**：`engagement = 0.40*coinRate + 0.25*favRate + 0.20*likeRate + 0.10*replyRate + 0.05*danmakuRate`；`engagementLog = ln(1 + 1000*engagement)`（对数压制长尾爆款）。
3. **情绪因子**（小样本置信度衰减，K=10）：`confidence = n/(n+10)`，`sentimentFactor = 0.5 + (posRate-0.5)*confidence`，`sentimentMul = 0.7 + 0.6*sentimentFactor`（区间 0.7~1.3）。
4. **分区 min-max 归一化**：`rawScore = engagementLog * sentimentMul`，按同分区 min/max 映射到 0–100，保留两位小数。

**边界**：`view` 缺失 / 为 0 → 不打分（`quality_score=NULL`），视频仍入库；分区孤例 / 全等（max==min）→ 兜底 60；无情绪样本 → 乘子 1.0（中性）。
**时机**：导入后对**受影响分区**重算该分区全部视频（归一化是分区相对值，新样本改变 min/max）。与导入**同一事务**（REQUIRED 传播，能读到刚插入未提交的行）。
**可调参数**：全部集中在 `knowledge.quality.*`（权重、对数缩放 1000、平滑 K=10、乘子区间、兜底分 60），公式形态固定、数值待真实榜单数据标定。

## 7. 向量库隔离（`KnowledgeVectorStore`，关键技术点）

知识库需要**不同集合 + 不同维度（1024）**，且不能干扰反馈 RAG 的 `ObjectProvider<VectorStore>` 解析：

- 本类是普通 Spring Bean，**内部私有持有**一个 `MilvusVectorStore`（集合 `creator_reference_video`、维度 1024、`IVF_FLAT` + `COSINE`），**绝不**把它注册成 `VectorStore` 类型的 Bean —— 从根上避免与反馈侧出现多 `VectorStore` Bean 歧义。
- **两层判断**才构建：业务开关 `knowledge.rag.enabled` + 基础设施 `EmbeddingModel` 是否存在（用 `ObjectProvider` 注入，`EMBEDDING_MODEL_TYPE=none` 时无该 Bean）。任一不满足 → `ready=false`、不连 Milvus。
- 构建后**手动调用 `store.afterPropertiesSet()`**（非 Spring 托管 Bean，容器不会替它回调），集合 schema 才会建出来。
- 建库失败（Milvus 没起、维度冲突）不拖垮后端：降级 `ready=false`，导入 / 列表照常。

## 8. 优雅降级

- `knowledge.rag.enabled` 默认 `false`：不连 Milvus、不调 Embedding。**导入 / 清洗 / 打分 / 列表照常工作**（这些不依赖向量库）。
- 关闭 / 未就绪时：`index/rebuild` → 400；`index/status` → `ragEnabled=false`；检索（5.2）走 SQL 兜底。
- 与 `creator.feedback.rag` 完全独立的开关，互不影响。

## 9. 配置键

```yaml
knowledge:
  rag:
    enabled: ${KNOWLEDGE_RAG_ENABLED:false}              # 业务总开关，默认关
    collection-name: ${KNOWLEDGE_RAG_COLLECTION_NAME:creator_reference_video}
    embedding-dimension: ${LLM_EMBEDDING_DIMENSIONS:1024} # 必须与 Embedding 输出维度严格一致
    index-batch-size: ${KNOWLEDGE_RAG_INDEX_BATCH_SIZE:10} # Qwen v3/v4 兼容模式单批硬上限 10
    initialize-schema: ${KNOWLEDGE_RAG_INITIALIZE_SCHEMA:true}
    milvus: { host, port, username, password, database-name }  # 复用 MILVUS_* 环境变量
  quality:        # 质量公式可调参数，均有 Java 默认值，yml 未显式配置
    coin-weight/favorite-weight/like-weight/reply-weight/danmaku-weight   # 0.40/0.25/0.20/0.10/0.05
    log-scale: 1000 / sentiment-smoothing-k: 10 / sentiment-mul-base: 0.7 / sentiment-mul-span: 0.6 / fallback-score: 60
```

> **注意**：`knowledge.rag.max-index-items` 未写进 `application.yml`，走 Java 默认 **200**（反馈侧才在 yml 显式配 `max-index-items: 300`，两者独立，勿混淆）。
> 启用知识库时需配 Embedding：`EMBEDDING_MODEL_TYPE=openai`、`LLM_EMBEDDING_MODEL=text-embedding-v4`、`LLM_EMBEDDING_DIMENSIONS=1024`、`LLM_EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com`、`LLM_EMBEDDING_PATH=/compatible-mode/v1/embeddings`、`LLM_EMBEDDING_API_KEY=<DashScope Key>`，并连上 Milvus（`MILVUS_*`）。

## 10. 离线采集脚本 `scripts/bilibili_reference_fetcher.py`

纯公开接口、不带 Cookie、自带 WBI 签名、礼貌节流。产出导入契约 JSON（`{source, tier?, category?, videos:[...]}`），可原样 POST 给 `/import`，也被 `/fetch-import` 的 `bv` 模式复用。

```bash
# 榜单批量（作者本地 cron）：抓分区榜单前 N 条
python scripts/bilibili_reference_fetcher.py rank --category 知识 --limit 10
# 单 BV（后端 fetch-import 复用此模式）
python scripts/bilibili_reference_fetcher.py bv BV1xxxxxxxxx --source manual_bv
```

| 子命令 | 专属参数 | 说明 |
|---|---|---|
| `rank` | `--category`(默认 全站) / `--rid` / `--source`(daily/weekly/monthly) / `--limit`(默认 10) | 抓分区榜单前 N 个视频 |
| `bv` | `bv`(一个或多个 BV / 链接) / `--category` / `--source`(manual_bv/seed) | 按 BV 采集，后端单 BV 路径复用 |

通用参数（写在子命令之后，靠 argparse `parents=[common]`）：`--output-dir`、`--tier`、`--max-comments`(50)、`--max-danmaku`(300)、`--comment-page-size`(20，上限 49)、`--comment-sort`(0 时间 / 1 点赞默认 / 2 回复)、`--delay`(0.8)、`--timeout`(15)。

产物落 `export/bilibili_reference/`：`rank_<rid>_reference.json`、`<bvid>_reference.json`、或多 BV 的 `manual_reference.json`。

分区解析规则：优先使用视频详情接口返回的 `tname`；如果 `tname` 为空但 `tid` 存在，脚本用内置 B 站分区号映射表兜底，并在命令行输出提示。这样是为了让单 BV 采集在前端未手动填写分区时仍能尽量保留视频自身分区，避免入库后无法参与分区质量分和同赛道过滤。

> **注意**：`ranking/v2` 是**滚动综合榜**，`daily/weekly/monthly` 只是来源溯源标注，并非真正按时间切分。脚本采集时 `tags` 暂留空（标签需额外接口，留待后续）。

## 11. 前端入口

- `App.vue`：顶部两个 surface 切换 `creator`（创作工作台）/ `knowledge`（案例库）。
- `KnowledgeWorkspace.vue` 三块：
  1. **采集导入**：BV 输入 + 层级 / 分区可选，「采集并导入」按钮（约 10–60 秒）；成功后清空输入、回第一页。
