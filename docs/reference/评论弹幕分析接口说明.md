# 评论弹幕分析接口说明

## 功能定位

评论弹幕分析模块用于处理用户主动粘贴的评论和弹幕样例，帮助创作者理解发布后的观众反馈。

当前接口已经包含三层能力：

1. 阶段 4.3 的同步 LLM 基线，负责保存样例并生成结构化反馈报告。
2. 阶段 4.4.1.3 的 BV 拉取、样例文件导入与基础仪表盘，负责保存单条评论/弹幕明细并返回图表数据。
3. 阶段 4.4.1.5 的反馈追问，负责基于当前任务报告和明细回答用户追问，并返回证据列表。

它输出：

1. 观众整体反馈摘要。
2. 高频观点。
3. 情绪倾向。
4. 争议点。
5. 误解点。
6. 下一期内容建议。
7. 互动回应建议。

第一版不做批量或定时的平台同步，不做复盘总报告。
当前实现允许用户在页面输入 BV 后，由后端执行项目内固定脚本并自动导入结果；这仍然是用户主动触发的任务级动作，不是后台定时同步。

## 表结构

### creator_user_feedback_detail

用途：保存一轮评论和弹幕样例。

关键字段：

| 字段 | 说明 |
|---|---|
| feedback_id | 反馈样例唯一标识 |
| task_id | 关联创作任务 |
| comment_samples | 评论样例 |
| danmaku_samples | 弹幕样例 |
| extra_context | 补充背景 |

### creator_llm_feedback_report

用途：保存一轮反馈分析结果。

关键字段：

| 字段 | 说明 |
|---|---|
| report_id | 报告唯一标识 |
| task_id | 关联创作任务 |
| feedback_summary | 观众整体反馈摘要 |
| hot_topics | 高频观点 JSON |
| sentiment_summary | 情绪倾向总结 |
| controversy_points | 争议点 JSON |
| misunderstanding_points | 误解点 JSON |
| next_content_suggestions | 下一期内容建议 JSON |
| interaction_suggestions | 互动回应建议 JSON |
| raw_output | LLM 原始输出 |
| parse_status | 解析状态 |

当前每个任务只保留一份最新样例和一份最新报告。

阶段 4.4.1 已新增：

| 表 | 说明 |
|---|---|
| `creator_feedback_item` | 保存单条评论/弹幕、分类、情绪和无意义标记 |
| `creator_feedback_metric` | 保存用户主动导入的视频基础指标 |

阶段 4.4.1 工作流相关表：

| 表 | 说明 |
|---|---|
| `creator_workflow_session` | 保存任务级 Agent 工作流会话 |
| `creator_workflow_message` | 保存工作流消息流 |
| `creator_workflow_step` | 保存分析步骤和失败回放信息 |

## API

### 保存样例

```http
POST /api/creator/tasks/{taskId}/feedback
Content-Type: application/json
```

请求体：

```json
{
  "commentSamples": "这期节奏很清楚，我第一次看懂了整个流程。",
  "danmakuSamples": "讲得太实用了 / 这一段信息密度很高",
  "extraContext": "发布后 24 小时内收集的样例"
}
```

说明：

1. `commentSamples` 和 `danmakuSamples` 至少填写一项。
2. `extraContext` 可选。
3. `taskId` 不存在时返回 404。

### 查询样例

```http
GET /api/creator/tasks/{taskId}/feedback
```

说明：

1. 任务不存在时返回 404。
2. 样例不存在时返回 404。

### 分析样例

```http
POST /api/creator/tasks/{taskId}/feedback/analyze
Content-Type: application/json
```

请求体：

```json
{
  "customGuidance": "可选，分析顺序、关注重点和建议风格等业务指导",
  "analysisFocus": "重点看观众是否理解核心方法",
  "extraRequirement": "给出下一期选题建议"
}
```

说明：

1. 主要样例从数据库读取，不需要重复提交。
2. `customGuidance` 为空时不添加本次业务指导，最长 2000 个字符。
3. 分析成功后任务状态更新为 `FEEDBACK_ANALYZED`。
4. 后端系统提示词固定维护角色、平台数据边界和 JSON 输出结构，前端不能覆盖。
5. 任务没有样例时返回 400。

### 查询报告

```http
GET /api/creator/tasks/{taskId}/feedback/report
```

说明：

1. 任务不存在时返回 404。
2. 报告不存在时返回 404。
3. 返回中同时包含结构化字段和 `rawOutput`，便于人工检查。

### 导入评论弹幕文件

```http
POST /api/creator/tasks/{taskId}/feedback/import
Content-Type: multipart/form-data
```

表单字段：

| 字段 | 说明 |
|---|---|
| `file` | 用户主动上传的 JSON/TXT 样例文件 |

校验规则：

1. 文件不能为空。
2. 文件大小不能超过 5MB。
3. 第一版只支持 `.json` 和 `.txt`。
4. JSON 优先支持 `scripts/bilibili_feedback_fetcher.py` 的输出结构。
5. TXT 只做区块级基础解析，响应里会返回提示信息。

响应示例：

```json
{
  "taskId": "creator-task-id",
  "commentCount": 120,
  "danmakuCount": 300,
  "metricImported": true,
  "warnings": []
}
```

说明：

导入成功后，后端会同步回填 `creator_user_feedback_detail`，所以仍可继续使用 `POST /feedback/analyze` 生成 LLM 报告。

### 拉取并导入 BV 样例

```http
POST /api/creator/tasks/{taskId}/feedback/fetch
Content-Type: application/json
```

请求体：

```json
{
  "bvInput": "BV1xxxxxxx",
  "maxComments": 50,
  "maxRepliesPerComment": 20,
  "maxDanmaku": 500,
  "format": "both"
}
```

说明：

1. `bvInput` 必填，支持 BV 号或包含 BV 的视频链接。
2. `maxComments`、`maxRepliesPerComment`、`maxDanmaku` 都有上限校验。
3. `format` 只支持 `json` 或 `both`，因为自动导入依赖脚本生成 JSON。
4. 后端固定执行 `scripts/bilibili_feedback_fetcher.py`，输出到 `export/bilibili_feedback`。
5. 成功后会返回输出目录、生成文件列表、评论数、弹幕数、指标导入状态和 warnings。

### 查询反馈仪表盘

```http
GET /api/creator/tasks/{taskId}/feedback/dashboard
```

返回内容：

1. 评论数量、弹幕数量、无意义/重复内容数量。
2. 评论分类统计。
3. 弹幕分类统计。
4. 情绪分布。
5. 高频关键词。
6. 弹幕时间段热度。
7. 高反馈评论，按评论点赞量和回复量排序。
8. 视频基础指标。
9. 最近导入明细。
10. 导入提示 warnings。

`creator_feedback_item` 中评论反馈强度字段：

| 字段 | 说明 |
|---|---|
| `like_count` | 评论点赞量，用于识别更有共鸣的评论。 |
| `reply_count` | 评论回复量，用于识别互动或争议更高的评论。 |

### 评论弹幕追问

```http
POST /api/creator/tasks/{taskId}/feedback/chat
Content-Type: application/json
```

请求体：

```json
{
  "question": "为什么你认为观众误解了 Agent 工具调用？"
}
```

校验规则：

1. `question` 必填，最长 1000 个字符。
2. 当前任务必须已有反馈报告或评论弹幕明细。
3. 后端只按 `taskId` 查询当前任务数据，不接收前端传入的证据文本。

响应内容：

1. `answer`：基于报告和证据生成的回答。
2. `evidenceItems`：本次回答参考的评论弹幕明细。
3. `reportUsed`：是否使用了已保存反馈报告。
4. `retrievalMode`：当前为 `MYSQL_REPORT_AND_CLASSIFIED_ITEMS`。
5. `ragEnabled`：当前为 `false`，后续接 Milvus 后再切换。

## 设计取舍

当前同步基线没有上 SSE。

原因是当前目标是先把“样例输入 -> 反馈分析 -> 数据库存档”这条线跑通。SSE 更适合在后续做过程可视化，不应该和主业务逻辑混在一起。

阶段 4.4.1 的升级方式：

1. 当前 `POST /feedback` 和 `POST /feedback/analyze` 保留为简单联调入口。
2. 已新增 `POST /feedback/import`，支持用户主动上传脚本导出的 JSON/TXT 样例文件。
3. 已新增 `GET /feedback/dashboard`，返回图表所需的结构化数据。
4. 已新增 `POST /feedback/chat`，支持用户围绕当前任务的反馈报告追问。
5. 第一版追问基于 MySQL 中的报告和分类结果回答，后续再接 Milvus 做 RAG。
6. 数据边界不变：不保存 Cookie，不绕过平台限制，不做批量或定时同步。

本阶段没有拆更多子表。

原因是 MVP 先要简单。反馈摘要、争议点和建议都属于一次分析结果，先放一个表里足够支撑演示和简历展示。

本阶段保留 `rawOutput`。

原因是 LLM 输出不稳定，保留原文可以做失败回放，也方便后面调整业务指导。
