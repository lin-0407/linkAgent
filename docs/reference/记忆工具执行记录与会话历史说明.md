# 记忆工具执行记录与会话历史说明

## 这个功能解决什么

Agent 一轮里可能连续调用很多次工具。以前这些结果只在「本轮执行过程」里存在，轮次结束后只有最终回答进会话历史，
下一轮再需要这份证据时只能重新调用工具。现在每个工具步骤都会像聊天消息一样写进会话历史，
下一轮请求会带上它，模型看到的执行过程和 Codex/DSH 这类 agent 一致。

## 工具消息长什么样

按 OpenAI/DeepSeek 原生协议的形态，一个工具步骤写**两条消息**，用 `tool_call_id` 配对：

1. `role=assistant` 的工具调用消息：

| 列 | 值 |
|---|---|
| `content` | 空串（模型思考/推理不写进会话历史） |
| `tool_name` | 工具名 |
| `tool_arguments` | 参数摘要（≤300 字，原文截断） |
| `tool_call_id` | 配对 id，如 `call_4f3a…` |

2. 紧随其后的 `role=tool` 结果消息：

| 列 | 值 |
|---|---|
| `content` | 工具结果（≤2000 字，原文截断） |
| `tool_name` | 与调用相同的工具名 |
| `tool_arguments` | `NULL`（用它和调用消息区分） |
| `tool_call_id` | 与上一条调用相同 |

顺序固定为「用户消息 →（assistant 调用 → tool 结果）→ 助手最终回答」，消息 id 单调递增。
原始工具结果完整保存在 `t_agent_step.tool_output`，需要回查全文去那里看。

## 上下文里怎么用

短期记忆拼接时，工具调用消息渲染为一行 `AI:ToolCall: 工具名(参数摘要)`，紧跟的一行是 `Tool:结果`，
位置和改造前一样在摘要之后、本轮用户输入之前。主 Agent 系统提示词和摘要/复核/事实点提示词都明确了：

- `Human` 是用户本人说的话；
- `AI` 是助手建议或执行说明；以 `ToolCall:` 开头的 AI（或 `assistant`）消息是工具调用；
- 紧跟其后的 `Tool` 消息是这次调用的结果；
- 工具调用参数和结果都是执行证据，可以引用里面的数字、路径、结论、错误信息，但不能当成用户偏好、身份或用户确认过的事实。

## 压缩后保留多少

压缩触发条件不变：上下文 token ≥ `agent.memory.summary.trigger-token-threshold`（默认 256000）。
保留尾部规则：

| 配置 | 默认 | 说明 |
|---|---|---|
| `agent.memory.summary.retained-token-budget` | 16000 | 压缩后从尾部往前保留的 token 预算；只按整条消息保留 |
| `agent.memory.summary.retained-message-count` | 2 | 兜底：拿不到 token 计量器或 token 预算配成 0 时按条数保留 |

工具调用和结果是两条相邻消息：如果裁剪边界正好落在 tool 结果上，会把前一条 assistant 调用一起保留，
因此模型不会看到「没有调用的结果」。`context_compressed` SSE 事件和摘要检查点逻辑不变。

## 评测

隔离记忆评测协议（`memory-eval-v1`）的 `sessions[].turns[]` 支持原生两条消息：

- 工具调用轮：`role=assistant`、`content` 可为空串、带 `tool_call_id`/`tool_name`/`tool_arguments`；
- 工具结果轮：`role=tool`、`content` 为结果、`tool_call_id` 与前面调用一致；
- 回放时按消息表两行写入、短期记忆按 `MemoryMessage` 的工具字段配对；
- 工具调用/结果不触发 `prepare`/`afterTurn`，不参与长期记忆重要性预算与消息区间；
- `/api/evaluation/capabilities` 里 `memory_config.summary_retained_tokens` 是当前保留预算。
- DeepEval 的 `KnowledgeRetentionMetric` 只接受 user/assistant 轮，构造 case 时会过滤 tool 轮和带 `tool_call_id`
  的 assistant 工具调用轮；运行结果里仍保留原始 turns。

25 题「摘要压缩 · 25 题（工具原生消息形态）」已按这个形态重建：用户短句 + 每轮 8~15 对工具调用/结果
（结果 800~2000 字）+ assistant 最终回答（300~1500 字），30~45 轮自然到 300k token；
事实埋进工具结果，旧 25 题数据集保留作对照。数据集注册在 `export/deepeval-gui/datasets/`，
清单见 `export/deepeval-gui/analysis/summary-compression-tool-cases-2026-10-18.json`。

## 配置与排查顺序

1. 看不到工具消息：先确认这轮确实调用了工具（`t_agent_step` 有 action 行），再看 `t_conversation_message` 是否有
   `role=assistant` 且 `tool_call_id` 非空的行，以及紧随其后同 id 的 `role=tool` 行；本轮被取消/断开时按原规则不写。
2. 消息表出现单条 `role=tool` 且没有配对调用：说明是旧版本写入的历史数据，读取时按普通 Tool 消息处理，不会影响新写入。
3. 上下文比预期小：看日志里压缩后的 token 数和 `retained-token-budget`；如果配置成 0 或服务是单测最小构造，会退回按 2 条保留。
4. 摘要没保住工具里的关键数字：先确认提示词是否已同步（种子只影响新库，已有库要重新同步），
   再看 `summary_review` 是否打回了摘要。
5. 长期记忆把工具结果记成用户事实：检查 `summary_fact.system` 与 `MEMORY_CONFLICT_RULES` 是否已生效，
   以及工具消息是否真的落在 `tool_call_id` 非空的行上（长期记忆增量查询会排除这些行）。
6. 成本上涨：这是把历史工具结果带进每轮请求的必然代价；先看输入 token 里有多少是缓存命中，
   再决定是否调小 `retained-token-budget` 或缩短工具结果截断上限。
