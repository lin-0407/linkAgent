# 发布前优化建议审查器说明

发布前优化建议审查器用于检查 AI 建议是否具备基础可信度。

它解决的问题是：模型可能给出看起来很完整的标题、简介和修改计划，但其中一部分可能没有证据支撑，甚至引用了不存在的证据编号。对于 UP 主来说，这类建议会把“模型猜测”伪装成“确定结论”。

## 工作流程

1. `PrePublishSuggestionService` 调用 LLM 或 Agent 生成原始建议。
2. 服务解析 JSON，填充标题建议、修改计划、缺失信息等结构化字段。
3. `PrePublishSuggestionAuditor` 读取结构化字段和当前证据包。
4. 审查器生成 `PrePublishAuditReport`。
5. 服务将审查报告序列化到 `creator_suggestion.audit_report`。
6. 服务把 `quality_status` 更新为审查状态。

## 审查状态

- `AUDIT_PASSED`：未发现明显问题。
- `AUDIT_WARNED`：存在需要人工复核的问题，但不一定是严重错误。
- `AUDIT_FAILED`：存在明确错误，例如引用了不存在的证据编号。
- `AUDIT_SKIPPED`：结构化解析失败或审查器未注入，无法完整审查。

## 规则说明

### 证据编号检查

标题建议和修改计划里的 `evidenceIds` 必须存在于当前 `evidenceRefs` 中。

如果模型输出 `E99`，但证据包只有 `E1`、`E2`，系统会记录 `INVALID_EVIDENCE_ID`。这说明模型可能编造了依据。

### 标题建议检查

标题建议需要尽量引用证据。

没有证据的标题不一定错误，但可信度较低，因此会记录 `TITLE_WITHOUT_EVIDENCE`。

### 高优先级动作检查

`HIGH` 优先级修改动作必须带证据。

原因是高优先级建议会影响作者最先改哪里。如果没有依据，容易误导作者投入精力到错误方向。

### 夸大承诺检查

审查器会标记明显无法保证的表达，例如“必爆”“爆款保证”“完播率翻倍”。

这类表达不能作为专业建议，因为当前系统没有真实平台算法和发布后数据，不能承诺播放增长结果。

## 当前边界

审查器是规则系统，不是第二个 LLM 裁判。它不会判断标题是否足够有创意，也不会判断风格是否完全符合某个账号。

这个边界是刻意保留的：规则审查稳定、低成本、可解释，适合作为建议生成后的第一道质量门。
