# 高级检索链路说明（阶段 5.2）

> 对应开发文档 `/docs/develop/阶段5.2-高级检索链路.md`。本文件是 5.2（a/b/c/d/e 全部切片）落地后的功能与接口说明，覆盖：检索全链路、5 刀切片、7 个新接口、配置键、双开关与优雅降级、前端面板。
> 承接 5.1「跨分区视频案例知识库（存储底座）」（见 `/docs/reference/跨分区视频案例知识库说明.md`）。5.1 把案例**存进去、向量化**了，5.2 给它装上**「查」的能力**。Agent 工具化与接入发布前优化 / 竞品（5.3）不在本阶段。

## 1. 功能定位与边界

- **解决的痛点**：5.1 只有存储底座，`index/status` 里的 `retrievalMode` 只是「预测值」，没有真正的检索本体。5.2 把底座变成**可检索链路**，对外暴露 `POST /search` 与前端检索面板，可独立 curl / 前端自测。
- **输入**：一段自然语言 `query`（如「知识区高完播的开场怎么做」）+ 可选过滤 `category` / `tier` / `topK` + 可选 `strategy`（查询增强策略）。
- **输出**：按相关性排序的父表案例卡片列表 + 命中的子条目证据（观众原话）+ **本次实际走了哪种检索模式 / 策略 / 是否精排**。
- **完整链路**（5 刀逐刀叠加）：查询增强（改写 / 多查询 / HyDE）→ 父召回（dense 或原生 dense+BM25 hybrid）+ 子召回（small-to-big）→ 合并去重 → SQL 关键词兜底 → Rerank 精排 → 证据回查。
- **降级红线（继承 5.1）**：`knowledge.rag.enabled=false` 或向量库未就绪时，检索**走 SQL 兜底且不报错**；hybrid / rerank 各自有独立开关，关闭即退回上一刀行为。**全部开关默认关 → 对 5.1 与彼此零回归**。
- **本阶段不做**：Agent 工具化与接入发布前优化 / 竞品（5.3）、知识库完整管理后台（5.4）、跨创作者权限隔离、多模态视频内容评分。

## 2. 检索全链路总览

所有开关全开时，`KnowledgeReferenceRetrievalService.search()` 的编排（关键：**`videoId` 是全链路窄腰**，父召回换引擎不影响下游）：

```
search(request):
  ① 入参归一：query.trim / category.trimToNull / tier 大写归一+白名单(非法 400)
              / topK 收敛[1,50] / strategy 归一(默认 REWRITE，非法 400)
  ② 门控：
     ragEnabled    = knowledge.rag.enabled
     hybridEnabled = ragEnabled && hybrid.enabled && hybridStore.isReady()
     vectorStore   = (ragEnabled && knowledgeVectorStore.isReady()) ? 父向量库 : null
     if !hybridEnabled && vectorStore==null:           ← 向量链路完全不可用
         return { mode=SQL, strategy=NONE, items=SQL兜底, evidence=[], reranked=false }   // 优雅降级
  ③ 查询增强(5.2b)：strategy==NONE ? [query] : enhance(query, strategy)→1~N 条 searchTexts（内部失败已退回[query]）
  ④ 候选池宽度：candidateK = rerank.enabled ? min(50, max(topK, candidatePoolSize)) : topK   // retrieve-wide
  ⑤ 父召回：hybridEnabled ? hybridSearchMulti(dense+BM25+RRF) : denseSearchMulti(dense)  → List<videoId>
            运行期异常 → 退 SQL 兜底（mode=SQL）
  ⑥ 子召回(small-to-big,5.2c)：hybridEnabled ? 子hybrid集合 : (childReady ? 子dense集合 : 跳过)
            → LinkedHashMap<videoId, List<itemId>>；独立 try，异常 → 父-only
  ⑦ 合并：mergeVideoIds(父在前, 子 keySet 在后, LinkedHashSet 去重, 截 candidateK)   // 无 RRF
  ⑧ 回查父表事实源：listByVideoIds(is_deleted=0) + 按 videoId 顺序重排
  ⑨ 命中足够(≥minVectorHitCount)？ mode=HYBRID/VECTOR，候选=向量结果
            否则 mode=*_WITH_SQL_FALLBACK，候选=向量结果 + SQL 兜底去重补足
  ⑩ Rerank(5.2e,可选)：用原始 query 对候选精排 → 截 topK；关闭/失败 → 保持原序、截 topK
  ⑪ 证据(5.2c-2)：buildEvidence(最终卡片, childMap) → listItemsByItemIds(is_deleted=0) 回查观众原话
  return { mode, strategy, enhancedQueries, items, evidence, reranked }
```

> **四层降级同构**（任一层挂掉都不拖垮主链路）：hybrid 失败退 dense（⑤）、子召回失败退父-only（⑥）、向量失败退 SQL（⑤⑨）、rerank 失败保原序（⑩）。延续反馈侧「向量失败退 SQL」的容错哲学。

`POST /topic-search` 是后续前端主用的主题优先入口：中块 dense 仍负责主题语义召回；hybrid 开启且就绪时，会额外用父 hybrid 集合补视频候选、用子 hybrid 集合补相关评论弹幕证据。三路 videoId 合并后仍按质量分形成 top20，再按 rerank 开关决定是否精排。该入口不会新建“中块 hybrid 集合”，响应 `mode` 可能是 `TOPIC_VECTOR` / `TOPIC_HYBRID` / `SQL`。

## 4. 对外接口

5.2 在 5.1 的 5 个接口（import / fetch-import / 列表 / index/rebuild / index/status）之上**新增 7 个**，统一挂 `/api/knowledge/reference-videos`：

```text
POST /search                       # 案例库检索（5.2a 起，b/c/d/e 逐刀增强同一接口）
POST /index/items/rebuild          # 子条目向量索引（增量，5.2c-1）
GET  /index/items/status           # 子条目向量索引状态（5.2c-1）
POST /index/hybrid/rebuild         # 父表原生 hybrid 索引（整库重灌，5.2d-1）
GET  /index/hybrid/status          # 父表原生 hybrid 索引状态（5.2d-1）
POST /index/hybrid/items/rebuild   # 子条目原生 hybrid 索引（整库重灌，5.2d-3）
GET  /index/hybrid/items/status    # 子条目原生 hybrid 索引状态（5.2d-3）
```

### 4.1 `POST /search` 检索

**请求体 `ReferenceVideoSearchRequest`（Jakarta Validation）**

| 字段 | 类型 | 校验 | 说明 |
|---|---|---|---|
| query | String | `@NotBlank` `@Size(max=500)` | 自然语言查询，必填（空查询直接 400，避免误把「列表」当「检索」） |
| category | String? | `@Size(max=64)` | 可选分区过滤 |
| tier | String? | `@Size(max=16)` | 可选层级过滤（Service 内大写归一 + 白名单 `BENCHMARK`/`COMPETITOR`/`OWN_HISTORY`，非法 → 400） |
| topK | Integer? | `@Min(1)` `@Max(50)` | 返回上限，空时用 `knowledge.rag.top-k`（默认 8） |
| strategy | String? | `@Size(max=16)` | 查询增强策略 `NONE`/`REWRITE`/`HYDE`/`MULTI_QUERY`，空时用配置默认（默认 REWRITE）；非法 → 400 |

**响应体 `ReferenceVideoSearchResponse`（6 字段）**

| 字段 | 类型 | 说明 |
|---|---|---|
| mode | String | 本次检索模式：`SQL` / `VECTOR` / `VECTOR_WITH_SQL_FALLBACK` / `HYBRID` / `HYBRID_WITH_SQL_FALLBACK` |
| strategy | String | **实际生效**的查询增强策略；走 SQL 兜底时回显 `NONE` |
| enhancedQueries | String[] | 增强后实际用于向量检索的查询（NONE / SQL 路径为空），便于核对增强是否合理、定位召回偏差 |
| items | `ReferenceVideoResponse[]` | 父表案例卡片（**复用 5.1 列表项**，前端卡片渲染零改动）；顺序即相关性 |
| evidence | `ReferenceVideoEvidence[]` | small-to-big 命中的子条目证据，按 videoId 分组、与 items 平级；无子召回 / SQL 路径为空（见下） |
| reranked | boolean | 本次是否经 qwen3-rerank 精排重排；关闭 / 失败 / SQL 路径为 false |

`ReferenceVideoEvidence`：`{ videoId, items: ReferenceVideoEvidenceItem[] }`；`ReferenceVideoEvidenceItem`：`{ itemId, content, sentiment, sourceType }`（即「这张案例卡片是被哪几条观众评论 / 弹幕召回的」）。

**错误约定**：`query` 空 / 超长、`tier` / `strategy` 非法 → 400（`ResponseStatusException`）。RAG 关 / 向量库未就绪 / rerank 失败 / 子召回失败**均不报错**——这些是降级、不是错误。

### 4.2 索引接口（3 对 rebuild/status）

| 接口 | 行为 | 关闭态 |
|---|---|---|
| `index/items/{rebuild,status}` | 子条目**增量**索引（扫 `PENDING`/`FAILED` 子条目 → 子 dense 集合 → 回写 `embedding_*`）；与父 `index/rebuild` 平行互不影响 | RAG 关 / 子库未就绪 → rebuild 400、status 200 显示未就绪 |
| `index/hybrid/{rebuild,status}` | 父表**整库重灌** hybrid 集合（drop → 自建 schema 建 → 从 MySQL 全量灌）；幂等可反复重建 | RAG/hybrid 关 → rebuild 400、status 200 显示未就绪 |
| `index/hybrid/items/{rebuild,status}` | 子条目整库重灌 hybrid 集合（同上，text=子条目原文） | 同上 |

- rebuild 请求体复用 `ReferenceVideoIndexRequest`（可空 `maxItems`，缺省用 `knowledge.rag.max-index-items`=200，硬上限 1000）；status 复用 `ReferenceVideoIndexStatusResponse`。
- **hybrid 状态语义**：hybrid 集合整库重灌、不在 MySQL 维护 per-card 状态，故 status 的 indexed/pending/failed 恒 0，`totalCount`=重灌源数量，`retrievalMode`=HYBRID/SQL；rebuild 响应给本次实际灌入数。**区别于** `index/items/*` 走子表 `embedding_status` 状态机的增量索引。

## 5. 配置键（`knowledge.rag`，全量默认关）

```yaml
knowledge:
  rag:
    enabled: ${KNOWLEDGE_RAG_ENABLED:false}                      # 业务总开关
    collection-name: ${KNOWLEDGE_RAG_COLLECTION_NAME:creator_reference_video}            # 父集合（Spring AI）
    child-collection-name: ${KNOWLEDGE_RAG_CHILD_COLLECTION_NAME:creator_reference_video_item}  # 子集合（5.2c）
    embedding-dimension: ${LLM_EMBEDDING_DIMENSIONS:1024}        # 与 Embedding 输出维度同源
    index-batch-size: ${KNOWLEDGE_RAG_INDEX_BATCH_SIZE:10}       # Qwen 兼容模式单批硬上限 10
    initialize-schema: ${KNOWLEDGE_RAG_INITIALIZE_SCHEMA:true}
    milvus: { host, port, username, password, database-name }    # 复用 MILVUS_* 环境变量
    # top-k(8) / min-vector-hit-count(3) / max-index-items(200) 走 Java 默认，未入 yml（需调再补绑定）

    # —— 5.2b 查询增强 ——
    query-enhancement:
      strategy: REWRITE          # 默认策略（Java 默认，未入 yml）；NONE/REWRITE/HYDE/MULTI_QUERY
      multi-query-count: 3       # MULTI_QUERY 条数上限（Java 默认）

    # —— 5.2e Rerank 精排（默认关）——
    rerank:
      enabled: ${KNOWLEDGE_RAG_RERANK_ENABLED:false}
      model: ${KNOWLEDGE_RAG_RERANK_MODEL:qwen3-rerank}          # 老 gte-rerank 已于 2026-05-30 下线
      base-url: ${...:https://dashscope.aliyuncs.com/compatible-api/v1}  # compatible-api（≠chat 的 compatible-mode）
      api-key: ${KNOWLEDGE_RAG_RERANK_API_KEY:${LLM_API_KEY:}}   # 默认复用 LLM 网关同一个 DashScope Key
      candidate-pool-size: ${...:20}                             # retrieve-wide 候选池
      timeout-ms: ${...:10000}

    # —— 5.2d 原生 dense+BM25 hybrid（默认关，需 Milvus 服务端 ≥2.5）——
    hybrid:
      enabled: ${KNOWLEDGE_RAG_HYBRID_ENABLED:false}             # 双开关：还需 knowledge.rag.enabled=true
      collection-name: ${...:creator_reference_video_hybrid}     # 父 hybrid 集合（自建 schema）
      child-collection-name: ${...:creator_reference_video_item_hybrid}  # 子 hybrid 集合（5.2d-3）
      text-max-length: ${...:65535}                              # BM25 text 字段 VarChar 上限（中文多字节）
      analyzer-type: ${...:chinese}                              # 中文分词器（无空格中文需中文分析器，否则 BM25 召回差）
```

## 6. 双开关、检索模式与优雅降级

| RAG | hybrid | rerank | 父召回走 | mode 可能值 |
|---|---|---|---|---|
| 关 | — | — | 不召回 | `SQL`（纯关键词兜底） |
| 开 | 关 | 关 | Spring AI dense（5.2a/b/c） | `VECTOR` / `VECTOR_WITH_SQL_FALLBACK` |
| 开 | 关 | 开 | Spring AI dense + rerank | 同上，`reranked=true` |
| 开 | 开 | 关/开 | 原生 dense+BM25+RRF（5.2d） | `HYBRID` / `HYBRID_WITH_SQL_FALLBACK` |

- **零回归关键点**：顶层 gate 为 `!hybridEnabled && vectorStore==null → SQL`。hybrid 关时 `hybridEnabled=false`，判断退化为 5.2a 原式 `vectorStore==null → SQL`，**字节级零回归**；hybrid 开时即便 Spring AI 老父库未就绪也能进向量链路（hybrid 用独立 v2 client / 独立集合）。
- **`HYBRID` 与 `VECTOR` 物理隔离**：hybrid 走 `KnowledgeHybridStore`（`MilvusClientV2` + 自建 schema 集合 `creator_reference_video_hybrid`），dense 走 `KnowledgeVectorStore`（Spring AI `MilvusVectorStore` + 集合 `creator_reference_video`）。迁移期两条路径并存，靠开关切换。
- **隔离铁律**：知识库向量库**不是** `VectorStore` 类型 Spring Bean，一切检索经 `KnowledgeVectorStore` / `KnowledgeHybridStore`，**不能**注入 `ObjectProvider<VectorStore>`（那是反馈侧集合，多一个 Bean 会打断反馈注入）。

## 7. 五刀切片速览

| 刀 | 做了什么 | 动存储 | 核心产出 |
|---|---|---|---|
| **5.2a** 最小检索闭环 | dense 语义检索父表 + SQL 关键词兜底 + 模式回显 | 否（复用 5.1c 父索引） | `POST /search` + 三段式 + 三态 mode |
| **5.2b** 查询理解 | 查询改写 / 多查询 / HyDE 三策略可切换（Spring AI 原生 Modular RAG 组件 + 中文 prompt） | 否 | `enhance(query,strategy)→List<String>` 统一抽象；多路召回 LinkedHashSet 去重（无 RRF） |
| **5.2c** 父子召回 | 子表向量化进独立子集合（c-1）+ small-to-big 召回 + 证据回显（c-2，方案 a：顶层 `evidence`） | 是（子集合） | 「卡片整体不匹配、但内部某条评论精确命中」的案例被**新增**召回，并回显观众原话证据 |
| **5.2d** 原生混合检索 | `MilvusClientV2` 自建 schema（dense+sparse+BM25 Function）整库重灌；父召回（d-2）+ 子召回（d-3）都迁 hybrid | 是（父/子 hybrid 集合） | 正统 dense+BM25+RRF，召回兼顾语义与关键词 |
| **5.2e** Rerank 精排 | qwen3-rerank 对候选精排（retrieve-wide → rerank → 截 topK） | 否 | 用原始 query 重排候选，`reranked` 回显是否生效 |

> 切片正交、可叠加：5.2e 与查询增强 / hybrid 自动兼容（候选都走同一 rerank 段）；5.2d 接入只换父/子召回数据源，下游回查 / 合并 / rerank / 证据零改（`videoId` 窄腰）。

## 8. 前端面板（`KnowledgeWorkspace.vue`）

- **检索区**（插在向量索引与案例列表之间）：查询输入框 + 分区 / 层级过滤 + **策略下拉**（默认 / 查询改写 / HyDE / 多查询）+「检索」按钮。
- **结果区**：复用案例卡片样式 + 顶部三类回显标签——**mode chip**（语义检索 / 原生混合 / 兜底 / 混合+兜底）、**增强策略标签** + 扩展查询回显、**「已精排 · qwen3-rerank」标签**（`reranked=true` 时）。
- **主题优先检索区**：`/topic-search` 的 mode chip 会区分“主题向量检索”和“主题混合检索”；后者表示父 / 子 hybrid 已参与本次候选或证据补召回。
- **召回证据**：每张检索结果卡片底部，若该 videoId 有 `evidence`，展示「召回证据 · 观众原话」引用条（正 / 负向用不同色 chip 区分）；无证据的卡片不显示。
- **索引面板**：在 5.1「向量索引」区下，新增「子条目索引」「原生 hybrid 索引」「子条目 hybrid 索引」三块（均镜像父索引的刷新 / 重建按钮 + 状态 chip，数据源分别指向对应 `/index/*` 接口）。
- 客户端 `api/knowledge.ts` + `types/knowledge.ts` 同步加检索 / 索引函数与类型；空过滤项不下发。**不动**创作工作台侧。

## 9. 本阶段不做

- 正式跨增强查询的 RRF 加权（多查询合并仍是 LinkedHashSet 朴素去重；hybrid 单查询内部已 RRF）。
- 查询增强 / 证据的缓存与限流、子召回的请求级开关 / A/B 对照字段、`maxIndexItemsChild`/`childTopK` 独立调参（实测需要再加，简单优先）。
- Agent 工具化与接入发布前优化 / 竞品（5.3）、知识库管理后台（5.4）、跨创作者权限隔离、多模态评分。
