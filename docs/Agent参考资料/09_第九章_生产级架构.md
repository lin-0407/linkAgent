# 第 9 章 生产级架构

## 9.0 概述

前 8 章让 Agent 系统"能干活、能上线、能扛流量、能算成本"——第 9 章让它"上线后第二天还活着"。五条并行补丁，无先后依赖。

| 暴露场景 | 问题 | 对应 |
|---|---|---|
| 用户盯空白屏幕等 5 秒 | LLM 非 ms 级响应 | **9.1 流式 SSE** |
| V26 任务执行一半服务重启 | 状态在 JVM 内存 | **9.2 异步+状态持久化** |
| 用户重复点 5 次提交 | 无幂等保护 | **9.3 幂等设计** |
| 另一团队想复用工具 | 工具与 Agent 强耦合 | **9.4 MCP 协议** |
| prompt injection 攻击 | LLM 无法区分指令/数据 | **9.5 安全防护** |

---

## 9.1 流式输出 SSE

**核心问题**：LLM 回答 3-8 秒，阻塞返回用户盯空白屏幕。流式 200ms 首字、边生成边显示。

### 关键 API

| 链式调用 | 返回类型 | 用途 |
|---|---|---|
| `.stream().content()` | `Flux<String>` | 纯文本 delta 推前端 |
| `.stream().chatResponse()` | `Flux<ChatResponse>` | 要 metadata |
| `.stream().chatClientResponse()` | `Flux<ChatClientResponse>` | 要 advisor context |

每帧是 incremental delta（OpenAI 协议），前端自行拼接。Spring MVC（Tomcat）不必切 WebFlux 就能返回 `Flux<String>`——Spring 6.x 通过 `ReactiveTypeHandler` + Servlet 3.1 异步 I/O 原生支持。

### 最小 SSE Controller

```java
@GetMapping(value = "/v26/ask-stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> ask(@RequestParam Long userId, @RequestParam String q) {
    return chatClient.prompt().user(q)
            .advisors(spec -> spec.param(CostAdvisor.USER_ID_KEY, userId))
            .stream().content();
}
```

**token usage 只在最后一帧**：中间帧 `getUsage()` 返回 `Usage.NULL`（Spring AI 空对象，非 Java null）。

### 流式 + Tool calling

默认 `internalToolExecutionEnabled=true`——Spring AI 内部 loop 透明执行 tool call，用户 `Flux<String>` 只看到最终文本。`.chatClientResponse()` 可能泄出 `hasToolCalls()==true` 中间帧需 filter。

## 9.2 异步 + 状态持久化

**核心问题**：V26 OrchestrationState 在 JVM 内存，kill -9 全丢。改造为事件溯源轻量版——每步 Worker 完成写 DB，重启按 taskId 读快照续跑。

### 接口改造

同步 `POST /v26/ask`（阻塞 30s）拆为两个接口：
- `POST /v26/submit` → 返回 taskId（~50ms），任务未跑就 insert PENDING
- `GET /v26/tasks/{taskId}/stream` → SSE 推每步进度

### OrchestrationState 持久化

```java
@Entity @Table(name = "agent_task")
public class AgentTaskEntity {
    @Id private String taskId;
    @Enumerated(EnumType.STRING) private Status status; // PENDING/RUNNING/COMPLETED/FAILED
    @Column(columnDefinition = "jsonb")
    private OrchestrationState state;
    private String finalAnswer;
    @Version private Long version; // 乐观锁，必装
}
```

### Worker 改造为事件溯源模式

每步一次事务：load state → 执行下一步 Worker → advance state → save。commit 后下一步前服务挂了也只丢"这一步还没存"的 Worker 结果。

**关键**：resume 时 LLM 调用不能重跑。OrchestrationState 必须把 WorkerResult 完整序列化进 state（含 LLM 摘要、structured output、token usage），下游 Worker 读 `state.findOutput(callId)` 拿到一致输入。

**乐观锁的定位**：多副本部署 + `@Scheduled resumeOrphanTasks` 同跑时，`@Version Long version` 让后写抛 `OptimisticLockingFailureException`，抓住退出不双写。但乐观锁只挡 DB 写入冲突，不挡外部 side-effect——需 9.3 幂等兜底。

### 耗时分档

| 任务预期耗时 | 推荐模式 |
|---|---|
| < 2s | 同步阻塞 |
| 2-10s | 同步 + 流式 SSE（9.1） |
| 10-60s | 异步 + 持久化 + SSE 进度（本节） |
| > 60s | 异步 + 持久化 + WebSocket/邮件通知 |

## 9.3 幂等设计

**核心问题**：幂等 = 同一请求重复执行 N 次和执行 1 次的最终效果一样。LLM Agent 必须在三层同时保护。

### L1 HTTP 层：requestId 去重

```java
@Component
public class IdempotencyFilter implements Filter {
    // X-Idempotency-Key → Redis SETNX → 已存在返回 425/缓存结果
}
```

前端每次点击生成 UUID 当 `X-Idempotency-Key`，重试复用同一 key。不要用 `userId + endpoint` 当 key。

### L2 Worker 层：callId 唯一索引

防 9.2 resume 时两个副本同时跑同一 task 的同一 step：

```java
@Entity @Table(name = "processed_worker_call",
    indexes = @Index(columnList = "taskId,callId", unique = true))
public class ProcessedCall {
    @Id private String id; // taskId+callId 拼接
    @Column(columnDefinition = "jsonb") private WorkerResult result;
}
```

双保险：findById 命中跳过（省 LLM 调用），unique 索引兜底（防 findById 和 save 之间竞态窗口）。

### L3 Tool 层：业务侧自己幂等

Tool 调外部服务时必须传业务系统自己的 idempotencyKey。Worker 调用时传 callId 当 idempotencyKey：`taskId + "-" + callId`。

Tool 分三类：**天然幂等**（query/findOrder，不用改）、**覆盖式幂等**（update/设置状态，通常不用改但确认非递增语义）、**必须改造**（create/发钱/发消息/placeOrder）。

**反直觉点**：幂等 ≠ retry safe——retry 时生成新 idempotencyKey 会让下游当新请求执行两次；幂等表 TTL 太短异步任务跑 30 分钟后过期；idem 表 INSERT 已 commit 但业务 INSERT 未 commit JVM 挂。

## 9.4 MCP：工具的"USB-C 接口"

**核心问题**：V26 的 `@Tool` 与 Agent 进程焊死，跨团队复用要么复制代码、要么自搭 RPC。MCP（Model Context Protocol，Anthropic 2024-Q4 推出）把工具拆成独立服务。

### 协议四元素

| 元素 | 语义 | 何时用 |
|---|---|---|
| **Tools** | 可调用动作（RPC 方法） | 99% 项目用到 |
| **Resources** | 可读取数据（HTTP GET/URI 寻址） | 跨团队工具市场 |
| **Prompts** | 可复用模板 | Server 端定义 prompt 复用 |
| **Completions** | 补全建议 | IDE 自动补全 |

### 最小 OrderMcpServer

依赖：`spring-ai-starter-mcp-server-webmvc`。`@Tool` 方法一行不改变成跨进程可调用的 MCP Tool。

```yaml
spring:
  ai:
    mcp:
      server:
        name: order-mcp-server
        version: 1.0.0
        type: SYNC
        protocol: SSE                # 1.1 还可选 STREAMABLE（推荐生产）/STATELESS
        capabilities:
          tool: true
```

### V26 App 改造为 MCP Client

```yaml
spring:
  ai:
    mcp:
      client:
        type: SYNC
        sse:
          connections:
            order-server:   { url: http://localhost:8090 }
            refund-server:  { url: http://localhost:8091 }
```

```java
@Bean
ChatClient defaultChatClient(ChatClient.Builder builder,
                              List<McpSyncClient> mcpClients,
                              CostAdvisor costAdvisor) {
    return builder
            .defaultAdvisors(costAdvisor)
            .defaultToolCallbacks(new SyncMcpToolCallbackProvider(mcpClients))  // 非 .defaultTools()
            .build();
}
```

**必须用 `.defaultToolCallbacks(...)` 不要用 `.defaultTools(...)`**——后者有重载接 `Object...`，会静默吞掉 `ToolCallbackProvider`（issue #2543）。

### 传输协议选型

| 协议 | 场景 |
|---|---|
| STDIO | Claude Desktop/本地 IDE 插件 |
| SSE (WebMVC) | 学生/入门/单实例 Server |
| Streamable HTTP (1.1 新) | **生产推荐** |
| Stateless Streamable (1.1 新) | 横向扩缩容 Server |

### 拆 MCP 要重做的四件事

1. **鉴权**：同进程靠 Java 方法访问权限，跨进程必须 OAuth2/API key
2. **错误处理**：跨进程规范化错误码，不暴露 stack trace
3. **幂等键传递**：跨进程后在 `@ToolParam` 显式声明
4. **超时和重试**：client 端超时默认 30s，重试要保幂等

### 判断标准

问"未来 12 个月内会不会有第二个 Agent 应用调这个工具"——会就拆 MCP，不会就留 `@Tool`。不要为想象中的复用提前拆。

## 9.5 安全防护：三层防御

**核心问题**：LLM 无法可靠区分"系统指令"和"用户输入"——把整个 context 当 prompt 处理。目标不是 100% 防住攻击，是把单层失守影响面降到可接受。

### L1 InputGuard：输入审查

双层检测：关键词/正则（<1ms，挡 60% 已知模式）+ LLM 分类（30-100ms，挡花样）。

```java
@Component
public class InputGuardAdvisor implements CallAdvisor, StreamAdvisor {
    @Override public int getOrder() { return Ordered.HIGHEST_PRECEDENCE; }

    @Override
    public ChatClientResponse adviseCall(ChatClientRequest request, CallAdvisorChain chain) {
        String userInput = extractUserText(request);
        if (KEYWORD_BLACKLIST.matcher(userInput).find()) return refuse(request, "敏感指令模式");
        if (isInjectionAttempt(userInput)) return refuse(request, "可能的注入攻击");
        return chain.nextCall(request);
    }
}
```

### L2 ToolGuard：工具白名单 + 风险分级（OWASP LLM06 直接对策）

```java
@Retention(RUNTIME) @Target(METHOD)
public @interface RiskLevel {
    Level value() default Level.READ;
    enum Level { READ, WRITE, SIDE_EFFECT }
}
```

| 风险 | 准入策略 |
|---|---|
| **READ**（findOrder/getUserProfile） | 任何认证用户可调 |
| **WRITE**（updateOrderStatus/setPreference） | 资源 owner/客服可调 |
| **SIDE_EFFECT**（initiateRefund/sendSms/deleteAccount） | **需人工二次确认** + 强日志 |

SIDE_EFFECT 工具的"二次确认"不能让 LLM 自己决定——前端看到 `PENDING_CONFIRMATION` 状态时强制弹出确认 UI。

### L3 OutputGuard：敏感输出过滤

检测类别：PII（身份证号/银行卡号/手机号/邮箱——正则）、凭据（API key/JWT/AWS access key——正则前缀特征）、内部 URL/IP。

流式场景更难：delta 帧可能切碎敏感串。优先用滑动 buffer 延迟发送最后 N 字符等下一帧再判（N=32 覆盖最长 PII 模式）。

### 四条铁律

1. **安全是 Day 0 不是 Day N+1**——L1 InputGuard 第一天就装
2. **不要依赖单一防线**——三层都要装，纵深防御是唯一可行策略
3. **攻击者也用 LLM**——2025 起 jailbreak 大量来自 LLM 自动生成的对抗 prompt
4. **审计 + 行为分析是终极兜底**——所有触发都带 traceId + userId 日志

## 9.6 引入时机矩阵

| 阶段 | 9.1 SSE | 9.2 异步持久化 | 9.3 幂等 | 9.4 MCP | 9.5 安全 |
|---|---|---|---|---|---|
| **POC** | 可选 | 不装 | 不装 | 不装 | **L1 InputGuard 装** |
| **MVP** | **装** | 不装 | L3 装（涉及钱） | 不装 | L1+L3 装 |
| **规模化** | 装 | **装**（任务 > 10s） | **三层都装** | 看复用需求 | **三层都装** |
| **生产** | 装+滑窗 OutputGuard | 装+多副本乐观锁 | 三层+跨服务透传 | **装**（跨团队） | **三层+间接注入防护** |

安全是 Day 0——L1 InputGuard 公开环境就装；最后才 MCP——没复用需求别提前拆。

### 五个跨补丁组合坑

1. **流式+异步混淆**：同时上 9.1 和 9.2 后简单查询走 submit→stream 反而比阻塞版慢。服务端显式区分 `/ask-stream` 和 `/submit` 两套端点
2. **持久化 resume + CostAdvisor 同步扣减 = 重启账单跳变**：异步任务成本在 `agent_task` 实体上单独累加 `accumulatedCostUsd`
3. **MCP 拆出 + L1 HTTP 幂等失效**：拆 MCP 后幂等防御只能靠 L3（idempotencyKey 由 LLM 显式传）
4. **ToolGuard 包装 + MCP ToolCallback 注入 = 风险分级失效**：推荐按风险等级拆分 MCP Server（OrderMcpServer 只放 READ，RefundMcpServer 只放 SIDE_EFFECT）
5. **InputGuard 装 ChatClient 入口 + RAG 文档绕过**：文档入库前做 InputGuard 扫描 + RAG 检索后拼 prompt 前 `DocumentPostProcessor` 二次扫描 + system prompt 加结构化定界符
