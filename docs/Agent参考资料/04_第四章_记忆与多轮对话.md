# 第 4 章 记忆与多轮对话：ChatMemory + Advisor

> **核心命题**：LLM HTTP 接口永远无状态。"记忆"= 客户端持有一份对话数组 + 每轮原样重发。工程任务：**存**（按 conversationId 分组攒消息）+ **取并重放**（下次同会话塞回 messages 数组）。版本基线 Spring AI **1.1.4**。

---

## 4.1 三层抽象的正交设计

| 层 | 接口 | 职责 | 不管什么 |
|---|---|---|---|
| **切面层** | `Advisor` (实际用 `BaseAdvisor`) | 在 ChatClient 调用前后切入：取历史塞 Request、写回 Response | 怎么淘汰、存哪里 |
| **策略层** | `ChatMemory` | 淘汰策略（窗口/摘要/Token计算）、SystemMessage 保护 | 落到磁盘还是内存 |
| **存储层** | `ChatMemoryRepository` | 存储介质（Map/JDBC/Cassandra/Mongo） | 什么时候淘汰 |

三层各管一件事、正交可替换：从 InMemory 切到 JDBC，业务代码一行不动。

```java
// 存储层接口
public interface ChatMemoryRepository {
    List<String>  findConversationIds();
    List<Message> findByConversationId(String conversationId);
    void          saveAll(String conversationId, List<Message> messages); // 整体替换语义
    void          deleteByConversationId(String conversationId);
}

// 策略层接口
public interface ChatMemory {
    void          add(String conversationId, List<Message> messages);
    default void  add(String conversationId, Message message) { add(conversationId, List.of(message)); }
    List<Message> get(String conversationId);
    void          clear(String conversationId);
}
```

两个关键细节：(1) `Repository.saveAll` 是整体替换语义 —— load → append → 截断 → saveAll；(2) `ChatMemory.get` 在 1.1 里没有 `lastN` 参数，"取多少条"是策略层内部的事。

## 4.2 版本演化：V10 → V14 问题驱动

| 版本 | 改动 | 暴露的新问题 |
|---|---|---|
| **V10** | 业务代码自己 `ConcurrentHashMap<sessionId, List<Message>>` 维护历史 | 六问题（见 4.3） |
| **V11** | 引入 `ChatMemory` + `InMemoryChatMemoryRepository` + `MessageWindowChatMemory` | 业务代码仍手动 add/get，样板没消 |
| **V12** | `MessageChatMemoryAdvisor` 接管"取历史+写回"，业务代码彻底干净 | 重启失忆；tool calling 中间消息不自动持久化 |
| **V13** | `JdbcChatMemoryRepository` 持久化 | 长对话 token 爆炸、关键事实被窗口截断 |
| **V14** | 自研 `SummarizingChatMemoryAdvisor` 摘要压缩 | 摘要必有损（第 5 章 RAG 检索式记忆补齐） |

## 4.3 V10 暴露的六个生产问题

1. **同一 sessionId 并发写**：两个线程拿到同一个 ArrayList 引用，并发 `add` 导致消息错乱/丢失
2. **永不淘汰 → OOM**：横向（sessionId 数量永远增长）+ 纵向（每个 list 无上限）
3. **无 token 预算意识**：每轮重发整段历史，N 轮总成本 ≈ O(N²)
4. **工具消息默认记不住**：`call().content()` 只返回最后一条带文本的 assistant 消息，中间的 `AssistantMessage(toolCalls)` 和 `ToolResponseMessage` 全不在返回值里。`MessageChatMemoryAdvisor` 也不自动保存这些中间消息
5. **SystemMessage 只在首次写一次**：业务想换 prompt 时改不动老会话
6. **多实例部署失忆**：`ConcurrentHashMap` 进程内，实例间不共享

## 4.4 V11：ChatMemory + Repository 归位

### 装配

```java
@Configuration
public class ChatMemoryConfig {
    @Bean
    public ChatMemoryRepository chatMemoryRepository() {
        return new InMemoryChatMemoryRepository();
    }

    @Bean
    public ChatMemory chatMemory(ChatMemoryRepository repo) {
        return MessageWindowChatMemory.builder()
                .chatMemoryRepository(repo)
                .maxMessages(20)
                .build();
    }
}
```

### SystemMessage 自动替换语义

`MessageWindowChatMemory` 收到新 `SystemMessage` 时，先移除已有的所有 SystemMessage 再追加新的。窗口截断时 SystemMessage 永不淘汰。这一语义同时解决：热切 system prompt 无需手动替换旧 system、长对话 system 永远不丢、V14 摘要写回时新摘要自动替换旧摘要不堆积。

## 4.5 为什么"取记忆/写回记忆"必须是 Advisor

五种"看似可行但不对"的方案：

| 方案 | 致命缺陷 |
|---|---|
| A 抽 `MemoryHelper` 工具方法 | 无强制性；参数列表膨胀；看不到 tool 循环 |
| B 包 `MemoryAwareChatClient` | 绕开 ChatClient fluent API；多个横切点堆成 God Class |
| C Spring AOP 切 `chat()` 方法 | 切点太粗；看不到 ChatClient 内部 tool 循环 |
| D 继承 `ChatModel` 重写 `call()` | 没有 conversationId 概念；晚于 ChatClient tool 循环 |
| E HTTP Filter | 太外层看不到 Java 对象；耦合 Web 层 |

**正确位置**：Advisor — 在 ChatClient 调用链之内、官方预留挂钩、可链式叠加。调用栈位置：`业务代码 → Advisor 链(按 order 排序) → ChatClient 内部 tool calling 自动循环 → ChatModel(HTTP 调 LLM)`。

## 4.6 V12：MessageChatMemoryAdvisor + Advisor API

### 接口骨架

- `BaseAdvisor`（99% 场景）：同时实现 Call + Stream，提供 `before(req)` / `after(resp)` 钩子
- `CallAdvisor`：只关心同步 `.call()`；`StreamAdvisor`：只关心流式 `.stream()`
- `ChatClientRequest request`（不可变快照）：`request.prompt()` 含 messages；`request.context()` 是 `Map<String,Object>`，conversationId 放在这里（key=`ChatMemory.CONVERSATION_ID`）
- `CallAdvisorChain chain`：必须主动调 `chain.nextCall(newRequest)` 才会推进；不调 = 吞请求

> `request.context()` 与 `ToolContext` 是两回事：ToolContext 给 `@Tool` 方法；advisor context 给 Advisor。两者都不进 schema、不进 messages。

### MessageChatMemoryAdvisor 内部逻辑（教学伪代码）

before: 写 user → 取历史 → 重建 prompt；after: 写 assistant。三行核心动作对应 V11 的"add user / get / add assistant"。

### V12 最终代码

```java
@Configuration
public class V12ChatClientConfig {
    @Bean
    public ChatClient chatClient(ChatClient.Builder builder, ChatMemory memory) {
        return builder
                .defaultSystem("你是 XX 商城客服助手...")
                .defaultAdvisors(MessageChatMemoryAdvisor.builder(memory).build())
                .build();
    }
}
```

业务代码五行链式调用，记忆完全隐身：

```java
public String chat(String conversationId, Long userId, String question) {
    return chatClient.prompt()
            .user(question)
            .tools(orderTools, refundTools)
            .toolContext(Map.of("userId", userId))
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
            .call()
            .content();
}
```

### 多 Advisor 链 —— order 规则

before 阶段：order 小的先执行；after 阶段：反向（order 小的后执行，洋葱模型）。生产建议：`< 0` 限流/鉴权、`0~100` 记忆类、`100~1000` RAG/Prompt 增强、`> 10000` 调用日志/token 统计。

## 4.7 V13：JdbcChatMemoryRepository

内置六种 `ChatMemoryRepository`：InMemory、JDBC、Cassandra、Neo4j、Mongo、CosmosDB。中小团队没特殊理由就走 JDBC。

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/agent_demo
  ai:
    chat:
      memory:
        repository:                    # ⚠️ 1.1 多了 .repository. 这一层
          jdbc:
            initialize-schema: always  # embedded(默认) / always / never
```

> **⚠️ 1.0 → 1.1 配置项变更**：旧前缀 `spring.ai.chat.memory.jdbc.*` → 新前缀 `spring.ai.chat.memory.repository.jdbc.*`（多了 `.repository.`）。

默认表名 `SPRING_AI_CHAT_MEMORY`，列：`conversation_id VARCHAR(36)`、`content TEXT`（不叫 `messages`）、`type VARCHAR(10)`（USER/ASSISTANT/SYSTEM/TOOL）、`timestamp TIMESTAMP`。

引入 starter 后自动注册 `ChatMemoryRepository` Bean，业务代码一行不动——兑现三层图的"换实现就是改一个 `@Bean`"。

**新问题——窗口截断丢关键事实**：`MessageWindowChatMemory` 先进先出固定窗口，不知道哪条消息更重要。两条解决路径：摘要压缩（V14，把被淘汰旧消息让 LLM 总结成一段塞回 system 区）+ 检索式记忆（第 5 章 RAG，向量化存 VectorStore 按语义检索）。

## 4.8 V14：摘要压缩 —— 自研 SummarizingChatMemoryAdvisor

> **[工程建议]**。`SummarizingChatMemoryAdvisor` 不是 Spring AI 内置，需自己写 Advisor。目的：解决窗口截断丢事实痛点。

**设计要点**：
- **触发条件**：`triggerSize`（消息数超此触发，如 30）+ `keepRecent`（保留最近 K 条原文，如 10）。参考起点：`maxMessages=50, triggerSize=30, keepRecent=10`
- **摘要模型**：用便宜小模型（gpt-4o-mini / DeepSeek-V3），不用主对话旗舰模型
- **防递归**：摘要必须用**独立的、不挂任何 ChatMemory 相关 Advisor 的** `ChatClient`
- **摘要存储**：利用 SystemMessage 自动替换语义，把"原始 system + 摘要"拼成一条新 SystemMessage

**完整代码** (SummarizingChatMemoryAdvisor)：before 钩子中取消息 → 超阈值则切分（前段进摘要、后段保留原文）→ 调便宜模型生成摘要（保留订单号/金额/用户决定/未完成事项；丢弃寒暄/重复确认/客套话）→ clear + 写回 `[sys+摘要, ...keepRecent条原文]`。装配时 order=-100 先于 MessageChatMemoryAdvisor(默认 0) 执行。

**局限**：摘要必有损、摘要本身花钱花时间、摘要的摘要会失真。更准的方案是检索式记忆（第 5 章 RAG）。

## 4.9 六条核心心智

1. **记忆不是模型给的，是客户端给的。** LLM HTTP 接口永远无状态。
2. **三层抽象正交、可替换。** Advisor（切面）/ ChatMemory（策略）/ ChatMemoryRepository（存储）。
3. **Advisor 是 ChatClient 调用链里的官方切面。** `BaseAdvisor.before/after` 是写自定义 Advisor 的首选基类。
4. **业务代码不该手碰记忆。** V12 用 `MessageChatMemoryAdvisor` 后业务代码 0 行碰记忆。
5. **两条独立的"调用作用域"侧信道。** Advisor 上下文（`.advisors(a -> a.param(...))`）vs Tool 上下文（`.toolContext(...)`），各管各的。
6. **SystemMessage 自动替换语义在三个地方救命。** 热切 prompt、长对话 system 不丢、摘要写回时不堆积。
