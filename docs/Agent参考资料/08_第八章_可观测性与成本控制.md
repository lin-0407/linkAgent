# 第 8 章 可观测性与成本控制

## 8.1 五层模型总览

用 L1-L5 五层（横切关注点，非 Agent 版本号）解决 5 个上线必需问题：单次请求 token/cost、慢节点定位、用户滥用检测、流量突变应对、跨 Agent 调用链追踪。

| 层 | 名称 | 核心交付 |
|---|---|---|
| L1 | Observation | 零代码暴露 metric——看到每个 Agent/Tool/Advisor 耗时和错误率 |
| L2 | Trace | traceId 跨 Agent 透传——单次请求所有 LLM 调用串成树 |
| L3 | Cost | token 计费 + per-user 预算——token×单价 + 预算前置检查 |
| L4 | RateLimit+降级链 | 限流 + 4 档降级——自动切便宜模型/缓存/静态兜底 |
| L5 | Dashboard | Grafana 12 panel + 4 告警——一块板子看清全貌 |

核心原则：L3 是核心（LLM 时代独有的"钱"问题），降级链每往后一档质量降一截成本降一档，可观测性成熟度应落后业务复杂度一个阶段。

## 8.2 Spring AI 1.1+ 已内置的 Observability 信号

Spring AI 1.1.4 在 ChatClient、Advisor、ChatModel、Tool、VectorStore、EmbeddingModel 上全部内置 micrometer-observation 埋点。加 `spring-boot-starter-actuator` + `micrometer-registry-prometheus` 即可产出，无需任何 `@Bean` 或 `@Observed`。

### 核心 Observation 名称（1.1.4 实测）

| Observation | 产出位置 | trace 角色 |
|---|---|---|
| `spring.ai.chat.client` | `ChatClient.call()`/`.stream()` | 最外层 span |
| `spring.ai.advisor` | 每个 advisor 执行 | 中间 span |
| `gen_ai.client.operation` | ChatModel/EmbeddingModel/ImageModel 共用 | 内层 span(HTTP 调用) |
| `spring.ai.tool` | `@Tool` 方法回调 | 叶子 span |

反直觉：EmbeddingModel 无独立 observation 名，与 ChatModel 共用 `gen_ai.client.operation`，靠 tag `gen_ai.operation.name`（取值 `chat`/`embedding`/`framework`）区分。

### 关键 Metric：`gen_ai.client.token.usage`

Histogram，单位 `{token}`，tag `gen_ai.token.type` 取值 `input`/`output`/`total`。这是 L3 Cost 计算的数据底层。

### 敏感内容默认关闭（重要）

prompt/completion/advisor 入参/vector query 内容默认不记录，生产绝对不要打开。

| 配置项（1.1.x 统一为 `log-*` 命名） | 默认 |
|---|---|
| `spring.ai.chat.client.observations.log-prompt` | `false` |
| `spring.ai.chat.client.observations.log-completion` | `false` |
| `spring.ai.chat.observations.log-prompt` | `false` |
| `spring.ai.chat.observations.log-completion` | `false` |

## 8.3 L1 Observation：零代码暴露 Metric

### 配置

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics      # 默认只暴露health/info
  endpoint:
    prometheus:
      access: read_only
  metrics:
    tags:
      application: ${spring.application.name}
      env: ${ENV:dev}
      instance: ${HOSTNAME:local}
  server:
    port: 9090                                       # actuator 独立端口
```

不加 `exposure.include: prometheus` 则端点 404。

### 验证清单：5 个一定能看到的 metric

| Metric 前缀 | 没看到说明什么 |
|---|---|
| `gen_ai_client_operation_seconds_*` | ChatModel 没调用 |
| `gen_ai_client_token_usage_*` | Provider 没返回 usage |
| `spring_ai_chat_client_*` | ChatClient 完全没被调用 |
| `spring_ai_advisor_*` | 没挂任何 Advisor |
| `spring_ai_tool_*` | 没触发工具调用 |

Prometheus 文本格式里点号全被替换成下划线——`gen_ai.client.token.usage` 输出为 `gen_ai_client_token_usage`。

## 8.4 L2 Trace：traceId 跨 Agent 透传

### 依赖

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>
```

加完自动完成：创建 OTel SDK、Micrometer Observation span 桥接、通过 `Slf4JEventListener` 把 `traceId`/`spanId` 注入 SLF4J MDC。

### 配置

```yaml
management:
  tracing:
    sampling:
      probability: 1.0                                # dev全采，生产回默认0.10
  otlp:
    tracing:
      endpoint: http://localhost:4318/v1/traces
```

### 关键补丁：跨虚拟线程 trace 透传（V25 必修）

Java 21 虚拟线程不携带 ThreadLocal，Micrometer Observation 当前 span 存在 ThreadLocal 里，`newVirtualThreadPerTaskExecutor()` 不自动复制→并发任务 span 变成孤儿 root trace。

**修复**：用 `ContextExecutorService` 包装 executor。

```java
import io.micrometer.context.ContextExecutorService;
import io.micrometer.context.ContextSnapshot;

ExecutorService vt = Executors.newVirtualThreadPerTaskExecutor();
this.executor = ContextExecutorService.wrap(vt, ContextSnapshot::captureAll);
```

所有 `CompletableFuture.*Async` 方法必须显式传带 context 的 executor。

## 8.5 L3 Cost：Token 计费 + Per-User 预算（本章核心）

三个组件闭环：`PricingCatalog`（token×单价=钱）→ `CostAdvisor`（前置预算检查+后置扣减）→ `CostRepository`（per-user-per-day 累积存储）。

### PricingCatalog：价目表用配置而非代码

```yaml
agent:
  pricing:
    catalog:
      gpt-4o-mini:        { prompt: 0.000150, completion: 0.000600 }
      gpt-4o:             { prompt: 0.002500, completion: 0.010000 }
      deepseek-chat:      { prompt: 0.000027, completion: 0.000110 }
      claude-haiku-4-5:   { prompt: 0.001000, completion: 0.005000 }
    default-model: gpt-4o-mini
    unknown-model-policy: STRICT     # STRICT=未配置抛异常 / LENIENT=按default-model算
```

金钱计算一律 BigDecimal；`unknown-model-policy` 默认 STRICT。价目表更新日期写在 yaml 注释 + startup 时 INFO 日志打出。

### CostAdvisor（核心）

```java
@Component
public class CostAdvisor implements CallAdvisor {  // 不能继承BaseAdvisor——短路逻辑失效
    public static final String USER_ID_KEY = "userId";

    @Override public int getOrder() { return Ordered.HIGHEST_PRECEDENCE + 100; }

    @Override
    public ChatClientResponse adviseCall(ChatClientRequest request, CallAdvisorChain chain) {
        Long userId = (Long) request.context().get(USER_ID_KEY);
        if (userId == null) return chain.nextCall(request);

        // 前置：查当日累积，超额则短路返回（L4降级链接管）
        BigDecimal spent  = repo.getTodaySpend(userId);
        BigDecimal budget = policy.dailyBudgetOf(userId);
        if (budget != null && spent.compareTo(budget) >= 0) {
            ChatResponse degraded = fallbackChain.run(request, FailureCause.BUDGET_EXCEEDED);
            return ChatClientResponse.builder()
                    .chatResponse(degraded)
                    .context(merge(request.context(), "degraded", "BUDGET_EXCEEDED"))
                    .build();
        }

        // 中段：调下游
        ChatClientResponse response = chain.nextCall(request);

        // 后置：算钱、累积
        ChatResponse cr = response.chatResponse();
        if (cr != null && cr.getMetadata() != null && cr.getMetadata().getUsage() != null) {
            Usage usage = cr.getMetadata().getUsage();
            String model = cr.getMetadata().getModel();  // 真实响应model
            BigDecimal cost = pricing.calculate(model,
                    nz(usage.getPromptTokens()), nz(usage.getCompletionTokens()));
            repo.addDailySpend(userId, LocalDate.now(), cost);
        }
        return response;
    }
}
```

**关键警告**：必须直接 `implements CallAdvisor`（不能继承 `BaseAdvisor`），必须最外层（`Ordered.HIGHEST_PRECEDENCE`）。

**反直觉点**：Worker 用 `ChatModel.call(prompt)` 完全绕过 CostAdvisor——Advisor 链是 ChatClient 层独有的。Worker 内部禁止注入 `ChatModel`，统一用 `ChatClient.Builder`。

### 流式 CostAdvisor

必须 `implements CallAdvisor, StreamAdvisor`。用 `ChatClientMessageAggregator.aggregateChatClientResponse(flux, consumer)` 透传 flux 不阻塞，stream 完成后回调一次扣减。bug #4458 兜底：某些 provider 返 usage=0，需 `if (getTotalTokens() == 0) return;`。

## 8.6 L4 RateLimit + 降级链

降级链 4 档：主模型(GPT-4o) → cheaper 模型(GPT-4o-mini) → 本地缓存 → 静态模板。每往后一档质量降一截、成本降一档。

### Resilience4j 四组件（2.3.0）

| 组件 | 解决什么 | Agent 用途 |
|---|---|---|
| **RateLimiter** | QPS 速率 | per-user 每分钟 10 次/全局每秒 50 次 |
| **Bulkhead** | 并发数 | 防单用户 100 并发占满线程池 |
| **CircuitBreaker** | 下游故障 | OpenAI 5xx 连续→自动切 Fallback 30 秒 |
| **TimeLimiter** | 单次超时 | LLM 调用挂 30 秒主动断 |

不列 Retry——Spring AI 已内置 `RetryTemplate`（默认 3 次重试），外层再加 = 3×3 = 9 次 HTTP 调用→触发风控 ban。

### Per-User RateLimiter：必须自管 RegistryStore 防内存爆炸

Resilience4j 默认 `InMemoryRegistryStore` 永不清理——百万 user = 百万 RateLimiter 实例常驻 JVM。修复：自定义 `RegistryStore`，用 Caffeine 包一层 `expireAfterAccess(10min)` + `maximumSize(100_000)`。

### 降级链：FallbackStrategy 接口 + 3 实现

```java
public interface FallbackStrategy {
    Optional<ChatResponse> tryHandle(ChatClientRequest request, FailureCause cause);
    int priority();   // 越小越优先
    enum FailureCause { BUDGET_EXCEEDED, RATE_LIMITED, CIRCUIT_OPEN, OTHER }
}
```

| Strategy | priority | 要点 |
|---|---|---|
| `CheaperModelFallback` | 10 | 只在 BUDGET_EXCEEDED/RATE_LIMITED 触发；调用时不能再经过 CostAdvisor |
| `CacheFallback` | 20 | Caffeine `expireAfterWrite(30min)`+`maximumSize(10_000)`；key=`MD5(prompt.contents)` |
| `StaticTemplateFallback` | 100 | 终端档，必须永远 present |

降级链每档必须独立 timeout：主路径 8s → CheaperModel 4s → CacheFallback 200ms → StaticTemplate 0ms。总耗时上限 `agent.fallback.total-timeout: 10s`。

### CircuitBreaker 注解用法

```java
@CircuitBreaker(name = "openai", fallbackMethod = "askFallback")
@Bulkhead(name = "openai", type = Bulkhead.Type.SEMAPHORE)
public ChatResponse ask(ChatClientRequest req) { ... }

public ChatResponse askFallback(ChatClientRequest req, CallNotPermittedException ex) {
    return fallbackChain.run(req, FailureCause.CIRCUIT_OPEN);
}
```

Fallback 方法签名规则：返回类型一致、参数一致 + 末尾追加 `Throwable`（或具体子类）、必须在同一类。

## 8.7 L5 Dashboard：Grafana 12-Panel + 4 告警

Dashboard 按角色分区（非按 metric 罗列），单块 ≤ 12 panel。

### 分区一：健康概览（顶部 3 panel）
- **Panel 1: 服务 SLO**（Stat 单值）—— p95 延时 / 错误率 / 降级率
- **Panel 2: QPS 趋势**（Time series）—— 叠一条 `offset 24h` 对比线
- **Panel 3: 错误堆叠**（Bar gauge by exception type）

### 分区二：流量与成本（中-左 3 panel）
- **Panel 4: Token 速率**（按 model+token_type 分）
- **Panel 5: 实时 Cost Rate**（USD/秒）—— 推荐 L3 CostAdvisor 内发 Counter `agent_cost_usd_total`
- **Panel 6: 当日 Top10 消费用户**（Table）—— 从 Redis Zset 读取，非 Prometheus（避免高基数爆炸）

### 分区三：Agent 性能（中-右 3 panel）
- **Panel 7: Advisor 链路耗时分解**（heatmap by advisor）
- **Panel 8: Tool 调用 Top10**（横条）
- **Panel 9: 跨 Model 延迟对比**（p50/p95/p99 by model）

### 分区四：韧性状态（底部 3 panel）
- **Panel 10: RateLimiter 配额耗尽率**
- **Panel 11: CircuitBreaker 状态时间线**（state timeline）
- **Panel 12: Fallback 触发分解**（堆叠面积，按 cause+strategy）

### 告警阈值（4 条）

| 条件 | 等级 |
|---|---|
| 错误率持续 5 分钟 > 5% | **critical**（值班电话） |
| p95 延时持续 10 分钟 > 10s | **warning**（IM 群） |
| 任一 CB==OPEN 持续 1 分钟 | **critical**（值班电话） |
| cost rate 较过去 1 小时均值飙 5 倍 | **warning**（IM 群） |

## 8.8 五坑——LLM 可观测性落地必踩

1. **Prompt 写进日志 → PII 泄漏**：生产 `application-prod.yml` 强制硬编码 `log-prompt: false` 不留 env override
2. **自家 Cost 和账单差三个数量级**：model 名拿错（应取 `ChatResponseMetadata.getModel()` 响应模型）、HTTP 超时本地不扣但 provider 已计费、价目表过期
3. **限流粒度错位，VIP 被误伤**：限流分桶——VIP 高额度 per-user 不共享全局；免费用户低额度 + 全局上限
4. **降级链反而拖慢整体 p99**：每档独立 timeout + 独立 executor；总耗时上限
5. **高基数 Metric 把 Prometheus 撑爆**：low cardinality 才能上 metric tag（userId/traceId 绝不）；Spring AI 默认 `gen_ai.*`/`spring.ai.*` 全是 low cardinality 设计

## 8.9 阶段化选型

| 阶段 | L1 Obs | L2 Trace | L3 Cost | L4 Limit | L5 Dashboard |
|---|---|---|---|---|---|
| **POC** | 最简 | 可选 | 不装 | 不装 | 不装 |
| **MVP** | 全装 | 全装 | InMem 版 | 不装 | 单块大盘 |
| **规模化** | +env tag | 全装 | Redis 版 | per-user+CB | +4 告警 |
| **生产** | 全装 | +tail-based | +周对账 | +per-tier | +Loki/Tempo |

### 上线前自检 7 问

1. `/actuator/prometheus` 是否暴露在独立端口、有鉴权？
2. 采样率生产是否降到 0.10、是否有 tail-based 兜底？
3. CostAdvisor 是否 order=HIGHEST_PRECEDENCE、是否所有调用都传了 userId？
4. RateLimiterRegistry 是否换了 CaffeineRegistryStore？
5. Spring AI 内置 RetryTemplate + Resilience4j Retry 是否只用一个？
6. dashboard 上 4 个 critical alert 是否都做过误告复盘？
7. ChatModel 直调（绕过 advisor）的代码路径是否有 ObservationHandler 兜底？

## 关键 API/技术点速查

- `ContextExecutorService.wrap(vt, ContextSnapshot::captureAll)` — 跨虚拟线程 trace 透传
- `CallAdvisor` 直接 implements（不能继承 `BaseAdvisor`）— 短路逻辑成立
- `Ordered.HIGHEST_PRECEDENCE` — CostAdvisor 放在 advisor 链最外层
- `ChatClientMessageAggregator.aggregateChatClientResponse` — 流式 cost 扣减
- `RateLimiterRegistry` + Caffeine `RegistryStore` — 防 per-user 内存爆炸
- `@CircuitBreaker(fallbackMethod=...)` + `CallNotPermittedException` 重载 — 熔断降级
- Micrometer `Counter` + low cardinality tag 规范 — 自定义 metric
