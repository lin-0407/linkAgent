# 阶段 5.5：提示词模板 DB 化与热更新踩坑记录

> 本文件记录阶段 5.5 实现和收尾中必须记住的坑点。阶段 5.5 已由作者自测通过后进入收尾。

## 1. 不做缓存反而更符合热更新目标

**问题**：提示词从代码迁到数据库后，直觉上容易想加内存缓存，避免每次模型调用都查库。

**处理**：本阶段明确不做缓存。`PromptService.get(key)` 每次直接查 `llm_prompt_template`。

**原因**：当前项目是单用户、非公网部署。一次大模型调用通常是秒级，按唯一键查一条提示词是毫秒级。缓存省下的成本很小，却会引入「更新提示词后如何刷新缓存」的问题。直接查库最简单，也天然支持热更新。

## 2. 数据库是唯一来源，缺 key 必须响亮报错

**问题**：如果提示词 key 查不到，是否要在代码里保留一份默认提示词兜底。

**处理**：不兜底。`PromptService.get(key)` 查不到时直接抛 `ResponseStatusException`，提示确认 `init.sql` 是否执行。

**原因**：作者要求不要把提示词硬编码在业务代码里。如果代码里还保留默认正文，就会重新变成双来源。双来源最容易出现「数据库改了，但实际用了代码默认值」这类隐蔽问题。

## 3. USER 提示词不能继续用 `%s`

**问题**：原来的用户提示词用 `.formatted(...)` 和 `%s` 位置占位符。迁到数据库后，前端编辑者只看到一串 `%s`，很难知道每个位置代表什么。

**处理**：USER 模板统一改成 `{varName}` 命名占位符，由 `PromptService.render(key, Map)` 做简单字符串替换。

**原因**：命名占位符更适合可编辑提示词。它不依赖参数顺序，也不会因为提示词正文里出现普通 `%` 字符而触发格式化异常。

## 4. `Map.of()` 不能接收 null value

**问题**：`render(key, Map)` 的调用点大多用 `Map.of(...)` 或 `Map.ofEntries(...)` 传变量。如果某个 value 是 `null`，`Map.of()` 会直接抛 `NullPointerException`。

**处理**：调用点传入 Map 前，继续使用 `TextUtil.trimToDefault(...)` 或已有上下文构造方法，把空值归一成可读的默认文本。

**原因**：提示词变量是给模型看的业务文本。把 null 变成「未提供」之类的明确文本，比让模板渲染阶段抛异常更容易理解，也更稳定。

## 5. 测试手动构造 Service 时不会自动注入 `PromptService`

**问题**：Spring 容器能自动注入新增依赖，但单测里手动 `new Service(...)` 的构造点不会自动补参数。提示词迁移后，漏传 `PromptService` 会导致编译失败。

**处理**：新增 `StubPromptService`，并把相关单测构造点补上。`AgentExecutorLongTermMemoryTest` 中手动 `new AgentExecutor(...)` 的 3 个构造点也已补 `new StubPromptService()`。

**原因**：提示词迁移是构造器级依赖变更。以后再改构造器时，要全仓搜索 `new 类名(`，不要只看 Spring Bean。

## 6. 测试断言不要再绑定提示词原文

**问题**：提示词可热更新后，测试如果继续断言系统提示词原文中的某句话，会让提示词内容微调直接打红测试。

**处理**：`StubPromptService.get(key)` 返回 `[test-prompt:key]`。测试断言稳定 key，例如 `pre_publish.system`。

**原因**：提示词正文是可调参数，key 才是代码契约。测试应该验证「调用了正确的提示词」，而不是锁死提示词每个字。

## 7. PowerShell 智能引号会造成 Java 编译期硬错误

**问题**：5.5-3 迁移过程中，个别 Java 字符串字面量被输入法带成了全角智能引号 `“ ”`。这不是运行时问题，而是直接编译失败。

**处理**：已把相关位置改回半角双引号 `"`，并全仓扫描 `.java`，确认无残留。

**原因**：Java 字符串字面量只能使用半角双引号。Windows 输入法或富文本复制很容易把引号替换成中文智能引号，写代码时要特别注意。

## 8. `HydeQueryTransformer` 的失败策略和普通取词不同

**问题**：普通业务调用里，提示词缺失应该 fail-loud。但 HyDE 查询增强本身是高级检索的附加增强，失败时不能拖垮主检索。

**处理**：`HydeQueryTransformer.transform(...)` 外层已有 try/catch。即使 `hyde.system` 缺失或 LLM 调用失败，也会退回原始查询。

**原因**：高级检索链路的设计原则是增强失败可降级。HyDE 是召回增强，不是业务主流程的硬依赖。

## 9. AgentExecutor 的两条系统提示词带变量

**问题**：`AgentExecutor` 的系统提示词不是纯静态文本，它需要把工具列表填入提示词。

**处理**：把 `agent_executor.system` 和 `agent_executor_structured.system` 也放入表中，但正文里保留 `{toolList}`，调用时用 `render(key, Map.of("toolList", toolDescriptions))`。

**原因**：这样既消除了业务代码里的大段提示词，又保留了运行期工具列表注入能力。

## 验证

作者已完成阶段 5.5 自测并通知收尾。后续如果重新修改提示词模块，建议至少回归：

```bash
cd backend
mvn -q -DskipTests compile
```

接口验证：

1. `GET /api/prompt-templates` 返回全部未删除提示词。
2. `GET /api/prompt-templates/{key}` 能读到指定正文。
3. `PUT /api/prompt-templates/{key}` 后无需重启即可读回新正文。
4. 缺 key 更新返回 404，空正文返回 400。
