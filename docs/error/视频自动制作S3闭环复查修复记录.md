# 视频自动制作 S3 闭环复查修复记录

日期：2026-10-21。修复基线为 `bebbbcb`。承接 [S3 媒体闭环与发布包](../develop/视频自动制作-S3媒体闭环与发布包.md)，本轮只修复已审查的调度与费用问题及其必要恢复路径，不增加前端、公开 API、Schema 或供应商调用。

## 1. 缺陷与修复

| 问题 | 原行为 | 修复后 |
| --- | --- | --- |
| 发布包完成后漏扫 | 构建后写 PACKAGE_READY 并等待依赖，但 SQL 候选没有该阶段，无法走最终完成步骤 | 候选包含 PACKAGE_READY，重新启动的 worker 也能接着完成 |
| 正常推进耗尽次数 | 整次运行每次领取都会增加 attempt_count，和默认三次上限直接比较，正常阶段切换也被当成失败 | 同一阶段使用持久化基线计算领取次数；成功推进才重置，重启不清零 |
| 旧费用按新汇率结算 | 预留保存汇率，实际结算却使用当前配置 | 重复预留和迟到结算读取原 Charge 的价格快照；配置变化不重算旧费用 |

同一阶段的尝试数为 `run.attempt_count - link.lease_generation`。当前 claim SQL 同时增加两者，成功的阶段推进将本代 generation 写入闭环，作为下一阶段基线。这个差值依赖该现有数据库约定；不能把 generation 独立改成随机数，或只在其中一个字段上增加计数。

`creator.creation.media.max-attempts=3` 保持不变，表示同一阶段含首次在内的最多三次领取。试映完成只推进到 PACKAGE_PENDING 并释放租约，下一次单独领取才开始构建包，因此首次构建也计数。没有通过提高默认阈值掩盖问题。

## 2. 恢复、取消与事务边界

- 媒体候选可恢复 WAITING_DEPENDENCY、wake 后留下的 QUEUED、租约过期的 RUNNING；不领取其他 worker 的活 RUNNING。
- 已有媒体闭环的运行由媒体 worker 恢复。固定工程候选排除它们，`claimFixed` 在任务行锁下再检查一次，拒绝陈旧候选抢回已交接的运行。
- CANCEL_REQUESTED 的扫描不受正常阶段白名单和次数上限限制，FAILED/MEDIA_BLOCKED 的暂停运行也可以取消并释放活动位置。
- 阶段 SQL 同时核对当前运行、代数及数据库租约时钟。阶段推进和父运行等待/暂停放在同一个短事务中，最终检查失败则整体回滚，旧执行者不能污染重试基线。
- 子任务的数据库受理与闭环归属同事务提交。不会先暴露可调度的试映，再把它补绑定到制作预算；这些事务内没有模型或媒体网络调用。

原 `retry-interval-ms` 尚未接入独立退避，本轮不宣称已经遵守该间隔；仍按现有轮询触发有界尝试。确定性业务冲突仍暂停等待作者处理，不自动进行额外付费重试。

## 3. 费用规则

账务适配器通过受任务、运行和 chargeKey 归属保护的查询读取原费用。重复预留仍校验能力、美元上界与价格依据，不能用同一 key 偷换调用；折算率配置变化本身不会改变原预留。

缺失或非法快照不使用当前汇率猜算。已发送且尚未结算的调用保留 UNKNOWN；未发送的调用直接拒绝。实际美元为零时结算为零，仅预留阶段允许提升至最小记账金额。归属和重复结算冲突不再全部被吞成“历史缺口”。

默认 7.20 仍只是部署的记账折算估值，文本单价仍用于 USAGE_ESTIMATE，不代表供应商账单或实时汇率；本轮没有确认新的市场价格，也没有真实费用消费。

## 4. 发布文案的实际数据形状

连续数据库测试使用统一 SQL 冻结的真实上下文，发现 `title_suggestions` 是 TEXT，进入 JSON_OBJECT 后的 `publishingPlan.titles` 为 JSON 字符串。旧打包代码仅接受数组，会把已有标题写成“未提供”。现同时接受数组与其中编码的数组，解析失败明确拒绝。测试检查实际 ZIP 内的冻结标题与简介，未改历史上下文或重生成文案。

三个原来仅在本地的测试文件 `CreationMediaWorkerTest`、`CreationMediaBillingTest`、`CreationPackageServiceTest` 本轮纳入版本管理。发布包单测的 ZIP 副本改放 JUnit 临时目录，结束时自动清理。
