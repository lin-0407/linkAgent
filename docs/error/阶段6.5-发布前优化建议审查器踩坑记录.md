# 阶段 6.5：发布前优化建议审查器踩坑记录

## 1. 不直接让审查器阻断建议保存

问题：审查规则第一版可能误判。如果审查器直接抛错，用户可能拿不到任何建议。

处理：本阶段只保存审查报告，并用 `quality_status` 标记质量状态。这样前端和评测能看到风险，但主流程不中断。

## 2. 审查器不再次调用 LLM

问题：用第二次 LLM 审稿可以做更细的语义判断，但会增加成本、延迟和不稳定性。

处理：第一版只做确定性规则，先覆盖证据编号、结构完整性和夸大承诺这类最容易稳定判断的问题。

## 3. `quality_status` 从证据状态升级为审查状态

问题：上一阶段 `quality_status` 表示 `EVIDENCE_COLLECTED`。加入审查器后，如果仍保留这个值，前端无法直接知道建议是否通过审查。

处理：保留 `generation_mode` 表示生成路径，用 `quality_status` 表示最终审查状态。

## 4. 旧库需要兼容补丁

问题：`CREATE TABLE IF NOT EXISTS` 不会给已有表增加新字段。

处理：在 `init.sql` 末尾增加基于 `INFORMATION_SCHEMA.COLUMNS` 的条件 `ALTER TABLE`，补齐 `audit_report` 字段。

## 5. 测试构造器要保持兼容

问题：测试里有直接 new `PrePublishSuggestionService` 的用法。新增构造参数后，如果不同步补 `null`，会导致编译失败。

处理：测试构造调用补充 `suggestionAuditor` 参数。包级构造器继续传 `null`，用于只验证 prompt 和解析逻辑的单测场景。
