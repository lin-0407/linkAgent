## R1：删除任务使运行和费用不可收尾

位置：`backend/src/main/java/com/link/linkagent/creator/task/service/CreatorTaskService.java:222-230`；`creator/creation/mapper/FixedProjectJobMapper.java:23`；`creator/creation/service/CreationRuntimeService.java:368-370`。

`deleteTask` 直接逻辑删除任务并删除材料，没有检查或收尾活动制作运行。固定工程扫描排除已删除任务，而取消、心跳、确认取消和费用结算又依赖仍然存在的任务锁。

实际复现了两个场景：

1. 自动受理并附加固定工程，确认扫描候选存在；通过真正 `CreatorTaskService.deleteTask` 在真实事务中删除任务。候选消失，但运行仍是 `QUEUED`，工作区 `active_run_id` 仍指向它，调用取消返回 404。
2. 在另一个任务创建运行，预留并标记调用已发送，然后删除任务。调用迟到结算返回 404，费用仍是 `RESERVED` 且 `sent_at` 非空。这里是测试费用记录，没有向供应商发请求或实际消费。

修复需要在逻辑删除前处理活动运行与费用收尾边界，并覆盖删除与领取的并发；不能仅让扫描忽略任务。

## R2：取消后不能退回自己的成片

位置：`AutomaticProductionPlanService.java:70-74`；`ProductionPlanMapper.java:231-243`；`ProductionPlanPersistenceService.java:99-100`；`MediaUploadService.java:555`。

自动受理插入更高版本的 `READY` 蓝图，立即被查询为当前蓝图。排队时取消后，其余 5 个步骤保持 `PENDING`，终止逻辑没有撤下这份蓝图，人工完成或跳过也被禁止。

真实数据库探针从原成片及已完成人工蓝图开始，确认原上传门禁可通过；受理自动制作后立刻取消。结果活动运行已释放、原成片版本仍保留，但当前蓝图仍是系统蓝图，上传自己的 MP4 时实际 `MediaUploadService.createUpload` 返回“请先完成或跳过制作蓝图中的全部步骤”。对象存储没有被调用。

修复应保证取消或失败后有明确回退路径，保留原有版本和上下文；不要通过伪造系统步骤完成来解除门禁。

## R3：跨语言小数摘要不一致

位置：`CreationInputRules.java:40-46`；`FixedProjectJobFiles.java:50-51` 及准备工程时的摘要重写；`renderer/linkagent_renderer/contract.py:59-62,123`。

实际 Java 21 调用生产 `CreationInputRules.renderDocument/renderInputHash`，与 Python 使用同一个简化输入进行对比：

```text
JAVA_CANONICAL={"gainDb":-1.0E-4}
JAVA_INPUT_HASH=8fad4473ddedec7fa49851ac1320af2aec71610ce1b54b5c69802cebbb918b64
PYTHON_CANONICAL={"gainDb":-0.0001}
PYTHON_INPUT_HASH=5fee7bb953b7b255cbb60439d1ba4b0a3fa7ef8c1a3bfe35a48b8c28bd89ab26
```

渲染审查另使用完整合法 V2 工程，把 `clip.gainDb` 设为 `-0.0001`，用 Jackson 数字表示对应的摘要后，实际 `load_project` 报 `INPUT_HASH_MISMATCH`。现有常用整数增益测试没有覆盖跨语言数字形式。

应统一摘要数字规范或采用双方完全一致的规范化协议，补旁白和原声增益的跨语言回归。没有执行完整 Java freeze → Python 的全链探针，不能将上述证据描述为完整后台制作复现。

## R4：目标时长与受理工程脱节

位置：`AutomaticProductionPlanService.java:72,185-187`；`FixedProjectJobPersistenceService.java:48-57`。

当前目标时长写入制作蓝图和自动受理请求摘要，运行授权输入则没有目标时长。附加工程核对身份和工程摘要，但没有比较蓝图目标与 `frameCount/fps`。

数据库探针保留原 48 帧、24fps 的 2000ms 固定工程，仅把自动制作请求改成 1000ms；自动受理和 `fixedJobs.attach` 均成功，运行仍为 `QUEUED`，数据库保存目标 1000ms、冻结工程实际 2000ms。这个探针验证工程准入，没有真实渲染，也没有假造试映完成。

问题是缺少任何核对或差异反馈。固定与自适应模式尚未进入当前请求字段，本次不自行规定帧级容差或改变用户已确认的时长语义。

## R5：旧任务请求清空新任务状态

位置：`frontend/src/composables/creator/useMediaUpload.ts:66-70`。关联 `PreflightTab.vue:145-147,413-419,473-505`。

静态确认的时序：A 的恢复请求正在等待 → 切换 B，`resetForTaskChange` 递增操作代数 → B 已恢复当前上传或成片 → A 迟到返回 404/410 → 内层异常分支没有检查操作代数，直接 `clearUploadState()`。

B 的上传、分片、成片和进度引用被清空，`activeVersionId` 也可能变空，探测/处理等操作入口随之不可用。后台对象和数据库不会因此丢失，正在上传的分片通常仍会继续，不能描述成后台上传被中断。应让这个异常分支遵守已有的操作代数检查。

遵守仓库前端命令边界，本轮未跑前端功能测试、type-check 或浏览器验收。

## R6：不显示的视频标题阻止渲染

位置：`renderer/linkagent_renderer/visuals.py:26-36,75-80`。

`VIDEO_CLIP` 明确不把元数据标题绘制在画面上，但构造器仍对所有标题进行字形覆盖和最多两行布局校验。实际合法 V2 视频工程且没有字幕时：

```text
title="one\ntwo\nthree" → TEXT_OVERFLOW
title="recording 🎉" → FONT_GLYPH_MISSING
```

两种输入都在编码前失败。应仅对实际绘制文字做这类检查，继续保持视频真实字幕的排版校验。

## R7：COVER 中间画面超出内存边界

位置：`renderer/linkagent_renderer/clips.py:40-42,106-110`。

目前仅限制源画面及 SAR 规范化面积。`COVER` 先整体放大再裁切，极端比例会生成远大于源和目标的中间画面。

实际 H.264 片段为 `32×1920`、4 秒、4266 字节，选择其中 2 秒、COVER、静音，通过协议和源素材校验。720p 目标对应中间 `1280×76800`，约 9830 万像素。512MiB 容器达到 `536752128` 字节，内存上限争用事件从 0 增至 24502，60.16 秒后 TIMEOUT。没有 OOM kill。

应在预检计算实际中间面积，或先安全裁切再缩放。仅检查源像素量不足以保证合成内存可控。
