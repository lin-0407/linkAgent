## 一、查询增强（5.2b）

### 1. 框架查询组件内置 prompt 是英文，对中文会劣化

**问题**：Spring AI 的 `RewriteQueryTransformer` / `MultiQueryExpander` 内置默认 prompt 是**英文**，直接用在中文 query + 中文案例库上会劣化召回，甚至让 LLM 输出英文改写。

**处理**：两者都显式注入**中文 `promptTemplate`**；HyDE 是自定义实现，本就写中文 prompt。

**原因**：查询增强的产物要喂中文向量检索，扩展文本必须保持中文语义；框架默认 prompt 面向英文场景，不能直接用。

### 2. 中文 promptTemplate 的占位符变量名必须与框架字节码一致

**问题**：自定义 `promptTemplate` 里的占位符若写错变量名，框架渲染时会因找不到变量而报错（不是静默忽略）。

**处理**：对 spring-ai 1.1.4 **字节码逐一核准**占位符名——`RewriteQueryTransformer` 用 `{query}` / `{target}`，`MultiQueryExpander` 用 `{query}` / `{number}`；`targetSearchSystem` 设中文「视频案例知识库」。

**原因**：占位符名是框架与模板的契约，属「引入的第三方方法必须真实可用」红线项，只能对字节码 / 官方核实，不能凭记忆拍。

### 3. spring-ai-rag 不写死版本是对的，.m2 里的 1.0.0 是障眼法

**问题**：`pom.xml` 加 `spring-ai-rag` 无版本号后，反编译 `.m2` 一度看到 **1.0.0**，疑似与项目 1.1.4 混版本。

**处理**：核实 `spring-ai-bom-1.1.4.pom`（第 89-90 行）确认 **BOM 管理 `spring-ai-rag = ${project.version}`（即 1.1.4）**；`.m2` 的 1.0.0 只是旧缓存、`find | head -1` 撞上了它。**结论：无版本声明正确，实际编译用 1.1.4，pom 不必锁版本。**

**原因**：BOM 统一管版本时子模块不该再写死版本；排查混版本要看 BOM 实际声明，而非 `.m2` 里 `find` 第一个命中的目录（缓存可能含历史版本）。

### 4. 查询变换走 ChatClient，绕过 LLMService 的字符护栏

**问题**：项目 `LLMService.validatePromptLength` 有 30000 字符护栏；查询增强若走它，会引入不必要的耦合。

**处理**：查询变换组件直接用 `ChatClient.Builder` 调 LLM，**绕过** `LLMService` 字符护栏；query 本身受入参 `@Size(500)` 约束，远低于 30000，无实际影响。`MultiQueryExpander.numberOfQueries` 另设硬上限（默认 3）防检索次数放大。

**原因**：增强是检索前的轻量扩展，入参已有更紧的长度约束；硬上限放在 multi-query 条数（检索次数 = N+1）这个真正的成本放大点上更对症。

## 二、父子召回 small-to-big（5.2c）

### 5. 同一个 MilvusServiceClient 上建两个集合，各自 afterPropertiesSet

**问题**：子集合向量化要在不破坏父集合的前提下新增一个 child `MilvusVectorStore`。

**处理**：`KnowledgeVectorStore` 内部**再持一个**指向子集合的 `MilvusVectorStore`，与父集合**共用同一个** `MilvusServiceClient` / 同 `EmbeddingModel` / 同维度（1024），仅集合名不同；`build()` 后各自 `afterPropertiesSet()` 建集合。

**原因**：这是本刀唯一未在现有代码出现过的集成用法（一个 client 建两个集合）；Milvus 标准用法，预期可用，但属「新集成点」需作者开库实跑确认（沿用 5.1「MilvusVectorStore 非 Bean 须手动 afterPropertiesSet」的教训）。

### 6. 子集合建库失败必须独立降级，不连累父检索

**问题**：子集合建库失败（维度冲突、集合损坏等）若让整个 `init()` 抛错，会把 5.2a/b 已能用的父检索一起带挂。

**处理**：`init()` 中父集合 `try/catch` **之后**追加子集合构建，用**独立 `try` + 独立就绪位 `childReady`**：子建库失败只 `warn`、父 `ready` 不受影响；父集合连 client 都没建出来（`milvusClient==null`）时跳过子集合。检索仅在 `isChildReady()` 时叠加子召回。

**原因**：子召回是**附加召回源**，「5.2c 对 5.2a/b 零回归」要求子链路任何失败都能独立降级。这是四层降级哲学在索引侧的落点。

### 7. 子文档反范式带 category/tier（子表本身没有这两列）

**问题**：5.2c-2 子召回要支持与父召回**同款** `category`/`tier` 过滤（复用 `buildFilter`），但子表 `creator_reference_video_item` 没有这两列。

**处理**：`listIndexableItems` 索引时 **JOIN 父表** `creator_reference_video` 带出 `v.category`/`v.tier`，写进子向量文档 metadata。

**原因**：父表这两列导入后极少变更，偶有变更下轮重建即修正，反范式成本可接受；换来子召回复用父检索同一个 `buildFilter`，过滤口径一致、零分叉。

### 8. ⚠️ 子召回提取 videoId 绝不能回退 document.getId()

**问题**：父侧 `extractVideoId` 在 metadata 缺失时回退 `document.getId()`（父文档 id 就是 videoId，回退安全）。但**子文档 id 是 itemId**——若子召回复用父侧提取逻辑，metadata 缺失时会把 **itemId 误当 videoId**，污染整个 small-to-big 上卷。

**处理**：子召回单列 `extractChildMetadata(document, key)`，**只读 metadata、不回退 getId()**；注释点明这是父子召回最隐蔽的差异点。

**原因**：父子文档的「主键语义」不同（父=videoId，子=itemId），凡按主键取值的逻辑（提取、SearchResult.getId）都要父子分别处理——这条贯穿 5.2c 与 5.2d-3。

## 三、Rerank 精排（5.2e）

### 9. gte-rerank 已下线，改 qwen3-rerank

**问题**：原计划用 DashScope `gte-rerank`，但它已于 **2026-05-30 下线**（作者指正属实）。

**处理**：联网核实后改用 **`qwen3-rerank`**（纯文本）；`KnowledgeRagProperties.Rerank.model` 默认 `qwen3-rerank`。

**原因**：「引入的第三方方法必须真实可用、不能过时」红线项，模型下线必须联网核实替代，不能照旧硬编码。

### 10. compatible-api ≠ compatible-mode：rerank 端点用错会报错

**问题**：`qwen3-rerank` 走 OpenAI 兼容端点，但路径是 `POST .../compatible-api/v1/reranks`——注意是 **`compatible-api`**（rerank 专用），**不是** chat 用的 **`compatible-mode`**；也不是老的 `/api/v1/services/rerank/...` 原生端点。三者用错都会报错。

**处理**：`base-url` 默认 `https://dashscope.aliyuncs.com/compatible-api/v1`，与 chat 的 compatible-mode 独立配置；注释 + 配置说明都标注差异。

**原因**：DashScope 同时存在 chat 兼容端点、rerank 兼容端点、原生端点三套路径，命名极易混淆，需在配置与文档双处固化正确值。

### 11. RestClient 的 baseUrl + 前导斜杠会替换路径段 → 404

**问题**：`RestClient.baseUrl(".../compatible-api/v1")` + `.uri("/reranks")` 时，按 RFC 3986，**前导斜杠的相对路径会替换 base 的整个路径段** → 实际请求 `host/reranks`（丢了 `/compatible-api/v1`）→ 404。

**处理**：**不设 baseUrl**，改为把完整绝对 URL（`baseUrl + "/reranks"`）拼好后整个交给 `.uri(...)`。

**原因**：URI 解析的「绝对路径替换」规则是标准行为，不是 bug；拼完整绝对 URL 是规避这类路径丢失最稳的写法。

### 12. rerank 响应只依赖 index 次序，不读分数字段

**问题**：rerank 响应顶层 `results:[{index, relevance_score}]`，若强依赖 `relevance_score` 字段名 / 数值，一旦上游改字段就崩。

**处理**：响应只用 `results[].index` 的**返回次序**（API 已按相关性降序）；private 嵌套 record **只声明 `index`**，其余字段靠 Spring Boot 默认「忽略未知字段」吃掉。`rerank()` 返回重排后的原始下标列表，**关闭 / 无 Key / 候选≤1 / 异常 / 超时 → 返回空序、保持原检索顺序**。

**原因**：只依赖「次序」这一最稳的契约面，把对响应结构的依赖压到最小；rerank 是锦上添花，任何失败都退回原序而非报错（同四层降级哲学）。

## 四、原生 dense+BM25 hybrid（5.2d）

### 13. 官方文档被墙 → 对 milvus-sdk-java 2.5.8 字节码 javap 核准

**问题**：Milvus 2.6 / sdk-java 的 hybrid / BM25 官方文档被墙，无法在线核实 API 签名；而「第三方方法必须真实可用」是红线。

**处理**：对 classpath 上的 **milvus-sdk-java 2.5.8**（Spring AI 1.1.4 自带）逐一 `javap` 核准签名——`MilvusClientV2.{createSchema,createCollection,createIndex,insert,hybridSearch,dropCollection,hasCollection,loadCollection}`、`AddFieldReq`、`DataType.{VarChar,SparseFloatVector,FloatVector,Int64}`、`Function(FunctionType.BM25)`、`AnnSearchReq`（dense→`FloatVec`、BM25→`EmbeddedText`）、`HybridSearchReq` + `RRFRanker`、`SearchResult.{getId,getScore,getEntity}` 等。

**原因**：文档不可达时，字节码是 API 真实性的最终事实源；核准过的签名才落地，避免引入不存在 / 不兼容的方法。

### 14. 同 jar 含 v1+v2，BM25/hybrid 无需升级依赖

**问题**：原以为原生 hybrid 要升级 milvus-sdk-java 依赖。

**处理**：核实发现 classpath 的 2.5.8 **同一个 jar 内含 v1（`io.milvus.client`）+ v2（`io.milvus.v2.*`）两套包**，BM25/hybrid 所需的 `io.milvus.v2.*` 现成可用，**无需改 pom**；ranker 用 SDK 2.5.8 自带 `new RRFRanker(int k)` 类形式（2.6 服务端才把 ranker 改 Function-RERANK 形式，但 SDK 用类形式）。

**原因**：先核实 classpath 现状再决定是否升级，避免无谓的依赖变更与潜在版本冲突（简单优先）。

### 15. 抛弃 Spring AI MilvusVectorStore，自建 schema + 手动算 embedding

**问题**：Spring AI 的 `MilvusVectorStore` 按它**固定 schema** 建集合，**没有** sparse 字段与 BM25 Function，无法承载原生 hybrid。

**处理**：新增隔离组件 `KnowledgeHybridStore`，内部私有持 `MilvusClientV2` + 自建 schema（`video_id` PK / `text` VarChar+中文 analyzer / `sparse` SparseFloatVector / `dense` FloatVector dim=1024 / `category`·`tier` 过滤字段）+ BM25 `Function(text→sparse)`；插入只写 text/dense/metadata，**sparse 由服务端 Function 自动生成**；dense 要**自己用 `EmbeddingModel.embed(List)` 算**（Spring AI 不再代劳）。集合 drop 重建 + 从 MySQL 全量重灌（MySQL 是事实源，无损）。

**原因**：固定 schema 的封装件装不下 sparse+Function，只能下沉到 raw v2 client 自建 schema；与现有 `KnowledgeVectorStore`（v1+Spring AI）并存、双开关切换，迁移期平滑。

### 16. v2 SDK 的若干编译期坑（已自查修正）

**问题**：自建 schema + hybridSearch 的几处编译期陷阱：① `analyzerParams` 若用 `Map.of(String,String)`，泛型 `Map<String,String>` 与 API 要求的 `Map<String,Object>` 不变（invariant）不可赋值；② `ConnectConfig` / `AnnSearchReq` 是 `@SuperBuilder`，其 builder 带通配符，赋给中间变量时类型推断会失败；③ `createCollection` 带 indexParams 后集合是否已 load 不确定。

**处理**：① `analyzerParams` 用 `Map.<String,Object>of(...)` 显式指定值类型；② `ConnectConfig` 用两分支单链 `build()`、`AnnSearchReq` 用 `var` + 逐句 `set` 规避通配符中间变量；③ `createCollection` 后**显式再 `loadCollection`**（幂等兜底）。

**原因**：Java 泛型不变性与 `@SuperBuilder` 通配符是编译期硬约束，必须在写法上规避；显式 load 是对「建集合是否自动 load」不确定性的防御性兜底。

### 17. ⚠️ 子 hybrid 集合 PK=item_id，video_id 必须 outFields + getEntity 取

**问题**：父 hybrid 集合 PK=video_id，搜索结果直接 `SearchResult.getId()` 取。但子 hybrid 集合 PK=**item_id**，video_id 是普通字段——若也用 `getId()` 会取到 itemId（同第 8 条父子主键差异）。

**处理**：子集合搜索 `HybridSearchReq` 必须 **`outFields("video_id")`** 带出非主键字段，再用 **`SearchResult.getEntity().get("video_id")`** 取（已对 2.5.8 字节码核准 `getEntity():Map<String,Object>`、`getId():Object`）；item_id 仍走 `getId()`。

**原因**：Milvus 搜索默认只返回主键 + 距离，非主键字段必须显式 `outFields` 声明才会带回——这是「主键语义父子不同」在 v2 检索侧的对应坑。

### 18. 子 hybrid 重灌源不看 embedding_status（与 5.2c-1 增量相反）

**问题**：5.2c-1 子表增量索引用 `listIndexableItems`（扫 `PENDING`/`FAILED`、维护子表 `embedding_status` 状态机）。子 hybrid 若照搬，会与 hybrid「整库重灌、独立集合」的语义打架。

**处理**：子 hybrid 用**新 mapper** `listAllItemsForHybrid`（全量未删子条目、**不看 embedding_status**，JOIN 父表带 category/tier）+ `countItemsForHybrid`；新 `KnowledgeReferenceItemHybridIndexService` 整库重灌。

**原因**：hybrid 是独立集合、drop 重建、不共享子表 `embedding_*` 状态机；重灌源必须是「全量事实」而非「增量待办」，否则重灌会漏掉已被增量标 INDEXED 的条目。

### 19. topic-search 不应误以为已有“中块 hybrid 集合”

**问题**：前端主链路切到 `/topic-search` 后，容易误以为打开 hybrid 开关就能让“中块主题召回”也走 BM25+dense。实际当前 hybrid schema 只有父卡片集合和子评论弹幕集合，没有中块 hybrid 集合。

**处理**：`KnowledgeReferenceTopicSearchService` 没有硬改中块召回源，而是保持中块 dense 作为主召回，再把父 hybrid 命中的 videoId 和子 hybrid 命中 item 上卷得到的 videoId 补进 top20 候选池；相关评论弹幕证据优先使用子 hybrid 命中，缺失再退子向量 / 代表证据。

**原因**：这样能复用现有 hybrid 索引和开关，避免为了“简单适配”新增第三套中块 hybrid schema、重灌接口和状态面板。业务上也符合当前主线：主题语义由中块 dense 负责，关键词和原话命中由父 / 子 hybrid 做补强。
