# 阶段 4.4.1.3：评论弹幕导入与仪表盘踩坑记录

## 1. 不要把导入接口做成后端采集接口

问题：

本轮目标是导入用户主动准备的样例文件，不是让后端根据 BV 号去抓取评论弹幕。

处理：

只提供 `MultipartFile` 上传，文件来源由用户本地脚本或人工整理完成。

原因：

这样能保持平台数据边界清楚，也避免项目主线被爬虫和风控问题拖走。

## 2. 不要直接替换旧反馈分析链路

问题：

阶段 4.3 的 `feedback/analyze` 已经能生成 LLM 报告，如果导入后只写明细表，旧接口就读不到样例。

处理：

导入成功后同步回填 `creator_user_feedback_detail`。

原因：

这样导入文件后仍能继续点击“分析反馈”，本轮只做增量升级，不重写已有闭环。

## 3. TXT 不能当成强结构数据

问题：

TXT 只是给人看的文本，标题、空行和评论元信息都可能变化。

处理：

TXT 只按当前脚本输出的区块做基础解析，并在响应里返回 warnings。

原因：

用户需要知道 TXT 解析不如 JSON 稳定，后续排查时不会误以为数据被精确结构化。

## 4. 规则分类只是第一版数据底座

问题：

评论弹幕分类如果一开始就全部交给 LLM，开发范围会扩大到批处理、失败重试、成本控制和结果回放。

处理：

先用轻量规则填充 `category`、`sentiment` 和 `is_noise`。

原因：

仪表盘需要的是可演示的数据结构。分类准确性后续可以单独升级，不影响导入、存储和展示链路。

## 5. 不要只保存评论文本

问题：

评论点赞量和回复量也是反馈信号。高赞评论通常代表更多观众共鸣，回复多的评论通常代表更多互动、争议或追问。

处理：

在 `creator_feedback_item` 中补充 `like_count` 和 `reply_count`，并在仪表盘增加“高反馈评论”区域。

原因：

复盘不是只看 AI 分类，也要看观众真实互动强度。否则会把一个 0 赞评论和一个高赞评论当成同等权重。

## 6. BV 入口要执行固定脚本，而不是暴露命令字符串

问题：

如果前端只展示命令文本、不接后端执行，用户还要自己打开命令行，体验会断在最后一步。

处理：

前端改成直接调用后端的 BV 拉取接口，后端只执行项目内固定脚本 `scripts/bilibili_feedback_fetcher.py`，并把输出落到 `export/bilibili_feedback`。

原因：

这样既保留 BV 使用入口，也不会把页面暴露成任意脚本执行入口；同时 JSON 导入和仪表盘可以在同一轮请求里完成。

## 7. 本轮未运行编译和测试

说明：

按项目约定，Maven、前端构建和运行任务由作者执行。

建议作者执行：

```bash
cd backend
mysql -u root -p < src/main/resources/sql/init.sql
mvn test

cd ../link-agent-frontend
npm run type-check
npm run build
```

## 8. BV 拉取失败不能只显示 Internal Server Error

问题：

页面点击“拉取并导入”后只显示 `Internal Server Error`，前端无法判断失败发生在任务查询、脚本定位、脚本执行、JSON 读取还是数据库入库。

处理：

1. 新增全局异常处理，统一返回 `message` 字段。
2. BV 脚本定位不再只依赖 `user.dir`，同时从 classpath 位置向上查找项目根目录。

原因：

后端在 IDE、命令行、Jar 包等不同方式启动时，工作目录可能不同。脚本属于项目根目录资源，根目录解析必须有兜底路径，否则脚本还没执行就会失败。
