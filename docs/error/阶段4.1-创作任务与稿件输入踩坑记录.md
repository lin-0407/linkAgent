# 阶段 4.1：创作任务与稿件输入踩坑记录

## 1. 不要把任务主表设计成大宽表

问题：

一开始容易把标题、简介、文稿、字幕都放进 `creator_task`。这样看起来简单，但后续接入评论、弹幕、文件、报告版本时，主表会不断膨胀。

处理：

拆成 `creator_task` 和 `creator_material`。

原因：

任务主表只表达“这次创作任务是什么”，材料表表达“这次任务有哪些输入”。这能让阶段 4.2 和 4.3 继续扩展材料或分析结果，而不频繁改任务主表。

## 2. 不要在 4.1 接入爬虫或 B 站账号授权

问题：

项目已经转向 B 站创作者工作台，很容易马上想接 BV 号、cookie、评论抓取、弹幕抓取。

处理：

阶段 4.1 只允许用户主动输入标题草稿、简介草稿、文稿和字幕。

原因：

简历项目第一版的竞争力来自 AI 应用闭环和工程可观测，不来自平台数据抓取。爬虫和账号授权会把合规、反爬和异常处理复杂度提前引入，影响主线。

## 3. MyBatis 查询结果不要直接依赖 response record

问题：

MyBatis 可以映射 JavaBean 很稳定，但直接映射 Java record 可能受到构造参数名、编译参数和框架版本影响。

处理：

数据库查询对象使用 `CreatorTaskRecord`、`CreatorMaterialRecord`、`CreatorTaskSummaryRecord`，Service 层再转换成 response record。

原因：

这和项目已有 `LongTermMemoryRecord` 风格一致，也更适合当前学习阶段定位问题。

## 4. 至少一项材料的校验要放在请求对象中

问题：

如果只在 Service 里判断材料是否为空，接口层不会形成统一的参数校验反馈。

处理：

在 `CreatorTaskCreateRequest` 中使用 Jakarta Validation 的 `@AssertTrue`。

原因：

这样可以继续遵守“所有对外 API 必须有入参校验”的项目约束，并且不需要额外引入 validation 库。
