# 阶段 4.2：发布前优化 Agent 踩坑记录

## 1. 不要直接把 LLM 输出当成稳定 JSON

问题：

LLM 很容易输出解释文本、Markdown 代码块或者夹杂多余说明，不能假设它每次都严格只给 JSON。

处理：

在 `rawOutput` 里保留原文，再尝试截取 JSON 并解析。

原因：

这样即使解析失败，也不会丢掉原始结果，后面还能人工回放和调 Prompt。

## 2. 不要一开始就把建议拆成很多子表

问题：

标题建议、标签建议、卖点、风险点看起来像不同实体，但在 MVP 阶段它们本质上都是一次发布前优化结果的一部分。

处理：

先放进 `creator_suggestion` 一张表。

原因：

先把功能跑通，等后续真的需要版本管理、人工编辑和对比评测，再考虑拆表。

## 3. 不要把 SSE 强行塞进建议生成接口

问题：

一看到“Agent”就容易想顺手做流式过程展示，但这会让第一版接口、前端和错误处理一起变复杂。

处理：

阶段 4.2 先只做分析和查询。

原因：

SSE 更适合作为下一步独立工作项，单独做会更容易排查前端渲染和后端推送问题。

## 4. 任务状态需要同步更新

问题：

如果只保存建议，不更新任务状态，列表页和详情页就看不出这个任务已经完成了发布前分析。

处理：

在分析成功后把任务状态更新为 `PRE_PUBLISH_ANALYZED`。

原因：

这样 4.1 和 4.2 就形成了一个最小的业务阶段流转，后面再加反馈分析和复盘时更自然。
