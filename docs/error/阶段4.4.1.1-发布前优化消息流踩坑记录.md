# 阶段 4.4.1.1 - 发布前优化消息流踩坑记录

## 1. 消息返回不能只依赖插入对象

问题：

`creator_workflow_message` 插入后，如果直接把插入前的 Java 对象返回给前端，`id` 和 `createTime` 可能为空。

处理：

在 `CreatorWorkflowMapper` 中补充 `findMessageByMessageId`，插入后重新查询消息记录，再返回给前端。

原因：

第一版没有强制使用 MyBatis generated key 和数据库默认时间回填机制，重新查询更直观，也方便作者理解数据库默认值来自哪里。

## 2. SSE 不能先于消息落库

问题：

如果一开始先做 SSE，前端能看到动态消息，但刷新页面后可能没有历史数据可恢复。

处理：

本轮先实现 `creator_workflow_session` 和 `creator_workflow_message`，SSE 放到下一轮。

原因：

消息流的核心不是“看起来实时”，而是任务级上下文可以持久化、恢复和追踪。

## 3. 自动启动工作流要避免旧任务残留

问题：

前端切换任务时，如果新任务工作流加载失败，旧任务的消息可能继续显示。

处理：

`loadPrePublishWorkflow` 开始时先清空当前会话、消息、输入框和选中消息，再请求后端。

原因：

这种失败状态比空状态更危险，因为用户会误以为旧材料属于当前任务。

## 4. 多 session 预留属于过度设计

问题：

最初设计时允许同一个 `taskId + stage` 创建多条 `creator_workflow_session`，并通过 `resumeLatest` 恢复最新会话。

这个设计存在隐患：

1. 前端没有展示“会话轮次列表”。
2. 用户无法选择前一轮、后一轮，也无法做轮次对比。
3. 多条 session 会变成数据库里用户看不见的隐藏复杂度。
4. 后续开发者可能误以为“重新生成建议”应该新建 session，导致同一任务的消息和结果被拆散。

处理：

当前阶段应该收敛为：

```text
1 个 task + 1 个 stage = 1 个 workflow session
```

用户多次补充要求、重新生成建议，都先作为同一个 session 下的多条 message / result 追加。

原因：

多 session 只有在产品明确提供“轮次选择、历史对比、版本管理”时才有业务意义。当前 MVP 页面没有这个入口，所以不应该提前引入多 session 复杂度。

后续修正建议：

1. `creator_workflow_session` 增加 `task_id + stage` 唯一约束。
2. 后端启动发布前工作流时，固定按 `taskId + PRE_PUBLISH` 查询已有会话。
3. 去掉或弱化 `resumeLatest` 概念，避免暗示当前阶段支持多轮会话选择。
4. 文档中明确：当前多轮调整属于同一 session 内的消息追加，不是多个 session。

## 5. 状态枚举必须写清楚中文含义

问题：

初版 SQL 注释只写了：

```text
CREATED / CONTEXT_LOADING / WAITING_USER_INPUT / RUNNING / WAITING_CONFIRMATION / CONFIRMED / FAILED / CANCELLED
```

这会让读表的人只能猜英文状态的业务含义。

处理：

已将 SQL COMMENT 和 Java 枚举注释改为“英文值 + 中文含义 + 业务解释”。

原因：

英文枚举值用于代码稳定引用，中文解释用于开发者理解业务状态。项目作者是中文使用者，数据库和枚举注释必须降低理解成本。
