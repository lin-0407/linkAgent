## 2. 实际遇到的问题

### 2.1 MyBatis 记录映射按列顺序装配

首次真实数据库运行中，`CreationMediaLink.stage` 读回为 `null`：`SELECT` 列顺序是 `... version_id, stage, processing_job_id ...`，而 record 构造参数顺序是 `... versionId, processingJobId, preflightReviewId, stage ...`。

原因：MyBatis 在未开启 `argNameBasedConstructorAutoMapping` 时按结果集列顺序装配 record 构造参数，与列名无关。本项目其他 mapper 的列顺序恰好与 record 一致，所以之前没有暴露。

修正：`CreationMediaMapper.COLUMNS` 与 `candidates()` 的列顺序改为与 record 完全一致，并加注释说明。

### 2.2 授权额度为 0 时依赖阶段无法预留

新增的“依赖阶段预留”测试最初沿用了通用的 `fullLease` 辅助方法，其整片授权上限为 0。`reserveDependency` 按既有规则拒绝“本次授权剩余金额不足”，说明授权边界对媒体阶段同样生效。

修正：测试改为单独创建 5 元授权的整片运行，而不是放宽生产校验。

### 2.3 视频理解预估缺失时不应直接失败

加入费用预留后，`PreflightVideoAnalysisServiceTest` 的 5 项用例因为预处理任务没有 `estimatedVisualCostUsd` 而失败。

修正：预估缺失时退回该能力的配置上界（`MEDIA_VIDEO` 默认 0.30 美元），不把“没有预估”当成错误；真实预估存在时仍优先使用预估。

### 2.4 发布包幂等 SQL 需要真实数据库验证

`CreationPackageMapper.begin` 使用 `INSERT ... ON DUPLICATE KEY UPDATE` 表达“READY 不重建、未完成可接手”。初版使用已弃用的 `VALUES()` 写法，且没有真实数据库用例覆盖；补了一条真实 MySQL 用例（接手改写代数、READY 后重复受理不改写对象事实）后，改为行别名写法并通过。

顺带确认：MySQL 对 ODKU 的更新计为 2 行、无变化计为 0 行，业务断言不能把返回行数当成成功标志。
