# 阶段 4.4：创作复盘报告踩坑记录

## 1. 不要只看本视频就下“优缺点”结论

问题：

只根据本视频材料和评论弹幕，很难判断本视频相对同类内容的优缺点。这样的复盘容易变成自我总结，缺少参照系。

处理：

新增竞品视频表和竞品分析报告表，允许用户主动整理同类型视频信息，再由系统生成竞品对照结论。

原因：

真实创作复盘需要基准参照，但 MVP 阶段仍然不能变成自动抓取平台数据。

## 2. 不要把竞品视频直接塞进复盘报告表

问题：

如果把竞品视频信息直接放进 `creator_report`，原始材料和 LLM 分析结果会混在一起，后续无法重跑竞品分析。

处理：

拆成 `creator_competitor_sample` 和 `creator_competitor_report`。

原因：

这样既能保留用户主动提供的原始参照，又能独立保存结构化竞品分析结果。

## 3. 不要把复盘报告做成对评论分析报告的简单转发

问题：

如果复盘接口只把 `creator_llm_feedback_report` 再包一层，报告会缺少发布前建议、任务材料和竞品分析上下文。

处理：

单独建立 `creator_report`，在服务层同时读取任务材料、发布前建议、反馈分析结果和竞品分析结果。

原因：

复盘报告是新业务产物，不是原有反馈报告的别名。

## 4. 不要把复盘输入重新设计成大文本提交

问题：

如果接口让用户再次提交完整稿件、建议、反馈和竞品视频，复盘就会变成重复录入。

处理：

复盘接口只接收少量指导字段，主体数据全部从数据库读取。

原因：

这样才能保持“前置分析结果 -> 复盘汇总”的闭环。

## 5. 不要过早引入版本管理

问题：

复盘报告本质上会演化出版本、批注和导出，但这些能力在第一版会明显增加复杂度。

处理：

当前阶段只保留每个任务一份最新复盘报告。

原因：

先让链路跑通，再补历史版本和审阅能力。
