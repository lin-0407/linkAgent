# 阶段 5.1：跨分区视频案例知识库踩坑记录

> 本文件记录 5.1（a/b/c）实现中**有意规避或必须特殊处理的技术坑**，均可从代码与注释实证，作为后续维护 / 排查与 5.2 接续的参照。
> 末尾「§验证」只列**建议命令与判断标准**（编译 / 运行由作者执行），不替作者宣称结果。若你在实际编译 / 运行中遇到本文未覆盖的报错，告诉我，我补进对应小节。

## 1. 第二个 VectorStore Bean 会打断反馈侧的注入

**问题**：反馈 RAG 通过 `ObjectProvider<VectorStore>.getIfAvailable()` 注入向量库。知识库若也注册一个 `VectorStore` 类型的 Spring Bean，容器里就有两个 `VectorStore`，`getIfAvailable()` 会抛 `NoUniqueBeanDefinitionException`，把原本好好的反馈链路一起带崩。

**处理**：`KnowledgeVectorStore` 做成普通 Bean，**内部私有持有** `MilvusVectorStore`，绝不把它暴露成 `VectorStore` 类型 Bean；索引服务直接注入 `KnowledgeVectorStore` 这个持有者，通过 `getVectorStore(): Optional<VectorStore>` 取用。

**原因**：知识库要的是「专用集合 + 1024 维」，与反馈集合语义、维度都不同，本就不该共用一个 Bean。把它藏进普通 Bean 内部，从根上消除多 `VectorStore` Bean 歧义，比事后用 `@Primary` / `@Qualifier` 打补丁更干净。

## 2. MilvusVectorStore 不是 Spring Bean，必须手动 afterPropertiesSet()

**问题**：自行 `MilvusVectorStore.builder(...).build()` 出来的实例不是 Spring 托管 Bean，容器不会替它回调 `afterPropertiesSet()`。直接拿去写入，会因为集合 schema 根本没建出来而在**首次写入时**失败。

**处理**：`build()` 后**手动调用一次 `store.afterPropertiesSet()`**，再标记 `ready=true`。

**原因**：`initializeSchema(true)` 只是声明「需要建集合」，真正触发建集合的动作在 `afterPropertiesSet()` 里。脱离 Spring 生命周期自管 Bean 时，这一步得自己补。

## 3. Qwen Embedding 单批硬上限 10，不能照抄反馈侧的 25

**问题**：反馈侧索引批大小是 25。知识库若照抄，调用 Qwen `text-embedding-v3/v4` 的 OpenAI 兼容端点时会报 `batch size invalid` —— 兼容模式单批硬上限就是 **10**。

**处理**：`knowledge.rag.index-batch-size` 默认 **10**，索引服务按它分批 `add`；并 `Math.max(1, ...)` 兜底防误配 0 死循环。

**原因**：不同 Embedding 供应商的批量上限不同，是供应商侧硬约束，不能跨链路照搬常量。

## 4. Embedding 维度必须与集合维度严格一致

**问题**：集合按 1024 维建好后，若 Embedding 实际输出别的维度（例如沿用反馈默认 1536），写入会报维度冲突。

**处理**：`knowledge.rag.embedding-dimension` 在 `application.yml` 里直接绑定到 `${LLM_EMBEDDING_DIMENSIONS:1024}` 这同一个环境变量，让「集合维度」与「Embedding 输出维度」共用一个真相源；启用知识库时务必把 `LLM_EMBEDDING_DIMENSIONS` 设为 1024（Qwen v4 推荐值）。

**原因**：维度是两处各自配置时最容易漂移的参数，用同一变量绑定能从配置层消除不一致。

## 5. EMBEDDING_MODEL_TYPE=none 时没有 EmbeddingModel Bean

**问题**：演示环境默认 `EMBEDDING_MODEL_TYPE=none`，此时容器里**没有** `EmbeddingModel` Bean。若用构造器硬注入 `EmbeddingModel`，应用直接启动失败。

**处理**：用 `ObjectProvider<EmbeddingModel>` 软注入，配合「业务开关 enabled + EmbeddingModel 是否存在」两层判断决定是否构建向量库；任一不满足就保持降级、不抛异常。

**原因**：RAG 是「可关基础设施」，关闭态必须能正常启动。软注入是 Spring 里处理「可能不存在的依赖」的标准手法。

## 6. 按 BV 去重表达不成数据库唯一约束

**问题**：想「同一 BV 不重复入库」，但 `bv_id` 可空（seed / 手动无 BV），且去重要排除软删（`is_deleted=0`）。带过滤条件、又允许多个 NULL 的「唯一」，普通唯一索引表达不了。

**处理**：去重放在导入逻辑：本批用 `Set<String> seenBvIds` 去本批内重复，配合 `countByBvId`（`is_deleted=0`）查库内已存在；命中则跳过计入 `skippedCount`。无 BV 的条目不参与去重。

**原因**：业务幂等条件（可空 + 软删过滤）超出了数据库唯一约束的表达力，放在服务层判断更贴合语义，也便于返回 `skippedCount` 给前端确认幂等。

## 7. MyBatis 回写 null 标量参数要显式 jdbcType

**问题**：`updateQualityScore` 的 `quality_score` 允许为 `null`（view 缺失 / 分区样本不足时不打分）。MyBatis 遇到值为 `null` 的标量参数无法推断 JDBC 类型，会直接报错。

**处理**：SQL 里写成 `#{qualityScore,jdbcType=DECIMAL}`，显式声明类型。

**原因**：MyBatis 靠参数值推断 JDBC 类型，`null` 时推断不出来；对「合法地写 NULL」的列，必须显式给 `jdbcType`。

## 8. ONLY_FULL_GROUP_BY 下的打分聚合查询

**问题**：打分输入用一条 `LEFT JOIN + 条件 SUM` 一次查齐「父表 6 项热度 + 子表正 / 负向条数」，`GROUP BY` 后还要 `SELECT v.*` 这些非聚合列。MySQL 默认开启 `ONLY_FULL_GROUP_BY`，直接 SELECT 非分组列会报错。

**处理**：`GROUP BY v.id`（主键）。其余 `v.*` 列对主键**函数依赖**，MySQL 在此情况下允许直接 SELECT；子表无记录时 `SUM(CASE...)` 自然得 0（非 null）。

**原因**：用主键分组让数据库识别函数依赖，既满足 `ONLY_FULL_GROUP_BY`，又用一次查询避免「先查视频再逐条查子表」的 N+1。

## 9. 质量打分必须与导入同一事务

**问题**：导入后要「对受影响分区重算全部视频质量分」，而重算靠 `SELECT` 读该分区视频。若打分另起事务，读不到导入事务里**刚插入、尚未提交**的新视频——新分区的第一条会永远算不出分。

**处理**：`recomputeCategories` 标 `@Transactional`，被已在事务中的导入流程调用时按 `REQUIRED` 合并进同一事务，从而读到未提交的新行，算完连同导入一起原子提交。

**原因**：归一化是分区相对值，新样本会改变该分区 min/max，重算与导入逻辑上是一个原子操作，必须在同一事务可见性下完成。

## 10. 向量索引服务不能加 @Transactional

**问题**：与 §9 相反——索引服务若包在 DB 事务里，一旦某批 Milvus 写入异常触发回滚，`embedding_status` 的回写会跟着回滚，但 Milvus 那边的实际写入**不归 DB 事务管**、不会跟着回滚，状态与向量库现状就分叉了。

**处理**：索引服务**不加 `@Transactional`**，按批 `add` + 按批回写状态；部分批失败写 `failedCount` / `warnings`，不整体回滚。

**原因**：跨「外部向量库 + 本地 DB」两套存储时，用「按批提交、状态如实反映每批结果」代替「一个大事务」，才能让 `embedding_status` 真实可信。这与 §9「纯 DB 内的打分用同一事务」是按存储边界做的不同选择。

## 11. 脚本路径 / 产物目录不能依赖当前命令行目录

**问题**：后端 `ProcessBuilder` 调脚本、脚本写产物，若都用「相对当前目录」的路径，从不同工作目录（或打包后）启动时会找不到脚本，产物也可能落到仓库外。

**处理**：后端向上逐级探测「包含 `scripts/bilibili_reference_fetcher.py` 的目录」作为项目根，固定写入项目根下 `export/bilibili_reference` 并校验该目录在根之下；脚本侧用 `PROJECT_ROOT = Path(__file__).resolve().parents[1]` 锚定默认输出目录。

**原因**：产物是运行副产物，应稳定落在项目内被 `.gitignore` 忽略的位置，与启动目录无关（沿用反馈脚本同款教训）。

## 12. argparse 父子参数顺序的经典坑

**问题**：给 `rank` / `bv` 两个子命令配通用参数（`--max-comments` 等）时，若直接加在子解析器上，通用参数写在子命令之后（`... rank --max-comments 50`）会因 argparse 父子顺序解析报错。

**处理**：用一个 `add_help=False` 的「父解析器」承载通用参数，再通过 `parents=[common]` 挂到各子命令上，允许通用参数写在子命令之后。

**原因**：两个子命令共享同一批通用参数，用 `parents=` 复用比逐个重复声明更省、且顺序友好。

## 13. ranking/v2 是滚动综合榜，不是按天 / 周 / 月切分

**问题**：`--source` 取 `bilibili_rank_daily/weekly/monthly` 容易让人误以为脚本真按时间维度取了不同榜单。实际 `ranking/v2` 返回的是**滚动综合榜**。

**处理**：脚本帮助文本里明确标注：日 / 周 / 月只是**来源溯源标注**，并非真正按时间切分；三个值落到导入契约的 `source` 字段，用于追溯而非表示时间范围。

**原因**：避免后续基于 `source` 做「按时间段分析」的错误假设。同理，脚本采集时 `tags` 暂留空（标签需额外接口），别误以为是漏采。

## 14. 规则情绪分类要「负向优先」

**问题**：纯关键词分类时，像「不实用」「不是干货」这类含正向词（实用 / 干货）却实为负向的内容，若先判正向会被误标 POSITIVE。

**处理**：`classifySentiment` 先扫负向关键词、命中即 NEGATIVE，再扫正向，否则 NEUTRAL。

**原因**：规则法是 5.1 的「先简单、零 LLM 成本」选择；负向优先是用最小代价压住最常见的一类误判。真要更准，留待后续按需替换为模型分类（当前不过度设计）。

## 15. 类级注释会随功能生长而过期（提醒）

**问题**：5.1a/b/c 是分步叠加实现的，部分类级 javadoc 仍写着「阶段 5.1a 只做导入落库 + 分页列表」，而该类实际已串入清洗（5.1b）与打分（5.1c）。注释与代码出现轻微漂移。

**处理**：本轮以接口说明文档（`/docs/reference/跨分区视频案例知识库说明.md`）为功能现状准绳；类级注释的「本阶段只做 X」措辞留作演进痕迹，后续触碰相关类时顺手校正即可，不专门起一轮改动（surgical change，避免无谓 diff）。

**原因**：分阶段叠加开发难免留下阶段性措辞；与其一次性大改注释，不如让权威说明集中在 reference 文档，注释在下次自然修改时同步。

## 16. Spring AI Embedding 的 base-url 不应携带 compatible-mode 路径

**问题**：Spring AI 1.1.4 的 OpenAI Embedding 默认 `embeddings-path=/v1/embeddings`，请求时用 `RestClient.baseUrl(baseUrl)` 再 `uri(embeddingsPath)`。如果把 `LLM_EMBEDDING_BASE_URL` 配成 `https://dashscope.aliyuncs.com/compatible-mode/v1`，默认 path 可能把 `compatible-mode` 路径覆盖掉，或形成错误路径，检索时表现为 `HTTP 404 - No response body available`。

**处理**：`application.yml` 暴露 `spring.ai.openai.embedding.embeddings-path`，并默认设为 `/compatible-mode/v1/embeddings`；推荐配置改为 `LLM_EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com` + `LLM_EMBEDDING_PATH=/compatible-mode/v1/embeddings`。

**原因**：`base-url` 负责协议和域名，`embeddings-path` 负责供应商路径，二者分开后不会被 RestClient 的绝对路径规则覆盖。Embedding 失败会导致向量检索无法生成 query 向量，所以中块召回会降级到 SQL。

## 17. 单 BV 采集不能只依赖 tname 取分区

**问题**：前端单 BV 导入时不填写分区，按设计应使用视频自身分区。但实测 `export/bilibili_reference/BV1oTLo6ZEPW_reference.json` 里顶层 `category` 和 `videos[0].category` 都是空，导致父表 `creator_reference_video.category` 如实落为空，后续分区质量分和同赛道过滤都用不上。

**处理**：脚本 `build_video_item` 不再直接写 `video_info.get("tname")`，改为 `resolve_video_category`：先取非空 `tname`；如果 `tname` 空但 `tid` 存在，用内置 `tid -> 分区名` 映射兜底；如果连 `tid` 也没有，才保留为空并输出提示。

**原因**：后端导入逻辑本身没有丢字段，`resolveCategory(video.category(), defaultCategory)` 已经是“视频自身分区优先，整批默认分区兜底”。根因在采集产物：B 站接口字段不稳定时只取 `tname` 会把可恢复的分区信息丢掉。用 `tid` 兜底能尽量保留分区语义，同时不要求用户必须手动填。

```bash

python -m py_compile scripts/bilibili_reference_fetcher.py
python scripts/bilibili_reference_fetcher.py -h
python scripts/bilibili_reference_fetcher.py bv not-a-bv      # 期望：业务错误，不吐 traceback

```

接口层判断标准：
1. **RAG 关闭（默认）**：`POST /import` 导入 seed → `GET /` 列表可见 → `GET /index/status` 返回 `ragEnabled=false`、`retrievalMode=SQL`；`POST /index/rebuild` 返回 400（提示开关未启用）。
2. **幂等**：同一批带 BV 的案例二次 `POST /import`，`importedCount=0`、`skippedCount` 等于重复数。
3. **边界**：空 `videos` / 非白名单 `source` / 非法 `tier` / 缺 `category` → 400 且提示清晰，不吐堆栈。
4. **隔离**：知识库 Bean 存在时，反馈侧追问 / 索引接口仍正常（不报 `NoUniqueBeanDefinitionException`）。
5. **开启 Qwen v4 + Milvus 后**：`index/rebuild` 成功，`embedding_status` 回写 INDEXED，单批 ≤10；`index/status` 的 `retrievalMode` 变 `VECTOR`。
