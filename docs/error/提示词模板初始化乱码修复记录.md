# 提示词模板初始化乱码修复记录

## 1. 问题

执行 `init.sql` 初始化后，`llm_prompt_template` 中部分中文提示词可能出现乱码，影响模型输出质量和前端设置面板展示。

这个问题不能只看 `init.sql` 当前正文是否正确。原因是提示词种子使用 `ON DUPLICATE KEY UPDATE`，原本不会覆盖已有 `content`。如果第一次初始化已经把乱码写进库里，后续即使 SQL 文件修好了，已有 `prompt_key` 也会保留坏正文。

## 2. 排查结论

当前源码侧没有发现提示词正文已经乱码。

更可能的风险点是执行链路：

| 环节 | 风险 |
|---|---|
| 手工执行 SQL | 未指定 `--default-character-set=utf8mb4` 时，客户端可能按非 UTF-8 解析中文 |
| JDBC 示例配置 | `.env.example` 曾写 `characterEncoding=utf8mb4`，容易误导连接参数 |
| 已有数据库 | 历史乱码正文不会被普通重复初始化覆盖 |

Docker Compose 的 `db-init` 已指定 `--default-character-set=utf8mb4`，风险主要集中在手工执行和历史脏数据。

## 3. 修复

本轮做了三处处理：

1. `init.sql` 顶部增加 `SET NAMES utf8mb4`。
2. `init.sql` 执行说明改为 `mysql --default-character-set=utf8mb4 -u root -p < init.sql`。
3. 提示词种子重复执行时，只有已有正文命中乱码指纹才覆盖 `content`。

乱码指纹包括 `�`、连续问号、常见 UTF-8 被错误解码后的 `Ã`、`Â`、`ä`、`å`、`æ`、`ç`，以及常见中文二次乱码片段。

## 4. 为什么不全量覆盖

提示词表支持 DB 热更新。开发者可能已经通过设置面板调优过正文。

如果每次初始化都执行 `content = VALUES(content)`，会把人工调优覆盖回种子版本，热更新就失去了维护价值。因此本轮只修复明显坏数据，不重置正常正文。

## 5. 回滚

修复前先备份：

```sql
CREATE TABLE llm_prompt_template_backup_20260705 AS
SELECT *
FROM llm_prompt_template;
```

如果修复后发现误覆盖，可按 `prompt_key` 回滚：

```sql
UPDATE llm_prompt_template t
JOIN llm_prompt_template_backup_20260705 b
  ON t.prompt_key = b.prompt_key
SET t.content = b.content,
    t.prompt_type = b.prompt_type,
    t.scene = b.scene,
    t.description = b.description,
    t.is_deleted = b.is_deleted;
```

## 6. 后续注意

1. 手工执行初始化脚本时必须指定 UTF-8 客户端字符集。
2. 新增提示词种子时不要改成无条件覆盖 `content`。
3. 如果后续真的要重置所有提示词，先让作者确认是否放弃设置面板里的人工调优内容。
