# 阶段4 - 创作工作台踩坑总结

## 一、数据库与事务

### 1.1 任务主表大宽表问题
**问题**：将标题、简介、文稿、字幕、评论、弹幕全部放入 `creator_task` 单表。
**原因**：单表设计看似简单，但后续每接入一种材料类型都需要改主表结构，扩展成本线性增长。
**解决**：拆分为 `creator_task`（任务元信息）和 `creator_material`（材料输入），评论弹幕另立 `creator_feedback` 表，竞品视频另立 `creator_competitor_sample` 表。

### 1.2 `@Transactional` 不能包裹 Milvus 写入
**问题**：在 `IndexService.rebuild()` 加 `@Transactional` 后，Milvus 写入异常触发 MySQL 事务回滚，`embedding_status` 回到旧值，但 Milvus 里向量已写入，状态与实际分叉。
**原因**：事务只能保证 MySQL 一致性，无法回滚已写入 Milvus 的向量数据。
**解决**：不加 `@Transactional`，按批逐条提交并逐条更新 `embedding_status`，让状态始终真实反映向量库现状。

### 1.3 已有本地库不会因 `CREATE TABLE IF NOT EXISTS` 自动补列
**问题**：`init.sql` 新增列后，已有 `creator_suggestion`、`creator_eval_result` 等表不会自动新增字段，运行时出现 `Unknown column` 错误。
**原因**：`CREATE TABLE IF NOT EXISTS` 只在表不存在时生效，已存在表不会被修改。
**解决**：在 `init.sql` 中加入基于 `information_schema.COLUMNS` 的条件式 `ALTER TABLE`，本地重复执行不会重复加列。演示环境可删除旧数据卷后重建。

### 1.4 SQL 初始化脚本不能残留半截兼容语句
**问题**：`sql/init.sql` 中遗留被截断的动态 SQL 片段，文件可读但执行时卡死初始化流程。
**解决**：在新增评测表前先补全所有已有表的兼容补丁语句。

### 1.5 软删除不能省略上下游关联
**问题**：任务硬删除后，历史分析记录（建议、反馈报告、复盘报告）引用断裂。
**解决**：任务和材料使用软删除（逻辑删除标记），历史结果继续保留，保证前后端证据链完整。

### 1.6 多 session 设计过度——同 task + stage 应唯一
**问题**：最初允许同一 `taskId + stage` 创建多条 `creator_workflow_session`，但前端无轮次选择入口，多条 session 变成隐式复杂度。
**解决**：收敛为 1 个 task + 1 个 stage = 1 个 session，`creator_workflow_session` 增加 `task_id + stage` 唯一约束，多轮调整属于同一 session 内的消息追加。

### 1.7 MyBatis 查询结果不要直接依赖 Java record
**问题**：MyBatis 映射 Java record 可能受构造参数名、编译参数和框架版本影响，不如映射普通 JavaBean 稳定。
**解决**：数据库查询对象使用普通类（Record 后缀），Service 层再转换成 response record。

## 二、Agent 与 LLM 调用

### 2.1 LLM 输出不是稳定 JSON
**问题**：DeepSeek 等模型可能输出解释文字、Markdown 代码块或多余说明，直接按 JSON 解析会丢失结果。
**原因**：LLM 本质是语言生成，不保证输出格式严格符合 JSON 语法。
**解决**：所有 LLM 调用保留 `rawOutput` 原始文本，再尝试截取 JSON 解析。解析失败时标记为 `RAW_ONLY`，保证原始结果不丢失，后续可回放调 Prompt。

### 2.2 发布前建议生成不应直接推进任务状态
**问题**：阶段 4.2 同步接口在生成建议后直接更新 `PRE_PUBLISH_ANALYZED`，工作流复用该方法时用户未确认建议但任务状态已推进。
**解决**：抽取 `generateSuggestion()` 只负责生成和保存，任务状态更新由独立的确认动作触发。"AI 生成结果"和"用户采用结果"是两个独立动作。

### 2.3 发布前优化不能先做 SSE
**问题**：先做 SSE 会让接口、前端和错误处理同时变复杂，且刷新页面后没有历史数据可恢复。
**解决**：阶段 4.2 先做同步分析和查询，SSE 作为后续独立工作项；工作流消息先落库再发布 SSE。

### 2.4 任务状态需要同步更新形成业务流转
**问题**：只保存分析结果不更新任务状态，列表页和详情页看不出当前业务进展。
**解决**：分析成功后更新对应状态字段（如 `PRE_PUBLISH_ANALYZED`），形成 DRAFT -> ANALYZED -> REVIEWED 的最小业务闭环。

### 2.5 失败后不能把会话锁死
**问题**：LLM 调用失败后会话状态停在 `FAILED` 且禁止重试，用户只能重建任务。
**原因**：失败通常源于模型服务、网络或输出格式问题，不代表业务会话不可继续。
**解决**：`FAILED` 状态允许用户继续发送补充要求并再次触发分析。

### 2.6 错误信息截断需为后缀预留长度
**问题**：`TextUtil.abbreviateWithSuffix(value, 500, "...")` 的最终长度可能超过字段长度，因 suffix 追加后总长超出限制。
**解决**：截断长度设为低于字段定义值（如 VARCHAR(500) 对应截断 480），确保后缀追加后不超限。

### 2.7 只改 Prompt 不改输出结构，建议仍然泛泛而谈
**问题**：只在 Prompt 写"请更有深度"但不改响应结构，模型倾向把深度压缩到几句泛泛理由。
**解决**：新增 `creatorDilemma`、`audienceHook`、`contentPositioning`、`actionableRevisionPlan` 等结构化字段，要求模型回答创作者困境、观众动机和下一步动作。

### 2.8 RAG 不是低质量建议的第一解法
**问题**：建议质量差的根因是分析框架浅，不是证据不足。直接接入 RAG 会把问题变成"带证据的浅建议"。
**解决**：先完成建议质量结构升级（2.7），再考虑将反馈追问或外部资料作为 RAG 证据源。

### 2.9 应优先解决质量结构而非数据抓取问题
**问题**：各子阶段多次倾向接入 BV 号、Cookie、评论抓取，但合规、反爬和异常处理会提前引入，偏离 AI 应用闭环主线。
**解决**：MVP 阶段所有输入由用户主动提供，爬虫和开放平台接入单独评估。

## 三、SSE 与消息流

### 3.1 消息必须先落库再发布 SSE
**问题**：先推送 SSE 再落库，若落库失败则前端看到的消息无法恢复。
**解决**：消息插入数据库后通过 `findMessageByMessageId` 重新查询完整字段，再由 SSE 事件发布。SSE 断线重连时重放当前会话已有消息，前端保留 HTTP 恢复按钮。

### 3.2 POST 和 SSE 同一条消息会导致前端重复
**问题**：前端发送补充消息时，POST 返回新消息，同时 SSE 也推送同一条 `message_created`，直接 push 出现重复。
**解决**：前端按 `messageId` 做 upsert —— 存在则替换，不存在则按 `sequenceNo` 排序插入。

### 3.3 SSE 不能是唯一状态来源
**问题**：SSE 断线、页面刷新或浏览器切后台时，前端可能错过事件。
**原因**：实时性只是体验增强，数据库才是可恢复状态。
**解决**：SSE 建立连接时重放已有消息；前端保留 HTTP 刷新按钮；消息落库为 SSE 发布的前置条件。

### 3.4 Nginx 代理 SSE 必须关闭缓冲
**问题**：Nginx 默认开启 `proxy_buffering`，工作流消息会缓存到最后一起返回。
**解决**：在 `/api` 代理段显式设置 `proxy_buffering off`、`proxy_cache off`，并拉长超时时间。

## 四、前端交互与状态

### 4.1 任务切换时必须清理旧状态
**问题**：切换任务后，旧任务的建议、仪表盘、消息、结果弹窗等状态可能残留。
**原因**：前端响应式状态在组件卸载时不会自动清空。
**解决**：创建任务、选择任务、重置工作台、重新保存样例时统一清空当前会话、消息、输入框、选中消息和 `resultModalTarget`。

### 4.2 任务更新后材料变化需回退状态
**问题**：修改标题、简介等材料后，旧建议和复盘结果与新材料不一致。
**解决**：只要材料字段发生变化，自动将任务状态退回 `DRAFT`，让用户重新生成后续结果。

### 4.3 文件选择状态不能只靠界面重建
**问题**：前端文件输入框重新渲染后，`File` 引用仍留在响应式状态里。
**解决**：切换任务、取消编辑、保存修改和导入完成后，同步清空文件 ref 并重建输入框 key。

### 4.4 样例文本不应占据真实输入区
**问题**：把演示用稿件、评论写成表单初始值，用户分不清哪些内容会真实提交。
**解决**：输入区初始化为空，改为简短框内隐性提示。可编辑指导仅在点击"恢复默认指导"时写入推荐内容。

### 4.5 `click.self` 不能准确判断弹窗遮罩关闭
**问题**：用户在弹窗内按下鼠标拖到弹窗外松开时，最终点击事件落在遮罩上，导致误关闭。
**解决**：记录 `pointerdown` 是否从遮罩开始，只有按下起点和最终点击目标都为遮罩时才关闭窗口。

### 4.6 删除需要二次确认
**问题**：任务列表直接放删除按钮，误点成本高。
**解决**：删除先进入侧栏确认条，用户再次确认后才真正执行。

### 4.7 编辑模式和创建模式不能共用空状态
**问题**：用户容易误以为在改当前任务，实际在新建。
**解决**：前端任务表单拆分为"创建/编辑"双模式，标题和按钮文案明确当前状态。

### 4.8 结果弹窗与入口分离
**问题**：建议、仪表盘、报告直接放在输入表单下方，页面变成"边填边读"的混合状态。
**解决**：大块结果迁移到 `creator-result-modal` 独立弹窗，主页面只保留入口按钮。发布前建议的确认面板和"采用本轮建议"按钮也放入弹窗内部。

### 4.9 发布前建议结果入口需显式可见
**问题**：用户关闭自动弹窗后，不知道 AI 分析结果入口在哪里。
**解决**：在发布前阶段表单下方增加"发布前 AI 分析结果已生成"入口卡片。

### 4.10 偏好模式需要快照而非实时读取
**问题**：结果弹窗直接读取当前 `preferenceMode`，用户生成后切换开关导致弹窗错误展示。
**解决**：前端在触发建议生成时保存 `preferenceMode` 快照，结果弹窗只展示生成时的模式。

### 4.11 前端可用态应与后端校验一致
**问题**：用户无材料直接提交后才收到后端校验错误。
**解决**：前端根据材料是否含有效文本禁用对应提交按钮，后端校验保留作为最终保护。

### 4.12 反馈追问结果不能跨数据版本残留
**问题**：用户重新导入样例或重新分析反馈后，之前的追问回答可能仍引用旧证据。
**解决**：保存样例、导入文件、BV 拉取和重新分析反馈时清理 `feedbackChatResult`。

## 五、接口设计与校验

### 5.1 至少一项材料的校验放在请求对象中
**问题**：只在 Service 里判断材料是否为空，接口层不形成统一校验反馈。
**解决**：在请求对象中使用 Jakarta Validation 的 `@AssertTrue` 自定义校验方法，遵守项目"所有对外 API 必须有入参校验"约束。

### 5.2 `taskId` 是 UUID 不是自增 ID
**问题**：接口校验写成 `@Min(1)`，但项目使用字符串 UUID 作为业务 ID。
**解决**：使用 `@NotBlank` + `@Size(max = 64)`，贴合真实数据结构。

### 5.3 接口路径风格需与已有 Controller 一致
**问题**：复盘报告导出写成 `/reports/markdown` 而现有分组是 `/report`，产生两套路径。
**解决**：导出路径收敛为 `GET /api/creator/tasks/{taskId}/report/markdown`。

### 5.4 追问接口不能接受前端传入报告或证据
**问题**：允许前端提交报告片段或证据列表会引入伪造依据的风险。
**解决**：请求体只接收 `question`，报告和证据由后端按 `taskId` 查询。

### 5.5 没有向量库时也要有证据结构
**问题**：第一版只返回纯文本回答会绑定前端展示结构，后续接 RAG 需重写。
**解决**：响应中保留 `evidenceItems`、`retrievalMode` 和 `ragEnabled` 字段。当前 `ragEnabled=false`，但前端已按证据列表展示。

### 5.6 Markdown 导出由后端统一生成
**问题**：前端自行把报告 JSON 拼成 Markdown，和后端格式形成两套来源。
**解决**：前端只下载后端返回的 `Blob`，报告转 Markdown 规则统一放在 `CreatorReportService`。

## 六、文件导入与脚本

### 6.1 文件导入需限制文件类型和内容长度
**问题**：用户误传二进制文件或超长文本，导致 UTF-8 解析出乱码或材料字段溢出。
**解决**：接口只允许 TXT、MD、SRT、ASS 等文本类型；导入沿用材料长度限制，不同材料类型分别做上限判断。

### 6.2 TXT 不能当成强结构数据
**问题**：TXT 格式的标题、空行和评论元信息可能变化，解析不可靠。
**解决**：TXT 只按脚本输出的区块做基础解析，响应里返回 `warnings` 提示解析精度不如 JSON。

### 6.3 脚本输出目录不能依赖当前工作目录
**问题**：从不同目录运行脚本时，相对路径输出到项目外部。
**解决**：默认输出目录改为脚本所在项目根目录下的 `export/bilibili_feedback`，并在 `.gitignore` 中排除。

### 6.4 脚本产物不能进入 Git
**问题**：评论和弹幕可能包含真实用户内容，误提交污染仓库且带来隐私风险。
**解决**：默认输出到 `export/bilibili_feedback/`，`.gitignore` 同时忽略 `export/` 和 `exports/`。

### 6.5 外部网页接口不是稳定依赖
**问题**：B 站网页接口可能调整参数、访问策略或风控规则，旧评论接口可能静默返回空列表。
**解决**：脚本优先尝试新版 WBI 签名接口 `x/v2/reply/wbi/main`，旧接口无结果时自动回退。遇到限制写入 `warnings`，不伪装成空数据。

### 6.6 BV 拉取失败需给出可排查的错误信息
**问题**：页面只显示 `Internal Server Error`，无法定位失败阶段。
**解决**：新增全局异常处理统一返回 `message` 字段；脚本定位不再只依赖 `user.dir`，同时从 classpath 向上查找项目根目录做兜底。

### 6.7 BV 入口执行固定脚本而非暴露命令字符串
**问题**：前端只展示命令文本却不接后端执行，用户体验断在命令行操作上。
**解决**：前端直接调用后端 BV 拉取接口，后端只执行项目内固定脚本 `scripts/bilibili_feedback_fetcher.py`。

### 6.8 评论需保留层级结构，弹幕和评论不能混装
**问题**：评论和弹幕语义不同——评论有楼层和回复关系，弹幕有播放时间轴。
**解决**：JSON 使用 `rootComments[]` + `replyComments[]` 保留讨论链路；弹幕按分 P 组织为独立顶级区块。

### 6.9 导入需同步回填已有链路表
**问题**：只写明细表不写 `creator_user_feedback_detail`，旧 `feedback/analyze` 接口读不到样例。
**解决**：导入成功后同步回填已有表，保证原有反馈分析闭环不被破坏。

## 七、评测与成本

### 7.1 评测结果必须保留原文而非只存分数
**问题**：后续复盘失败原因时只能看到低分，看不到具体输出。
**解决**：评测结果表强制保留 `raw_output`、`failure_reason`、`elapsed_ms` 和 token 字段。

### 7.2 Prompt 版本号不能替代快照
**问题**：同一版本名可能被人改过内容，只存版本号无法复现当时输出。
**解决**：额外保存 SHA-256 哈希，版本号给人看，哈希用于确认内容一致性。

### 7.3 评测阶段必须与用例阶段一致
**问题**：发布前优化用例的错误标记为反馈分析结果，导致后续统计混乱。
**解决**：评测结果落库前校验 `targetStage` 是否与用例一致，不一致直接拒绝。

### 7.4 不能把人工评分说成自动准确率
**问题**：`accuracyScore` 是人工分项评分，不是模型自动准确率。
**解决**：文档和字段说明统一称为"准确性分项均值"。真正的准确率需要标准答案、自动判定规则或多评审一致性。

### 7.5 `List.of` 不能放 null
**问题**：统计分项评分时评分字段允许为空，`List.of(null, ...)` 会抛异常。
**解决**：改用普通数组遍历，忽略 null 分项，只统计实际填写的评分。

### 7.6 标准差解释稳定性，不能替代质量判断
**问题**：分数波动低只说明输出稳定，不代表质量更高。
**解决**：版本对比同时展示均分、准确性均值、成功率、token 总量和评分覆盖率，避免单一指标误导。

### 7.7 统计接口不能复用分页查询
**问题**：Prompt 统计需要全量数据，但复用 `listResultsByCaseId(caseId, limit)` 会在超 100 条时截断。
**解决**：Mapper 增加统计专用全量查询方法，页面列表继续分页，统计接口独立读取全量。

### 7.8 usage 缺失不能伪造成 0
**问题**：模型供应商未返回完整 usage，写成 0 会误导成本统计。
**解决**：token 字段使用 `Integer`，供应商未返回时保留 `null`。Spring AI 空 usage 三个 getter 都返回 0，服务层归一化为 `null`。

### 7.9 前端可选 token 字段不能默认 0
**问题**：开发者测试弹窗草稿默认值 0 会覆盖后端自动推导逻辑。
**解决**：耗时和 token 可选字段默认 `null`；token 输入最小值设为 1，后端用 `@Positive` 和服务层归一兜底。

### 7.10 成本保护统一放在 LLMService
**问题**：各业务 Service 分别做成本限制，后续新入口容易漏掉。
**解决**：保护逻辑集中在 `LLMService.validatePromptLength`，所有模型调用共享同一条保护线。

### 7.11 成本超限必须在模型调用前触发
**问题**：Spring AI 请求发出后再处理异常已失去保护意义。
**解决**：在构建 `ChatClient` 请求前先执行 prompt 长度校验。

### 7.12 成本保护默认开启适用于演示环境
**问题**：保护默认关闭，Docker 演示时可能忘记打开。
**解决**：`LLM_GUARD_ENABLED` 默认 `true`，通过环境变量允许显式关闭。

## 八、前端视觉与主题

### 8.1 全局样式抽离避免主题分裂
**问题**：全局样式集中在 `App.vue`，新增页面时容易复制样式导致主题分裂。
**解决**：将全局视觉语言抽离到 `src/styles/theme.css`，在 `main.ts` 统一引入。

### 8.2 撞色主题需要结构锚点和状态色
**问题**：只用石榴红和雾粉桃会导致单一色相堆叠，缺少工程控制台的稳定感。
**解决**：加入墨色作为结构锚点，青绿和金色作为状态与焦点色，建立视觉层次。

### 8.3 视觉强度不能牺牲交互可读性
**问题**：强视觉页面容易压暗内容阅读区和按钮状态，尤其会话列表、Markdown 和代码块。
**解决**：保留明确的内容底色、滚动区域、焦点样式和移动端断点。

### 8.4 任务管理区收敛为中性工作台视觉
**问题**：颜色和阴影过重像按钮和卡片的堆叠。
**解决**：弱化粉色背景、硬阴影和渐变，用标题、状态、材料数和蓝色激活线建立层级。

## 九、配置与基础设施

### 9.1 OpenAI Embedding 自动配置 `matchIfMissing=true`
**问题**：`spring.ai.model.embedding` 未设置时 `OpenAiEmbeddingAutoConfiguration` 默认激活。
**原因**：Spring AI 1.1.4 自动配置的 `matchIfMissing=true` 在属性缺失时也满足条件。
**解决**：显式配置 `spring.ai.model.embedding: ${EMBEDDING_MODEL_TYPE:none}`，`none` 不等于 `openai`。

### 9.2 `VectorStore` 不能强依赖注入
**问题**：`VECTOR_STORE_TYPE=none` 时没有 `VectorStore` Bean，`@Autowired` 启动报 `NoSuchBeanDefinitionException`。
**解决**：改用 `ObjectProvider<VectorStore> vectorStoreProvider`，`getIfAvailable()` 返回 null 时走 SQL 兜底。

### 9.3 提示词安全——不接受完整系统提示词作为可编辑参数
**问题**：前端编辑完整系统提示词可删除角色边界和结构化输出要求。
**解决**：接口字段收束为 `customGuidance`，后端固定系统提示词保持不变，用户指导仅进入业务输入区。新旧 `localStorage` 键隔离防止缓存还原受保护内容。

### 9.4 创作者偏好不混入通用长期记忆
**问题**：通用长期记忆保存用户事实和回答风格，创作者偏好保存内容创作经验，混在一起导致互扰。
**解决**：新增 `creator_preference` 表，只从复盘报告的 `creatorPreferenceInsight` 沉淀偏好。仅保存 `PARSED` 且偏好非空的报告。

### 9.5 初始化库名不能与连接串分离
**问题**：`init.sql` 写死库名为 `link_agent`，Compose 再放可变 `MYSQL_DATABASE`，出现脚本写 A 库、后端连 B 库。
**解决**：演示环境固定库名为 `link_agent`，减少首次启动配置分叉。

### 9.6 AI 交互台浮窗不能复用页面级组件
**问题**：`AgentConsole.vue` 包含侧边栏、统计、全屏按钮等页面布局，直接复用体积过重。
**解决**：新增 `AgentFloatingWindow.vue`，只复用 `useAgentChat`、`MessageBubble`、`ChatComposer`、`ErrorNotice`。浮窗仅在创作工作台模式下挂载，不与 Agent 控制台同时渲染。
