# RAG 主题优先检索与视频分析上下文踩坑记录

## 1. 不能只返回父视频卡片

**问题**：父块命中只能说明整条视频整体相关，不能说明标题、定位或观众反馈哪一点相关。

**处理**：先检索主题中块，再用命中的 `videoId` 展示视频卡片。

**原因**：创作者需要的是“为什么这个案例值得看”，不是一组没有解释的视频。

## 2. 不能把未展示视频的主题解释返回给前端

**问题**：如果 `matchedTopics` 返回 top20 所有候选解释，但当前页只展示 5 张卡片，前端会拿到暂时不可见的视频解释。

**处理**：`matchedTopics` 只保留当前页卡片对应的主题。

**原因**：解释要和当前可见卡片对齐。

## 3. 中块候选数要大于视频候选数

**问题**：一个视频最多有多个主题中块。如果只检索 20 个中块文档，可能去重后凑不出 20 个视频。

**处理**：中块向量检索取 60 个文档，再收敛成 20 个唯一视频。

**原因**：刷新 4 页最多需要 20 个视频候选。

## 4. 向量 metadata 过滤后还要 MySQL 二次过滤

**问题**：中块向量文档里的 `category` / `tier` 来自索引时的 metadata，后续 MySQL 事实源可能更新。

**处理**：回查视频卡片时再次按 `category` / `tier` 过滤。

**原因**：最终展示必须以 MySQL 事实源为准，不能只信向量库副本。

## 5. rerank 不能按当前页单独精排

**问题**：如果每次只对当前 5 张卡片精排，刷新到第 2 批时排序口径就变成“局部最优”，不能代表 top20 的整体相关性。

**处理**：先形成 top20 候选池，再对 top20 做一次 rerank，最后按 page 切片。

**原因**：这样“换一批”展示的是同一组精排结果的后续区间，排序口径稳定。

## 6. rerank 不能只看主题，不看评论弹幕

**问题**：主题只能说明视频大概在哪个创作方向相关，不能说明观众到底为什么买账或反感。

**处理**：topic-search 先在 top20 候选视频范围内按 query 检索子向量集合，再把相关评论 / 弹幕加入 rerank 文本。

**原因**：视频卡片排序要优先反映和当前问题相关的真实观众反馈；完整评论弹幕仍放在点击卡片后的 `analysis-context` 阶段，避免检索阶段上下文过重。

## 7. 不能用热门评论替代相关评论

**问题**：点赞高的评论通常代表情绪强或段子好，不一定回答用户这次的问题。

**处理**：子向量集合可用时，先用 query 在候选视频内部检索评论 / 弹幕；只有子向量不可用时才退回热门代表证据。

**原因**：排序依据必须服务当前 query，而不是服务评论本身的热度。

## 8. 中块零命中不能直接空结果

**问题**：案例列表里父视频显示“已索引”，但 `topic-search` 实际先查主题中块集合。如果中块集合未索引、或 query 更像标题/BV 精确查找，中块向量可能正常返回 0 条，前端就显示“展示 0 张”。

**处理**：中块召回异常、零命中、或中块命中后父表回查为空时，统一退回 SQL 质量分兜底。

**原因**：父表存在且标题可匹配时，不应该因为中块层没覆盖就空屏。RAG 是增强层，不能破坏基础检索可用性。

## 9. SQL 兜底不能只做整串 LIKE

**问题**：用户输入 `【Re0手书/强欲if】 寂句`，库里标题可能是 `【Re0手书/强欲if】寂句`。整串 `LIKE` 会被空格、括号、斜杠等符号差异误杀。

**处理**：SQL 兜底从 query 提取中英文数字关键词片段，按片段 `AND` 匹配标题、简介、亮点摘要和 BV 号；没有可用片段时才退回整串 `LIKE`。

**原因**：兜底检索的职责是“别漏掉显然存在的案例”，不是做复杂相关性排序。排序仍交给质量分，真正关键词打分留给 hybrid/BM25。

## 10. 前端必须暴露主题中块索引状态

**问题**：前端只有父表、子条目、hybrid 索引入口，用户看到父表“已索引”会误以为主题优先检索也可用，但 `topic-search` 依赖的是 `creator_reference_video_chunk` 中块集合。

**处理**：索引面板补充“主题中块索引”的状态与重建入口，调用 `/index/chunks/status` 和 `/index/chunks/rebuild`。

**原因**：运维界面必须按实际检索依赖展示状态，否则排查时会把父表索引状态误判成中块检索状态。
