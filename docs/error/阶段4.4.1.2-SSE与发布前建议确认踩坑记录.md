# 阶段 4.4.1.2 - SSE 与发布前建议确认踩坑记录

## 1. 生成建议不能直接推进任务状态

问题：

阶段 4.2 的同步接口在生成建议后会直接把任务状态更新为 `PRE_PUBLISH_ANALYZED`。

如果工作流复用这个方法，用户还没确认建议，评论弹幕阶段就会被打开。

处理：

抽出 `PrePublishSuggestionService.generateSuggestion`，只负责生成和保存建议，不更新任务状态。

原因：

工作流里“AI 生成结果”和“用户采用结果”是两个动作。后者才代表业务阶段真正完成。

## 2. 本机 POST 和 SSE 会造成消息重复

问题：

前端发送补充消息时，POST 接口会返回新消息；同时 SSE 也会收到同一条 `message_created`。

如果直接 `push`，消息流会重复。

处理：

前端按 `messageId` 做 upsert：

```text
存在则替换
不存在则插入并按 sequenceNo 排序
```

原因：

SSE 是实时通知，不应该要求前端区分“自己发的消息”和“别人发的消息”。

## 3. SSE 不能成为唯一状态来源

问题：

SSE 断线、刷新页面或浏览器切后台时，前端可能错过事件。

处理：

1. 消息先落库，再发布 SSE。
2. 建立 SSE 连接时重放当前会话已有消息。
3. 前端仍保留“刷新消息”按钮，从普通 HTTP 接口恢复历史消息。

原因：

实时性只是体验增强，数据库消息才是可恢复状态。

## 4. 失败后不能把会话锁死

问题：

LLM 调用失败后，如果会话状态停在 `FAILED` 且禁止再次分析，用户只能重新建任务。

处理：

`FAILED` 状态允许用户继续发送补充要求，也允许再次触发发布前分析。

原因：

失败通常来自模型服务、网络或输出格式，不代表业务会话不可继续。

## 5. 错误信息长度要小于数据库字段

问题：

`TextUtil.abbreviateWithSuffix(value, 500, "...")` 的最终长度可能超过 500，因为 suffix 会额外追加。

处理：

工作流错误信息截断长度设置为 480，确保加上省略号后仍低于 `VARCHAR(500)`。

原因：

异常信息来自外部模型或底层框架，不应该因为错误文本太长导致二次数据库异常。

## 6. 本轮未执行 Maven 编译

项目约定：

所有 `mvn` 编译和测试命令由作者执行。

作者需要执行：

```

```

## 7. 刷新后任务列表查不到旧会话

问题：

工作台任务列表按 `userId` 查询。页面刷新后前端表单里的用户 ID 会回到空值，随后请求会退回 `default` 用户。

如果任务是用自定义用户 ID 创建的，刷新后任务列表就查不到该任务，工作流也就没有机会通过 `resumeLatest` 恢复最新会话。

处理：

第一版先临时保存 `userId` 和 `taskId`，但这个方案仍然把“用户 ID”暴露给了单人工作台用户。

最终处理：

1. 后端 `GET /api/creator/tasks` 在不传 `userId` 时查询全部任务。
2. 前端移除用户 ID 输入框，创建任务时不再主动传 `userId`。
3. 前端只把上次选中的 `taskId` 保存到 `localStorage`，刷新后优先恢复该任务。

原因：

工作流消息和会话已经落库，真正丢的是前端任务上下文。当前项目是单人开源作品集，不应该让用户理解账号隔离概念。
